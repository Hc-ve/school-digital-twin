## 1. 案例 A · 通用数字孪生大屏设计规范

来源：CSDN《5 个数字孪生可视化大屏设计技巧》（2026-03）
https://blog.csdn.net/weixin_29193359/article/details/158674352

| 问题 | 答案（原文口径） |
|---|---|
| 一屏放几个图表？主次怎么分 | 四区制：**全局态势区（主视觉）占屏 40%–50%**、**核心 KPI 区 10%–15%**、**详细分析区 25%–35%**、**控制筛选区 5%–10%**。主视觉在中央，分析区在两侧或底部 |
| KPI 数字多大？放哪 | "超大、简洁的数字字体"，位于**屏幕四角或顶部**；关键数据可达 120px（1920 基准），说明文字不小于 24px |
| 用了哪些图表类型？为什么 | 未指定类型，但明确要求"趋势图、分布图、列表"三类分别承担"支撑和解释主视觉区的状态" |
| 色彩怎么用 | 三色语义：状态色（绿/黄/红，高饱和、全局一致、**禁止滥用**）、数据色（**同一色相不同明度**，或色盲友好色板）、环境色（深蓝黑 `#0f1423` 一类，**避免纯黑**）。"高亮强调色谨慎使用，仅用于最重要的交互反馈" |
| 有无实时曲线？刷新频率 | 未给频率，但给了原则：**"对数据流进行聚合与降频"，例如每 500ms 聚合一次**；高频交互要防抖节流 |
| 一屏信息密度 | "一个屏幕，一个核心故事"；用**钻取（Drill-down）**降密度：全局只显示概要，点开才加载细节 |
| 什么细节显得专业 | 深色底非纯黑、微纹理；图元"填充优先于描边"（细线在远距离消失）；状态不只靠颜色，要结合形状；"流畅 60 帧远比多一个特效重要" |

**能照搬**
- 四区占比 → 我们只有"KPI 带 + 分析区"两区，但比例可直接用：KPI 带占内容区高 12%（60/500），分析区占 88%。
- **"数据色用同一色相不同明度"** —— 这条直接决定 donut 五段不能用五彩，必须单色相分级。
- **500ms 聚合** —— 我们已是 0.5s 刷新 + 5Hz 采样，口径正好对上。

**不能照搬（及原因）**
- KPI 120px / 说明 24px：这是 **1920×1080 基准**。我们画布 1000×720，等比折算 120×(1000/1920)=**62px**，但 62 会挤掉标签行。本项目 KPI 数值上限取 **28（token `FsDisplay`）**。
- 玻璃态/背景模糊：内置管线无 `_CameraOpaqueTexture` 通路，做模糊只能 GrabPass，**已裁（掉帧）**。
- 粒子流 / 生长动画 / 聚焦脉冲：零图片资源 + 内置管线，全部不做（本期也不做动效）。

## 2. 案例 B · 数据可视化图表选型指南

来源：CSDN《数据可视化图表选型指南：七种高频图表适用场景与避坑》（2026-10）
https://blog.csdn.net/weixin_30000735/article/details/167361617

| 问题 | 答案 |
|---|---|
| 一屏放几个图表 | 未直接给，但给了"一张图颜色不超过五种，超过就该拆图"；类别超 12 个应合并长尾 |
| KPI 放哪 | 未涉及 |
| 图表类型与理由 | **柱状图**＝把数值映射为**长度**，人眼对长度差异感知精度最高，"类别对比的第一选择"；**折线图**＝暗示**连续性**，横轴必须是连续变量（时间），"时间序列的天然选择"；**环形图/饼图**＝部分与整体，但"人眼对角度的感知精度远不如长度"，**必须同时满足三条才可用：类别 ≤5、占比差异明显、确实要强调"某部分占整体"** |
| 色彩 | "一张图的颜色不超过五种"；顺序型数据应用**单一色相、亮度单调变化**，禁止彩虹色 |
| 实时曲线 | 数据点不宜过多，"时间跨度很长时先聚合再画" |
| 信息密度 | 柱状图类别 7–12 个；折线图**超过 4 条就要拆**；堆叠段 3–5 段 |
| 专业细节 | **柱状图纵轴必须从 0 开始**（否则比例失真）；**折线图纵轴可以不从 0**，但范围至少覆盖数据实际范围的 50%；**横向条形适合长标签**；**按数值降序排列**，"读者不需要在脑子里做排序"；直接标注优于图例 |

**能照搬**
- **横向条形 + 降序**：楼层能耗与 Top5 都用横向条，且按值降序（我们当前楼层是按楼层号排，要改）。
- **环形图三条件**：我们恰好 5 段（含"其他"），占比差异明显，语义就是"部分占整体" → 环形图**成立**，但要单色相分级。
- **折线图纵轴可不从 0**：功率曲线用自适应量程，但必须标出 min/max 刻度值（当前没有刻度文字，这是"像 PPT"的原因之一）。
- **条形图基线为 0**：横条宽度必须按 `值 / 最大值` 计算，不允许截断基线。

**不能照搬**
- "柱状图类别 7–12 个"：我们楼层只有 3–4 段（1F/2F/室外），远低于下限 → **不适用柱状图密度规则**，改用"条 + 数值 + 占比"三列，避免大片空白。
- "直接标注代替图例"：donut 的 5 段太窄，直接标在扇区上会重叠 → 仍用图例，但**图例必须与扇区同序、同色**。

## 3. 案例 C · 优锘 ThingJS-X 智慧校园（含西安交大落地）

来源：https://x.thingjs.com/campus.html

| 问题 | 答案（原文口径） |
|---|---|
| 一屏几个图表 / 主次 | 未给数量；但明确"**以校园三维场景为交互中心，以统计列表或图表或曲线等仪表盘的形式**，对学校整体情况进行介绍"。三维是中心，图表是**旁证** |
| KPI 放哪 | 未明确，但"以**领导视角**展现校园重点统计信息" |
| 图表类型与理由 | "统计列表 / 图表 / 曲线 / 仪表盘"四类并列，按"介绍—监控—分析"分工。绿色校园板块："**以统计图表展示绿色节能整体统计信息**，辅助后勤管理者进行成本控制" |
| 色彩 | 未给值；以"颜色区分显示当前是占用、空闲或预约的状态"——**颜色只承载状态，不承载装饰** |
| 实时曲线 | 未给频率 |
| 信息密度 | 分板块（全景概览 / 平安 / 绿色 / 教务），**一屏只讲一个板块**，靠场景切换而不是堆图表 |
| 专业细节 | 多级下钻（校园→楼栋→楼层→房间）；"孪生体—孪生体集合—孪生场景—孪生业务"的分层范式 |

**能照搬**
- **"三维是交互中心，图表是旁证"** → 数据统计页可以没有三维，但**必须一眼看出"这些数是从哪来的"**（口径行）。
- **颜色只承载状态**：donut 的分级色是"类别色"不是"状态色"，所以不能用 StatusNormal/Warning/Alarm 当类别色（我们当前 donut 第 2、3 色正是绿和橙 —— 会让人误读成"正常/警告"）。

**不能照搬**
- 多级下钻：需要点击图表钻取到房间级，属交互逻辑，**本期不做**（只做静态表现层）。
- 零代码平台的"仪表盘组件库"：他们是 WebGL + SVG 组件，我们是 UGUI 自绘，**组件形态不可移植**，只能借信息结构。

## 4. 案例 D · 校园多建筑能耗监测与节能决策平台（真实落地，本项目最接近的参照）

来源：https://monitor.1wind.cn/（实查页面结构与字段）

| 问题 | 答案（页面实测） |
|---|---|
| 一屏放几个图表 / 主次 | **9 个模块**同屏：实时趋势 Top3、能耗排行 Top10、6 个 KPI、实时功率曲线（最近 60 分钟）、实时告警（10 条）、节能建议（6 条）、全校建筑级热力图、口径说明、简报入口。**主视觉是排行 + 曲线**，热力图占最大面积 |
| KPI 数字多大 / 放哪 | 6 个 KPI **集中成一横排**：当前功率 770.0 kW / 今日电量 2042.4 kWh / 今日费用 1876.0 ¥ / 今日碳排 2036.3 kg / 今日峰值 2903.2 kW / 未处理告警 10 条。**每个都带单位，单位字号明显小于数值** |
| 图表类型与理由 | 折线（60 分钟功率，看趋势）、排行表（建筑维度，做对比）、Top3 卡（抓前三，抢注意力）、热力图（空间分布）。**排行用表格而不是柱状图**——因为要同时看"功率 + 变化率"两列 |
| 色彩 | 深底 + 单一青色强调；告警用红色小面积（未处理告警数字）；**变化率用 ↓ 绿/↑ 红还是反过来未统一**（这是它的缺点，见下） |
| 实时曲线 | **"实时功率曲线（最近 60 分钟）"**，右上角有 `更新 13:47:00` 时间戳；有"3 分钟演示"回放控件 |
| 信息密度 | 约 **40 个数字 + 4 个图 + 10 行告警**。密度很高，靠"模块标题 + 细分隔"切块，不靠大留白 |
| 什么细节显得专业 | ① **顶部有"口径说明"按钮**；② **更新时间戳精确到秒**；③ 排行表带**变化率**列；④ 告警每条给"位置 / 时间 / 建议"三行；⑤ 节能建议带**预计节省 kWh + ¥ + kgCO₂**；⑥ 单位全部标在数值旁 |

**能照搬（本项目直接采用 5 条）**
1. **KPI 横排 + 单位小字**：数值与单位分离，单位 11px。
2. **右上角更新时间戳**：`更新 14:42:07`，放在页脚口径行。
3. **口径说明可见**：页脚一行写清"≈ 估算 · 按额定功率×台数 · 刷新 0.5s"。
4. **排行表带第二列**：我们的 Top5 已有"值 + 占比"，正好对应它的"功率 + 变化率"。
5. **模块标题 + 细分隔线**：不靠大留白切块。

**不能照搬**
- **9 个模块 / 40 个数字**：我们只有 5 块内容，且画布只有 1000×720（它是 1920+）。硬堆密度会变成 9px 小字糊成一片 → 我们保持 **5 块 + 4 个 KPI**，密度约 1/5。
- 热力图：需要二维网格 + 色阶映射，UGUI 要逐格 Image（几十个 drawcall），**零图片资源下不划算**，且我们没有"建筑级空间分布"数据。
- 3 分钟演示回放：属交互/时序存储，本期不做。
- 碳排/费用换算：数据层没有电价与碳因子，**不能造假**。

## 5. 案例 E · Siemens Building X Energy Manager（国外）

来源：What If Design《Energy dashboard design: 12 patterns from real climate tech products》（2026）
https://whatifdesign.co/feeds/blog/energy-dashboard-design

| 问题 | 答案（原文口径） |
|---|---|
| 一屏几个图表 / 主次 | 未给数量；给了 12 个 pattern，其中核心是"**System-at-a-Glance 状态层**"——先回答"一切正常吗"，再让人下钻 |
| KPI 放哪 | 顶部状态层；**"Status labels with severity, not just raw numbers"**（要状态词，不只是裸数字） |
| 图表类型与理由 | **Target-vs-Actual 记分卡**（消耗/成本/碳排对预算）；**Time-Series Trend**（季节、峰值、衰减）；**Benchmark/Baseline**（对同类建筑）；**Sankey 分项流**（园区→房间级分表） |
| 色彩 | 状态分级（high/medium/low/informational），**告警按优先级分带**，不把所有告警等同对待 |
| 实时曲线 | 支持时间范围与粒度切换、YoY 对比；**要标注已知事件**（检修、固件升级、停电） |
| 信息密度 | "progressive disclosure"——先摘要，细节靠交互 |
| 专业细节 | ① **"Visible timestamps, so users know how current the data is"**；② 对比必须有基线（目标/上期/同类），否则数字无意义；③ 告警中心要分级 + 去重 + 有归属 |

**能照搬**
- **"要状态词，不只是裸数字"** → 我们的"告警中 4 台"比"4"好；KPI 标签必须带语义（"在线率"而不是"在线"）。
- **"可见时间戳"** → 页脚更新时间。
- **对比必须有基线** → 我们没有历史存储，所以**不做同比**，但可以做"占比"（Top5 占全楼百分比）——这是同一思路的可行版本。

**不能照搬**
- Target-vs-Actual / YoY / Sankey：全部依赖时序库与预算基线，本项目**无历史存储**（只有 300 点内存环形缓冲），做了就是编数据。
- 告警分级带：属告警中心职责，本页不重复。

## 6. 案例 F · ENERGY STAR Portfolio Manager（国外基准体系）

来源：同上文引用（EPA 建筑性能指南）

| 问题 | 答案 |
|---|---|
| 一屏几个图表 | 评分卡 + 基准对比 + 趋势 |
| KPI 放哪 | 顶部 1–100 分（**单一主指标**），其余为支撑 |
| 图表类型与理由 | 基准条形（本楼 vs 同类中位数 50 分）；**气象归一化**后再比，否则跨气候不可比 |
| 色彩 | 分数色阶（绿→黄→红），**只给主指标上色** |
| 实时曲线 | 无实时，按月/年 |
| 信息密度 | 极低：**一个主指标 + 三个支撑** |
| 专业细节 | **"Label the baseline and the methodology plainly"**——基准与方法必须写在界面上；样本量、时间口径都要标 |

**能照搬**
- **"一个主指标 + 支撑"** → 本页主指标是"当前总功率"，其余三张 KPI 是支撑。所以**只有总功率卡允许视觉加重**（大一号或带负载率副标），其余三张同权。
- **"方法必须写在界面上"** → 页脚口径行（≈ 估算、口径、刷新率）。

**不能照搬**
- 气象归一化 / 同类基准：需要外部数据集，**断网环境不可能**。

## 7.5 案例 I · 施耐德 EcoStruxure Building Operation（楼宇设备管理方向）

来源：施耐德电气官方产品页 https://www.schneider-electric.cn/zh/product-range/62111-ecostruxure-building-operation楼宇运营系统/
配套：EcoStruxure 楼宇解决方案页 https://www.schneider-electric.cn/zh/work/campaign/innovation/buildings.jsp
参考：EBO WorkStation 用户手册（book118 公开摘要）；PME 告警分级（前序 §5 已引）

> 补这个案例的理由：现有 5 个真实案例偏"能源计量"（Siemens Building X、ENERGY STAR 都是能耗视角），
> 缺**设备管理**视角。而本项目的核心是**设备 + 能耗双线**，设备侧的组织方式必须有出处。

| 问题 | 答案 |
|---|---|
| 一屏放几个图表？主次怎么分 | **不以图表为中心**。EBO WorkStation 的界面是四区：**设备树（左）+ 图形页（中）+ 报警列表 + 趋势图**。主视觉是"设备树 + 图形页"，KPI 不是中心 |
| KPI 数字多大？放在哪 | **没有"大屏 KPI 带"**。数值直接标在图形页的设备/点位上（如某台空调旁标"24.5 °C"）。官方口径："在一个便捷视图中提供多个建筑系统和设备的**洞察、控制和管理信息**" |
| 用了哪些图表类型？为什么 | ① **趋势图（Trend Log）**——时间序列，回答"这台设备过去怎么变的"；② **报警列表**——按优先级排序，回答"现在哪里坏了"；③ **排程表**——回答"它什么时候该开"。**没有环形图/饼图**：读者是运维工程师，要精确值与定位，不要"占比" |
| 色彩怎么用 | 状态色三分（正常/报警/故障）+ 图形页自定义底图。**装饰极少**——BMS 界面里颜色只用来标状态，不是用来好看 |
| 有没有实时曲线？刷新频率 | 有 Trend Log，**采样间隔可配**（秒级到分钟级），由点位的"趋势记录"属性决定 |
| 一屏信息密度多少 | 很高，但靠**设备树折叠**控制：默认只展开到"楼栋—楼层"，点开才见设备与点位 |
| 哪些细节让它"看起来专业" | ① **设备树层级 = 站点→楼栋→楼层→设备→点位**，路径本身就是唯一 ID；② **报警带优先级带 + 确认状态**（PME 分 high/medium/low/informational 四带）；③ 每个点位带**单位与时间戳**；④ 符合 BACnet 标准，点位命名有规范 |

**能照搬（2 条，直接影响本项目）**

1. **"设备树路径就是 ID"** —— 我们的 `1号教学楼-2F-201-001灯具` 与 EBO 的 `站点/楼栋/楼层/设备/点位` 是同一套思路。
   → 落点：列表显示**短码** `2F-201`（折叠到"楼层—房间"），详情卡显示**全码**（展开到"设备—序号"）。
   这就是已裁决的「编号降级方案」的行业依据，不再是我们的临时妥协。
2. **"数值必须带单位与时间戳"** —— 已在图纸 §9.2 文案规范里落为硬规则。

**不能照搬（3 条，全部是本项目约束）**

| 不能照搬 | 原因 |
|---|---|
| 设备树侧栏 | 我们左轨 200 已被 5 个模块占满，再放树会挤爆；且 1000×720 放不下"树 + 图形页 + 报警 + 趋势"四区 |
| 不做 KPI 大屏 | EBO 面向运维工程师（天天用，知道去哪找）；我们的数据统计页面向答辩演示（评委 5 秒要看懂总量）。**受众不同，不能照抄形态** |
| 图形页自定义底图 | 需要图片资源（平面图/系统图），违反**零图片资源** |

> **这个案例最重要的结论**：设备管理方向的专业感来自**"路径化编号 + 精确值 + 状态"**，不是来自更多图表。
> 所以本页不做第 5 块图，把力气花在"编号分级"和"口径可见"上——这与 §10.1 第 5 条一致。

## 8. 案例 H · 仪表板设计工程实践（InetSoft / WolfPixel）

来源：https://www.inetsoft.com/info/department_dashboard_tips_techniques ；https://www.wolfpixel.agency/blogs/dashboard-design-best-practices

| 问题 | 答案（原文口径） |
|---|---|
| 一屏几个图表 | **"5 to 9 visual elements total (including KPI cards)"**；"Cap primary metrics at five" |
| KPI 放哪 | **"top-left corner is the most valuable real estate"**；F/Z 型扫描，左上权重最高 |
| 图表类型与理由 | 位置编码 > 长度 > 角度/面积/色饱和度（感知精度排序）。所以条形优于饼图；**"Pie only for two or three slices with obvious differences"** |
| 色彩 | **"Limit the palette to 3–5 core colors and use bright accents sparingly"**；"consistent color meaning"；"avoid rainbow" |
| 实时曲线 | "Usually, no" —— 除非是运维监控，否则实时会让人过度反应微观波动 |
| 信息密度 | 5–9 个视觉元素；"Cramming produces tiny type, dense charts, unusable touch targets" |
| 专业细节 | ① **"Keep consistent chart heights within each row to establish rhythm"**（同行等高）；② "Use a consistent grid… 12-column grid with a fixed gutter"；③ "Remove chart chrome"；④ "Group related metrics using spacing rather than heavy borders"；⑤ "Use low-contrast gridlines in charts" |

**能照搬（本项目直接采用 4 条）**
1. **同行等高** → 我们当前行1 高 200、行2 高 190，**必须统一为 196**。
2. **5–9 个视觉元素** → 我们 4 KPI + 4 图 = 8，正好在区间内。**不能再加第 5 块图**。
3. **固定 gutter 的栅格** → 全部间距取 4 的倍数，卡片间 16，卡内 12。
4. **低对比网格线** → 图表网格用 `ChartGrid`（Δ11.5），不用 `Track`（白@0.09，Linear 下 Δ 会到 60+，盖过折线）。

**不能照搬**
- 12 栏响应式栅格：UGUI 绝对定位 + 两套固定宽度（420/640/768），**没有响应式**，栅格只作对齐依据。
- "实时通常不要"：我们是数字孪生演示，**实时曲线是卖点**，保留，但把"波动"讲清楚（标 min/max）。

## 11. 三条反向结论（行业没做、但我们必须做的）

调研里所有案例都在 1920+ 画布、有历史库、有 WebGL 后处理。我们三条必须**反着来**：

1. **密度必须低于行业**：行业 9 模块，我们 5 块。**少不是缺陷，是画布决定的下限**。
2. **装饰必须少于行业**：他们靠模糊/发光/粒子堆"科技感"，我们只有顶点色 + 1px 描边。**科技感必须靠"信息组织"而不是"视觉特效"**——这恰好也是 H 案例说的"去掉 chart chrome"。
3. **口径必须比行业更显式**：他们的数据可信（有真实表计），我们的功率是 `TwinPowerEstimate` 估算。**估算必须在界面上写清**，否则答辩一问就穿帮（这条已写入 P00 裁决 C-28）。

## 12. 给设计图纸的 6 条硬输入

1. 类别色 = **单色相 4 级 + 1 灰**，禁用 StatusNormal/Warning/Alarm 当类别色。
2. 楼层与 Top5 **按值降序**，条形基线为 0。
3. 两行图表卡**等高 196**，gutter 16（列）/ 12（行）。
4. 图表网格用 `ChartGrid`（Δ11.5），不用 `Track`。
5. 每卡标题右侧必须有 source 小字；页脚必须有口径 + 时间戳。
6. 视觉元素总数锁死 **8 个**（4 KPI + 4 图），不再增块。
