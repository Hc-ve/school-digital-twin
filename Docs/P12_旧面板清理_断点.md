## 零之补充：Play 实测暴露的回归（**这是本轮唯一真 bug，请重点看**）

### 症状

主理人 Play 5 分钟，抽屉「告警中心」页 `共 0 条`，一行都没有。

### 根因（链路完整，四步）

```
① 我把 EnsureHistoryPanel() 整块删掉
        ↓ 连带把**它内部那一句 EnsureHistory() 调用**也删了
② 场景里没有 TwinAlarmHistory 组件（grep 确认 0 处）
   全项目也没有任何其它地方 AddComponent 它
        ↓
③ TwinAlarmHistory.Instance 恒为 null
        ↓
④ TwinSystemPage.RefreshAlarm() 里 `if (history != null) history.GetRecent(...)`
   → 静默跳过 → 一条也不填 → 界面显示「共 0 条」，Console 干净
```

### 我的判断错在哪

错在把**两件事当成一件**：

| 方法 | 建的是什么 | 该不该删 |
|---|---|---|
| `EnsureHistoryPanel()` | **面板**（UI 层）`TwinAlarmHistoryPanel` | ✅ 该删 |
| `EnsureHistory()` | **数据组件**（数据层）`TwinAlarmHistory` | ❌ **不能删**，它是生产方 |

面板是**消费方**，数据组件是**生产方**。删消费方时把生产方一起带走，
表现为「界面还在、里面全空」——而且：

- **编译器不报**：`EnsureHistory()` 还在类里，只是没人调，C# 对私有未用方法不告警（本项目已确认）
- **判据测不出**：我上一版加的 `P12-15`「不再 AddComponent 旧面板」是 grep 源码，
  它查得到"那句 AddComponent 还在不在"，查不到"运行时到底有没有这个实例"
- **Console 干净**：`RefreshAlarm` 用的是 `if (history != null)` 静默跳过，
  不是报错 —— 这正是本项目反复记的「漏了不报错、只是看起来没反应」

### 修复

`TwinDetailPanel.BuildUI` 里，在 `BuildSourceBar()` 之后补回一句 **`EnsureHistory();`**，
并写了 17 行注释说明「为什么这一句不能跟着面板删」。

配套判据（防再犯）：
- `P12-29` BuildUI 必须显式建告警历史数据组件（`^            EnsureHistory\(\);` 行首锚，防注释误匹配）
- `P12-30` `EnsureHistory` 声明仍在
- `P12-31` `EnsureHistory` 内部仍自己 `AddComponent`，不依赖场景预置

### 这条 bug 的通用教训（我建议进基线 §1.6）

> **删「消费方」时，必须逐个确认它内部有没有顺带创建「生产方」。**
>
> 判断方法：删完 `grep -n "Xxx.Instance" ` 全部使用点，
> 再问一句「Xxx 这个实例，**谁负责 new 出来**？」——
> 如果答案只有「我刚删掉的那个方法」，那就是这类 bug。
>
> 这类 bug 的三个特征（全部满足，所以极难发现）：
> ① 编译器不报 ② 判据 grep 源码也测不出（源码里那句还在）③ 运行时静默降级不报错。

## 零、先说三件会改变任务包判断的事

任务包里有三处前提与实际代码不符。我没有按错前提动手，先列出来。

### 0.1 抽屉工具行的「录制」不是 Unity Recorder，是**另一个同名真功能**（重要）

任务包写：

> 删「录制」「设置」两项（**录制是 Unity Recorder 的编辑器功能，运行时做不到**）

**实际不是。** 图 2 那条横条（`TwinDetailPanel.BuildSourceBar`）里的「录制」，走的是：

```
OnRecordButton() → TwinSourceSwitcher.ToggleRecord() → TwinRecorder.StartRecording()
```

`TwinRecorder` 是本项目自研的**运行时数据落盘器**（`Assets/_Project/Scripts/Data/TwinRecorder.cs`），
把数据总线上的每一条样本写成 JSONL，供 `TwinPlayer` 事后回放。它**运行时完全可用**，
而且已经在跑（截图里 `■ 录制` 那个状态就是它）。

**结论：删抽屉工具行的「录制」这个决定仍然正确，但理由要换。**

正确理由不是"运行时做不到"，而是：

> **同一个词在同一个屏幕上对应两套行为。**
> 抽屉工具行的「录制」只会弹假 Toast，浮卡横条的「录制」是真落盘。
> 答辩时若有人问"这个录制录到哪了"，指着抽屉那项是答不出来的。

任务包里那条错误前提如果被照抄进文档，下一个人会以为"项目没有运行时录制能力"，
进而可能删掉浮卡那条真功能 —— 那是把 200 行有用代码当垃圾。

### 0.2 三个旧面板的 H / T / G 快捷键**从未接上**（比"遗留"更严重）

任务包描述它们是"按 H / T / G 打开的浮层"。我按 G1（`case` 分支存在 ≠ 生效）的做法
先查了"谁调它"，结果：

`BuildUI()` 末尾把三个面板建出来了，但**代码里没有任何按键处理能把它们打开**。
唯一能碰到 `TwinControlPanel` 的路是抽屉工具行的「设置」→ `ToggleLegacyPanel()`。

也就是说这三块面板的真实状态是：**建了、占着内存和图层、但用户永远打不开**。
这比"迁移期遗留"更坏 —— 它是**死代码 + 假承诺**（注释写着"按 H 打开"）。

删它们的收益因此比任务包预估的更大：不只是省 3539 行，还消掉了一个
"注释说能按 H 打开、实际按了没反应"的纯假文档。

### 4.5 「数据源」轮换：我写错两版，第二版会**死锁**（请重点看）

这段是本轮最值钱的东西，因为它又一次证明"读代码觉得对"不够。

**第一版**：没有录像就跳过回放。实算连点：

```
Mock → MQTT → Mock → MQTT …        （回放被静默跳过）
```

**问题**：用户看到"只有两个源在来回跳"，实际是"第三个被跳过了"。两种解释在界面上完全一样 —— 正是本轮要消灭的形态（假入口的变种：让用户以为功能不存在）。

**第二版（更糟）**：照常切过去，失败就提示。实算发现**死锁**：

```
起始 MQTT、回放无录像：
  点1 → 试回放 → 失败 → _current 仍是 MQTT
  点2 → 试回放 → 失败 → _current 仍是 MQTT
  点3 → 试回放 → 失败 → …          ← 用户永远回不到 Mock
```

**根因**：`TwinSourceSwitcher.SwitchTo()` 只在**成功路径**上写 `_current`。而我的轮换基准读的是 `_current`。失败时它不动 → 每次都推同一个 next → 永久卡住。

**这是"读代码看不出来"的典型**：两个版本各自都自洽，只有把"失败时 `_current` 不变"这个事实代进去跑一遍才暴露。

**第三版（最终）**：抽屉自己维护 `_srcCursor`（上次**尝试**到哪），用它推下一个，而不是读"当前生效的源"。两者成功时相同，失败时才分道 —— 而失败恰恰是最需要继续能往下点的时候。

实算验证（穷举三种起始 × 有无录像）：

```
无录像、从 Mock 连点 5 次：
  1 切MQTT 成功 → 生效 MQTT
  2 试回放 失败(无录像) → 生效仍 MQTT
  3 切Mock 成功 → 生效 Mock          ← 能回来，不死锁
  4 切MQTT 成功 → 生效 MQTT
  5 试回放 失败 → 生效仍 MQTT

无录像、从 MQTT 连点 4 次：
  1 试回放 失败 → 生效仍 MQTT
  2 切Mock 成功 → 生效 Mock
  3 切MQTT 成功 → 生效 MQTT
  4 试回放 失败 → 生效仍 MQTT

有录像、从 Mock 连点 4 次：
  1 切MQTT  2 切回放  3 切Mock  4 切MQTT     ← 完整走一圈
```

**为什么不"失败就重置成 Mock"**：那会让"连点两下"变成"第二下必然跳回 Mock"，用户以为按钮坏了。游标是唯一能表达"我想切到第三个、它现在不可用、我再点一下去下一个"的做法。

**已加判据**：`P12-21`（游标字段存在）+ `P12-22`（轮换基准读游标而非 `CurrentKind`）—— 后者锁的正是死锁的根因那一行。

### 9.2 回放控制条：为什么单独一条

数据源条 540 宽已排满（14 + 56 + 3×72 + 8 + 86 = 380，状态区只剩 118px），
塞不下「暂停 + 轨道 + 时长 + 倍速」。控制条浮在其上方，**只在回放源时显示**。

两个实现要点：

**① 暂停不挂住后台线程** —— 挂住的话恢复时要补"暂停了多久"，否则一恢复就狂吐积压样本、
曲线雪崩。改成暂停时一直把 `_playbackStartWallTs` 往前推：
等待循环的目标时刻永远算成"还没到"，线程空转但不吐数据，恢复时时间轴自然接上。

**② 跳转只写请求、不当场改游标** —— `_cursor` 由后台线程推进，
主线程直接写会和它的 `_cursor++` 打架（表现：跳过去又被改回来）。
主线程写 `_seekTargetTs`，后台线程在自己的节奏里搬到对应下标。
传**时间戳**而不是下标，因为 UI 侧只有百分比，而样本在时间上不是均匀分布的。

**③ 事件必须挂在带 Graphic 的节点上** —— `TwinPlaybackBar` 不是 MonoBehaviour，
挂在 `_root`（纯 RectTransform、无 Graphic）上收不到任何 Pointer 事件。
单独建 `TwinPlaybackDragArea` 挂在轨道那层 Image 上。
另外**单击也要能提交**：手指没移动时不产生 Drag，`OnEndDrag` 不触发，
表现为"点了没反应"—— 所以额外挂 `IPointerClickHandler`。

### 9.3 顺带修掉一个隐患

`TwinPlayer.FindLatestRecording()` 原来自己 `GetFiles` + 比 `LastWriteTime`（本地时间），
而 UI 侧录像清单走 `ListRecordings`（UTC）。两套排序规则只要有一处不同，
就会出现「列表里第一个」和「实际回放的那个」不是同一个文件 —— 两边看起来都正常。
现在统一走 `RecordingReader.ListRecordings()`。
