## 0. 结论先行

**问题不在图表样式，在数据来源。**

当前数据图表的**形态**（数值大字 + 单位、阈值带量程条、迷你趋势线、状态胶囊、数据新鲜度、告警列表）已经是 Grafana 单指标面板那一套，形态上不存在差距。

差距只有一条，而且是架构性的：

> **行业里时序数据永远独立于界面存在。界面打开只是"读"，不是"开始记"。**
> 我们现在的 `TwinSparkline` 是界面的一部分，`Clear()` 在页面打开时调用，所以曲线从空白长出来。

五家产品（Grafana / ThingsBoard / WinCC / 紫金桥 / Azure Digital Twins）在这条上完全一致，只是存储介质不同（外部库、本地归档、自研实时库、ADX）。我们受"无数据库、断网单机"约束，**唯一可行解是进程内内存环形缓冲**。

**方案**：新增 `TwinMetricHistory` 静态类，300 点 / 指标 / 5Hz，常驻采样，界面打开时回填。内存约 223 KB，采样开销 < 0.1ms/s。

## 2. 逐案例调研

### 2.1 Grafana —— 单指标 Stat 面板

| 维度 | 实际做法 |
|---|---|
| 采样频率 | **不采样**。数据由数据源（Prometheus / InfluxDB 等）产生，Grafana 只查询 |
| 缓冲长度 | **无本地缓冲**。每次刷新按时间范围重新查询 |
| 刷新机制 | Dashboard 级 `refresh` 参数。**官方默认下限 5s**，可通过 `grafana.ini` 改到 1s（社区资料） |
| 打开时回填 | **每次查询即回填**。Sparkline 由查询返回的 time column 直接绘制 |
| 时间窗口切换 | **有**。`$__from` / `$__to` 作为查询参数下发给数据源 |

**证据（官方文档原文）**

> "Area - Shows the graph sparkline in the background of the value. **This requires that your query returns a time column.**"
> —— https://grafana.com/docs/grafana/latest/panels-visualizations/visualizations/stat/ `官方`

> 刷新间隔默认下限 5s，可改配置降低
> —— https://blog.51cto.com/dongweizhen/7895346 `社区`

**能照搬**
- **视觉形态**：数值 + 背景 sparkline 的叠加方式（我们已在用）
- **体验目标**：打开面板即见完整曲线，不等数据"长出来"

**不能照搬**
- **查询式架构**：依赖外部时序库 + 每次刷新发查询。本项目无数据库、断网运行，这条路直接排除。

### 2.2 ThingsBoard —— 设备遥测

| 维度 | 实际做法 |
|---|---|
| 采样频率 | 由**设备侧决定**，平台按消息时间戳入库，不额外限频 |
| 缓冲长度 | PostgreSQL 默认；Cassandra 用于高写入量与长保留。**TTL 可配**，三层优先级：租户配置 > 规则节点配置 > 系统级配置 |
| 刷新机制 | WebSocket 推最新值 + REST 拉历史 |
| 打开时回填 | **REST API 按时间范围查询**，支持 interval + aggregation |
| 时间窗口切换 | **有**。查询参数含 startTs / endTs / interval |

**证据（官方文档）**

> "ThingsBoard stores time-series data in **PostgreSQL** by default. For high-volume deployments, **Cassandra** is supported... A separate **latest values** table is maintained for fast access to the current readings."
> —— https://thingsboard.io/docs/user-guide/telemetry/ `官方`

> TTL 三层优先级：消息元数据 TTL 属性 > 规则节点配置 > 租户配置 > 系统级配置
> —— https://thingsboard.io/docs/user-guide/telemetry/ `官方`

**未查到**：TTL 的具体默认天数（随版本与部署方式不同，官方文档未给单一固定值）。**不编数字。**

**能照搬**
- **"当前值表 + 历史表"分离**：`TwinAnchor.Values` 天然就是"当前值表"，新增缓冲就是"历史表"，职责不混

**不能照搬**
- 持久化与 TTL 三层配置。单机断网、无数据库，没有"保留多少天"的需求

### 2.3 Siemens WinCC —— 工业 SCADA 代表

| 维度 | 实际做法 |
|---|---|
| 采样频率 | **采集周期（Acquisition cycle）最小 500ms**，默认 500ms |
| 缓冲长度 | **归档大小（Archive Size）** 可配，循环归档自动覆盖最旧数据 |
| 刷新机制 | 变量记录运行系统周期写入归档，趋势控件读归档 |
| 打开时回填 | **OnlineTrendControl 选时间范围查归档** |
| 时间窗口切换 | **有**，趋势控件带"时间范围选择" |

**证据（西门子官方）**

> "采集周期(Acquisition cycle)：读过程变量周期，**最小 500ms**。归档/显示周期(Archiving/Display cycle)：归档..."
> —— https://www.ad.siemens.com.cn/productportal/prods/pcs7_top_v2/pcs7_engineering/pcs7_os_engineering/os_archive/OS_Archive_FAQ/OS_Archive_FAQ.htm `官方`

> 归档配置含 Archive Size 与时间配置两个核心参数，循环归档
> —— https://wenku.csdn.net/doc/19pb0cfein `社区`

**能照搬**
- **"采集周期"与"归档/显示周期"分离**：采集可以快（500ms），归档可以慢（60s）。这直接支撑我们"5Hz 采样 / 60s 窗口"的选型——采样频率和显示窗口本来就是两个独立参数
- **循环覆盖**：容量满了丢最旧，不扩容、不落盘

**不能照搬**
- **500ms 采集频率**。我们 53 台设备 × 95 指标，500ms 采样 = 每秒 190 次全量遍历；而数据源本身不是 500ms 更新的，采了也是重复值

### 2.4 紫金桥 RealSCADA —— 国产组态

| 维度 | 实际做法 |
|---|---|
| 采样频率 | **两种模式：定时保存 + 变化保存（死区压缩）** |
| 缓冲长度 | 自研实时数据库 + 历史库，容量按配置 |
| 刷新机制 | 过程数据库周期扫描 |
| 打开时回填 | 从历史库按时间范围读 |
| 时间窗口切换 | 有 |

**证据（厂商资料）**

> "通过紫金桥组态软件自身的过程数据库，可以通过两种方式自动保存数据点的历史记录，**定时保存和变化保存**"
> —— https://www.gkong.com/learn/learn_detail.asp?learn_id=50383 `厂商`

> 紫金桥是国内少数同时掌握组态软件与工业实时数据库核心技术的厂商，两者底层一体化设计
> —— https://baijiahao.baidu.com/s?id=1874485018149496224 `厂商`

**能照搬**
- **"变化保存"（死区压缩）思想**：值不变不存点，工业界靠它压存储量

**不能照搬（本期）**
- 死区压缩会让**时间轴不均匀**，画曲线前必须重采样。我们 300 点总量只有 223KB，为省这点内存引入重采样算法，收益为负。
- **但要在代码里留注释**，作为将来扩容（比如扩到 1 小时窗口）的入口。

### 2.5 Azure Digital Twins —— 数字孪生平台

| 维度 | 实际做法 |
|---|---|
| 采样频率 | 由设备/上游决定 |
| 缓冲长度 | **平台本身不存时序**，需单独配置「数据历史连接」写入 **Azure Data Explorer (ADX)** |
| 刷新机制 | 事件路由 → ADX 落库 → 查询 |
| 打开时回填 | ADX 查询（KQL 时间过滤） |
| 时间窗口切换 | 有 |

**证据（微软官方）**

> "数据历史记录是一项 Azure 数字孪生功能，用于自动将图形更新历史记录化到 Azure 数据资源管理器中。"
> —— https://docs.microsoft.com/azure/digital-twins/how-to-use-data-history `官方`

> 需显式创建连接：`az dt data-history connection create adx ...`
> —— https://learn.microsoft.com/zh-tw/cli/azure/dt/data-history/connection/create `官方`

**能照搬**
- **分层思想**：孪生模型本身不负责时序，时序是**外挂的一层**。这正是本方案要做的——`TwinMetricHistory` 挂在 `TwinAnchor` 之外，不动孪生模型本身

**不能照搬**
- 外部时序库。零外部依赖是硬约束

## 3. 横向对比

| 产品 | 时序存哪 | 采样频率 | 打开时怎么出曲线 | 窗口切换 | 存储形态 |
|---|---|---|---|---|---|
| Grafana | 外部数据源 | 不采样（查询式） | 查询返回 time column | 有 | 无本地存储 |
| ThingsBoard | PostgreSQL / Cassandra | 设备决定 | REST 查历史 | 有 | 持久化 + TTL |
| WinCC | 归档文件 / 库 | **≥500ms** | 趋势控件查归档 | 有 | 循环归档 |
| 紫金桥 | 自研实时库 | 定时 / 变化两种 | 查历史库 | 有 | 实时库 + 历史库 |
| Azure DT | 外挂 ADX | 上游决定 | KQL 查询 | 有 | 外部时序库 |

### 共同点（"行业标准"的实质）

1. **时序独立于界面**——界面打开只是读，不是开始记
2. **采集周期与显示周期分离**——采集快、显示窗口可长可短
3. **容量上限 + 循环覆盖**——不无限增长
4. **界面按时间范围查询回填**——不依赖"打开后累积"

### 我们能做到 / 做不到

| 共同点 | 我们能否做到 | 方式 |
|---|---|---|
| 时序独立于界面 | ✅ 能 | 常驻采样器，与任何 UI 解耦 |
| 采集与显示分离 | ✅ 能 | 5Hz 采集，60s 窗口 |
| 容量上限 + 循环覆盖 | ✅ 能 | 环形缓冲 300 点 |
| 按范围查询回填 | ✅ 能 | 打开时批量灌入 `TwinSparkline` |
| 持久化（关掉程序还在） | ❌ 不能 | 无数据库，且任务包禁止落盘 |

## 4. 与项目现状的差距

| 项 | 现状 | 差距 |
|---|---|---|
| 数据形态 | `TwinAnchor.Values` 只有当前值 + 上一个值（`PreviousValue`） | **无序列** |
| 趋势线 | `TwinSparkline` 256 点 / 60s，**纯 UI 缓冲** | 页面打开时 `Clear()`，从空白长出 |
| 采样时机 | 由 UI 的 `RefreshValues()` 驱动（浮卡 10Hz） | **界面不开就不采样** |
| 两处一致性 | 浮卡与详情页各自持有一个 `TwinSparkline` | 两条线不共享历史 |

**实际观感**：点开设备 → 曲线是平线 → 约 3 秒后才成形。

## 5. 落地方案

### 5.1 结构

```
TwinAnchor.Values（当前值，唯一数据源，不动）
        │
        │ 5Hz 只读采样（常驻，与 UI 无关）
        ▼
TwinMetricHistory（内存环形缓冲，300 点/指标）
        │
        ├──► TwinDetailPanel（浮卡）  打开时批量回填
        └──► TwinDeviceDetailPage（详情页）打开时批量回填
```

### 5.2 关键参数

| 参数 | 取值 | 依据 |
|---|---|---|
| 缓冲长度 | **300 点 / 指标** | 5Hz × 60s，与现有 `TwinSparkline` 窗口一致，界面代码不用改 |
| 采样频率 | **5Hz（0.2s）** | 低于 WinCC 的 500ms，因为数据源本身不是高频；高于 Grafana 最低 5s，因为曲线要平滑 |
| 采样入口 | 常驻 runner，`RuntimeInitializeOnLoadMethod` 自举 | 对应 Azure DT「时序独立于孪生模型」的分层 |
| 回填方式 | 打开时批量灌入，**不调 `Clear()`** | 对应 Grafana「查询即回填」 |
| 内存占用 | 95 指标 × 300 点 × 8 字节 ≈ **223 KB** | 可忽略 |
| 采样开销 | 5Hz × 95 = 475 次/秒字典查找 | 估算 < 0.1ms/s，可忽略 |

### 5.3 数据结构（避免每帧 GC）

```csharp
// 外层 key 用 TwinAnchor 引用，内层 key 用 metric 字符串（复用已存在的引用）
// —— 每次采样不做字符串拼接，否则 475 次/秒会产生持续 GC
private static readonly Dictionary<TwinAnchor, Dictionary<string, Ring>> _store;

private struct Sample { public float T; public float V; }   // 8 字节

private sealed class Ring
{
    private readonly Sample[] _buf = new Sample[Capacity];
    private int _head, _count;
    public void Push(float t, float v);
    public int CopyTo(List<Sample> dst);   // 回填用，按时间升序
}
```

> **【为什么不加死区压缩】** 紫金桥的"变化保存"能省存储，但会让时间轴不均匀、画线前必须重采样。
> 本项目 95 指标 × 300 点 = 223KB，为省这点内存引入重采样算法，收益为负。
> **若将来扩到 1 小时窗口（18000 点/指标 ≈ 13MB），再考虑加死区压缩。**

| 文件 | 改动 | 规模 |

### 5.5 边界声明（重要）

这套东西**不是新数据源**：

- 不改变任何数据链路口径：`TwinAnchor.Values` 仍是唯一数据源，`TwinMetricHistory` **只读不写**
- 不落盘、不建库、不接外部存储
- 不改图表样式：`TwinSparkline` 渲染逻辑一行不动，只改"喂数据的时机"
- 本质是**现有数据的短期缓存**。关掉它系统照常运行，只是曲线又变回从空白长

## 6. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 常驻采样影响帧率 | 475 次/秒字典查找 | 已估算 < 0.1ms/s；实测后若超标，降到 2.5Hz |
| 设备动态增删导致缓冲泄漏 | 内存缓慢增长 | 53 台固定场景，可忽略；加一条"设备销毁时清理"兜底 |
| 回填时 `TwinSparkline` 容量不足 | 曲线截断 | **已核实无此问题**：`TwinSparkline._capacity = 320`（320 点 ≈ 64 秒 @ 5Hz），大于方案的 300 点，回填正好装下 |
| 浮卡改动影响已验收组件 | 回归风险 | 浮卡只改 `Clear()` 一行，其余不动 |

> **已核实**：`TwinSparkline._capacity = 320`（320 点 ≈ 64 秒 @ 5Hz），**大于**方案的 300 点。
> 回填 300 点正好装下，**容量不用改**。这也是把缓冲定为 300 而不是 320 的原因之一——
> 留 20 点余量，避免回填瞬间触发 `RemoveAt(0)` 的批量搬移。

## 7. 验收标准

1. 点开任意设备 → **立即**看到完整 60 秒曲线，无"从空白长出"过程
2. 关闭再打开另一台设备 → 曲线同样是完整的
3. 浮卡与详情页显示同一台设备时，**两条曲线形状一致**
4. Console 无新增 GC 尖峰、无报错
5. 断网状态下行为不变（本方案不依赖任何网络）
