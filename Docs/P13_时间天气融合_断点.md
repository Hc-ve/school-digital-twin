### 0.1 CS0118：`'Weather' is a namespace but is used like a type`（6 处）

**根因**——这是个值得记住的 C# 名字解析陷阱，不是笔误：

```
枚举全名   SchoolTwin.Weather.Weather
             └──── 命名空间 ────┘└枚举┘
             —— 命名空间和里面的类型**同名**
```

在 `SchoolTwin.Twin` 里写 `Weather v` 时，C# 的解析顺序是：

| 顺序 | 查找位置 | 结果 |
|---|---|---|
| ① | 当前命名空间 `SchoolTwin.Twin` 的成员 | 没有 `Weather` |
| ② | **外层命名空间 `SchoolTwin` 的成员** | 有 `SchoolTwin.Weather`（**命名空间**）→ **命中，到此为止** |
| ③ | `using SchoolTwin.Weather;` 引入的类型 | 轮不到 |

第 ② 步先命中了命名空间，于是编译器认为"你拿命名空间当类型用"。

**为什么移植时没发现**：天气包自己那 8 个文件都在 `SchoolTwin.Weather` 内部，
第 ① 步就命中枚举，所以它们全部正常。**这个坑只在跨命名空间消费时暴露**——
而队员原来的 `CampusUI.*` 结构下，`CampusUI.Environment` 里并没有一个叫 `Weather`
的**子命名空间**，所以原包也不报错。是"改成 `SchoolTwin.Weather` 之后"才出现的。

**修法**（`TwinWeatherBridge.cs:22`、`TwinTimeWeatherCard.cs:9`）：

```csharp
using WeatherKind = SchoolTwin.Weather.Weather;
```

**为什么选别名，不改枚举名**：`EnvModels.cs` 里两个枚举的名称与**数值顺序**是队员包的
接口约定（序号可能进存档/序列化），改名会连带影响 9 个移植文件；别名只影响两个
消费者文件的可读名，改动面最小、风险最低。

### 0.2 Shader `_LightColor0` 未声明

**根因**：`_LightColor0` / `_SpecColor` 定义在 `UnityLightingCommon.cginc`，
而它只被 `Lighting.cginc` 引入（`AutoLight.cginc` 只引 `HLSLSupport` + `UnityShadowLibrary`，
不含灯光颜色）。我改写 URP 版时只补了 `UnityCG` + `AutoLight`，漏了 `Lighting`。

URP 版里主光颜色由 `Light` 结构体带进来，所以原版没有这个 include —— 是**改写时的遗漏**。

**修法**（`SnowGround.shader:76`）：补 `#include "Lighting.cginc"`。

> 顺带核实过：`_WorldSpaceLightPos0` 在 `UnityCG.cginc:191` 已被引用，随 UnityCG 到位；
> `ShadeSH9` 在 `UnityCG.cginc:359`，是纯函数无关键字依赖；`UNITY_LIGHT_ATTENUATION`
> 只在 `#ifdef DIRECTIONAL` 下定义 —— 编译日志里该变体确实带 `DIRECTIONAL`，成立。

### 0.3 Shader `texCUBElod` 找不到重载

**根因**：d3d11 下 Unity 把反射探针拆成两半声明（`HLSLSupport.cginc:480`）：

```hlsl
#define UNITY_DECLARE_TEXCUBE(tex) TextureCube tex; SamplerState sampler##tex
```

而 `texCUBElod` 要求纹理与采样器**合并成一个 `samplerCUBE`**，两半拆开时
d3d11 就只剩 `texCUBElod(samplerCUBE, float4)` 一个候选，全都对不上——
报错信息里列的四个候选正是这个原因。

**修法**（`WetGround.shader:186`）：

```hlsl
half4 enc = UNITY_SAMPLE_TEXCUBE_LOD(unity_SpecCube0, R, _Gloss);
```

这是 Unity 的跨平台封装宏，按平台自行展开（`HLSLSupport.cginc:491`）：

| 平台分支 | 展开结果 |
|---|---|
| d3d11 等 | `tex.SampleLevel(sampler##tex, coord, lod)` ← 分离采样器 |
| GLES 等 | `texCUBElod(tex, half4(coord, lod))` |

> `UNITY_SAMPLE_TEXCUBE_LOD` 是 **3 个参数**（tex, coord, lod），
> 与 OpenGL 分支那个 2 参数的 `texCUBElod(tex, half4(...))` 不是一个东西，别混。

## 一、施工第一步先验：68 盏 Area 灯的 lightmapping 实际模式

任务包要求"施工第一步先验，结论写进回执"。**已做，结论如下。**

直接解析场景 YAML（`Assets/TirGames/SchoolScene/Scenes/SchoolSceneDay.unity`，
按 `--- !u!108` 切 Light 文档，共 **69 个**）：

| `m_Type` | `m_Lightmapping` | 数量 | 含义 |
|---|---|---|---|
| 3（Area） | **2** | **68** | **Baked** |
| 1（Directional） | 1 | 1 | Mixed |

按 Unity 官方枚举 `LightmapBakeType`（`UnityCsReference/2022.3/Runtime/Export/Graphics/GraphicsEnums.cs`）：

```csharp
Realtime = 4,  Baked = 2,  Mixed = 1      // [Flags]，2 的幂
```

**结论：68 盏 Area 灯全部是 Baked。**

**据此的施工决策（与方案 §3.3 一致）**：

- **接受「夜晚室内保持亮」，不重烘光照**。Baked 灯不受实时光照参数影响，
  压暗它们只能重烘烘焙贴图 —— 任务包明令禁止，且答辩前重烘有炸场景风险。
- 所以夜间压暗**只作用在三处**：① 平行光的实时直射 ② 环境光（`RenderSettings.ambientIntensity`）
  ③ 后处理曝光（`postExposure`）。室内被 Baked 灯照亮的墙面/地面**会保持原亮度**。
- 这个"室内亮、室外暗"的组合在夜景里其实**不算破绽**：室内开着灯本来就是亮的。
  但它确实不是"整屏变暗"，答辩时若被问到，口径就是「室内灯是烘焙的，夜晚室内保持照明」。

> ⚠️ 一处**自我订正**：我上一轮曾写「实测 `2` = Mixed，推翻了方案预判」，**那是错的**。
> 当时凭记忆列的映射表把 2 当成了 Mixed。查官方定义后确认 `2` 就是 Baked，方案 §3.3 正确。
> 教训：枚举数值必须查官方定义，不能凭记忆写映射表再拿它去判案。

## 五、关键设计决策

### 5.1 `TwinDialDragArea` 为什么必须拆成独立文件

Unity 只认「**文件名 = 类名**」的 MonoBehaviour 为可挂载组件。上一版把本类写在
`TwinTimeWeatherCard.cs` 里，编辑器里能跑（已编译进 dll），但这是**同型病的一种**：
同一个东西在两处有定义。拆开后 49 行独立文件，符合项目其余脚本惯例。

### 5.2 为什么必须有 `TwinWeatherBridge` 这一层

本项目已踩过 4 次的同型病：**同一件事只能有一个状态源/出口**。天气这件事天然有两套：

| 侧 | 类 | 管什么 |
|---|---|---|
| 视觉 | `SchoolTwin.Weather.EnvironmentState` | 7 档天气 + 3 档昼夜：天空盒、平行光、雾、雨雪粒子、云穹顶、积水、积雪 |
| 数据 | `SchoolTwin.Data.TwinClimate` | 4 档天气 + 连续小时数：室温、湿度、室外温度 |

如果 UI 里分别写两行 `env.SetWeather(...)` + `TwinClimate.SetWeather(...)`，
只要有人在别处只调了其中一行（**自动轮换 `WeatherDirector` 就会调第一行**），
就会出现「天在下雪、室温按晴天算」——两条数据都"正常"，放一起才发现矛盾。

**已收口的 3 个入口**：面板选天气（P13-12）、自动轮换（P13-11）、表盘拖动（P13-14）。

**7 → 4 档映射采用多对一，是有意的**：

| 视觉（7） | 数据（4） | 理由 |
|---|---|---|
| Clear | Sunny | 晴就是晴 |
| Cloudy / Overcast / Fog | Cloudy | 都是"太阳被挡"，日较差同族 |
| Rain / Storm | Rainy | 模型里没有雨量项，雷雨对室温无附加影响 |
| Snow | Snowy | 雪 |

`TwinClimate` 的 `WeatherBiasC` 只区分四种物理行为，硬给雾和雷雨各分一档，
唯一结果是多两个数值几乎相同的分支。

### 5.3 `postExposure` 为什么走反射而不是直接引用

直接 `using UnityEngine.Rendering.PostProcessing;` 会让整个工程的编译**依赖后处理包**。
删包就瘫痪编译。走反射则**删包只掉功能，不瘫痪编译**（判据 P13-34）。

两个必须同时做到的细节：

1. **`m_Resources` 是私有 `[SerializeField]`**，只能靠 `layer.Init(res)` 赋值；
2. **`volume.profile` 的 getter 会 Instantiate 副本**，必须写 `sharedProfile`
   （否则改的是临时副本，场景里那个卷永远是默认值）。

还有一处：`FloatParameter` 继承 `ParameterOverride<float>`，`value` 与 `overrideState`
都是 **public 字段**，**只写 value 不置 overrideState 不生效**（判据 P13-35）。

### 5.4 卡片居中为什么不用图纸的绝对 (260,180)

本项目主画布是 `match=0` 的 CanvasScaler：**窗口比例变则画布高度变**
（P29-3.6 已记录过 1069×654 窗口下画布只有 1004×614）。

那时绝对 y=180 会让卡片偏上/偏下，而"居中"才是图纸的真实意图。
改用中心锚点后：1000×720 下算出来仍是 (260,180)，其它尺寸下自动保持居中。

### 5.5 拖动的 dy 符号（最易错处）

面板内部是"y 向下"（`Place` 的 y 向下），但 `atan2` 必须用数学坐标（y 向上）。
命中区是 200×200、pivot 左上角，所以圆心在命中区局部坐标里是 `(100, −100)`：

```csharp
float dx = localPoint.x - cx;        // cx = 100
float dy = localPoint.y - cy;        // cy = −100，这一减已包含"向上为正"的换算
float deg = Mathf.Atan2(dx, dy) * Mathf.Rad2Deg;   // 0°=正上方，顺时针为正
double hour = deg / 15.0;            // 360°/24h = 15°/h
```

写错这个符号的后果是 12 点方向被判成 6 点，指针整个上下颠倒。

#### 根因：场景里从来没有 `EnvironmentState`

**「点了按钮什么都没有」不是按钮坏了，是接收方不存在。** 而这条 `return` 不报错，
所以从 Console 到画面全都"正常" —— 这类静默失败最难查。

已排除的其他假设（逐个验过，都不是原因）：

| 假设 | 结论 |
|---|---|
| `EnvSample.Rain` 预设值太小 | ❌ 不是。`rain = 1.0f` × `RainRateMax = 3200` |
| 粒子构建配置错 | ❌ 不是。`maxParticles = 9000`、`gravityModifier = 1.3f`、`renderMode = Stretch` 都正常，且 `BuildRain` 内部有 `ps.Play()` |

| 相机太高 `altFade` 归零 | ❌ 不是。第三人称相机初始 y=6.0，60m 以下 `altFade = 1` |
| 判成室内 `indoor` 导致归零 | ❌ 不是。用户在室外（但头顶 40m 有遮挡时仍会判室内，已留诊断项） |

#### 修法：运行时自举（**不往场景摆任何物件**）

新增 `Assets/_Project/Scripts/Weather/TwinWeatherBootstrap.cs`（约 200 行）：

```csharp
[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.AfterSceneLoad)]
private static void Mount() { ... }
```

四个设计决定及理由：

| 决定 | 理由 |
|---|---|
| **用 `AfterSceneLoad` 自举，而不是让用户跑菜单挂组件** | ① P13 任务包明令「禁止手动往场景摆天气物件」，上一版方案本身就违规；② 本工程已有成形做法：`TwinPerfBootstrap` 修「F6 没反应」用的就是这套（同样是"组件从未挂进场景"、同样按 guid 查到引用数 0）；`TwinPowerController` / `TwinBellScheduler` / `TwinDeviceModel` / `TwinDevicePresenter` / `TwinDrawer` 全是自举 |
| **用 `TwinRuntime.Instance` 当"是不是孪生场景"的判据** | 不硬编码 `SchoolSceneDay`（场景名一改就静默失效）；按 guid 查过 `TwinRuntime` 只在 Day 场景有一份，与"孪生演示场景"等价；与 `TwinPerfBootstrap` 口径一致。菜单/废弃场景因此不会被塞进天气系统 |
| **必须新建独立 `[Environment]` 根节点，不能挂 `TwinRuntime` 身上** | `EnvironmentState.Awake` 第一句就是 `DontDestroyOnLoad(gameObject)`。挂到 TwinRuntime 上会把 **Bus / Registry / 所有数据源线程一起搬进 DontDestroyOnLoad 场景**，切场景后旧 runtime 不销毁，第二份起来时两个实例互相 Destroy。这是"挂错父物体"造成的最坏情况 |
| **`WeatherDirector.auto = false`** | 答辩时天气每 90~200 秒自己跳会打断讲解节奏，演示要的是"我点它就变" |

顺带修掉**三个创建点 → 一个**（同型病）：

| 位置 | 原来 | 现在 |
|---|---|---|
| `TwinWeatherBootstrap` | —— | `EnvironmentState env = go.AddComponent<EnvironmentState>()` ← **唯一** |

## 十、本轮教训（写给下一轮的我）

1. **枚举数值必须查官方定义**。我上一轮凭记忆写了 `2 = Mixed` 的映射表，还拿它去
   批评方案错了。实际 `2 = Baked`。凭记忆写的对照表一旦进判据，会一路错到底。
2. **改命名空间不是"批量替换字符串"就完事**。`CampusUI.X` → `SchoolTwin.Weather`
   时，若新名字与某个类型同名，会在**消费者侧**炸出一片 CS0118。移植后必须
   逐个消费者文件验证，不能只验证被移植的文件。
3. **"编译失败"和"没有编译"是两件事**。dll 时间戳没变，我第一反应是"Unity 没编译"，
   实际它编译了、失败了、所以没写 dll。判据要看 **Editor.log 里有没有该轮 CompileScripts**，
   不能只看 dll mtime。
4. **一个纹理采样写法在两个管线/两个平台下可能完全不同**。`texCUBElod` 在 GLES 下能用、
   在 d3d11 下因为采样器被拆开而失效 —— 这类"只在目标平台报错"的问题，
   静态审代码审不出来，只能靠真机编译。
5. **写判据前先实测命中数**。本轮 41 条全部事先跑过，所以一次全绿；
   但 P13-10 那条我漏转义了一个 `)`，写成了 `ToData\(v\);`（少了 `\)`），
   结果是"永远不命中、判据永远红"。**判据本身也要验证**。
6. **同一个坑我踩了第三次，说明"记住"不管用，只能靠判据拦**。
   `Weather` 命名空间遮蔽同名枚举这件事，我在 `TwinWeatherBridge` 踩过一次、
   在 `TwinTimeWeatherCard` 踩过第二次，然后**新写两个 Editor 工具时又踩了第三次**（5 处 CS0118）。
   教训：光在文件里写注释"别再犯"没用，必须加 `grep` 判据 —— 现已补 P13-44 / P13-45。
7. **别急着让用户跑菜单，先问"这件事该不该由用户做"**。
   我把"往场景挂组件"做成菜单让用户点，理由是"编辑器装配走 Editor 脚本"——
   但任务包明令禁止往场景摆天气物件，而项目里早就有运行时自举的成形做法。
   **方案错了，做得再规范也是错。** 判断标准应是"这件事的正确答案在哪个层"，
   而不是"我手上这把锤子能怎么敲"。
8. **`cat >> file <<'EOF'` 里的反斜杠会被 MSYS 吃掉**。我往 `status_checks.txt`
   追加 10 条判据，其中 `\[` / `\(` 被路径转换改成了 `/`，导致 P13-46 变成
   `/[RuntimeInitializeOnLoadMethod/(...)/]` —— 一个永远不命中的判据。
   写含正则的文件必须走 Edit/Write 工具，不能用 heredoc
   （上一轮 `cat >> << EOF` 因正文含 `csc.exe` 被安全扫描拒过，那是另一个原因，结果一样）。

| ① 远场盘 | `snowGroundFar.gameObject.SetActive(false)` | **无变化** | 否定 z-fighting（queue 2995 vs 2996）。远场盘与近场盘在重叠区只差 0.05m 抬升，即使有 z-fighting 也只是**远场盘外缘**的一圈，不可能横贯室内 |
| ② `_EdgeFade` | 0.55 → 0.35，`discard` 阈值 0.003 → 0.02 | **无变化** | 否定淡出尾段半透亮环。实测边缘淡出带在半径 `r∈[0.35,1]`，投影在**屏幕最外侧竖边**，不是横线 |
| ③ 抬升量 | `SnowGroundLiftNear/Far` 0.30/0.35 → 0.05 | **无变化** | 否定「雪面比墙底高 0.30m 形成悬空亮边」 |
| ④ **`SnowOnTrees`** | 见 11.3 | **白线消失** | ★ **真根因** |

### 11.2 为什么 ①②③ 必然全错（先算完再动手，不是试出来的）

雪盘几何本身**在数学上不可能**产生那条线，两条独立证据：

1. **几何证据**（自检日志实测）：`竖直面（高差>1.6m）= 0 处`、`mesh.bounds Y 跨度 = 0.20m`。
   一块跨度只有 0.20m 的水平面，没有任何竖直面，产生不了横线。
2. **投影证据**：雪盘世界高度 `y∈[-0.20, 0.00]`，相机在其上方 3m。
   90m 见方雪盘在 `fov=60 / 高度 1080` 下，最远角点的投影只到**屏幕行 571**
   （画面中心 540 之**下**）。而白带实测在画面中心之**上**（室内截图行 291 / 视口中心 328，
   室外截图行 575 / 视口中心 573）。方向都不对。

⚠️ 教训：**候选清单是主理人根据截图猜的，不是实测的**。
我在前四轮里一直被"雪盘"这个前提牵着走，反复改 `DrapeSnow` 的限幅逻辑，
而日志早已证明雪盘是干净的。**应当先用量化证据排除，再动手改代码。**

### 11.3 真根因：`SnowOnTrees` 两个 bug 叠加

```
① SnowOnTrees.cs:73   SampleHeight 漏加 terrain.GetPosition().y
   Terrain.SampleHeight() 返回**地形相对高度**，本场景 Terrain 的
   m_LocalPosition.y = -0.5 → 所有树根雪堆整体**抬高 0.5m**

② SnowOnTrees.cs:88   顶点用**世界坐标**写入 mesh（wx/wz/wy 全是世界量）

③ WeatherVisuals.cs:750  用 SetParent(transform, false) 挂成子节点
   而本组件 LateUpdate 每帧 transform.position = cam.transform.position
   → 世界坐标又被平移了一次，位置彻底错乱

④ 结果：几十块 pileRadius=3m 的**水平圆盘**，y 全部相同，且恰好压在
   相机眼高（≈ -0.48）附近 → 视线与这堆平面**共面**
   → 透视把圆盘全部压扁，收束成**一条横贯全屏的横线**
   → 材质 renderQueue=2997（高于近场 2996 / 远场 2995），所以它盖住墙体和人物
```

这一条能解释用户观察到的**全部**特征，且相互自洽：

| 观察到的现象 | 由哪一环解释 |
|---|---|
| 颜色恒定 `(R179±5.5, G189±3.2, B208±7)` | 同一材质、同一朝向（全是水平面）、同一光照 |
| 偏蓝白、与雪同色 | `_SnowColor=(0.92,0.95,1.0)` + `_SkyColor` 提亮 |
| 能盖住树干与墙体 | `renderQueue=2997`，排所有雪盘之上 |
| 室内也有 | 树遍布校园，室内视线同样穿过这堆平面 |
| 透镜形、中间厚两端尖灭 | 水平圆盘被压扁后的透视外形 |
| **是回归 bug**（用户 17:59 截图已有） | `SnowOnTrees.cs` 与 `EnsureTreeSnow` 都是提交 `c3871f9`（**11-04 11:56**）才引入的 |

### 11.4 采用的修法（3 处）

| # | 文件 | 改动 |
|---|---|---|
| 1 | `SnowOnTrees.cs` `Build()` 开头 | `transform.SetParent(null, true)` + `position=Vector3.zero` + `rotation=identity` + `localScale=one`。<br>把自身从跟随相机的层级摘出来，钉死世界原点 —— 顶点是世界坐标，transform 就必须是单位变换 |
| 2 | `SnowOnTrees.cs:73` | `float wy = tpos.y + terrain.SampleHeight(...) + 0.02f;`（补齐地形 Y 偏移） |
| 3 | `WeatherVisuals.cs` `EnsureTreeSnow()` | 不再 `SetParent(transform)`；改用 `Object.FindObjectOfType<SnowOnTrees>(true)` 做幂等判断（因为对象已脱离本层级，`GetComponentInChildren` 会漏判导致重复创建） |

### 11.5 留给下一轮的判据（已写进自检日志）

`BuildIndoorAudit` 新增两条，Play 一眼可判：

1. **雪面世界 Y vs 相机眼高**：`差 < 0.30m` 即打印警告
   —— 一段水平半透明面片，高度一旦穿过眼高，必然在屏幕上收成横线。
   这条判据**不需要截图**就能定性，是本轮最该早有的检查。
2. **`TreeSnowPiles` 位置**：打印 `pos` / `parent` / `transform归零` / `包围盒 Y 区间`。
   正常应为 `pos=(0,0,0)`、`parent=null(已脱离，正确)`、`transform归零=是(正确)`。

### 11.6 本轮教训

1. **"是回归 bug"这个信息比任何候选清单都值钱。** 主理人一句「之前没这个 bug」，
   配合 `git log --diff-filter=A` 一查，`SnowOnTrees.cs` 是 11:56 引入的、
   而 17:59 的截图已有白线 —— 五分钟锁定。
   **以后遇到"诡异、稳定、位置恒定"的渲染问题，第一个动作应是查新增文件，不是查代码细节。**
2. **颜色方差是最强的分类器**：`sd(R/G/B) = 5.5/3.2/7.0` 说明是一块**恒色面片**，
   而不是半透明叠加（叠加会随背景变化）。这类量化特征比肉眼看"白线"可靠得多。
3. **候选清单不能代替证据。** 我在 ①②③ 上花了四轮，而日志里的
   `竖直面=0 / 跨度=0.20m` 早就把雪盘排除了。
