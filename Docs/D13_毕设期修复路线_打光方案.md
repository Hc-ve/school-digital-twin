## 0. 结论（三句）

1. **答辩期那条「运行时绕过」路线在毕设期仍然不通，但理由变了**：不是时间不够，是它必然牺牲立体感（C-73 已正式关闭）。转毕设真正打开的是「重烘 / 补光」这些此前被 72h 冻结、止损闸禁掉的选项。
2. **但「重烘能修好」这个前提本身没验证过，且现参数不支持乐观**：`m_PVRBounces: 2`、`m_CompAOExponent: 1.25`；下表面 `N·L = 0`，直接光恒为 0、只靠两次间接反弹，AO 还会额外压暗翅片缝隙。照现状整场重烘，暖气片大概率仍黑。
3. **靶子已经有了，不必等 494 条全量清单**：C-84 已把主理人 play 实测「暖气片 **9/9 全黑**、窗框 **13/14 黑**」写入台账，这是第一验收标准、可信。建议第一步**直接对这批确定对象做小范围、可逆、零资产改动的验证**，而不是再等一轮工具返工。

> ⚠️ 第 3 条**偏离定盘 C-86 刚定的排序**（D14 → 工具三缺陷 → v4 清单 → UV 块真清单），属需裁决的冲突点，见 §6。我不擅自改顺序。

## 2. 硬约束：为什么重烘不是必然解（文件实证）

`Assets/TirGames/SchoolScene/Scenes/SchoolSceneDaySettings.lighting` 实测：

| 参数 | 值 | 含义 / 后果 |
|---|---|---|
| `m_EnableBakedLightmaps` | 1 | 只开烘焙 GI，无实时 GI |
| `m_PVRBounces` | **2** | 间接反弹仅 2 次；背光面只能靠反弹取光 |
| `m_CompAOExponent` | **1.25** | AO 偏强，翅片缝隙 / 竖梃内角会被进一步压暗 |
| `m_AmbientMode` | 0（Skybox） | 环境光走 Skybox，对朝下面贡献接近 0 |
| `m_PVRSampleCount` / `m_PVRDirectSampleCount` | 512 / 32 | Progressive Lightmapper 参数，说明该 `.lighting` 已被 Unity 2022 升级过，非 2017 原档 |
| `m_LightmapMaxSize` / `m_BakeResolution` | 1024 / 30 | 图集分辨率上限，翅片级细节本就烘不进去 |

物理链条（总纲 §3.1 已定性，未变）：69 盏光源全在天花板下方朝下照 → 吊顶下表面、暖气片翅片背面、窗框竖梃内角的法线背对主光 → `N·L = 0` → 直接光 0；间接光只有 2 次反弹且被 AO 1.25 压制 → 该 UV 块烘成 0。

> **推论**：仅重烘、不加任何补光或反弹面，输入条件没变，输出仍是 0。**重烘前必须先解决「这些面凭什么收到光」**，否则烧机时只会得到一张新的黑图。
> 另：内置管线的 Bake 是整场景行为，**没有「只烘某几个对象」的原生开关**；C-73 说的「局部重烘」需要额外方案（独立场景副本 + 专用图集 + 运行时重定向），成本高且要断点配合。

## 4. 第一步落地方案：一次编辑器占用，三件产出

> 全部为**离屏 batchmode 渲染 + 运行时内存操作**，不保存场景、不写 `.asset`、不改材质、不重烘。跑完即释放编辑器。

| # | 动作 | 产出 | 占用 |
|---|---|---|---|
| **A · D14 验证**（定盘点名可立即发） | 三块吊顶 `ZalTop` / `PCClassTop` / `DirectorTop` 在「保留 -1」与「临时去掉 -1」两种状态下同机位渲染对比 | **P33 报告** + 6 张对比图，定路径表是 12 条还是 9 条 | 约 90 秒 |
| **B · 新路线验证（我提出）** | 对 1F 走廊暖气片与 `Windows1` 窗框区域，**运行时临时加一盏朝内/朝下的实时补光**（内存中 `AddComponent<Light>`，不落盘），渲染 before/after | 判断「不重烘、不压平立体感」能否去黑 | 同一轮 |
| **C · C-85 UV 块判读** | 导出 `Windows1` 四个子网格的 UV2 范围 + 对应图集区域亮度映射 | 给断点的 UV 块级输入，确认「1 亮 3 黑」的块边界 | 同一轮 |

**为什么 B 值得先验（技术依据，标注为待验证假设）**：
Unity Standard shader 在 `LIGHTMAP_ON` 分支下**仍会叠加实时直接光**，lightmap 只替代烘焙/间接光。此前「抬环境光无效」是因为 ambient 属间接光、被 lightmap 取代（PNG 字节一致实证）；但 P17 案例（`pixelLightCount` 4→12 + `ForcePixel` 后灯管周围天花板变亮）证明**实时直接光确实能照亮这些面**。故「补实时光」与「抬环境光」不是一回事，前者是尚未被证伪的新路线，且不放弃烘焙明暗。

**B 的已知风险（必须一起验）**：
- 现有 Directional 是 `m_Lightmapping: 1`（Baked），完全不参与实时渲染；补光须**新增**，不能改现有灯（改了就是动烘焙基线）。
- `pixelLightCount: 12` 已被 P17 占用；新增实时光可能抢名额，导致族⑥「灯管周围天花板又变暗」复发。
- 补光范围控制不当会整体提亮房间，需目视确认墙面/地板不发灰（沿用 P30 验收口径）。

> **推荐顺序**：先 B（可逆、零资产、成本最低）→ B 不成立再评估 A 类局部重烘 → UV 块贴图直改作为兜底（工程内无 EXR 编码库，实现成本最高）。

## 5. 三阈值裁决（C-87 归打光，基于 rescan 实测给初判）

| 阈值 | 当前值 | 我的裁决 | 依据 |
|---|---|---|---|
| `RenderBlackThreshold` | 0.10 | **维持 0.10，但须注明只作用于「渲染最暗帧」** | 暖气片最暗帧 0.0382–0.0902 全可抓；ZalTop 反例 0.2803 不会误判 |
| `LocalDarkRatioThreshold` | 15% | **建议提到 40%** | 真黑样本 57%–100%，15% 会把正常明暗过渡一并抓进来 |
| `RenderBrightReference` | 0.25 | **维持 0.25，且明确只用于 ZalTop 反例断言，不参与对象分类** | ZalTop 渲染 0.2803 > 0.25 成立 |

**但阈值治不了 C-83 的误报**：`DoorWindowsWood1`（原生深色木门）渲染最暗 0.0755、暗占比 67%、UV 0.0914，数值形态与真黑暖气片几乎一样。提高阈值到 40% 也分不开它。根因是**缺 albedo 归一化 / 原生深色材质白名单**，属 C-86 三缺陷之一。

> **裁决建议**：三个值先按上表记入「暂定」，**不要现在拍死**。等工具三缺陷修复 + 主理人 Ctrl+R 出 v4 清单后，用可信数据一次性定死，避免把基于不予采信样本的数值锁进判据库（重演 C-84「用坏尺子校另一把」）。

## 7. 顺带完成：C-89 缺号核查（定盘指派）

| 项 | 实测 |
|---|---|
| 口径 | `24 × _comp_light.exr` + `24 × _comp_dir.png` = 48 文件（与 C-89 一致） |
| 缺失 | **`Lightmap-23_comp_dir.exr`**（0–22 共 23 个 exr 齐全，23 号只有 png） |
| 配套 | 23 号的 `_comp_dir.png` / `.png.meta` / `_comp_light.exr` / `.exr.meta` **全在** |
| `.meta` 计数 | `_comp_dir.exr.meta` **23** 个 / `_comp_dir.png.meta` **24** 个 |
| 判定 | 属 2017 年烘焙产物格式不统一的历史残留（0–22 号 exr 与 png 双份并存、各有独立 guid；23 号只出了 png）。**与暖气片/窗框发黑无因果**——发黑是 UV 块无光，方向贴图缺失只会丢方向性高光，不会让面变纯黑 |
| 建议 | **不单独立项、不补文件**，随将来重烘一起统一；与定盘「不影响运行时」的判断一致 |

> 诚实标注：`LightingData.asset` 是 Unity 5.6 二进制格式，内部引用未以文本 `guid:` 形式存储，我**未能确证运行时引用的是 exr 路线还是 png 路线**；但 24 张 png 全部有 `.meta`（即全部是可导入资产），足以支持「不缺可用方向贴图」的结论。
