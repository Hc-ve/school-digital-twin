## 〇、一句话结论

**„效果很假" 不是参数没调好，是形态范式错了。**

我第一轮把粒子当成「点」来调 —— 放大、加不透明度、换柔边贴图。
无论怎么调，出来都是**点阵**。而参考图里是**沿吹风方向拉长的光丝交叠成雾**。

点阵和雾丝是两个不同的东西，不是同一件事的两个档位。

## 一、五轮排查的完整路径（含三次误判）

### 第一轮：白色硬边方块（真缺陷）

**现象**：截图里每个粒子是一个白色方片，像纸屑在空中飘。

**根因**：`BuildParticleMaterial()` 只做了 `Shader.Find`，**没给 `_MainTex`**。
`Particles/Standard Unlit` 的 `_MainTex` 默认是白图 → 每个粒子 = 硬边白方块。

**修法**：代码生成柔边贴图（零素材红线不破）。

**教训**：`Shader.Find` 成功不等于材质可用。用粒子材质必须显式设贴图。

---

### 第二轮：点太小太散（真缺陷，但修错了方向）

**现象**：方块没了，但变成一堆散开的小白点，像加湿器。

**我改的**：

| 参数 | 原来 | 改成 |
|---|---|---|
| `startSize` | 0.055~0.135 | 0.18~0.42（3 倍） |
| `rateOverTime` | 22 | 14 |
| `startColor.a` | 0.14 | 0.30 |
| `shape.angle` | 12° | 8° |

**结果**：还是不像气。用户反馈「效果很假」。

**这里我犯了一个长周期的错**：我把「不像气」归因成「参数不对」，
连续两轮都在**同一个范式内微调参数**（大小、透明度、密度、锥角）。
而真正的差别在范式 —— 见第三轮。

> **判据**：如果你已经调了 3 个以上参数、方向都合理、结果仍然"不对"，
> 那多半不是参数问题，是**你选的这个东西本身不对**。停下来换范式。

---

### 第三轮：对照参考图，发现是范式错（关键转折）

用户给了**队员王绍锋实现的空调风反馈截图**。两张图放一起对比：

| | 参考图（王绍锋） | 我的第一版 |
|---|---|---|
| 单个粒子 | 沿吹风方向**拉长**的光丝 | 各向同性的**圆点** |
| 粒子之间 | 互相交叠、边缘融合成一片雾 | 各走各的、空隙清晰 |
| 形状 | 不规则、有卷曲 | 规整的圆 |
| 边界 | 看不见 | 每一颗都能数清 |

**结论：把粒子做成"圆点"，无论调多大都是点阵。点阵永远不像气。**

这一轮改的是四件事，缺一件都不成：

**① 渲染模式 `Stretch`**

```csharp
pr.renderMode = ParticleSystemRenderMode.Stretch;
pr.lengthScale = 2.3f;
pr.velocityScale = 0.35f;
pr.alignment = ParticleSystemRenderSpace.View;
```

`Stretch` 沿**速度在屏幕上的投影方向**拉伸 —— 朝哪飞就往哪拉长，方向自动正确。

**② Noise 模块（丝状感真正来源）**

```csharp
noise.enabled = true;
noise.strength = new ParticleSystem.MinMaxCurve(0.11f);
noise.frequency = 0.40f;
noise.scrollSpeed = new ParticleSystem.MinMaxCurve(0.22f);
noise.damping = true;
```

只有 Stretch 没有 Noise，出来的是一把**笔直的针**，像激光。
丝之所以像丝，是因为轨迹被低频噪声推着走，会卷、会摆、会互相穿插。

**③ 基础尺寸反而要收小**（0.18~0.42 → 0.10~0.22）

拉伸会放大到 2~3 倍长。基础尺寸不收小，拉出来是「一片巨大的白布」。

**④ 速度提上去**（0.45~0.85 → 0.75~1.35）

Stretch 的长度 ∝ 速度。第一轮速度太慢，就算开了拉伸也只有短短一截。

### 第四轮：两个隐性错，比参数影响更大

**① 重力方向反了**

第一版 `gravityModifier = -0.015f`。
负值是**往上飘**（那是烟、是热气）。冷气是**下沉**的。

改成 `+0.012f`。

这一条单独看无所谓，但叠在「本来就是点阵」上，
整个效果就变成「一堆白点往上飘」—— 和空调冷气是**相反的物理**。

**② 混合模式用了 Additive，在白墙教室里等于没效**

第一版我把 `_DstBlend` 设成 `One`（加色混合），理由写的是
「气流是发光的雾气，重叠处自然变亮」。

**这个理由只在深色背景成立。** 本项目的教室是：
- 白墙 / 浅色黑板
- 白天光照，环境光很亮

加色混合在亮背景上**不产生可见差异**（白 + 白 = 白）。
结果就是「白墙上多了一块更白的糊」，丝状结构全被吃掉。

改成 `SrcAlpha / OneMinusSrcAlpha`（Alpha Blend）：
在亮背景上表现为**真实的半透明白雾**，能看见丝的边缘。

> **这是本轮最值得记的一条**：一个在教程里被反复推荐的设置（Additive =
> 发光雾气），换到「亮背景」这个具体环境里就完全失效。
> **参数的正确性依赖于环境，不依赖于它看起来多合理。**

---

### 第五轮：贴图从「实心圆」改「高斯长尾」

第一版 `(1 - r²)²` —— 中心很实、到 r=1 处刚好归零。

在**圆点**形态下没问题。但一旦 Stretch 拉伸：
四次方衰减的中段（r≈0.5~0.8）掉得不够快，横向拉 2~3 倍后
变成一根**边缘清晰的实心棒**，像拉丝的糖。

改成高斯 `exp(-4.2 r²)`：

| r | alpha |
|---|---|
| 0 | 1.000 |
| 0.35 | 0.593 |
| 0.55 | 0.281 |
| 0.75 | 0.094 |
| 1.00 | 0.015 → 裁成 0 |

长尾一路拖到边缘才归零，拉长后就是**两端渐隐的丝**。

分辨率也从 64 提到 128 —— 丝被拉长后，64px 的横向插值有可见锯齿。

### 第六轮：Shape 的 rotation 那一行，让粒子在往下掉（最隐蔽的一个）

这一轮是在**改完前面五轮、自检代码时**发现的。它不是"效果不够好"，
是**方向根本错了** —— 但前面五轮的所有现象都能"解释得通"，所以一直没怀疑到它。

**错误代码**：

```csharp
shape.rotation = new Vector3(90f, 0f, 0f);   // 注释当年写的是"锥轴朝本地 +Z"
```

**这句注释本身就是错的。**

Unity 的 `ParticleSystemShapeType.Cone` **默认就沿本地 +Z 发射**。
`shape.rotation` 是**相对本地坐标系的附加旋转**，不是"设置发射方向"。

绕 X 轴转 90° 的效果是把锥轴从 `+Z` 转到 **`-Y`（垂直向下）**。

**而 `root.transform.rotation` 已经做了这件事**：

```csharp
root.transform.rotation = Quaternion.LookRotation(blowDir, Vector3.up);
```

`LookRotation` 让本地 +Z 对齐 `blowDir`（朝房间内部、略向下 10°）。
所以：

| 层 | 实际朝向 |
|---|---|
| Transform 的 +Z | 朝房间内部（正确）✅ |
| Shape 转完之后实际发射方向 | 本地 -Y = **世界垂直向下** ❌ |

**粒子其实是在从出风口垂直往下撒，根本没朝房间吹。**

为什么前面五轮没发现：
- `simulationSpace = World` + `startSpeed 0.75~1.35` → 粒子有初速，
  在空中还是会散开一点，看起来"有东西在飘"
- 空调装在 2.4~6m 高，往下撒的粒子**正好落在视线里**，
  不像"朝墙里吹"那样一眼可见
- 前五轮我一直在看"粒子长什么样"，从没验证过"它往哪飞"

> **这是本轮最值得记的一条教训**：
> 一个**方向错误**可以伪装成"参数不对"很多轮。
> 因为方向错了以后，现象仍然是"有粒子在飘"，
> 而你会一直去调颜色、大小、透明度。
>
> **每隔几轮就该回到最基础的问题上验证一次**：
> 它现在到底往哪个方向发射？（用 Scene 视图的 Gizmo 一眼就能看出来）

**修法**：

```csharp
shape.rotation = Vector3.zero;   // Cone 默认沿 +Z，方向由 Transform 决定
```

**同一轮还修了发射区形状**：

`radius = 0.42` 是**一个直径 84cm 的圆盘** —— 那是加湿器喷头，不是空调。
真实壁挂空调出风口是**沿机身长边的一条窄缝**（约 3~5cm 高）。

用 `shape.scale` 把圆压成椭圆：

```csharp
shape.scale = new Vector3(1f, 0.28f, 1f);   // 垂直方向压到 28%
```

（本地 X = 沿墙方向，因为 Transform 的 Y 朝上、Z 朝吹风方向）

`shape.scale` 只影响**发射区形状**，不影响粒子尺寸 —— 这一点容易混淆。

## 二、三次误判（都是我脑子里先有结论，再去找证据）

### 误判一：两次把「两台空调在 6 米高空」当成 bug

**我怎么想的**：

日志里 5 台出风口位置：
```
Class1-2   y=2.33
Class1-3   y=2.48
Class1-4   y=2.47
Class2-1   y=6.26   ← 6 米
ClassDirector y=6.01 ← 6 米
```

「真实壁挂空调不会装到 4 米以上」→ 这两台是假锚点 → 粒子飘在天花板上看不见。

甚至已经把 `IsMockAnchor()` 写完了：

```csharp
if (go.transform.position.y > 4f) return true;   // 真实壁挂空调不会装到 4 米以上
```

**幸好接进去之前先翻了房间里的候选清单。判断是错的。**

真实的房间地板高度：

| 房间 | 地板参照物 | 地板 y | 空调 y | 离地 |
|---|---|---|---|---|
| Class1-2 | `Split01b` / `FlowerHolder01b` | ≈1.5 | 2.43 | 0.9 m |
| Class1-3 | `Split01c` / `FlowerHolder01b` | ≈1.5 | 2.58 | 1.1 m |
| Class1-4 | `Split01a` / `Blueprints05` | ≈1.5 | 2.57 | 1.1 m |
| **Class2-1** | `Table02` / `Radiator01 (3)` | **≈3.5** | 6.36 | **2.9 m** |
| **ClassDirector** | `TableOffice1` / `Radiator01 (2)` | **≈3.5** | 6.12 | **2.6 m** |

**关键事实：`Interior` 里有两层楼，二楼地板在 y≈3.5。**
`Class2-1` 和 `ClassDirector` 都在二楼，6 米对它们来说是**正常吊装高度**
（离地 2.6~2.9m，和一楼的 0.9~1.1m 是同一种相对关系）。

**如果我把 `IsMockAnchor` 接进去会怎样**：二楼两台被误判成假锚点 →
跳过 L1 走 L2 → 在房间里找「形状像空调」的 → 找到的还是那个 y≈6.1 的
`Split01a`（它形状完全正确）→ 但是 `TryFindAcByShape` 里有
`b.center.y < 1.60f || b.center.y > 3.40f` 这条高度筛选 → **真实空调被排除**
→ 退回 L3 兜底 → 「朝房间中心吹」，位置差得更多。

**一个错误的判据接进去，会让两台本来正确的空调变得更差。**

**附加发现**：`[MockPoints]/AC_Class2-1` 名字里带 Mock，
但它**身上真的有一个尺寸 (0.15, 0.30, 1.05) 的 Renderer** ——
和一楼三台 `Split01a/b/c` 完全同规格。

> **名字里带 Mock 不等于没有几何体。判断要看数据，不要看名字。**

**教训**：
1. 判据里的**每一根阈值，都必须有本场景实测的数值撑着**。
   「真实壁挂空调不会装到 4 米以上」是一句听起来很对的话，
   而它错在**默认了这个场景只有一层**。
2. **写好了不等于要接进去**。在接之前翻一眼实测数据，省下了一场误伤。

### 误判二：把「房间根节点位置」当成「房间中心」

**我怎么想的**：`GameObject.Find(zone).transform.position` 就是房间中心。

**实测把它打断了**：

Class1-3 的空调 x=12.42、Class1-4 的 x=12.92，**在同一侧墙**，
但推导出的吹风方向一个朝 `(-0.97,…)`、一个朝 `(+0.97,…)`。
**同一面墙不可能反着吹。**

根因：`transform.position` 是**根节点的 pivot**，
而 FBX 导出的空父节点 pivot 经常在门口、墙角、或世界原点 —— 不是房间中央。

投影符号跟着 pivot 偏 → 一半空调朝墙里吹。

**修法**：取房间里**所有 Renderer 的合并包围盒中心**（几何中心）。
这个量不受 pivot 影响，只跟房间里实际摆了什么有关。

**再加一层保险**：投影接近 0 时（房间特别窄、或空调恰好在中线），
改用**离墙远近**判断 —— 壁挂空调必然贴墙，朝远的那侧吹。

### 误判三：第一版的形状判据一条区分力都没有

第一版探针在 Class1-2 房间打出两个 ★：

```
★ "Split01b"         size=(0.15,0.30,1.05)   ← 真空调
★ "FlowerHolder01b"  size=(0.64,0.50,0.27)   ← 花盆架，误判
```

花盆架怎么混进来的：

| 判据 | 阈值 | 花盆架的值 | 结果 |
|---|---|---|---|
| `horizMax > 0.5` | 0.5 | 0.64 | ✅ 过 |
| `horizMin < 0.50` | 0.50 | 0.27 | ✅ 过 |
| `s.y < 0.70` | 0.70 | 0.50 | ✅ 过 |
| `y ∈ [1.6, 3.4]` | — | 1.87 | ✅ 过 |

**四条全过。**

差别不在绝对值上，在**比例**上：

| | 长边 | 厚度 | 高度 | 长/厚 | 长/高 |
|---|---|---|---|---|---|
| 真空调 `Split01a` | 1.05 | 0.15 | 0.30 | **7.0** | **3.5** |
| 花盆架 `FlowerHolder01b` | 0.64 | 0.27 | 0.50 | **2.4** | **1.3** |

补两条比例判据：`长边/厚度 > 3.0`、`长边/高度 > 2.5`。

同时收紧绝对值：厚度 `< 0.30`（原 0.50 太宽）、高度 `< 0.45`（原 0.70 太宽）。

> **绝对值判据永远会被「刚好落在范围内」的东西骗到。
> 比例判据才是形状的本质。**

## 三、API 名字踩的两个坑（编译失败 CS1061）

```csharp
noise.octaves = 1;                          // ❌ CS1061
noise.octaveCount = 1;                      // ✅

pr.renderAlignment = ...ParticleSystemRenderAlignment.View;   // ❌ CS1061 + CS0103
pr.alignment = ParticleSystemRenderSpace.View;                // ✅
```

**规律**：Inspector 里显示的标签名和 API 属性名经常不一致。

| Inspector 标签 | API 属性 | 类型 |
|---|---|---|
| Render Alignment | `alignment` | `ParticleSystemRenderSpace` |
| Octaves | `octaveCount` | `int` |
| Render Mode | `renderMode` | `ParticleSystemRenderMode` |

**不要凭 Inspector 的英文猜 API 名。** 写之前查一眼。

## 四、判据自己写错的两条（比代码错更该记）

### P14-05：`StopEmitting` 匹配到 4 处，报红

判据原文 `grep:1:...:ParticleSystemStopBehavior\.StopEmitting`。

`StopEmittingAndClear` 里**包含** `StopEmitting` 这个子串 ——
而 `StopEmittingAndClear` 是用在**初始化时清屏**的，属于正常操作。

收窄成 `ParticleSystemStopBehavior\.StopEmitting\)`（带右括号），
因为关机路径的写法是 `Stop(true, ParticleSystemStopBehavior.StopEmitting)`，
而清屏那条是 `StopEmittingAndClear)`。

### P14-13：署名判据永远红

判据要求 `grep:1:AcAirflowFeedback.cs:王绍锋`。

但 `status.py` 的 `eval_check` **默认剔除注释行**（`strip_comments`）——
这是为了防止「判据命中注释里的旧代码」（一天踩三次的老坑）。

而署名**天然写在注释里**（那是文档，不是代码）。
两条正确做法撞在一起，结果是一条永远红的判据。

**修法**：改查踩坑日志（md 文件不剔注释）。

> **这是「两个各自正确的设计组合起来错误」的又一例**（上一次是
> `SnowOnTrees` 的世界坐标 + 跟随相机）。
> 判据工具该剔注释（对），署名该写注释（对），组合起来判据查不到（错）。
> **遇到「永远红/永远绿」的判据，先怀疑判据本身，别去改代码讨好它。**

## 九、第二轮：气流通过了，但**完全没有嗡鸣声**

> 主理人验收原话：「效果看着还行，就是没有空调运行的嗡铭声，不真实」

### 先确认"链路通了没有"，别急着调音量

日志证明链路是通的：

```
[P14] 空调反馈已构建：5 台成功
[P14] Class2-1/AC/Unit_01 开 → 气流启动 + 嗡鸣淡入     ← 回调执行了
```

所以不是"没触发"，是**声音本身太弱或频段不对**。
这两种情况的修法完全不同，必须先把它们分开 —— 这就是后来加 `LogAudioSelfCheck()` 的原因。

### 根因一：音量只有提示音的 1/6

把两个数算出来对比：

| | 算式 | 峰值 |
|---|---|---|
| 「滴」提示音 | 波形 0.42 × `_beepVolume` 0.75 | **0.315** |
| 嗡鸣（上一版） | 谐波和 ≈1.13 × 0.30 × `HumMaxVolume` 0.16 | **0.054** |

差 **5.8 倍 ≈ −15 dB**。

而 `HumMaxVolume = 0.16` 当初是照"背景音不该盖过提示音"定的 ——
那句话本身没错，但没人算过它到底有多小声。
**"低调"和"听不见"是两件事，中间只隔一个乘法。**

→ 先改成 `0.55`。谐波部分 ≈0.19、风噪部分 ≈0.28，总峰值 ≈0.47，
与提示音同量级略高。提示音是 800Hz 短促脉冲，人耳对瞬态比对稳态敏感，
所以「滴」仍然盖得住。

**然后主理人现场试听说「音量有点大」，裁决调到 1/3 → `0.18`。**

于是这个值走完了三档：

| 值 | 相对提示音 | 结果 |
|---|---|---|
| 0.16 | 1/6（−15dB） | **听不见** |
| 0.55 | 1.5×（+3.5dB） | 听得见了，但**偏吵** |
| **0.18** | ~1/2（−6dB） | 折中：一直听得见，又不盖过人声 |

`0.18` 时总峰值 ≈0.154，约为提示音（0.315）的一半，即 −6dB。
标准音频分级里，**稳态背景声比瞬态提示音低 6dB 是常见做法**：
提示音仍然清楚，但空调不会在答辩说话时抢注意力。

> **教训（这算第四轮了）**：音量这种"感觉量"，**代码里算不出来也猜不出来**，
> 必须一轮一轮试听。我一开始想把它算准（"应该比提示音低多少 dB"），
> 结果算出了一个听不见的值。
> **该靠耳朵定的东西，就别指望靠算式定。**

> **另一个细节**：从 0.55 到 0.18 是线性幅度 ×1/3，**不是**感知上的"三分之一"。
> 人耳的响度感知近似对数，幅度 ×1/3 ≈ 响度降约 9.5dB ≈ 主观"小了一大半"。
> 主理人说"1/3"时如果指的是**主观响度**的 1/3，幅度应该 ×0.5 左右（约 0.28）。
> 我先按**幅度** ×1/3 实现（0.18）—— 因为"音量条拉到 1/3"通常指的就是幅度。
> 如果听着还是偏大，就改成 0.28；如果偏小，就回到 0.22 附近。
> **这个歧义必须写下来，否则下一轮又得重新猜。**

### 根因二（更关键）：真实空调声的主成分根本不是谐波

上一版只有 50/100/150Hz 三个正弦。

**纯谐波听起来像变压器/镇流器，不像空调在吹风。**

真实空调的运行声 = **压缩机的低频谐波 + 出风的宽带湍流噪声**，
而且**风噪占大头**。只叠谐波，就算音量够、就算喇叭放得出，
听感仍然是"电器嗡嗡"而不是"空调在运行"。

→ 加一层**带通白噪声**（风噪），占总音量 **55%**，谐波降到 45%（只作底噪基底）。

带通范围 `180 ~ 2400 Hz`，两端都有理由：

| 边界 | 值 | 为什么 |
|---|---|---|
| 下限 | 180 Hz | **笔记本内置喇叭的低频死区在 150~250Hz**，再低等于白给 |
| 上限 | 2400 Hz | 再高就变成"嘶嘶"的电视雪花声，不是风噪 |

### 根因三：3D 衰减把远处的声音吃掉了

上一版 `spatialBlend=0.75 / Linear / min 2 / max 16`。

Linear 滚降在 8m 处只剩 50%，再乘 spatialBlend 的 0.75 权重：
实际贡献 ≈ `0.5 × (1-0.75+0.75×0.5) ≈ 0.31`。

**而答辩演示时人站讲台，5 台空调都在 6~10m 外。** 等于正好落在最亏的位置。

→ `spatialBlend 0.45 / min 3 / max 30`。
空调嗡鸣本来就是弥漫的环境声，不需要精确声像；
满 3D 反而像"耳机里有个点"，不自然。

### 这里我犯了两个错（都是"凭直觉写，没算"）

#### 错误一：带通用的"两个低通相减"，低频根本不衰减

第一版 `MakeBandNoise` 的思路：
白噪声分别过 `fc=2400` 和 `fc=180` 两个低通，然后 `high - low`。

看起来是"高频减低频 = 带通"。**用 Python 算 z 域传递函数，它被证伪了**：

| 频率 | 2 级 | 3 级 | 4 级 |
|---|---|---|---|
| 40 Hz | −8.1 dB | −4.7 dB | −2.5 dB |
| 120 Hz | −0.9 dB | +1.4 dB | +2.4 dB |
| 400 Hz | +0.4 dB | +0.2 dB | −0.3 dB |
| 2000 Hz | −4.5 dB | −6.8 dB | −9.0 dB |

**加级数只会让低频更响。**

原因：两个低通在低频都趋近 1，相减趋近 0；但级数越高它们"趋近"得越慢，
差值反而更大。这个结构在低频**不是高通**。

→ 改成 **高通级联 + 低通级联串起来**：

```
20 Hz  −38.3 dB
40 Hz  −26.6 dB
120 Hz −10.3 dB
500 Hz  −1.6 dB   ← 通带
1 kHz   −1.9 dB
2 kHz   −4.8 dB
4 kHz  −11.5 dB
8 kHz  −20.9 dB
```

各 2 级：1 级转折太软（低频仍漏），4 级以上转折太陡（听起来"假"，真实风噪很平缓）。

#### 错误二：给噪声循环做交叉淡化，反而制造了可听的变化

直觉：噪声首尾不连续，必须交叉淡化，于是写了「多生成 0.5s，
末尾 0.5s 与开头 0.5s 交叉混合」。

**实测数据否掉了这个直觉**（Python 复现同一算法，量"接缝跳变"在
"噪声自身相邻采样差"里的百分位）：

| 循环长度 | 接缝跳变 | 噪声自身相邻差 p99 / max | 接缝百分位 |
|---|---|---|---|
| 2 s 直接截断 | 0.2201 | 0.1987 / 0.2840 | 99.7% |
| **4 s 直接截断** | **0.1059** | 0.1944 / 0.2787 | **76.9%** |

4 秒直接截断时，接缝跳变只落在 **76.9 百分位** ——
比 1/4 的正常采样差还小，**被噪声自身的波动完全掩蔽**，根本听不出来。

而交叉淡化反而制造两个问题：

1. **末尾 0.5s 变成两段独立噪声的混合 → 方差减半**
   → 每次循环到那里"突然变轻"，**那才是真正可听的变化**
2. 白噪声的统计特性被破坏，听感"不自然"

→ 4 秒**直接截断**，不做交叉淡化。循环同时从 2s 提到 4s，
避免宽带噪声的"洗衣机"式重复感。

### 附带修的一个真问题：`Pause()` 的副作用

上一版：

```csharp
if (HumLevel > 0.001f && !isPlaying) Play();
else if (HumLevel <= 0.001f && isPlaying) Pause();
```

两个问题：

1. `Pause()` 会**释放混音器通道**。5 台空调反复申请/释放，低配机器上会挤掉提示音。
2. `Pause()` 之后 **`time` 不归零**，下次 `Play()` 从那个位置继续 ——
   每次开空调起始相位都不同。

→ 改成 `HumStarted` 标志位：**只 Play 一次，之后永不 Pause**，
安静时靠 `volume = 0` 无声播放。代价是 5 条 4 秒 clip 的空转（CPU 可忽略），
换来「零起播延迟 + 相位永远连续」。

断电是唯一例外：`Stop()` 真停 + 复位 `HumStarted`。

### 这一轮的三条教训

1. **"listen" 之前先"measure"。**
   我说"音量为 0.16 应该够低调"，但从没算过它和提示音的比值。

3. **"必须交叉淡化"这类常识，要拿数据检验。**

   而交叉淡化带来的方差变化，倒是**真的可听**。
   **不要为了解决一个听不见的问题，引入一个听得见的问题。**
