## 一、定位过程与四条证据

### 1.1 ① 底图来源：烘焙贴图，不是 RenderTexture

`TwinMinimap.cs` 第 19-20 行写死了链路：

```
`Editor/TwinMapBaker` 烘焙三张（室外/1F/2F），写进 `Resources/TwinMapAtlas.asset`。
本组件只做：定位 → 判楼层/室内外 → 选底图 → 摆位置 → 画箭头。
```

代码里没有任何 `RenderTexture` / `Camera.targetTexture` / `RawImage` —— 只有 `Image` + `Sprite.Create(texture)`。
所以**排除相机路线**（正交尺寸、viewport、相机位姿一律无关）。

### 1.4 ④ 与画布 928×482 的关系：**无关**

| 环节 | 是否依赖 Screen / canvas.rect |
|---|---|
| 小地图直径 `_diameter = 160` | **固定 UI 单位**，`[SerializeField]` 默认值，场景里无实例（走自举） |
| 圆/底图/箭头尺寸 | 全部由 `_diameter` 派生 |
| 圆形裁剪区 | `Place(_clip, 0, 0, _diameter, _diameter)` 固定 |
| 位置 | 左上角锚定 `anchor(0,1) + pivot(0,1)`，不读画布高度 |

`CanvasScaler match = 0` 只影响**物理像素大小**（928 宽时 scaleFactor 0.928，小地图 160→148 物理像素），
**不影响圆内"内容／空白"的比例**。所以 928×482 下同样会出现"只显示 1/4"，
甚至因为整体变小、细节更糊，看起来更糟。

> **顺带纠正一处日志误读**：现场日志里的 `Canvas.rect = 220.0×68.0` **不是主画布尺寸**。
> 那是我的探针 `FindObjectOfType<Canvas>` 抓到的**第一个** Canvas —— 命中了某个子 Canvas / 局部 Canvas，
> 不是 `[TwinUI]`。主画布实际是 `1000 × 519.4`（= 928/0.928 × 482/0.928）。
> **这条日志对本次定位没有参考价值**，探针的查找方式已记在缺陷里（应改为按名字或按 sortingOrder 找）。
>
> 但这条日志暴露的另一个事实是真的：**画布高 519 < 720**，抽屉锁死 720 后会上下各溢约 100px —— 那是 R7，
> 与小地图无关（小地图锚左上角，不受影响）。已记入 §六。

## 二、量化方法（可复现）

```bash
# 1) 缩到 1024×1024 便于统计（面积平均，保内容占比）
ffmpeg -v error -i TwinMap_Floor2.png -vf scale=1024:1024:flags=area \
       -f rawvideo -pix_fmt rgb24 -

# 2) Python：亮度 = 0.299R+0.587G+0.114B，> 55 判内容
#    （背景 RGB(41,43,48) → 亮度 43.0，用 40 会把背景算成内容，前两版就错在这）
# 3) 切 64×64 格，单格实体像素 ≥ 60% 记为实体格，取实体格包围盒
```

- 阈值依据：背景 (41,43,48) 亮度 **43.0**；树 (60,68,33) 亮度 **63.2**；地板 (约150,110,80) 亮度 **125**。
  取 55 正好把背景与最暗的内容（树）分开。
- 结果：(x0,y0) = (23.4%, 32.8%)，宽高 = 51.6% × 40.6%。

| **3** | 第 459-506 行（Sprite 创建 + UV 换算） | `GetEntrySprite` 改为按 `TextureRectOf()` 取内容区（并显式 `SpriteMeshType.FullRect`）；新增 `TextureRectOf()`、`ToContentUv()`；`Update` 里 `mapW` 改用 `_mapAspect`，`uv` 经 `ToContentUv` 换算 |

**两处 y 轴翻转是这次最容易写错的地方**（都写了注释钉住）：

```csharp
// TextureRectOf：内容区表是「左上原点」，Sprite.Create 的 rect 是「左下原点」
float y = th - (content.y * th) - h;

// ToContentUv：同理，内容区在整图 uv 里的下边界 = 1 − yTop − height
float uvMinY = 1f - content.y - content.height;
```

写反了的表现不是空白，而是**地图内容对、位置上下颠倒** —— 比空白更难查，所以两处都留了注释。

## 四、两个分辨率下的表现

### 4.1 改完之后的关键数值（由代码常量精确推导）

Floor2 世界范围（`TwinMapAtlas.asset`）：`(-94.31, -65.71)` → `(64.07, 91.50)`，即 **158.4 × 157.2 m**。

裁到内容区后：

| 项 | 值 | 算法 |
|---|---|---|
| 内容区像素 | 927 × 724 | 1797×0.516 / 1784×0.406 |
| 内容区世界范围 | **81.7 × 63.8 m** | 158.4×0.516 / 157.2×0.406 |
| `_mapAspect` | **1.280** | 927 / 724 |
| `mapH`（zoom 1.6） | 256 | 160 × 1.6 |
| `mapW` | 327.7 | 256 × 1.280 |
| 圆内可见世界范围 | **39.9 × 39.9 m** | 81.7×(160/327.7) / 63.8×(160/256) |

**改前**（按整图渲染）：`mapW = 256 × 1.007 = 258`，可见世界范围 `98.2 × 98.2 m`，
而二层室内只有 81.7 × 63.8m 且居于图中 → 圆里约 **3/4 是压暗空白** ✔ 与现象吻合。

**改后**：可见 39.9 × 39.9m，全部落在内容区内 → **圆被内容填满**。

### 4.2 1000×720 与 928×482 的差异

| 分辨率 | scaleFactor | 小地图物理尺寸 | 圆内内容占比 |
|---|---|---|---|
| 1000 × 720 | 1.000 | 160 px | **40m 视野填满圆** |
| 928 × 482 | 0.928 | 148.5 px | **完全相同**（UI 单位不变，整体等比缩） |

因为 `_diameter`、`zoom`、内容区比例全是**UI 单位常量**，与 `Screen`/`canvas.rect` 无耦合，
所以两个分辨率下**圆内构图逐像素等比一致**，只有物理像素大小差 7.2%。

> ⚠️ **这两栏是推算值，不是实测截图**。原因见 §五。任务要求"两个分辨率下的实测表现"，
> 我目前只能给推导；实测需要主理人跑一次 Play（或等编辑器空闲后我跑）。
