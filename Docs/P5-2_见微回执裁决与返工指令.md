## 4. Power 单位缺陷：你报对了，比你说的更严重（另立 P6，不在本轮）

### 4.1 实测数据

catalog 里 44 个 `Power` 点位，单位与量程分布：

| Category | Unit | Min | Max | 台数 |
|---|---|---|---|---|
| AC | **kW** | 0 | 3.5 | **5** |
| Light | W | 0 | 120 | 16 |
| PC | W | 0 | 300 | 20 |
| PC | W | 0 | 3600 | 1 |
| Projector | W | 0 | 500 | 2 |

`MockDeviceAgent` 播种值：灯 `42`、**空调 `1.2`**。
`LivePowerOf` 的实现是：

```csharp
if (a.TryGetValue("Power", out pv) && pv.Value > 0.01f) return pv.Value;  // 直接返回，无单位换算
```

**于是空调开机被算成 1.2 W，而非 1200 W —— 少算 1000 倍。**

### 4.2 影响量化

| 项 | 现状（1.2 当瓦） | 修正后 |
|---|---|---|
| 5 台空调合计 | **6 W** | **6000 W** |
| 全楼总功率 | ≈ 7.3 kW | ≈ 13.3 kW |
| 空调占比 | 0.08% | **45.1%** |

**这不只是"数字不对"，而是"KPI 的主项被抹掉了"**：全楼最大的耗电设备在统计页上贡献 0.08%，于是页面看起来"空调几乎不耗电"——这是**业务结论级的错误**，答辩被问一句「空调占多少」就穿帮。

### 4.3 为什么不在本轮修

| 原因 | 说明 |
|---|---|
| 它会改所有数字 | KPI / 曲线 / 房间能耗 / Top3 四个块的数值全变，见微所有示意值要重算 |
| 它跨了三个专家的边界 | 数据播种（断点）、口径确认（心跳）、示意图（见微） |
| 本轮已经有 4 件事在施工 | 合并会让"改完看不出是哪个改动导致的" |

**裁决：本轮不修，立 P6。** 但**必须马上告知断点"不要顺手修"**——否则他会在施工中看到 1.2 觉得不对，顺手加个 `* 1000`，把这一轮的视觉验收全部污染。

### 4.4 P6 的正确修法（给你和断点、心跳都看一下）

**不要在 `LivePowerOf` 里加 `if (category == "AC") return v * 1000;`** —— 那是把单位约定硬编码进业务逻辑，下一个人加个 kW 单位的新设备又要改一次。

**正确做法：单位归一化下沉到读取层。**

```csharp
// TwinAnchor 或 TwinPowerEstimate 内新增
private static float PowerWattOf(TwinAnchor a)
{
    TwinValue pv;
    if (!a.TryGetValue("Power", out pv)) return 0f;
    string unit = UnitOf(a.TwinId, "Power");     // 从 catalog 的 TwinMetricDefinition.Unit 读
    if (unit == "kW") return pv.Value * 1000f;
    return pv.Value;                              // W 与未知单位一律按 W
}
```

依据：`TwinCatalog.cs:12` 的 `TwinMetricDefinition.Unit` **已经存了单位**，catalog 里有 `Unit: kW`，
所以这个信息是**现成的、权威的**，不需要新增配置、不需要改数据源。
`LivePowerOf` 改成调 `PowerWattOf`，`SumLivePower` / 房间聚合 / Top 排序三处自动正确。

**顺带修两条**（同一批做）：
1. `TwinDeviceModel.cs` 里 `Power` 的 `Kind` 全部写成 `Bool` 是错的（读数是 Float/Int，Bool 是开关量）。`Kind` 目前无人读取，属于**潜在陷阱**——先改对，免得将来有人用它做类型转换时踩到。
2. catalog 里 `PC` 有一条 `Max: 3600`，其余 20 条是 `300`。需要心跳确认：**那个 3600 的点位是不是「整间机房」语义**（如果是，它是聚合点，不该和单台 PC 一起求和，会重复计算）。
