## 四、真根因：三处叠加

### ① 主因：`PcScreenPlayer.Destroy()` 全项目 0 处调用

```
$ grep -rn "\.Destroy()" Assets/_Project/Scripts/Present/
（空）
```

方法写了、逻辑也对，但**从来没有被调用过**。而 `PcScreenPlayer` 是普通 C# 类
（不是 MonoBehaviour），它的字段不会因为 GameObject 被销毁而自动清空。

每次进 Play 就 new 出 4 个播放器，每个持有：
- 1 个 `VideoPlayer` + 1 个 `AudioSource`
- 3 张 RT：主脑 2048²（≈16MB）、两台幕布 1024²（≈4MB）、机房 512²（≈1MB）

不解码器不释放 → 累积到第 3 次就起不来了。

### ② `TwinDevicePresenter.OnDestroy()` 只销毁材质，一个播放器都没释放

```csharp
foreach (... in _screens)
{
    if (kv.Value != null && kv.Value.Material != null) Destroy(kv.Value.Material);
}
```

注释还写着「运行时的东西必须自己销毁，不 Destroy 就会在每次进出 Play 时泄漏一份」——
**它想到了这件事，但只想到了材质，漏了播放器**。

### ③ `Destroy()` 自身也有三个漏洞（即便被调用也不干净）

```csharp
public void Destroy()
{
    if (_player != null && _player.isPlaying) _player.Stop();   // ❌ 只 Stop 不销毁
    ...
    if (_go != null) { Destroy(_go); _go = null; }              // ✅ 但没先解绑事件
}
```

| 漏项 | 后果 |
|---|---|
| `_player` 组件本身没销毁 | `_go` 是它的宿主，靠销毁 `_go` 间接收掉，但没有解绑事件 |
| 没解绑 `prepareCompleted` | 委托持有播放器实例引用，把实例吊住 |
| `_player` 没置 null | 非 MonoBehaviour 不会变"伪 null"，`if (_player != null)` 会**误通过**，继续往死对象上 `Prepare()` |

第 3 条最阴：它让"已经死了"的播放器看起来还活着，于是重试永远重试、永远不成功。

## 五、为什么 255 条警告不是原因

主理人的判断「应该是这些警告引起的」**方向是对的**（警告确实全由这个功能产生），
但因果要反过来：

```
解码器耗尽（原因）
   ↓
prepared 永远 false
   ↓
Tick() 每 3 秒重试一次、且**无上限**
   ↓
255 条同样的警告
```

警告是**症状的复读**，不是病因。而且它造成了实际伤害：
**把真正的错误全埋掉了**。所以修法里必须包含"给重试加上限"——

> **日志的用处是定位，不是复读。**
> 一个"永不放弃的重试"看起来是兜底，实际是把一个可诊断的故障变成一片噪音。

现在改成最多 2 次，之后**放弃并清屏**，只留**一条** `LogError` 说明原因与怀疑方向。

## 七、两条可直接复用的判据

### 判据 A：「同一会话内先成功后永久失败」= 资源累积，不是逻辑错

只要看到这个形状，直接去查**创建了但没释放**的东西，不要从算法时序开始猜。

```
同一份输入 + 同一份代码 + 前 N 次成功、第 N+1 次起必然失败
   → 泄漏 / 句柄耗尽 / 静态状态累积
```

本次用 `grep -c` 数回调次数就锁定了（`就绪后补播` 8 次 vs 播放器创建 20+ 次）。
**计数比读代码快**，因为代码里"该释放但没释放"是**看不见的**（不存在的代码不会提示你）。

### 判据 B：`grep "\.Destroy()"` 有定义但 0 调用 —— 必须查

`IDisposable` 风格的方法在这个项目里不止一个。以后凡是见到
「写了一个 `Destroy()` / `Dispose()` / `Release()`」，顺手 grep 一次调用点：

```
grep -rn "\.Destroy()" Assets/_Project/Scripts/<目录>/
```

**空结果就是 bug。** 这条比读代码可靠，因为"忘记调用"没有任何编译期提示。

## 八、顺带修掉一个会掩盖问题的设计

`errorReceived` 之前完全没接。VideoPlayer 的失败是**静默的**：
既不回调 `prepareCompleted`、也不打日志，外部只能看到 `isPrepared=false`。

这导致三种完全不同的原因在现场表现**一模一样**：

| 真实原因 | 修复方向 | 现场表现 |
|---|---|---|
| 素材编码不支持 | 重新转码 | prepared=False |
| 文件被占用/不可读 | 查文件锁 | prepared=False |
| 解码器耗尽 | 释放播放器 | prepared=False |

**这就是这个 bug 查了这么久的真正原因** —— 不是难，是**没有可分辨的证据**。
接上 `errorReceived` 之后，这三种情况第一眼就能分开。

> **教训 ②：一个只报告"成功"、不报告"为什么失败"的异步接口，
> 会让所有失败长得一样。接上错误出口的成本是一行代码，收益是省掉几小时。**

## 十二、先推翻自己：那个"决定性证据"是假的

上一轮我写的决定性证据是：

```
grep -c "屏幕视频就绪" → 每次 Play 都有 4 条
grep -c "就绪后补播"   → 只在前 8086 行出现
```

据此结论「前 2 次 Play 正常，第 3 次起永久失败」。

**这条推理的前提是错的。** 回去读代码：

```csharp

Debug.Log("[P26] 屏幕视频就绪：" + name);   // ← 紧跟着就打印"就绪"
```

这行日志打印在 `Prepare()` 之后**同一帧**，此时一帧都没解出来。
它证明的只是「创建了播放器」，不是「视频就绪」。

> **教训 ①（本轮最贵）：一行名字错的日志，能把整轮排查带偏。**
>
> 我按这行日志统计了 16 次 Play，得出「前 9 次都正常」的结论，
> 并据此去修"跨 Play 泄漏"。改完症状一模一样 ——
> 因为那 9 次里 `prepareCompleted` 其实**早就不触发了**，只是被这行假日志盖住。

**正确的计数口径**是 `就绪后补播`（它在 `OnPreparedPlay` 回调里，骗不了人）：

| 会话 | Play#1 | Play#2 | ... | 第一次 0 回调 | 之后 |
|---|---|---|---|---|---|
| 上一次（Editor-prev.log） | 4 | 4 | | **#3** | 全部 0，且重进 Play 也不恢复 |
| 本次（Editor.log） | 21 | 8 | | **#10** | 全部 0，且重进 Play 也不恢复 |

## 十三、~~真根因：会话级累计耗尽（不是泄漏）~~ ← **本节结论已被证伪，见第十八节**

> ⚠️ **保留原文是为了留下错误路径，不要照这里的结论行动。**
>
> 十八节给出了直接反证：重启 Unity 后有**全新进程**，
> 累计到 **47 次 Prepare / 13 建 12 销毁 / 跨多次进出 Play** 全程正常；
> 而故障现场只有 **4 次 Prepare（全是全新实例）** 就全黑。
> 「累计 200~300 次才耗尽」与这两个数据都不相容。

关键事实：**退出重进 Play 不恢复，连域重载都救不回来。**

这排除了所有「C# 侧状态没清」的可能 —— 域重载会把静态字段全部重置。
残留只可能在**原生解码层**。

再看"累计 Prepare 次数"与失效点的关系：

| 会话 | 失效发生在 | 当时累计 Prepare |
|---|---|---|
| Editor-prev.log | Play#3 | **206 次** |
| Editor.log | Play#10 | **289 次** |

~~量级一致（200~300），临界点不同 —— 这是**累计资源耗尽**的典型特征。~~

**这个推理的漏洞**：两个样本、两个不同的临界点，恰恰说明它不是一个阈值。
"量级一致"是我在只有两个数据点时给自己找的说辞 ——
真正的阈值现象应该有一个可复现的固定值。**我把"看起来像个规律"当成了规律。**

### 关键是：在这上面「重试 Prepare」永远不可能成功

失败时的现场状态（主理人 18:36 截图）：

```
on=True playing=False prepared=False frame=-1 retry=2/2 prep=Pending
```

- `prep=Pending` → 我们确实发出了 prepare，且一直没等到回调
- `errorReceived` **一次都没报**（日志 0 条）→ 解码器自己认为"没出错，只是还没好"

一个既不回成功、也不报失败的对象，在它身上反复 `Prepare()` 等于对空喊话。
**重试的对象本身是坏的，重试多少次都一样。**

这正是上一轮 5 处修复全部正确、却依然失败的原因：
那 5 处解决的是「实例没被销毁」，而这里是「会话已经耗尽」——
**修好了前者，后者照旧。**

## 十四、改了什么（P30）

| # | 改动 | 为什么 |
|---|---|---|
| 1 | `屏幕视频就绪` → `已请求准备（不是就绪）` | 假日志会带偏排查方向（见十二） |
| 2 | 新增 `RebuildPlayer()`：**换 VideoPlayer 实例** | 已死的会话救不回来，只能换新的 |
| 3 | 超时后不再"原地再 Prepare"，直接 `RebuildPlayer()` | 原逻辑在对空喊话 |
| 4 | `_rebuildCount` 上限 2 | 防止"重建→失败→重建"变成新死循环 |
| 5 | 会话累计存 `EditorPrefs` | 域重载开着（`m_EnterPlayModeOptionsEnabled: 0`），静态变量每次清零 |
| 6 | `ResetSessionCounters()` | 一键归零，方便复验"从零能跑多久" |
| 7 | `Destroy` 补 `errorReceived -=` | 与 `prepareCompleted` 同理，订阅会吊住实例 |

### 为什么不重建 RT

`ScreenRT` / `_videoRT` 已经被材质和 18 台座位的 `_EmissionMap` 引用。
换掉它们要同步改所有引用点 —— 那是另一场事故。
病灶是解码会话，**只换 VideoPlayer 组件，别的不动**。

`RebuildPlayer` 里用 `DestroyImmediate` 而不是 `Destroy`：
`Destroy` 延迟到帧末生效，同一帧再加同名组件会得到两个并存、`GetComponent` 拿到哪个不确定。

## 十五、复验方法（重要）

**第一步必须先清零**，否则在已经耗尽的会话里测什么都没有意义：

```
Console 执行：SchoolTwin.Present.PcScreenPlayer.ResetSessionCounters();
```

**第二步看这一行**（每次创建播放器都会打）：

```
[P30] xxx 已请求准备（不是就绪）← ...　【跨Play累计】Prepare=N 建=M 销毁=K 存活=L | 本次Play Prepare=n
```

判据：
- `存活` 应该始终是个位数（4 块屏 + 机房 = 5）。**持续上涨就是真泄漏**
- `本次Play Prepare` 应该 ≤ 10。改前是 30+
- 累计到 180 会提示 `⚠️ 已接近历史失效点`

**第三步**：连续进 5~8 次 Play，每次都应有开机动画。
若某次出现 `[P30] 换了一个新的 VideoPlayer 实例`，
说明**重建机制生效了**（这是好事，说明它在自救），
但同时也说明累计已经到临界 —— 该重启编辑器了。

## 十六、这一轮真正的教训

> **「修了一个真 bug」不等于「修了这个 bug」。**

两轮修的都正确：`Destroy()` 全项目 0 调用是真缺陷，`_bulkSeatUntil` 失效是真缺陷。
但它们都不负责"累计 200 次后永久失效"这件事 —— 那是第三个、独立的缺陷。

判断"是不是同一个 bug"的唯一办法，不是看现象像不像，而是看**判据有没有变**：

| 现象 | 上一轮认为的原因 | 判据支持吗 |
|---|---|---|
| 屏幕全黑 | 播放器未释放 | ❌ 释放之后照样黑 |
| 重进 Play 不恢复 | 资源累积 | ⚠️ 方向对，但**域重载应该清掉 C# 侧，它没恢复 → 不在 C# 层** |
| 每次都 4 块屏同时失败 | 连环 Prepare 打断 | ✅ 这条上一轮改对了，之后不再连环，但仍失败 |

> **第三条是分水岭**：修好"连环 Prepare"之后，`本次Play Prepare` 从 30+ 降到 6，
> 症状却没变 —— 这一条就足以证明"打断"不是充分原因。

## 十八、【2026-11-05 19:50】重启 Unity 后一切正常 —— 真根因定为编辑器进程级解码器挂死

### 事情经过

19:47 主理人发来截图：机房 18 台全部显示 Windows 桌面，视频在正常播。
主理人同时说了一句关键的话：**「我刚刚好像重启了 Unity」**。

**我没有改任何代码。** 所以这不是被修好的，是被重启好的。

### 反证一：重启后跑得比故障时多得多，完全正常

| 时刻 | 跨 Play 累计 | 状态 |
|---|---|---|
| 重启前 Play#18 | `Prepare=4 建=4 销毁=0 存活=4`（**全是全新实例**） | 全黑 |
| 重启后本次 Play | `Prepare=47 建=13 销毁=12 存活=1` | **全正常** |

重启后累计 **47 次 Prepare**、跨**多次进出 Play**（`建=13 销毁=12` 说明 Play 被重进了 12 次以上），
开机 / 关机 / 切视频 / 显示待机图全部正确。

而故障现场只有 **4 次 Prepare**、4 个**全新**实例就已经全黑。

**「累计 200~300 次才耗尽」与这两组数据都不相容。** 十三节的结论作废。

### 反证二：视频其实一直在播，不是"没播出来"

这是推翻"prepare 永不完成"的直接证据。本次 Play 里 `SetOn(False)` 时的真实状态：

```
prepared=True  frame=121   blit=474 → 742 → 1086 → 1592 → 1938 → 2170
```

- `frame=121`：`boot.mp4` 共 205 帧，确实解码到了第 121 帧
- `blit` 单调累加到 2170：`Graphics.Blit` 每帧都在跑，合成链路健康

**主理人截图里的画面是真视频画面。** 我特意用 ffmpeg 抽出 `boot.mp4` 末帧与
`desktop.jpg` 逐字节比对（缩放 192×120 后取 md5）：
`57efa652…` vs `5c29c67e…` —— **不是同一张图**，排除"看到的是待机图"的误判。

### 反证三：`就绪后补播 → frame=-1` 也是假证据

`OnPreparedPlay` 里在 `vp.Play()` **之后立刻**读 `vp.frame`，
当帧解码还没产出，必然读到 `-1`。

**字段没错，读的时机错了** —— 和 `屏幕视频就绪` 是同一类错误：
**测量工具在说谎。** 这次差一点又按它去查"播放启动失败"。

### 反证四：那条引擎警告信息量为零

日志里这条是 **Unity 引擎**打的，不是本项目代码：

```
Unexpected timestamp values detected. This can occur in H.264 videos
not encoded with the baseline profile. Timestamps will be skewed...
```

核实全部 4 个素材：

| 素材 | profile | has_b_frames |
|---|---|---|
| `master/boot.mp4` | **High** | 2 |
| `master/shutdown.mp4` | **High** | 2 |
| `videos/01_数字孪生科普.mp4` | **High** | 2 |
| `videos/02_数据可视化大屏.mp4` | **High** | 2 |

**这条警告在每一次 prepare 成功时都会打**，而本次 Play 视频全部正常。
它只是"时间戳被校正了"的提示，**不是故障原因**。

> ⚠️ 我上一轮差点把它当成根因（"High profile + B 帧导致时间戳异常 →
> 解码器挂起"）。**这条假设已经被上表直接否掉**：同样的 High profile 素材，
> 重启后一次都没出问题。

### 真根因（按现有证据能达到的最强表述）

> **Unity 2022.3 的 `VideoPlayer` 在 Editor 下反复进出 Play 后，
> 原生解码会话在进程内挂死。C# 层的 `Destroy()` 是健全的
> （12/13 都被正确释放，`存活=1` 正常），坏在进程级原生状态，
> 域重载清不掉，只有重启编辑器进程能恢复。**

三条支撑：
1. 重启进程 → 立刻恢复（唯一变量就是进程）
2. `建=13 销毁=12` → `Destroy()` 调用链健全，不是泄漏
3. `errorReceived` 全程 0 条 + `prep=Pending` → 解码器既不回成功也不报失败，
   正是原生会话挂起的特征

**这是编辑器侧限制，不是本项目代码缺陷。** 打包后的 exe 不经过 Editor 的
Play 循环，预期不受影响（待验证，见十九节）。

### 这一节最贵的教训

> **我连续三轮都在故障现场里找"代码哪里写错了"，
> 而故障现场从一开始就带着一个我没问过的变量：这个编辑器进程已经跑了多久。**

- P26：断言"播放器未释放" → 修了，症状不变
- P29：断言"并发 Prepare 打断" → 修了，症状不变
- P30：断言"累计 Prepare 耗尽" → 修了，症状不变

**三次都做了"找证据支撑一个假设"，一次都没做"验证这个假设能否被推翻"。**

最有价值的一步，是问一句：**"重启一下会怎样？"**
这个问题零成本、五分钟能验证，我却绕了两小时。

判据：**当现象"诡异、稳定、位置恒定"且修复无效时，
先换环境（重启 / 换机器 / 打包），再换代码。**
