## 零、TL;DR —— 这条坑一句话

> **一个用世界坐标构建 mesh 的组件，被挂成了"每帧跟着相机跑"的父节点的子节点。**
> 几十块同高度的水平圆盘被额外平移了一次，恰好压在相机眼高上，

## 一、坑 1：世界坐标 mesh 被挂到跟随父节点下 → 「水平面收束成横线」

### 现象

主理人截图（室内、室外各一张）：

> 「室内室外还有这个诡异的白线」

白线的量化特征（我用 PIL 逐像素测出来的）：

| 特征 | 实测值 | 说明 |
|---|---|---|
| 颜色 | `R179±5.5 / G189±3.2 / B208±7` | **方差极小 = 恒色面片**，不是半透明叠加（叠加会随背景变化） |
| 色相 | 偏蓝白 | 与雪同色（`_SnowColor=(0.92,0.95,1.0)` + `_SkyColor` 提亮） |
| 位置 | 横贯全屏、随视角平滑滑动 | 到哪都在同一个"高度"上 |
| 遮挡关系 | **盖住墙体、树干、人物** | 它在所有东西**前面**（队列 2997，最高） |
| 外形 | 透镜形，中间厚两端尖灭 | 水平圆盘被压扁后的透视外形 |
| 出现位置 | 室内、室外**都有** | 树遍布整个校园 |

结果**几乎每张图都被标成白带**（天花边缘、墙裙、Unity 工具栏全部命中）。
方法本身不成立，已弃用。**图像阈值不能代替真实排查。**

### 数学上早就该排除雪盘

两条独立证据，任意一条都足够：

**证据 A（几何）**：自检日志实测 `竖直面 = 0 处`、`bounds Y 跨度 = 0.20m`。
一块跨度 0.20m、没有任何竖直面的水平面，**产生不了横线**。

**证据 B（投影）**：雪盘世界高度 `y ∈ [-0.20, 0.00]`，相机在其上方 3m。
90m 见方雪盘在 `fov=60 / 高度 1080` 下，最远角点投影只到 **屏幕行 571**（画面中心 540 之**下**）。
而白带实测在画面中心之**上**（室内行 291 / 视口中心 328；室外行 575 / 视口中心 573）。
**方向都不对。**

> ⚠️ 这两条证据在第一轮就已经有了。我看到了，但没停下来。
> **看到证据 ≠ 用证据下结论。** 这是本轮最该反省的地方。

### 真相

主理人已经点明这是**回归 bug**。按这个方向，`git log --diff-filter=A` 一查：

```
$ git log --format="%h %ad" --diff-filter=A -- Assets/_Project/Scripts/Weather/SnowOnTrees.cs
c3871f9  11-04 11:56   ← SnowOnTrees.cs 在这一刻才被引入
```

而主理人 17:59 的室内截图里**白线已经存在**。时间线完全吻合。

代码级因果链：

```
① SnowOnTrees.cs:73   Terrain.SampleHeight() 返回的是**地形相对高度**，
                      本场景 Terrain 的 m_LocalPosition.y = -0.5
                      漏加 terrain.GetPosition().y  →  雪堆整体抬高 0.5m

② SnowOnTrees.cs:88   顶点用**世界坐标**写入 mesh：new Vector3(wx+lx, wy+bump, wz+lz)

③ WeatherVisuals.cs:750   SetParent(transform, false) 挂成子节点
   而本组件 LateUpdate 每帧：transform.position = cam.transform.position
   →  那一堆世界坐标又被平移了一次，位置彻底错乱

④ 结果：几十块 pileRadius = 3m 的**水平圆盘**，y 全部相同，
   且恰好压在相机眼高（≈ -0.48）附近
   →  视线与这堆平面**共面**
   →  透视把圆盘全部压扁，收束成一条横贯全屏的横线
   →  renderQueue = 2997（高于近场 2996 / 远场 2995），所以它盖住墙体和人物
```

### 修法（3 处）

| # | 文件 | 改动 |
|---|---|---|
| 1 | `SnowOnTrees.cs` `Build()` 开头 | `transform.SetParent(null, true)` + `position = Vector3.zero` + `rotation = identity` + `localScale = one`。<br>**顶点既然是世界坐标，transform 就必须是单位变换** |
| 2 | `SnowOnTrees.cs:73` | `float wy = tpos.y + terrain.SampleHeight(...) + 0.02f;`（补齐地形 Y 偏移） |
| 3 | `WeatherVisuals.cs` `EnsureTreeSnow()` | 不再 `SetParent(transform)`；幂等判断改用 `Object.FindObjectOfType<SnowOnTrees>(true)` |

第 3 条是**修法 1 的必然后果**，容易漏：
对象一旦脱离父层级，原来的 `GetComponentInChildren<SnowOnTrees>()` 就找不到了，
每次重建都会**再生成一个** → 雪堆翻倍。必须改成全场景查找。

### 新增的两条自检判据（关键）

| 判据 | 位置 | 为什么它比什么都重要 |
|---|---|---|
| **雪面世界 Y vs 相机眼高**，差 < 0.30m 即警告 | `BuildIndoorAudit` | 一段水平半透明面片，高度一旦穿过眼高，**必然**收成横线。这条判据**不需要截图就能定性** |
| **`TreeSnowPiles` 的 `pos` / `parent` / 包围盒 Y 区间** | `BuildIndoorAudit` | 正常应 `pos=(0,0,0)`、`parent=null(已脱离)`。若 `parent` 有名字就是 bug 回归 |

> 第一条是本轮**最该早有的检查**。它把"看图猜"变成了"读一行日志"。

### 教训

> **「是回归 bug」这个信息，比任何候选清单都值钱。**
>
> 遇到"诡异、稳定、位置恒定"的渲染问题时，**第一个动作应该是查新增文件**，不是查代码细节：
> ```
> git log --diff-filter=A -- <可疑目录>     # 哪些文件是新增的
> git log -S"<关键方法名>" -- <文件>        # 某个方法是什么时候进来的
> ```
> 五分钟能锁定的事，我在代码细节里泡了 2 小时。

> **颜色方差是最强的分类器。**
> `sd(R/G/B) = 5.5 / 3.2 / 7.0` 说明这是一块**恒色面片**；
> 如果是半透明叠加，三个通道的方差会随背景大幅波动。
> 这类量化特征比肉眼看"白线"可靠得多 —— 而且**可以在写代码之前就得出结论**。

> **"水平面"在透视下的退化，要当成一个独立的故障模式来记。**
> 任何水平的面片，只要高度穿过相机眼高，就必然变成一条横线。
> 以后再看到"横贯全屏的线"，第一个要问的是：
> **"场景里有没有一块高度约等于相机眼高的水平面？"**
> 这个问题可以在 30 秒内用一行日志回答。

## 二、坑 2：`Terrain.SampleHeight` 返回的是**相对高度**，不是世界高度

这个坑是坑 1 的**必要组成**，值得单独记 —— 它太容易漏。

```csharp
// ❌ 错：以为它返回世界高度
float wy = terrain.SampleHeight(new Vector3(wx, 0f, wz));

// ✅ 对：加上地形自身的世界 Y
float wy = terrain.GetPosition().y + terrain.SampleHeight(new Vector3(wx, 0f, wz));
```

本场景 `Terrain` 的 `m_LocalPosition = (-98.5, -0.5, -86.5)`，
**漏加之后所有顶点整体抬高 0.5m**。

而 0.5m 这个偏移量，恰好把"树根雪堆"从地面推到了**相机眼高**附近 ——
如果没有这个偏移，即使父子关系错了，雪堆也在地面高度，
最多是"雪堆位置乱飞"，**不会**变成一条横线。
就是这个 0.5m 让它变成了最坏的那种表现。

> **教训：`SampleHeight` / `SampleHeight` / `TerrainData.heightmap` 全是相对量。**
> 项目里凡是涉及地形的采样，都要问一句"这个值加地形偏移了吗？"
> 这个坑以前踩过（`WeatherVisuals.ProbeOutdoorGround` 里有注释），**这次换个文件又踩了一次** ——
> 说明写在注释里不管用，同类 API 要在**所有调用点**统一检查。

## 三、坑 3：修了主 bug，引入一个隐蔽的次生 bug

修法 1 把 `SnowOnTrees` 从父层级摘出来了。如果只改这一处，会出现：

```
SnowOnTrees.Build() 里 SetParent(null)
        ↓
WeatherVisuals.EnsureTreeSnow() 里 GetComponentInChildren<SnowOnTrees>()
        ↓
        null  ← 因为它已经不在子层级了
        ↓
每次 EnsureTreeSnow 都会再 new 一个 TreeSnowPiles
        ↓
树根雪堆翻倍、翻三倍…
```

**编译器不报错、运行时也不报错**，只是雪堆变多、可能有 z-fighting。

修法：`Object.FindObjectOfType<SnowOnTrees>(true)`（带 `true` 表示包含未激活对象）。

> **教训：改"层级关系"的时候，必须把所有依赖这个层级的查找一起改。**
> 判断方法：`grep` 一遍 `GetComponentInChildren` / `transform.Find` / `transform.GetChild`，
> 凡是查找范围被你的改动影响的，全部要检查。**改结构 ≠ 改一行。**

## 四、坑 4：诊断脚本自己编译不过（`CompareFunction` 缺 using）

我用 `P13SliverProbe.cs` 做"逐层剥离"取证工具时，写了：

```csharp
if (m.HasProperty("_ZTest"))
    always = m.GetFloat("_ZTest") == (float)CompareFunction.Always;   // ← CS0103
```

报错：`error CS0103: The name 'CompareFunction' does not exist in the current context`

**根因**：`CompareFunction` 在 `UnityEngine.Rendering` 命名空间，文件只写了 `using UnityEngine;`。

**修法**：用完全限定名，**不补 using**：

```csharp
always = m.GetFloat("_ZTest") == (float)UnityEngine.Rendering.CompareFunction.Always;
```

为什么不补 `using UnityEngine.Rendering;`：这个命名空间里有 `GraphicsSettings` / `ShaderTagId` 等
与 `UnityEditor` 侧同名的类型，在一个 Editor 文件里补整条 using 有引入**新歧义**的风险；
而这里只需要一个枚举值，完全限定最省事也最安全。

**验证方式**（不用等编译）：全项目 grep 一遍
```
$ grep -rn "CompareFunction" Assets/ --include=*.cs
WeatherVisuals.cs:1215:  ... == (float)CompareFunction.Always;
```
`WeatherVisuals.cs` 的 using 列表里正是那两行（`UnityEngine` + `UnityEngine.Rendering`），
且它所在的 `Assembly-CSharp.dll` 编译成功 —— **有成功先例就说明命名空间是对的**。

> **教训：修编译错误时，先找项目里同一个 API 的成功用例，别凭记忆补 using。**
> 这一条和 P27 坑 1 的「凭记忆写枚举值映射表」是同一类错误：
> **记忆不可靠，项目里的实际代码才可靠。**

### 这一坑的附带发现（值得记）

控制台显示 **2 个红点**，但 `Editor.log` 里：
```
$ awk 'NR>100644 && /error CS/' Editor.log | wc -l
3
```
**只有 1 个不同的错误**（`242,61` 同一行出现了 3 次，是 Unity 内部重复计数）。

> **教训：控制台上的"错误数量"不可信，要看日志里的去重结果。**
> 我曾一度以为"2 个错误说明还有一处没找到"，准备去翻别的文件 ——
> 差点又浪费一轮。正确做法：`grep "error CS" Editor.log | sort -u`。

## 五、坑 5：运行时程序集和编辑器程序集要分开看

诊断过程中出现一个容易误判的状态：

| 程序集 | 时间戳 | 含义 |
|---|---|---|
| `Assembly-CSharp.dll` | **22:39** | 运行时脚本，**编译成功**（含白线修复） |
| `Assembly-CSharp-Editor.dll` | 16:08 | 编辑器脚本，**编译失败**（`P13SliverProbe.cs` 的错）一直卡着 |

于是出现"改了代码但 Play 还是旧的"这种错觉的风险：
**两个程序集是独立编译的，一个失败不影响另一个。**

验证运行时修复是否真的进去了，我用了这个方法 —— **在 dll 里搜字符串**（注意 .NET 用 UTF-16LE）：

```python
data = open(r"Library\ScriptAssemblies\Assembly-CSharp.dll","rb").read()
for s in ["TreeSnowPiles", "雪面世界Y", "与眼高差"]:
    print(s, data.count(s.encode("utf-16-le")))
```
结果 `3 / 2 / 1` —— 确认新代码已编译进去。

> **教训：判断"代码有没有生效"，看 dll 时间戳只能判"有没有编译"，
> 想确认"确实是这一版"，得去 dll 里找新加的字符串。**
> 用 UTF-8 会搜不到（.NET 元数据里字符串是 UTF-16LE），我第一次就搜错了，得到一堆 0。

## 五之二、坑 6 & 坑 7：天气视觉「跟随相机」而非「跟随角色」（**待修，11-04 登记**）

> 与坑 1 白线**同一个病根**：天气层的定位基准取了相机，第三人称下相机在角色身后上方，两者不重合。
> 坑 1 已修（雪堆改世界锚点），但**水花层与室内外判定仍在用 camPos**，故这两个 bug 仍在。

### 坑 6：雨天水坑/水花跟着镜头跑，不跟着角色

**现象**：第三人称下雨，脚下的水花（splash）不长在角色脚下，而是长在**镜头正下方投影点**；
角色走动时水花滞后/偏移，转视角时水花横扫。

**根因**（已核代码）：`WeatherVisuals.cs:2190`
```csharp
splashRoot.position = new Vector3(camPos.x, groundY + 0.03f, camPos.z);
```
`splashRoot` 跟随的是 `camPos`（相机世界坐标）。第三人称相机在角色**身后 3~5m、上方**，
所以水花锚点 = 相机在地面的投影，不是角色脚下。

**修法（待做）**：splash 锚点改用**玩家位置**（`_playerModel` / CharacterController 的 transform），
而非 camPos。第一人称两者重合、无差异；第三人称必须用玩家。
⚠️ 雪盘已改「世界锚点」是对的方向，但雪盘锚点也应基于玩家而非相机（见 :2185 snowAnchor 同样取 camPos.x/z）。

### 坑 7：室内仍下雨/下雪

**现象**：角色走进教室/走廊，头顶有天花板，但雨雪粒子照常下、地面积水照常铺。

**根因**（已核代码）：室内外判定 `indoor` 的头顶遮挡射线**从相机位置发出**
（`WeatherVisuals.cs:190` 注释自承：「第三人称相机在玩家身后上方，向上射线可能打到玩家自己的
手臂/模型，或从窗户/门口斜射出去」）。相机在屋外、墙边、门口时，向上射线打不到天花板 →
误判 `indoor=false` → 当成室外，雨雪不淡出。

**修法（待做）**：头顶射线起点改用**玩家位置 + 眼高**（不是相机位置），
与坑 6 同源；`queriesHitBackfaces` 已开（:55），补「起点=玩家」即可。
`indoorFade` 的淡出机制（:820 dt×3）本身是对的，错的只是**采样起点**。

### 两坑的共同教训（升格进 P00 §1.6 D 类）

**天气/环境视觉层的一切「跟随」与「采样」，基准都应是玩家角色，不是相机。**
第三人称下相机与角色是两个点，用相机做基准的每一项都会在第三人称露馅。
第一人称测试通过 ≠ 第三人称通过 —— 这条必须进回归清单。

## 九、一句话总结

> **两个各自正确的设计，一旦组合就可能变成完全错误的行为，而编译器对此一言不发。**
>
> 「顶点用世界坐标」是对的，「父节点跟随相机」也是对的。
> 错的是**把它们放在一起**。
>
> 这类 bug 只有两个抓手：
> ① **看画面**（人眼是唯一的检测器）；
> ② **看新增文件**（回归 bug 的查法是考古，不是调试）。
