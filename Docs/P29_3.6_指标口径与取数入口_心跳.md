## 〇、三条结论（先看这个）

1. **`153` 在代码里不存在。** 全工程 `Assets/_Project/Scripts/**` 只有 3 处出现 153，全在**注释**里（`TwinHomePage.cs:16`、`TwinMetricCard.cs:13`、`TwinDrawer.cs:17`），没有任何一处参与取值。它是 P3 完成后的**目标值**（53 + 100 盏路灯），不是当前数据。
2. **当前 UI 显示 53 是正确的，但属于"偶然正确"。** 6 个 BAK 锚点恰好全挂在未激活层级（`[MockPoints]`，`m_IsActive=0`），`TwinAnchor.Start()` 没跑，所以没注册。**一旦有人勾上那个容器，设备总数会立刻变成 59，且 6 个 BAK 会被算成"在线"**——这是必须现在就堵掉的隐患。
3. **`P29_3.5` §2.1 的在线/离线定义自相矛盾。** 「在线 = {Normal, Warning, Alarm}」+「离线 = Offline/Unknown」，Stale 这一档两边都不算，只要有一台设备数据陈旧，`总数 = 在线 + 离线` 这条验收（R1）立刻不成立。本文档给出修正定义。

## 二、153 与 53 差异说明

**53 是当前真实在跳变的设备数，153 是 P3 完成后的目标数，两者不是同一个时间点上的两个统计口径，而是"现在"与"以后"。**

拆开看：`153 = 53 + 100`。这 100 是 P3 要接入的室外路灯（`P28_统一管理系统方案.md` §588「P3 设备 + 编号 + 路灯」一栏写明路灯 100 盏）。所以在 P3 之前，任何界面出现 153 都是**把未来值当成现在值在展示**，答辩时被问"哪 153 台？"是答不出来的。

153 的流传路径是「设计稿 → 文档 → 代码注释」，全程没有经过数据层：`P29_UI科技风视觉统一与面板改版方案.md:211` 的副标设计成 `1号教学楼 · 5 个模块 · 153 台设备`，`TwinHomePage.cs` 的类注释照抄了 `[设备总数 153][在线 151][告警 2]`，`TwinMetricCard.cs` 的注释又照抄了一遍。于是"153"看起来像代码里的常量，实际上一次取值都没参与过。

**另外还有一个 59，是真正危险的数字。** 它不在任何文档里，但它是 `TwinRegistry.All.Count` 的**潜在**输出值——59 个锚点全部注册时的结果。当前因为 BAK 层级未激活而没暴露。谁把 `[MockPoints]` 那个未激活的容器勾上（比如排查问题时手一抖），设备总数立刻从 53 变 59，在线数同步 +6（原因见 §5.2），而场景里没有任何一台新设备在跳变。**这才是 R10「面板数字与场景里实际在跳变的设备对不上」的真实技术根因**，比文档里的 153 更值得堵。

所以口径收敛的目标不是"把 153 改成 53"，而是**把"设备总数"从"当前场景里碰巧注册了几个锚点"变成"在册且启用的设备数"**——前者随层级激活状态漂移，后者由 `TwinId` 白名单规则决定。

## 三、`Active` 的定义（四项全部满足才算）

`P29_3.5` §2.1 只写了「已接入 Registry 且 `Active == true`」，但代码里**没有任何 `Active` 字段**。以下是本文档给出的判定规则，逐条可测：

| # | 条件 | 判定方式 | 为什么必须有 |
|---|---|---|---|
| A1 | 已注册 | `TwinRegistry.TryGet(twinId)` 命中 | 没注册的锚点收不到数据，不算设备 |
| A2 | `TwinId` 不以 `BAK` / `BAK2` 开头 | `!twinId.StartsWith("BAK", Ordinal)` | BAK 是历史备份，不是设备。现有 8 处编辑器工具已在用这条规则（`TwinP17Diag` / `TwinP18Expand` / `TwinP19Expand` / `TwinP23Switches` / `TwinPlaceDevices` / `TwinExpandPoints` / `TwinDevicePresenter` / `TwinControlPanel`），**本条只是把它提升为全局口径**，不新造规则 |
| A3 | 物体在激活层级内 | `anchor.gameObject.activeInHierarchy` | 未激活的锚点不跑 `Start()`，也不会被注册，A1 已覆盖；此项用于**运行时动态禁用**场景（如整层楼临时关掉） |
| A4 | 组件 enabled | `anchor.enabled` | 允许单独关掉某个锚点的数据接收而不删物体 |

**明确不纳入 Active 判定的**：
- ❌ **是否有数据（`HasData`）**——纳入会导致设备总数随数据到达而跳动，答辩现场数字往上爬，比数字不对更难看。
- ❌ **是否有阈值配置**——未配阈值是配置缺失（`Unknown`），不是设备不存在。
- ❌ **是否在 `TwinCatalog` 里**——目录是"在册"，Active 是"在线可驱动"。当前 53 对 53 恰好一致，但 P3 路灯若先建锚点后补目录，两者会短暂分离，不应让设备总数跟着目录走。

**口径单位说明（答辩要能答）**：这里的"台"= **点位**，不是物理设备台数。一个点位可以代表一组物理设备——`ClassComputer/PC/Room_01` 一个点位代表整间机房 19 台电脑，`Class1-2/Light/Main_01` 一个点位代表整个房间的照明。所以"53 台"的准确说法是"53 个已接入点位"。

## 四、单一取数入口（接口契约）

### 4.1 签名（断点按此实现，不要改名字）

```csharp
namespace SchoolTwin.Twin
{
    /// <summary>
    /// 设备指标的唯一定量出口。UI 只允许读这里，禁止自己遍历 Registry。
    /// 所有值都是快照，同一帧内读取多次结果一致（保证"同屏一致"）。
    /// </summary>
    public static class TwinDeviceStats
    {
        // ---- 设备维度（分母口径，同 scope）----
        public static int ActiveDeviceCount   { get; }  // 设备总数
        public static int OnlineDeviceCount   { get; }  // 在线
        public static int OfflineDeviceCount  { get; }  // 离线
        public static int StaleDeviceCount    { get; }  // 数据陈旧（已含在离线内）
        public static int AlarmDeviceCount    { get; }  // 告警（含 Warning）

        // ---- 其他维度（不同 scope，见 §6）----
        public static int ControlScopeCount     { get; } // 受控（静态白名单）
        public static int UnackedAlarmEventCount{ get; } // 未确认告警【条】，事件维度
        public static int CatalogPointCount     { get; } // 目录条目，仅供对账，不上 UI

        /// <summary>快照版本号。UI 每帧比对，变了才刷文字，避免无谓的 Canvas 重建。</summary>
        public static uint Revision { get; }

        /// <summary>重建快照。只允许 TwinAlarmCenter 每 0.2s 调用一次。</summary>
        public static void Rebuild();

        /// <summary>单点判定，供列表/台账按行过滤，避免各处重写 BAK 判断。</summary>
        public static bool IsActiveDevice(TwinAnchor anchor);
    }
}
```

`TwinRegistry` 需补两项（其余不动）：

```csharp
public int ActiveCount { get; }              // A1+A2+A3+A4 全满足的数量，增量维护
public event Action RegistryChanged;         // 注册/注销时触发，供快照立即重算
```

### 4.2 刷新时机（这张表决定 UI 会不会抖）

| 字段 | 维护方式 | 刷新时机 | 读取成本 |
|---|---|---|---|
| `ActiveDeviceCount` | **增量维护**（`Register` +1、`Unregister` −1，条件不满足不计） | 注册/注销瞬间；`RegistryChanged` 时同步 | **O(1)**，不遍历 |
| `OnlineDeviceCount`<br>`OfflineDeviceCount`<br>`StaleDeviceCount`<br>`AlarmDeviceCount` | 每轮遍历 Active 集合累计 | **0.2s**，复用 `TwinAlarmCenter` 已有的 `Update` 轮询循环 | O(n)=53，单次约 53 次属性读，可忽略 |
| `ControlScopeCount` | 常量 | 永不刷新（`TwinControlScope.Count`） | O(1) |
| `UnackedAlarmEventCount` | 从 `TwinAlarmHistory` 取 | 0.2s，与告警中心同拍 | O(1) |
| `CatalogPointCount` | 资产加载时 | 场景启动一次 | O(1) |
| `Revision` | 任一字段变化时 +1 | 同上 | O(1) |

**为什么复用 `TwinAlarmCenter` 的 0.2s 循环而不是新开一个 Update**：它本来就在 `Registry.All` 上遍历（`TwinAlarmCenter.cs:125-131`），顺手算 4 个计数不增加任何遍历成本；新开一个 Update 就多一遍 53 次属性读，还会和告警中心的时序错开，出现"告警卡显示 2、告警中心列表 3 条"的对不上。

**⚠️ 一个必须避开的坑**：统计**不能读 `TwinAlarmCenter` 内部的 `Entry.Status`**。断电抑制逻辑（`TwinAlarmCenter.cs:154-176`）会把断电回路的点位状态强改成 `Unknown` 并计入 `SuppressedCount`。如果统计读的是抑制后的状态，**拉一次闸，全部设备会被算成"离线"，设备总数不变但在线数暴跌**——而事实是设备在线、只是没电。所以统计口径必须直接读 `anchor.StatusOfWorst()` 与 `anchor.IsStale`，与抑制状态完全解耦。同理 `TwinCircuit` 的断电逻辑不得参与统计。

## 六、告警数与设备总数是否同一 scope —— **否，三处三个口径**

这是本任务第 ③ 问。实测代码里"告警"存在三种互不相同的统计范围：

| 位置 | 口径 | 维度 | 单位 |
|---|---|---|---|
| `TwinHomePage.cs:318` KPI 卡 | `Alarm` ∨ `Warning` | **设备** | 卡面写"台" |
| `TwinAlarmCenter.cs:206` `NeedsAttention()` | `Warning ∨ Alarm ∨ Stale ∨ Offline` | **设备**（含离线） | — |
| `TwinDetailPanel.cs:2276` 告警列表 | `NeedsAttention` ∨ (`Unknown` ∧ `HasData`) | **点位+指标** | 行数 |
| `TwinAlarmHistory.TotalCount` | 累计 + 进行中 | **事件** | 次 |

三处不同 scope 同时显示在同一个抽屉里，这就是"面板数字对不上"的另一半原因。

### 6.1 对齐方案（建议，需定盘裁决）

**L1/L2 的「告警」KPI 统一用 `AlarmDeviceCount`（设备维度，单位"台"）。**

理由：
1. 卡片单位已经是"台"（`TwinHomePage.cs:125` 传入 `"台"`），若背后是事件数，就成了"53 台设备有 60 台告警"——答辩必被追问。
2. 与"设备总数 / 在线"同 scope，三个数字可以在同一张卡组里横向比较。
3. 事件维度的需求由告警中心页内自己表达（"未确认 N 条"），不占用首页 KPI。

**告警中心页内**用 `UnackedAlarmEventCount`，文案必须带"条"字：`未确认 3 条`，不得写成"3 台"。

### 6.2 一个必须先补的功能缺口

`P29_3.5` §2.1 写的是"**未确认**告警数（已确认/已恢复不计）"，但代码里**没有"确认（Ack）"这个概念**：`TwinAlarmHistory` 只有 `Ongoing`（`EndTime <= 0`）与已关闭两态，`OngoingCount` 是"进行中"，不是"未确认"。

因此 §2.1 的告警口径目前**无法实现**。两条路，请裁决：

- **方案 A（推荐）**：本轮不做 Ack，`UnackedAlarmEventCount` 语义降级为"进行中告警条数"，文案写 `进行中 3 条`。改动为零，答辩讲得清。
- **方案 B**：补 Ack 机制（`TwinAlarmHistory` 加 `AcknowledgedAt` 字段 + 告警中心页加"确认"按钮 + 全部确认/单条确认）。工作量落在断点与见微，且引入"确认后还响不响"的一串判定，不建议在收口阶段做。

### 7.1 现在就要留好的两个接口

## 九、边界与不做

- **不改 UI**：本文档只给口径与接口，`TwinHomePage` / `TwinDrawer` / `TwinSystemPage` 的改读由断点执行。
- **不改场景**：不动 `[MockPoints]` 的激活状态、不删 6 个 BAK 锚点（它们仍可能被编辑器工具引用）。
- **不改 `TwinId` 命名**：白名单与历史录像依赖现有 ID，`BAK` 前缀仅作为过滤依据，不重命名。
- **不扩需求**：不设计 Ack 流程、不做设备影子、不做历史时序存储（R5/R6 另案）。
- **不写 C# 实现**：本文档的接口签名是契约，实现归断点。
- **电力总功率 / 今日用电**：`Power` 单位 W 与 kW 混用 26 处，聚合口径不在本任务范围，维持 `TwinSystemPage.cs:373` 的 `NoData` 处理不变。
