## 1. 问题：短码丢掉类型段，51 台撞号

### 1.1 根因

`TwinCode.Short()` 只取「房间号 + 原始序号」：

```csharp
// 旧实现
string room = Room(zone);
if (string.IsNullOrEmpty(seq)) return room;
return room + "-" + seq;          // ← 只到这里，category 拿到了却没用
```

而 `Split()` 早就把 `category` 拆出来了 —— **拿到了却没用**，这是缺陷的直接形态。

### 1.2 为什么会撞

场景里每类设备的序号**都在自己那一类里从 `_01` 起算**：

```
ClassComputer/Light/Main_01      → 序号 001
ClassComputer/AC/Unit_01         → 序号 001
ClassComputer/Door/Entrance_01   → 序号 001
ClassComputer/PC/Master_01       → 序号 001
ClassComputer/PC/Seat_01         → 序号 001
ClassComputer/Projector/Main_01  → 序号 001
ClassComputer/Sensor/Temp_01     → 序号 001
```

七条不同的物理设备，旧短码全是 `1F104-001`。

### 1.3 实测规模（`SchoolSceneDay.unity` 全部 `_twinId`，剔除 BAK）

| 指标 | 旧短码 | 新短码 |
|---|---|---|
| 设备数 | 70 | 70 |
| **唯一短码数** | **34** | **70** |
| 撞号组 | 15 | **0** |
| **不可单独指认的设备** | **51 台（73%）** | **0 台** |

撞号最严重的三组：

| 短码 | 撞号台数 | 涉及设备 |
|---|---|---|
| `1F104-001` | **7** | 机房 门/暖气/灯/主脑/1号座位/投影/温度传感器 |
| `1F101-001` | 5 | 1-2班 空调/门/暖气/灯/温度传感器 |
| `2F201-001` | 5 | 2-1班 空调/门/灯/CO₂传感器/温度传感器 |

### 1.4 为什么这是 P0

主理人原始诉求是「**对场景所有模型设备进行编号统计，避免遗漏设备**」。
现在 73% 的设备编号不唯一 —— 不是"漏了设备"，而是"设备都在、但没法被单独叫出来"。
答辩时评委指着两行同号问「这是同一台还是两台」，答不上来。

## 2. 修法：加类型字（方案 A）

### 2.1 上中下三策

| 方案 | 短码样例 | 代价 |
|---|---|---|
| **A · 加类型字 + 保留原序号** | `2F203-灯001` | 只改 `Short()`；列表/详情/告警条自动同步；编号自带语义 |
| B · 序号改房间内全局流水 | `2F203-001`…`2F203-011` | 格式不变，但要重排全部序号；「机房 11 号机」会变成 `-012`，与场景座位号对不上 |
| C · 只在详情页展示全码 | 列表仍撞号 | 列表上的实操问题没解决 |

**选 A**。理由是 B 会把"编号"和"场景里的座位号"拆成两套事实，将来对不上；A 只动一个方法。

### 2.2 类型字表

### 2.3 为什么 PC 和 Sensor 必须按设备名细分

只按 `Category` 出字会让三类电脑全叫「电」：

```
PC/Master_01  主脑      → 若不细分，也是「电」
PC/Seat_07    座位机    → 「电」
PC/Room_01    整间聚合  → 「电」
```

`1F104-电001` 会同时指主脑和 1 号座位 —— **换个说法又撞回来**。
传感器同理：`Temp_01`（温度）与 `CO2_01`（CO₂）量的是完全不同的物理量。

所以 `Split()` 多返回一个**设备名段**，`TypeGlyph(category, name)` 据此细分。
已实测：加细分后 70 台 → 70 唯一，撞号 0。

### 2.4 三层格式同步改动

| 格式 | 旧 | 新 | 用在哪 |
|---|---|---|---|
| 全码 | `1号教学楼2F203办公室001灯具` | `1号教学楼2F203办公室001灯具` | 详情卡 —— **三段全部唯一，本来就不撞** |
| 短码 | `2F203-001` | **`2F203-灯001`** | 列表台账、能耗榜、告警行 |
| 带类型 | `2F203 灯具` | **`2F203 灯具001`** | 异常 Top3、右栏告警条 |

> ⚠️ `Full()` 全码本身**不撞号**（房间类型 + 序号 + 类型名已经足够区分），
> 但为了与短码同步，`Full()` 里也改用了细分名 `TypeLabel()`：
> `PC/Master_01` 显示「主脑」而不是「电脑」，`Sensor/CO2_01` 显示「CO₂传感器」而非「传感器」。

## 5. 顺带算清：联动开机增量 3.115 kW 是对的，任务包的 3.24 算错了

### 5.1 校验和精确闭合

| 时刻 | 校验和 | ÷200 | 显示 |
|---|---|---|---|
| 联动开机**前** | `1735000` | **8675 W = 8.675 kW** | 8.7 ✅ |
| 联动开机**后** | （日志未记录基准） | 按算式 **11790 W = 11.79 kW** | 11.8 ✅ |

### 5.2 增量逐项分解

联动开机下发的是 **20 条命令**（不是 18 条）：主脑 + 投影 + 18 座位。

| 设备 | 开机前 | 开机后 | 增量 |
|---|---|---|---|
| 18 座位 | 30 W/台（`200 × 0.15` fallback） | 180 W/台 | 18 × 150 = **2700 W** |
| 主脑 | 30 W | 180 W | **150 W** |
| 投影 | 45 W（`300 × 0.15`） | 310 W | **265 W** |
| | | | **合计 3115 W** |

**8675 + 3115 = 11790 W = 11.79 kW** → 显示 11.8。闭环，无缺口。

### 5.3 任务包的 3.24 错在哪

任务包写「增量 ≈ 3.24 kW = 18 × 180」，把 **180 W 当成了绝对增量**。
但每台电脑开机前不是 0 W，而是 `RatedPower(PC) × 0.15 = 30 W` 的**待机底噪** ——
这是 `LivePowerOf` 对"有测点但读数为 0"设备的兜底，是设计如此。

```
任务包期望：18 × 180       = 3240 W
实际增量：  20 台各减去底噪 = 3115 W
差：                        = 125 W
```

差值的构成：18 座位各少算 30 W（−540），但多算了主脑 150 + 投影 265（+415），净 −125。

**结论：`LivePowerOf` 的算术是对的，验收判据的期望值写错了。** 建议按 3115 W（±显示舍入）验收。

### 5.4 顺带修正我上一轮的误判

上一轮我看到「8.7 → 11.8 差 3.1，比 3.24 少 0.14」，判断"缺口存在"。
拿到校验和 `1735000` 之后精确复算：**11790 W 精确等于 8.675 + 3.115**，没有缺口。
当时的 0.14 是我用显示值（8.7/11.8，各带 ±0.05 舍入）倒推产生的假象。

两个挂着的裁决点已裁定 **可接受**，但在落实时实跑全部 70 条，发现三处必须修的问题。

### 12.2 落实时发现的问题一：告警条差 1.5px 溢出

按 70 条实测宽度，`WithType` 最长文案 `2F201 温度传感器001` 需 **109.5px**，

直接画到右边的告警等级（「警告」「数据陈旧」）上 —— 表现是两个字被编号压住。

### 12.3 问题二：用截断兜底会毁掉唯一性

第一版修法是套 `FitText` 从尾部截，结果是 `2F201 温度传…001`。两个问题：

1. **编号里带省略号**，读的人第一反应是"数据是不是没显示全"
2. 若截掉尾部（常规做法），`001/002/003` 三台传感器会变成同一个字符串
   —— 把 P7「70 台唯一指认」的成果当场抹掉

**根因不是宽度算错，是三层编号只给了两档长度**：短码 1 个字、全码全名，
中间没有过渡。而 `WithType` 恰恰是用在窄栏的那一层。

### 12.4 修法：补中间档 `TypeMid`

| 层 | 方法 | 长度 | 用在哪 | 宽度 |
|---|---|---|---|---|
| 短码 | `TypeGlyph` | 1 字 | 列表台账 | ~65px |
| **中码** | **`TypeMid`（新增）** | **2~3 字** | **告警条、异常 Top3、窄态** | **≤85px** |
| 全码 | `TypeLabel` | 全名 | 详情卡（可折 2 行） | ≤194px |

`TypeMid` 的映射：

| 原设备 | `TypeGlyph` | `TypeMid` | `TypeLabel` |
|---|---|---|---|
| `Sensor/Temp_01` | 传 | **温度** | 温度传感器 |
| `Sensor/CO2_01` | 碳 | **CO₂** | CO₂传感器 |
| `PC/Master_01` | 主 | 主脑 | 主脑 |
| `PC/Seat_07` | 电 | 电脑 | 电脑 |
| `PC/Room_01` | 组 | **整组** | 机房电脑 |
| 其余 | 单字 | 与全名同 | 全名 |

唯一性靠**同房间内不重名**保证，不靠堆字数。实测 70 条：

```

WithType  唯一 70/70  撞号组 0
Full      唯一 70/70  撞号组 0
```

`WithType` 最长从 109.5px 降到 **76.5px**，告警条（106px）余量 30px。

### 12.5 问题三：`Alarm` 只有短码字没有中文名

实跑 70 条时发现走廊那台烟感显示成 **`1F105 Alarm001`** —— 中英混排。

## §13 P10 设备管理全屏态点行无反应（2026-11-03）

### 13.1 症状

主理人 play 实测 + 三张截图：全屏 → 设备管理 → 点任意一行，**什么都看不出来**。
行不点亮、右栏不变、没有任何反馈，判为"死按钮"。

### 13.2 两个根因叠加，只修一个都修不好

**根因 ①：右栏形态判定有两个出口**

```csharp
// Show(Mode mode) 里，原来这两行是**无条件**的
SetGroupActive(_alarmGroup,  false);
SetGroupActive(_detailGroup, false);
```

注释当时写的是「交给 `RefreshHome` 裁决，在这里硬切会和它打架」——
那句话在 **Home** 模式下成立，但 System 模式下 `RefreshHome` 根本不跑
（`Refresh` 里只有 `Mode.Home` 才调它）。于是详情组在 System 里永远是关的。

更要命的是 `SelectTab` 里还有第三处：

```csharp
if (_asideGroup != null && _asideGroup.gameObject.activeSelf == (index == 4))
    _asideGroup.gameObject.SetActive(index != 4);   // 只认"是不是统计页"
```

它不认"设备管理页正在看详情"，从详情切走再切回来，辅栏会被无条件打开、
和详情组**同时显示**，两层内容叠在 200px 右栏里。

**根因 ②：选中来源晚一帧**

即使 ① 修好，判定读的是 `TwinDetailPanel.SelectedAnchor`。
那个属性背后是 `_selected`，而 `_selected` 是在 `TwinDetailPanel.Update()`
里从 `TwinPicker.Selected` 抄过来的 —— **晚一帧**。

点行的调用链是**同帧同步**的：

```
Button.onClick → OnDeviceRowClicked → TwinPicker.Select() → Refresh(true)
```

于是 `Refresh(true)` 里读到的还是点击前的旧值（null），右栏原地不动；
真正切换要等 `TwinDrawer.Update` 的 0.5s 节流 —— 用户看到的还是"点了没反应"。

### 13.3 修法

**收成唯一出口** `ApplySystemAside()`，`Show` / `RefreshSystem` / `SelectTab` 共用：

| 页 | 右栏内容 | 判据 |
|---|---|---|
| 设备管理 `_tab==1` | 选中→设备详情；未选→辅栏 | `sel != null` |
| 数据统计 `_tab==4` | 让位给画布（满宽） | 恒关 |
| 其余三页 | 辅栏（筛选/小结/追溯） | 恒关两态 |

里面只读 `TwinPicker.Selected`（与行高亮同源同帧）。
`SelectTab` 里那段 `_asideGroup` 硬切**整段删掉**，只负责把 Tab 状态设好。

### 13.4 顺带补齐的三件事

**① Esc 退详情这一层**

详情右栏上一直挂着「Esc 返回」，但之前按 Esc 会**直接把整个抽屉收掉** ——
那句话是假文案，而且退得比"回辅栏"还狠。新增 `TwinFullLayer.HandleEscape()`，
由 `TwinDrawer.OnEscape` 在退页栈**之前**调用。

**② 行高亮只有一层，等于没做**

原来只有 `AccentDim` 填充（Accent @0.035，亮度差 Δ18），在深色行底上几乎看不出变化。
补成三层，逐层递进：

| 层 | 未选中 | 选中 | 作用 |
|---|---|---|---|
| 底 | `Color.clear` | `AccentDim` | 面的轻重（Δ18） |
| 边 | 全屏 `Border` / 窄态 `clear` | `AccentLine` 1px | 行边界从"无"变"有" |
| 字 | 窄态「详情›」`TextMuted` | `Accent` | 一眼看出哪行是当前项 |

**两态同步改**（`TwinSystemPage.RefreshDevice` 同步补描边）：
未选中行**不给描边** —— 窄态构建时就是 `Color.clear / 0f`，
给未选中行补 `Border` 会让整张表突然浮出 64 条行框，观感全变。

**③ 告警中心点行"只开闸门不刷新"**

`OnAlarmRowClicked` 结尾只有 `_nextRefresh = 0f;`，注释却写「立刻刷一次」——
那只是把节流闸门打开，真正刷还要等下一帧。补上 `Refresh(true)`，和设备管理页一致。

### 13.5 教训（本项目第三次同类）

而且 ② 这个坑**本文件里已经用 C-31 的注释写过一次**
（`RefreshDevicePage`：「选中态直接读 `TwinPicker.Selected`，不要读 `SelectedAnchor`」）——

主理人选择「**全屏也做成整页详情（推荐）**」——全屏点行后不再挤右栏，改为在中间区域铺一张完整详情页，两态信息量完全一致。

### 14.3 修法

**核心决定：详情页只有一份实现，由它自己按宿主切宽度。**

```
窄态：_x=184  _w=440  _bottom=506
全屏：_x=16   _w=968  _bottom=568
```

判据只有一个 —— `TwinDrawer.IsFullScreen`（**不新增标志位**，多一个标志就多一处两态不同步的可能）。

配套四处收口，少一处就出画面 bug：

| # | 位置 | 改了什么 | 不改的后果 |
|---|---|---|---|
| a | `TwinDrawer.ApplyFullMode()` | 三态互斥：全屏+无详情→只开全屏层；全屏+有详情→只开 `_content`；窄态→只开 `_content` | 详情页 Push 进关着的 `_content`，看不见，还是"点了没反应" |
| b | `TwinDrawer.Update()` 每帧互斥检查 | 加 `IsDetailOnTop()` 例外 | 下一帧把详情页连父节点一起关掉，一闪就回三栏 |
| c | `PopPage` / `OnBackClicked` / `OnEscape` | 三条退出路径都补 `ApplyFullMode()` | 返回后停在一张空内容区（三栏没了、页也没了） |
| d | `TwinDeviceDetailPage.Update()` | 每帧比一次 `IsFullScreen != _full` | 详情页开着时点最大化 → 页栈没变 → `OnShow` 不触发 → 内容仍挤在 440 那一条 |

同时 `TwinFullLayer.ApplySystemAside()` **砍掉第三态**：System 下 `_detailGroup` 恒关。理由见下。

### 14.4 三个自己踩出来的坑（都是先写完再复查发现的）

**坑一：全屏下沿算错坐标系（648 → 568）**

第一版写 `FullBottom = 720 − 60 − 12 = 648`，看着对，其实量错了对象：本页活在 `_content` 里，而 `_content` 的矩形是 `720 − 头带80 − 底带60 = 580`，左上角在 `_root` 的 y=80。所以本页的 y 从头带下沿起算，可用下沿是 `580 − 12 = 568`。

写 648 会排出下边界 80px，且 `_content` 挂了 `RectMask2D` —— 表现是"告警列表被切了半截"。**看的是统计页的 620，那是 `_root` 坐标，换算过来 540 就落在 568 内**，两页其实一致。

**坑二：全屏要不要保留左轨 200**

第一版保留了（`FullX=216, FullW=768`），理由是"导航不能丢"。否掉了，三个理由：

- **语义站不住**：左轨 5 个 Tab 是「校园管理系统」的页内导航，而详情页是被 Push 到它上面的下一层。开着详情页点 Tab，是切页还是换设备？页栈答不出来，只会造出"栈顶详情、底下电力管理"的矛盾态。
- **保留也点不动**：全屏层此时关着，要让左轨可见就得再开一层，裁剪与射线又要重新对齐。
- **窄态本来就不是这样**：窄态详情页是全宽 640 + 头部返回键。两态要一致，全屏就该同样全宽。

最终 `FullX=16, FullW=968`（1000 − Pad×2），与窄态同构，靠抽屉自己的头部导航。

**坑三：同一件事又出现两个出口（空态显隐）**

给告警区补空态时，我第一版在 `BuildAlarmArea`（按"要几行"）和 `RefreshAlarms`（按"实际填几行"）**两处**都写了 `SetActive`，判据还不一样（前者 `rows==0`、后者 `_alarms.Count==0`）。后者更错：`_alarms.Count` 是"建了几个节点"，有告警时它是 4，拿它判会让空态和告警行同时出现。

收成一处：`BuildAlarmArea` 只负责建节点 + 定位，**显隐全部由 `RefreshAlarms` 按 `n == 0` 裁决**。

> ⚠️ 这正是 P10 那次事故的同型复发。P10 的教训写进了 `ApplySystemAside` 的注释，但**没有变成一条检查动作**，所以这次又犯。补的检查动作是：**凡是写 `SetActive` 的地方，先问"这件事还有没有第二个地方在判"**。

### 14.5 顺带修掉的两处（不改也能跑，但会出观感问题）

1. **`Object.Destroy` 延迟到帧尾** → `RebuildForHost` / `RebuildMetrics` / `BuildAlarmArea` 全部改成"先 `SetActive(false)` 再 Destroy"。否则新旧节点本帧叠在一起，切换形态时闪一下。
2. **告警标题复读**：原来无记录时标题写「告警与异常 · 无记录」，下面又有一句空态，同一层两行都在说没告警。标题改成只写分类，判据交给空态标签。

### 14.6 全屏的余量怎么用

全屏可用高 408（160→568），窄态 346。指标少的设备（烟感 1 项、门 1 项）块高封顶后，下方会剩 100~180px 空白 —— 直接留白看着像"没加载完"。

处理：`metricH` 封顶后的**余量加进告警行高**（28 → 最高 46），而不是塞占位框。行变高让「时间 · 状态 · 设备名」读得更开，下边界也正好贴到 568。**把空白变成信息**，不加新东西。

> 为什么不加行数：行数是"这台设备历史上出过几条告警"，由数据决定。UI 为了填满多显示几条，会让人以为告警变多了。

## 15. P11-b —— 详情页偶尔只剩骨架（2026-11-03 主理人第二次截图）

### 15.1 症状

主理人：「有时候点击设备详情显示这样……**全屏窄屏都出现过，这是没加载出来吗。有时候正常，有时候就这样**」，附第三张截图。

截图里**有的**：返回键「← 返回列表」、三列**标签**（位置 / 类型 / 电力）、分割线、底部工具行。
截图里**没有的**：全码、状态胶囊、三列的值、指标块、量程条、趋势线、告警区。

不是"加载慢"—— 等多久都不会出来。是**根本没建**。

### 15.2 根因：`RefreshAll()` 只挂在三条路径的一条上

上一版 `OnShow()`：

```csharp
if (!_built) Build();
else if (wasFull != _full) RebuildForHost();
else RefreshAll();          // ← 只有 else 这条刷
```

而这两个方法的职责是**割裂**的：

| 方法 | 建了什么 |
|---|---|
| `Build()` | 返回键、全码 `Text`（空字符串）、胶囊、三列标签与值节点、分割线 |
| `RefreshAll()` | 全码文本、胶囊状态、三列值、**指标块**（`RebuildMetrics`→`BuildMetricRow`）、**告警区**（`BuildAlarmArea`） |

于是 `Build()` 和 `RebuildForHost()` 两条路径产出的是**空骨架**：

- 首次打开走 `!_built` → `Build()` → 骨架，然后 **什么都不调**。
  `Update()` 的 0.1s 刷新只跑 `RefreshValues()`，它改的是**已存在的 `_rows`** 里的文字，不会建块 → 块**永远不出现**。
- 形态切换走 `RebuildForHost()` → 内部 `Build()` → 同样空骨架。

### 15.3 为什么"有时候正常"

这页是**复用实例**（`OpenDeviceDetail` 里 `GetComponentInChildren<TwinDeviceDetailPage>(true)`），`_built` 一旦为真就一直是真。

- 只要之前进过一次、且那次走的是 `else RefreshAll()` 分支 → 后面都正常；
- "**第一次进**"和"**刚切过形态**"这两种必然空。

所以表现出来就是随机 —— 并且越频繁切换形态越容易撞上，正好对上主理人「全屏窄屏都出现过」。

### 15.4 修法

两处都补成"建完必填"：

```csharp
// OnShow：无条件刷，三条路径都覆盖
if (!_built) Build();
else if (wasFull != _full) RebuildForHost();
RefreshAll();                       // ← 提到 if 外面

// RebuildForHost 内部：让方法自身完整，不靠调用者记得刷
Build();
RefreshAll();
```

`RefreshAll()` 是幂等的（只读 `_anchor` 重算 DOM），多调一次没有副作用。

### 15.5 教训（本项目第四次同型）

P10 是"右栏形态判定两个出口"，P11 是"空态显隐两个出口"，这次是"**建骨架和填内容分属两个方法，却只在一个出口配对**"。

三次的形状完全一样：**一件事被拆到两处，其中一处忘了跟着改**。

这次能立刻定位，靠的是主理人截图的**细节**——"三列标签在、值是空的"。标签由 `Build` 建、值由 `RefreshAll` 填，这个差异直接指向"只跑了 Build 没跑 RefreshAll"。**所以截图要尽量给全，空白处比有内容处更有信息量。**

补的检查动作（比上次那条更具体）：

> 凡是一个方法**只建了一半**（骨架/容器），就要问：**另一半由谁建？所有调用路径都调了吗？**
> 如果答不上来，就把两半合成一个入口 —— 别指望调用者记得配对。

### 15.6 判据（2 条，接在 P11-18 后）


# 16. P27 数据真实性（2026-11-03）

## 16.1 一句话结论

**坏的不是某个 case 分支，是「每个指标各自一条独立正弦波」这个结构。**
`MockSignalGenerator` 把 14 种指标一视同仁，指标之间零物理约束。
所以修法不是打补丁，而是**按物理含义分类，让环境量从同一个气候模型派生**。

## 16.2 四个报障点 → 四个真实根因

| 主理人看到的现象 | 根因 | 覆盖范围 |
|---|---|---|
| PC 关机、0 台，CPU 仍 20% | `CPULoad` 不在任何播种/派生表里，跑通用正弦 | 21 个 PC 点位 |
| 「其他用电设备全部这样」 | 不只 PC：`Smoke` 从未播种 → 每 45s 冲 100 obs/m 假报火警 | 烟感 1 个点位 |
| 灯关了状态还黄着 | `Brightness=0` 被回差强留 Warning（`0 < 20+4` 恒成立） | 16 个灯点位 |
| 详情页胶囊冻住 | 胶囊只在 `OnShow` 刷一次，10Hz 走 `RefreshValues` 不碰它 | 两态详情页 |
| 室温/暖气/CO₂ 乱跳 | 环境量套用功率的秒级正弦 + 叠加 ±3% 噪声 | 4 类指标 |

## 16.3 结构：环境量物理模型（本轮主体）

```
室外温度（月份 + 天气 + 24h 正弦，峰值 14:30）
    │
    ├─ 一阶热惯性（滞后 3h、幅度 ×0.3）── 供暖季只压这一项（×0.04，到 20°C）
    │
    └─ 室内得热（按作息平滑插值，1.1°C/小时的物理上限）
              ↓
          室内温度  ──→ 温湿度传感器的 Temperature
              │
              ├─ 饱和含湿量（Magnus）── 含湿量 ÷ 饱和值 → 湿度
              └─ 质调节曲线（室外越冷出水越热）→ 暖气 SupplyTemp
CO₂：同一张得热表判定"有人"，45min 锯齿（线性爬升 + 指数换气）
```

**关键设计**：室温不是自己造周期，而是从室外**派生**。
主理人那句追问（"后面做时间天气系统会跟着变吗"）直接决定了这个结构 ——
现在只调 `TwinClimate.SetWeather()` / `SetHourOverride()`，室温曲线立刻跟着变，
`MockSignalGenerator` 一行都不用改。

## 16.4 实算发现的三个错误（看代码看不出来的）

这是本轮最重要的教训：**物理模型必须实算，不能靠"读起来对"**。

| 错误 | 症状 | 根因 |
|---|---|---|
| 供暖季室温 15.5~16.2°C | 教室偏冷 4°C | 把「得热」也一起钳掉了 → 钳制必须在得热**之前** |
| 7 月湿度 **−3 %RH** | 负数，物理不可能 | 线性式 `52-(T-20)*4.5` 外推越界；RH 是"含湿量÷饱和含湿量"，后者指数增长 |
| 7 月供水 **22~33°C** | 供水比室温还低 | 质调节在非供暖季无意义（锅炉没开采暖循环） |
| 12:00 室温瞬跳 0.8°C | 纯阶跃得热 | 50 吨建筑不可能因下课铃丢热 → 改 smoothstep 插值 |

修后实测（12 月 × 4 种天气 × 每 15 分钟，共 48 组合）：

| 场景 | 室外 | 室内 | 日内变幅 | 湿度 |
|---|---|---|---|---|
| 1 月 多云 | −4~0 | **19.3~20.3** | 1.0 | 31~34% |
| 7 月 晴 | 25~34 | **28.3~31.9** | 3.6 | 32~53% |
| 11 月 雨 | 5.5~8.5 | **19.7~20.7** | 1.0 | 40~61% |

供暖季"一整天几乎不动、稳定 20°C 附近"，这才是真实暖气教室的样子。

| ③ | `IsSmooth` 上方留了一串悬空 `///` + 孤立 `</summary>` | 上一轮插入 `ResetBootClock` 时**把 `<summary>` 开标签吃掉了**。不影响编译，所以编译器不报 |

③ 是本轮最值得记的一条：**这类残损编译器不会发现**，而本项目大量依赖注释讲"为什么"。
已补判据 `P27-60` 断言"`IsSmooth` 前紧邻一个 `}`"，防止再次被插入打断。

## 17.2 CPU 负载模型（新增）

```
boot = 0.80 · exp(−sinceOn / 12)        开机冲刺，τ=12s
idle = 0.11 + 0.03 · sin(2π t/90 + φ)   空闲基线 8~14%
load = max(boot, idle)                  量化 0.1%，上限 92%
```

实测回落曲线：

| 开机后 | 0s | 5s | 12s | 20s | 25s | 60s+ |
|---|---|---|---|---|---|---|
| 显示 | 80.0% | 52.7% | 29.4% | 15.1% | **11.0%** | 11.0% |

峰值 80% **永不越过 WarnHigh=85** —— 这是"开机拱一下但不再擦线"的关键。

**记账 key 必须是 `twinId`，不能用 `phase`。**
理由不是"相位每帧变"（`seq` 每帧开头重置为 0，对固定 (i,k) 其实是常量），
而是**相位是数值、不是身份**：两台机器相位撞了就记成同一次开机，
表现为"同时开机，一台直接是空闲值"。twinId 天生唯一。

## 17.3 静态状态跨 Play 泄漏（新增一条）

`BootStart` 存的是**数据源时间轴上的 t**，而 t 每次 Play 从 0 重来。
上一轮记的 `start=42` → 这一轮 `elapsed = 0−42 < 0` → clamp 成 0 → 判"刚刚开机"。

目前**不表现**（开局播种把 21 台 PC 压成 override 0，用户点开机又会 `ResetBootClock`），
纯属卫生问题。但与 `s_muted` / `s_overrides` 是同一类坑，且"第一轮正常、第二轮才怪"极难查。
已并入同一个清理入口 `MockDataSource.ResetStaticsOnLoad`。
