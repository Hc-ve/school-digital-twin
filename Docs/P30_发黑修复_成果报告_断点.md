## 〇、一句话

**黑不是材质坏了，是「那块 UV 位置烘焙时本来就没收到光」。** 用 `lightmapIndex = -1` 让该渲染器脱离烘焙、改用环境光，是唯一零资产改动的解法。但有三类情况它救不了，见 §三。

## 一、修好的原因（三层，逐层说清）

### 1.1 为什么黑 —— 光照贴图的采样结果就是 0

Unity 烘焙时把**光照结果烘进一张贴图**，每个渲染器的每个面按 UV2 坐标去这张图上取颜色。

这些对象（吊顶下表面、朝内的墙）有个共同特征：**可见面朝下或朝内，背对全部 69 盏光源**。内置管线的 Directional 烘焙模式按法线投影，朝下的面投到 0 —— 于是它在贴图上占的那块**就是纯黑**。

实测证据（检测工具采样结果）：

| 对象 | 图集 | 图集整体均值 | 该对象 UV 块平均亮度 |
|---|---|---|---|
| `SchoolBuilding/ZalTop` | 15 | **0.3132（正常）** | **0.0353（全黑）** |
| `SchoolBuilding/PCClassTop` | 10 | 0.1617（偏暗） | **0.1093** |
| `SchoolBuilding/DirectorTop` | 20 | 0.1135 | **0.0851** |
| `SchoolBuilding/Box001` | 22 | 0.1443 | **0.1785（62% 的面为 0）** |

**关键**：图集本身有光（ZalTop 那张均值 0.31 是正常的），黑的是**它占的那一小块**。
所以「换材质」「提图集亮度」都没用，问题定位在图集上的具体一块。

### 1.2 为什么 `lightmapIndex = -1` 能修

`lightmapIndex` 是渲染器「去第几张贴图上取光」的索引。

- `>= 0` → 去第 N 张贴图取（这块取到的是 0，所以黑）
- **`-1` → 不参与烘焙**，Unity 改用「实时光源 + 环境光（Ambient）」

**环境光是个全局常量**：不管面朝哪个方向，都能拿到一个基础亮度。所以原本纯黑的面变成均匀的水泥色。

**这也是为什么它对这个场景特别有效**：现场是室内、光源固定、不需要动态光影，环境光的均匀性反而符合"室内墙面"的观感。

### 1.3 为什么有副作用 —— 失去明暗过渡

脱离烘焙 = 不再有"靠近窗户亮、靠近角落暗"的渐变。所以：

| 类型 | 改了的效果 | 判断 |
|---|---|---|
| 墙 / 吊顶 / 楼板 / 边条（大面积平面） | 从纯黑变成均匀色，**看不出变平** | ✅ 可以改 |
| 桌椅 / 门板 / 马桶 / 海报（有立体感） | 直接变"一块纯色板"，失去体积 | ❌ 不能改 |

**筛选原则就是这么定的**：只修建筑结构件，不修家具。

### 1.4 为什么有些地方改不了 —— 那里没有几何

主理人反馈「走廊天花板」「计算机教室墙」点不中。这符合项目踩坑日志 `P00 §1.6 C4` 的两条判据：

> ① **点选不到 = 没有 Renderer = 空**
> ② **y=0 网格能显示在那里 = 那里能看穿**

截图里那些黑色区域能看到斜向格纹（Unity 的 y=0 地面网格），两条都符合。

**结论：那些位置没有墙/天花板，看到的是建筑外的虚空。** 任何光照手段都无效（没有东西可照），需要补几何。详见 §四。

## 四、一处重大误判的修正（走廊天花板）

### 4.1 我一开始判断错了

主理人反馈「走廊天花板点不中」，我按 `P00 §1.6 C4` 的判据（「点选不到 = 没有 Renderer = 空」）
判定为**几何缺失**，并建议打光加 Plane 遮挡。

**这个判断是错的。** 打光用洋红扫描实测推翻：

| 检查 | 方法 | 结果 |
|---|---|---|
| 走廊上方有没有几何 | 站走廊正中 (-2, 1.6, 31) 抬头渲染，洋红 = 无几何 | **0% 洋红** —— 有几何、纯黑、灯管浮空 |
| 走廊全线天花板 | 沿 X 每 2m 向上渲染 26 次 | z ≥ 28.5 全段 **0.0%**；z 18~27 是露天庭院（本就无顶，正常） |
| 计算机教室 -Z 墙 | 沿 X 每 1m × 高度 3 档渲染 36 次 | 全部 **0.0% 洋红**，墙在，只是有一条黑带 |

### 4.2 真正的原因：合并网格，不是缺失几何

`SchoolScene/Exterior/SchoolBuilding/Corridor` 是**一个 13 材质槽的巨型单网格**：

| 项 | 值 |
|---|---|
| Renderer 数量 | **1 个** |
| 包围盒 | **52.36 × 3.56 × 24.05 m** |
| 材质槽 | 13 个（ConcreteWall6d/6e/6g、Wood3、FloorLinoleum4a/4b、TileWhite02、TileArmstrong01_01 等） |
| lightmapIndex | **4**（仍在走烘焙） |

走廊的天花板、两侧墙、地面、装饰线**全在这一个 mesh 的不同材质槽里**。
Unity 点选只能到 Renderer 级 —— 点天花板、点墙、点地面，选中的必然是同一个 `Corridor`。

**所以「点不中」的真相是「没有第二个对象可选」，不是「那里没有几何」。**

### 4.3 修复与验证

加进路径表后，主理人 play 确认：走廊天花板恢复正常，**且地面没有明显变平**（走廊铺地胶，本来明暗就弱）。

### 4.4 对 `P00 §1.6 C4` 的补充

原判据是两条（点不中 = 空 / 能看到网格 = 看穿），**漏了第三种情况：大网格单 Renderer**。

**建议补第三条：点选后看 Hierarchy 高亮的是哪个对象 —— 若同一个对象包办了整个房间的所有表面，
那叫「合并网格」，不是「缺失几何」。判据要加上「一个 Renderer 是否覆盖多个面」。**

## 六、踩坑记录（6 条，全部实际踩过）

| # | 现象 | 根因 | 教训 |
|---|---|---|---|
| **1** | 走廊天花板「点不中」，选中的总是 `SchoolBuilding` 或 `Corridor` | `Corridor` 是 **13 材质槽的单个巨型 mesh**（52×3.6×24m），天花板/墙/地面/装饰线都在里面。点选只能到 Renderer 级 | **「点不中」有三种原因，不是只有「没几何」**：① 真的空 ② 被遮挡 ③ **一个 Renderer 包办多个面（合并网格）**。判据要加第 ③ 条 |
| **2** | 检测工具 v1 漏掉 `Floor2`（二楼天花板元凶） | 按**整个网格平均亮度**判，而 Floor2 上表面（三楼地面）有光、下表面全黑，平均被拉高 | 要**两个指标一起看**：平均亮度 + **黑点占比**。局部整片黑会被平均掩盖 |
| **3** | 检测工具 v2 仍漏掉 `Corridor` | 黑点占比也是按整个 Renderer 平均。`Corridor` 只有天花板黑、墙地面亮，整块被稀释到 60% 以下 | **大对象会稀释小面积的严重缺陷**。对「单 Renderer 覆盖多个面」的对象，平均值类判据全部失效 —— 只能靠人工指认或按材质槽拆分 |
| **4** | 按「图集均值 < 0.25」筛出 856 个候选，实际只有 108 个真黑 | 1024² 图集里大部分像素是没被 UV 覆盖的**空白 padding（纯黑）**，把均值拉低 | **图集均值不是判据，误报率 87.4%**。必须按每个面的 UV2 去采样 |
| **5** | 新增的 `autoPaths` 字段代码里写了默认值，但已挂载的组件读不到 | Inspector 里**已经序列化过的组件**，其字段值会覆盖代码默认值（`P00 §1.6 A1`） | 默认值不能只写在字段声明里，要在 `Awake()` 里做 fallback：`autoPaths` 为空就用内置 `DefaultPaths` |
| **6** | `lightmapIndex` 改了保存场景也不生效 | 它存在 `LightingData.asset` 的二进制里，场景 `.unity` 中 **0 处 `m_LightmapIndex` 文本字段** | 这类字段**只能运行时赋值**，无法落库。也因此不能加 `[ExecuteAlways]`（编辑器执行但存不进去，只会把场景弄脏） |

**附：两条工具链坑**

- **`grep -E '\| 8[0-9]% \|'` 统计不准** —— shell/ERE 里 `\|` 的转义行为不稳定，同样的模式在 `grep`（BRE）下能匹配、`grep -E` 下返回 0。改用 `awk -F' | '` 按字段解析，结果稳定。
- **Unity 进程的工作目录不是工程根** —— Editor 脚本里写 `File.Exists("Temp/x")` 会静默找不到。必须从 `Application.dataPath` 反推工程根。
