## 1. 结论与诊断证据链

### 1.1 一句话结论

夜晚档「室内近黑」的根因**不是缺灯，是环境光被压没**：
时间天气系统把环境光的内容来源（天空盒）与强度、再加全屏曝光，三者连乘压到近零；
室内本就零实时光（Area 面光只支持烘焙、D13 后为零），于是只剩灯管脚下的小光斑。
修法 = **不动天气系统**（动它室外必然跟着亮，撞「不能过曝」红线），
在室内补一层**灯具语义驱动**的实时点光源，随昼夜档缩放、随灯具开关启停。

### 1.2 实验 A（2026-11-13 主理人实测，判读「亮了」）

play 中把 环境光照 Source 从「天空盒」改成「渐变」，仅此一项，室内立刻可见变亮（截图存档于会话）。
⇒ 「天空盒→SH 环境光」链路**确诊**为夜晚室内近黑的主因。

### 1.3 主理人实测对账（代码值 ↔ 照明窗口所见，逐项吻合）

### 1.4 夜晚+雨天，室内一个墙面像素的照度连乘（预期推算）

| 环节 | 数值 | 出处 |
|---|---|---|
| SH 内容：_SkyTint | 雨 (0.42,0.47,0.55) × skyMul 0.20（b 再 ×1.70）≈ (0.084,0.094,0.19) | Build() :236-250 |
| SH 内容：_Exposure | 雨 0.70 × 0.34 = **0.238** | Build() :246 + ApplyAll :299 |
| × ambientIntensity | 雨 0.60 × 夜 0.30 = **0.18** | 见 1.3 |
| ⇒ 墙面环境光（预期） | ~0.004 线性 | 推算 |
| × postExposure | −1.45−0.25 = −1.70 EV ⇒ **÷3.25** | ApplyPostExposure :418-421 |
| ⇒ 最终 | **~0.001 线性 ≈ 全黑**，与图1 断电态、夜晚教室截图一致 | — |

而灯具自带 glow（intensity 2.0、range 3m）在 1~2m 处照度 ≈ 0.7~1.5，÷3.25 后仍可见 → 灯管脚下那一小圈；
3m 之外归零 → 「灯只发光不照人」。走廊两层各 15 个 glow 争 12 个逐像素名额，落选者降级顶点光 →
部分灯管连小圈都没有。**全部与主理人截图所见吻合。**

### 1.5 为什么不是探针、不是 Bloom、不是 Directional

- 4 个 LightProbeGroup 烘焙数据随 LightingData 空壳失效（勘误已核），但探针只影响**动态物体**（角色），
  解释不了静态墙面全黑；
- PPS_Bloom.asset 里 Bloom `intensity overrideState=0 value=0` → **Bloom 当前根本没生效**，
  "Bloom 炸开"不是现存风险（交接书里 0.85/0.50 只写在零调用的 TwinLightingPreset.Night 里）；
- 两场景 Directional 是 **Mixed**（m_Lightmapping:1，场景 YAML 实测，P00 v1.49/总纲 §3.1 写反了），
  太阳/月亮有实时直接光 —— 室外的亮度因此与室内拉开差距，正是「室外还可以、室内暗」的原因之一。

## 2. 修法总览：两条语义轴，各管各的

主理人 2026-11-13 实测确认的语义（截图三连：14:10 同一时刻 晴/雨/雪）：
**天气变 → 环境光强度变；灯具亮度不变。** 这就是真实语义（灯是电的，跟天气无关），本方案严格沿用：

| 轴 | 归谁管 | 变化来源 | 本方案动作 |
|---|---|---|---|
| **环境光轴**（天空盒 SH + 曝光 + 雾） | EnvironmentState（现状不动） | 昼夜档 × 天气档 | **一个参数都不碰**（约束 6） |
| **灯具轴**（灯管自发光 + 每盏小 glow） | TwinDevicePresenter（现状不动） | Power 回读 + 回路通断 | **一个参数都不碰** |
| **补光层**（本方案新增） | IndoorFillLight | 昼夜档 × 灯具开关 × 走廊应急底光 | 新文件，运行时建灯 |

补光层在语义上是**灯具照明**的延伸（光从灯的位置来、灯关它就灭），不是"环境补光"——
所以它不需要、也不允许去改 ambientMode / ambientIntensity / postExposure（那三条是环境光轴的专属参数）。

## 3. Q1 · 布点策略推导

### 3.1 预算约束：12 个逐像素名额怎么分

QualitySettings Ultra 档 `pixelLightCount: 12`（第 256 行，`m_CurrentQuality: 5` 实测确认）。
内置管线前向渲染下，每个物体按重要性取最近 ≤12 盏逐像素光，**超出静默降级为顶点光**
——顶点光打在两三角面的大平面上插值不出亮度（族⑥，P17 踩过两次）。
当前场景的现实基线：灯具 glow 全部 ForcePixel，全开时走廊一个物体面前就有 15 个候选（两层各 15，
但跨层 3.56m > range 3m 不入选，实际单层 15）→ **走廊已经超预算，这正是"有的灯管有光圈有的没有"的原因**。

⇒ 推论 1：补光层数量必须**少而精**，走廊单层活跃补光 ≤3；
⇒ 推论 2：补光点放在**半高（离地 2.2m）**而不是贴着灯管——墙面/地面物体的包围盒中心离半高更近，
   重要性排序里补光点自然赢过远处 glow；天花板物体仍然偏好最近的 glow。
   这样两层分工：**glow 管"灯管脚下的点"，补光管"灯管之间的面"**，互不抢活。

### 3.2 走廊（Corridor1/Corridor2）：候选网格 + 就近启用，不是移动跟随

- 走廊 X∈[−45,25]（TwinRoomBounds 实测，约 70m，主理人小地图确认 L 形视觉），灯管间距 3~4.2m。
- 方案：沿 X 每 **7m**（≈灯管间距 2 倍）铺一个候选点（每层 10 个），z 取走廊中线，y = 离地 2.2m；
  运行时只启用**离相机最近 3 个**，range 9.5m → 覆盖相机前后 ~15m 可视段。
- **为什么不是"2 盏跟随移动"**：移动会有 7m 级跳变，要淡出→挪→淡入来掩蔽，状态机复杂度换不来观感；
  启停方案 disabled 的灯**零成本**，启用瞬间落在 range 衰减尾部（远处本来就暗），人眼看不出"多了一盏"。
- **为什么不是静态全开**：20 盏全开 = 走廊物体面前 15+20=35 个候选，全部挤爆 12 名额，
  glow 与补光一起降级，画面反而变差。这是"多灯共享像素预算"问题的唯一可行解。
- **为什么用相机而不是玩家做基准**：补光层的目的是"照亮相机看到的室内区域"。
  第一人称两点重合；第三人称相机在角色后上方 3~5m，覆盖相机≈覆盖角色；
  自由相机模式下角色停在原地、视野飞走，跟随**玩家**会把光照在没人看的房间（F19 的结论
  ——跟随基准必须是玩家——针对的是雨落脚下/头顶遮挡这类**物理归属**，补光是**渲染归属**，不适用同一条）。
  相机解析复用 `EnvironmentState.FindActiveCamera()`（已修过 Camera.main 的两个坑、排除小地图 RT 相机）。

### 3.3 房间（教室/食堂/礼堂/体育房）：按面积 1~3 个，沿长轴中线均布

- 数量 = clamp(面积/55, 1, 3)：教室 85m² → 2 个；食堂/礼堂 ≈360m² → 3 个封顶；体育房 ≈29m² → 1 个。
- 教室账本：2 补光 + 6~8 glow = 8~10 候选 ≤ 12 ✓（预算安全）。
- 食堂/礼堂账本：3 补光 + 20+ glow > 12 ✗（预算紧张）——见 §10 风险 R3，靠"半高赢排序"缓解，
  若实测天花板光圈被挤掉，把这两间的 HallIntensity 降 0.2 或数量降 2 即可回摆。
- 三间标记牌承载的房间（ClassComputer/ClassDirector/ClassTeachers，P4-6：头顶没有灯具实例）：
  glow 从来没建过、灯管自发光也没有，**这三间是全楼夜晚最黑的房间**，本层给它们各 2 个补光点后
  反而是受益最大的房间。

### 3.4 楼梯间：本轮不建，明确说清

主理人尚未指认楼梯间位置（摸底回执 (c)-2 未回复），本轮**不猜坐标**（方法论 23：派工清单必须来自实测）。
楼梯间有灯具测点并登记 TwinRoomBounds 后，本层**自动**覆盖（逻辑不用改一行）；
若是无测点的纯楼梯间，在 `TwinRoomBounds` 加一行 + Registry 建测点，或由负责人裁决是否在
IndoorFillLight 里加硬编码点表（那会引入第二份坐标表，需裁决后做）。

## 4. Q2 · 昼夜/天气联动：自读档位 + 自平滑，不订阅 OnChanged

**选了什么**：每帧读 `EnvironmentState.Instance.timeOfDay` 得目标倍率
（Day 0.05 / Dusk 0.55 / Night 1.0），用 `MoveTowards` 以 1.8s 走完全程平滑过去。

**为什么不选 OnChanged 回调**：
1. OnChanged 在 `Set()` 里**切换瞬间发一次**（EnvironmentState.cs:162），过渡期 2.4s 内不再发——
   订阅方要自己复刻一遍过渡插值，等于把天气系统的缓动逻辑抄一份，两处迟早不同步；
2. Set() 即使同档重复调用也会发（same 判断只影响 tt，不影响 OnChanged），订阅方要做去重；
3. 自读 + 自平滑与 ApplyAll 的每帧写入**没有任何共享写入点**（它写 RenderSettings/后处理，
   我只写灯），不存在"打架"的前提；天气系统将来改过渡曲线、改档位枚举，只要 timeOfDay 字段还在，
   这边零改动。

**为什么灯具档不读天气**：主理人实测语义（§2）——灯的亮度跟天气无关。补光点归属灯具轴，
强度里没有任何天气项；雨天夜里室内偏暗的那部分，由环境光轴（天气系统）自己表达，两边天然不重复补偿。

**Instance 为 null 的兜底**：按黄昏档（0.55）取中，宁可靠中不靠两端；Day 场景自举必挂 EnvironmentState，
这只防"异常顺序"的极端情况。

## 5. Q3 · 断电语义裁决（这是语义决策，明说不回避）

**判断：补光层 = 灯具照明（断电必须灭）+ 走廊应急底光（断电不清零）。**

| 区域 | 断电/关灯时 | 语义依据 |
|---|---|---|
| 教室/机房/办公室等**房间** | 补光归零，房间变黑 | 真实语义：房间没人没灯就是黑的。答辩演示「断 1F 电」时教室暗下去是对的；P4-6 三间无灯具房间也按此逻辑（本层给的是灯具位的光，灯不存在/灯关就是黑） |
| **走廊（Corridor1/Corridor2）** | 补光压到 **22%**（EmergencyFloorFactor=0.22） | 真实建筑走廊有**应急疏散照明**（电池供电，断电常亮）+ 窗外月光/环境反射。交接书原图1 判读「断电时灯灭是设计正确的，但走廊黑到看不见地板不符合真实」——22% 档让地板轮廓可辨而不至于把走廊照成来电状态 |

**实现口径**：走廊补光强度 = 基准 × 昼夜倍率 × max(灯具开关量, 0.22)。
灯开着 → 全量；灯关/断电 → 0.22。灯具开关量与 TwinDevicePresenter.SyncLamp **完全同口径**
（回读 `Power`>0.5 + `TwinCircuit.IsPowered`，读事实不读命令），断电判定不会与表现层打架。

**回滚**：`EmergencyFloorFactor` 改 0 = 严格"断电全黑"语义；`SetEnabled(false)` = 整层下线。
若主理人裁决"走廊也不该有应急光"，改一个常数即可，不需要改结构。

## 6. Q4 · 过曝防护：量化判据

| 判据 | 数值 | 手段 |
|---|---|---|
| 灯下白斑 | 天花板正上方补光点直下处照度 ≤0.5 线性（albedo≈0.8 时亮度 ≤0.4） | 补光点离灯管平面 1.1m、离天花板 ≥1.3m，1/(1+d²) 衰减天然压住；起点强度 1.2~1.6 下实测预计 0.35~0.48（**预期，需 play 确认**） |
| 亮度层级 | 灯管 glow 光斑 > 补光泛光 > 环境光，三层不得倒挂 | glow 2.0/3m 未动；补光 1.2~1.6/9.5m；倒挂了就降 CorridorIntensity |
| Bloom | 资产值 intensity 0（未覆盖）→ 当前无 Bloom，**不用防**；若将来启用，threshold 1.0 下补光最高面亮度 ~0.5 也不会进 bloom | 不改后处理（约束 6） |
| 后处理曝光 | −1.70EV 是全局的，补光强度已按 ÷3.25 预折算 | 绝不通过改 postExposure"修"室内 |
| 验证方法 | play 截图后查：①灯管脚下是否成片纯白（>240/255 面积）；②补光点直下天花板是否出现第二圈白斑；③室外墙面是否比补光前变亮 | 任一出现 → 降 BaseIntensity 0.2 一档再看 |

**环境光补偿声明（D13-06 新语境）**：本方案**不用** ambientIntensity/AmbientLight 做任何补偿——
环境光轴完全归天气系统，本层一行都没碰。D13-06 判据（grep0 约束 `P30FixCeilingLightmap.cs:ambientIntensity`）
不受影响；本文件全文无该关键字。

## 9. 放弃的方案与理由

| 方案 | 为什么放弃 |
|---|---|
| 全局 Trilight/Flat 夜色环境光（实验 A 的路线当修法） | ambient 是**全局**的，室外同步变亮 → 撞老师「室外不能过曝」红线；且属"抬环境光"族（约束 6 只允许细微补偿，这不是细微） |
| 调 EnvironmentState 的 sunMul/ambMul/expMul | 修的是室外+室内一起的轴；室外会跟着变；且那是已验收系统，D13 刚结案不容再动 |
| 调 postExposure 给室内留余量 | postExposure 是全屏乘算，没有"只给室内"的通道（约束 6 明令禁止） |
| 调亮 _lampEmission 当解法 | 只会让灯管更白，周围照样黑（约束 5；TwinDevicePresenter 注释里 0.6 上限的推导同样适用） |
| 每盏灯管一个补光光源 | 走廊 30 盏灯管 → 30+ 候选，挤爆 12 名额，集体降级顶点光（约束 7 明令禁止；P17 两次踩坑同款） |
| 禁用/接管 TwinDevicePresenter 的既有 glow | 会破坏已验收的教室观感；跨系统改别人的运行时对象，ApplyLamp 写 intensity 与我禁 enabled 会形成两写入源（F16 教训） |
| 修改 TwinDevicePresenter.cs 让 glow 联动昼夜 | 违反交付约束（单新文件）；且 glow 参数是主理人三轮调出来的验收结果 |
| 补光点跟随移动（2 盏走廊移动池） | 移动跳变需淡入淡出掩蔽，复杂度高；启停方案零成本且无跳变（§3.2） |
| 重烘 lightmap | D13 已证整套烘焙数据不可用且刚清理完毕，倒退 |
| 切 URP / 加后处理插件 | 禁令（约束 2 / P00 §2.6） |
