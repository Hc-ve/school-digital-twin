## 零、这份文档解决什么问题

本包从 P35 到 P42 一共调了 40 多次灯，每次翻车的原因**高度集中在 4 类**：

| 类别 | 占比 | 典型症状 |
|---|---|---|
| ① 不知道该动哪一层 | 最多 | 明明加了灯、提了强度，画面没变化 |
| ② 常量被多个分区共用 | 次多 | 修 A 区，B 区跟着变暗 |
| ③ 写常量的口径错（少/多乘一层倍率） | 隐蔽 | 扫参 0.75 → 落地实际 0.60，差 25% |
| ④ 取证口径错，读数本身是假的 | 隐蔽 | 数值"证明"没效果，其实改对了 |

下面第 2~5 章逐条对上这 4 类。第 6 章是取证操作手册，第 7 章是本包基线锚点表。

## 一、本包的灯是三层，不是一层 —— 先认清各自管哪个面

这一节是所有调光判断的前提。**弄错层 = 后面全错。**

| 层 | 灯的命名 | 类型 | 位置 | 管哪个面 | 常量前缀 |
|---|---|---|---|---|---|
| **Fill**（补光） | `Fill_<Zone>_NN` | Spot 朝下 150° | 灯管高度 − 1.14m（约 y=2.2） | **地面 + 墙中下段** | `Room/Corridor/Hall + TubeRange/TubeIntensity` |
| **Base**（底光） | `Base_<Zone>_NN` | Point 全向 | 离地 1.5m | **墙面上部**（唯一能照到的层） | `BaseRange*/BaseIntensity*` |
| **Wash**（洗顶） | `Wash_<Zone>_NN` | Spot 朝上 150°（P42 起 Kitchen 为 Point） | 顶板下 0.9m | **天花板** | `WashRange/WashIntensity*` |

> 三层合计 **205 盏**（Fill 86 + Base 36 + Wash 83）。场景总灯数 404 盏，其余是灯具自发光 glow、太阳、场景原有灯。

### 1.1 为什么必须分成三层（不要合并）

- **Fill 是 Spot**：真实荧光灯有灯罩，往上几乎不发光。P36 把初版 Point 改成 Spot 就是为了
  让天花板不在锥内 —— 全向 Point 直射 1.39 倍辐照必然硬削顶（本包无 Tonemapper）。
- **Base 必须是 Point**：它的使命是消除 Spot 锥体在墙上的硬边界。全向光在墙面上只有距离
  衰减、没有锥边。再给 Base 上 Spot 等于把病根复制一层。
- **Wash 单独一层**：天花板离灯管 1~2m，Fill 的 150° 锥够不着（在锥外），必须贴顶单独洗。

### 1.2 每层在几何上「照不到什么」（最关键的一张表）

| 面 | 法线 | Fill | Base | Wash（Spot） |
|---|---|---|---|---|
| 地面 | +Y | ✅ 主供 | ○ 补 | ❌ 朝上，锥外 |
| 墙中下段 | 水平 | ✅ 在锥内 | ○ 补 | ❌ |
| **墙面上部 / 柱身 / 梁侧面** | 水平 | ❌ **锥外**（面在灯上方） | ✅ **唯一光源** | ❌ |
| 天花板 | −Y | ❌ 锥外（P36 特意排除） | ○ 补 | ✅ 主供 |
| 梁底 | −Y | ○ | ○ | ✅ |

> **竖面上段死黑 = 只有 Base 能救**。P42 的正解就是让 Wash 也能照到竖面（改 Point），
> 因为 Base 只有 2 盏、位置还在柱子背后。

## 二、完整乘算链（写常量前必须走一遍）

这是第 3 类翻车的根因。**每一盏灯的最终强度都是 5 个因子连乘**，代码在 `Apply()`：

```
Fill:  intensity = z.BaseIntensity      × ds × factor     × f × dim
Base:  intensity = z.BaseLightLevels[j] × ds × baseFactor × f × dim
Wash:  intensity = z.BaseLightLevels[j] × ds × baseFactor × f × dim
```

| 因子 | 取值 | 说明 |
|---|---|---|
| `ds`（昼夜倍率） | `_dayScale > 0.08 ? _dayScale : 0` | 白天晴天 0.05 → **ds=0，整层 disabled** |
| `factor`（Fill 专用） | `max(LampScale, 走廊?0.22:0)` | LampScale 是**连续**调光值（0.2~1.0 波动） |
| `baseFactor`（Base/Wash 专用） | `LampTarget > 0.5 ? 1 : (走廊?0.22:0)` | **二值**。P37i 裁决：反弹跟"开关"语义，不跟调光 |
| `f` | BaseFade/Eligible 淡入淡出 0~1 | 同层切换时 0.25s 过渡 |
| `dim` | `_nightDimOn ? z.NightDim : 1` | P41c 夜档降档，**只在 Night 档生效** |

### 2.1 `ds` 的实际取值（背下来）

| 时间/天气 | `_dayScale` | 整层是否点亮 |
|---|---|---|
| 白天 Clear | **0.05** | ❌ 低于 EnableGate(0.08) ⇒ **全灭，零成本** |
| 白天 Cloudy | 0.22 | ✅ |
| 白天 Overcast / Fog | 0.44 | ✅ |
| 白天 Snow | 0.46 | ✅ |
| 白天 Rain | **0.50** | ✅（P40 定稿值，已验收） |
| 白天 Storm | 0.58 | ✅ |
| Dusk | 1.00 | ✅ |
| Night | 1.00 | ✅ |

> `_dayScale` 有 **1.8s 平滑**（DayLerpSeconds）。改完档位必须等 ≥2s 再截图，
> 否则拍到中间态（灯半亮、画面偏暗）。

### 2.2 🔴 第 3 类翻车的判断口诀

> **扫参得到的强度值是「生效值」，代码常量的「原始值」。**
> `常量 = 目标生效值 ÷ (ds × dim × factor)`

P42 实例：扫参 0.75 得柱面 0.20，直接写常量 0.75 → 实际生效 0.75 = 常量 × ds(1.0) × dim(0.8)，
即 0.75 是**常量值**、生效只有 0.60，柱面只到 0.151。
正确写法：`0.75 / 0.8 = 0.9375`。

**所以：任何"扫出来的值"落地前，先把 §2 那 5 个因子在目标状态下各是多少写出来。**

### 2.3 `dim` 为什么用 `timeOfDay == Night` 判，不用 `_dayScale` 数值

P40 之后 Dusk 也是 1.0，白天雨天是 0.50。**拿倍率判会把黄昏/雨档一起压暗。**
所以 `_nightDimOn` 单独读 `EnvironmentState.timeOfDay == Night`。

## 三、常量地图：哪些常量被几个分区共用（第 2 类翻车的根因）

### 3.1 分区判据（代码里的分流规则）

```
IsCorridor  = 走廊（按分区名/几何）
area        = 分区包围盒 XZ 面积
bigRoom     = !IsCorridor && area > 200㎡
```

### 3.3 四档精度：从粗到细，按需选

改灯有 4 种粒度，**永远选能满足需求的最细那一档**：

| 档 | 手段 | 影响范围 | 本包实例 |
|---|---|---|---|
| **① 全局常量** | 改 `HallTubeIntensity` 等 | 多分区 | P39f 礼堂降亮（无奈，体育馆连带） |
| **② 白名单 × 倍率** | 分区名数组 + 一个系数，在 `Apply()` 里乘 | 精确到分区，**只改强度** | P41c `NightDimZones={ActZal,Kitchen}` × `NightDimFactor=0.8` |
| **③ 白名单 × 形状** | 分区名数组 + 改灯的类型/参数 | 精确到分区，**不改强度不改盏数** | **P42 `WashOmniZones={Kitchen}`** |
| **④ 单分区字段** | 给 `ZoneFill` 加字段，建灯时赋值 | 最精确 | `NightDim` 字段本身 |

> **判据：老师点名了几个空间，就降几档精度。**
> 点名 1 个 → 用 ③ 或 ④；点名全体 → 才可以用 ①。

### 3.4 白名单模式的标准写法（可复制）

P42 的两种白名单，是后续扩范围的标准模板：

```csharp
// ③ 形状型：名单内改 Spot→Point
private static readonly string[] WashOmniZones = { "Kitchen" };
private const float WashOmniIntensityBig = 0.9375f;

// 在 BuildCeilWash 开头判定
bool washOmni = false;
for (int k = 0; k < WashOmniZones.Length; k++)
{
    if (!string.Equals(z.Zone, WashOmniZones[k], StringComparison.Ordinal)) continue;
    washOmni = true; break;
}
// 建灯与强度分别走两个出口
z.BaseLights[idx] = CreateWashLight(..., zoneWashRange, washOmni);
z.BaseLightLevels[idx++] = washOmni ? WashOmniIntensityBig
                                    : (bigRoom ? WashIntensityBig : WashIntensity);
```

```csharp
// ② 倍率型：名单内整体降档
private static readonly string[] NightDimZones = { "ActZal", "Kitchen" };
private const float NightDimFactor = 0.80f;
// 建分区时：z.NightDim = 在名单内 ? NightDimFactor : 1f;
// Apply() 里：float dim = _nightDimOn ? z.NightDim : 1f;
```

> 用 `StringComparison.Ordinal` 精确比，**不要用 Contains / StartsWith** —— 本包分区名有
> `Class2-1` / `Class2-2` / `ClassDirector` 这类前缀重叠的，模糊匹配必误伤。

## 四、症状 → 该动哪一层（决策树）

按顺序问，问到"是"就停。**不要跳步，跳步就是第 1 类翻车。**

```
症状是什么？
│
├─ 整个空间都暗（连地面都暗）
│   └─ ① 先查 ds 是否=0（白天晴天就是 0，属预期，不是 bug）
│      ② 查同层判定是否命中（见 §6.3）—— 这是最常见的"假故障"
│      ③ 才是 Fill 强度 / range 不够
│
├─ 只有竖面上段黑（墙上部 / 柱身 / 梁侧面）
│   └─ 算 cos(N,L) 与锥角夹角（§5.1）。锥外 ⇒ 只能靠 Base 或把 Wash 改 Point
│
├─ 只有天花板黑
│   └─ Wash 层：查 ceilY 众数投票是否落对（§5.3），查 range 是否够
│
├─ 天花板过曝发白 / 削顶
│   └─ Wash 或 Base 太亮；先看 clip% 与 >0.7 面积（§6.2）
│
├─ 天花板亮但梁/柱成剪影（明暗反差过大）
│   └─ 🔴 这不是"补光不够"，是"补光只补了顶"。
│      判据看梁区 std：>0.14 就已成剪影。正解是让光也到竖面，不是降天花板。
│      （P40 雨档 0.62 首版就栽在这里）
│
├─ 地面有白斑 / 反光刺眼
│   └─ 材质光泽度，走 GlossClamp（§5.4），不是灯的事
│
├─ 一节亮一节黑（斑马线）
│   └─ Wash 步距 WashSpanStep=6 与 range 不匹配；或 ceilY 逐盏不同（应全区统一）
│
└─ 灯数没变但画面亮度跳变
    └─ 逐像素名额分配随相机重排。查 forcePixel 总数 vs pixelLightCount(48)
```

### 4.1 「剪影」与「过暗」是两回事，判据不同

这是 P40 最重要的教训，值得单列：

| 现象 | 判据 | 该做什么 |
|---|---|---|
| 过暗 | 天花板 mean < 目标值 | 提 Wash 强度 |
| 剪影（对比过强） | **梁区 std > 0.14** | **降 Wash 强度**，或让光到竖面 |
| 两者同时 | mean 低但 std 高 | 不能靠提亮解决，必须改配光 |

P40 实测：雨档 0.62 时天花板 mean 0.506（比晴天基线 0.491 还高）、但梁区 std 0.193，
横梁被衬成死黑剪影。**照度达标、明暗结构垮掉。** 降到 0.50 才两者兼顾。

> **口诀：补光不是"越亮越好"，是"越匀越好"。只看 mean 一定翻车。**

## 五、本包的四个已知陷阱（都真实踩过）

### 5.1 锥角剔除：cos(N,L) 高照样照不到

P42 核心教训。柱面点 `cos(N,L)=0.997`（照度条件极好），但**灯→点方向与锥轴夹角
101.5° > 半角 75°**，恒在锥外。

**判据**：`angle = acos(dot(normalize(point - lightPos), lightForward))`
`angle > spotAngle/2` ⇒ 该灯对这点的贡献为 0。

本包 Fill/Wash 都是 150°（半角 75°），所以**面在灯的上方且贴得近 ⇒ 必然在锥外**。

### 5.2 Base 抬高反而更暗

P42 实测：Base 从 1.5m 抬到 2.2/2.8/3.2m，柱面 0.09→0.09→0.08→**0.09**，甚至更低。
原因：离面更远，距离衰减压过了角度改善。**"靠近一点"不总是最优。**

### 5.3 ceilY 众数投票（P39e）

洗顶灯高度取"向上射线命中面的**众数**"，不是最高命中。
- 取最高 → 体育馆 2 个局部高顶(7.75) 把整区抬到 7.75，**10 盏灯穿进主顶板(6.75)里**
  → 150° 锥从板缝漏光 = 椭圆不明光斑。
- 取众数 → 6.75（10/12 票）→ 灯挂 5.85，全部在主顶板下方。

⚠️ **已知缺陷（未修）**：平票裁决时 `ceilY` 初值为 0，`ceilValue < ceilY` 永假，
平票由字典遍历顺序决定。实测 `ActZal`(7/10 票) 与 `Class2-1`(三票各异) 会落兜底
`y = floorY + 3.7`，灯挂在真实顶板上方。**改投票方向会直接改变 ActZal 结果，
属未验证回归，需单独立项逐区验收后再动。**

### 5.4 地板/桌面反光：GlossClamp 必须"只降不升"

P39h 首版用无条件 `SetFloat(0.62)`，把原本 0.40/0.50/0.13 的**低反光面往上抬到 0.62**，
反而加重高光。改成 `Mathf.Min(原值, 目标)` 才对。

P41 又发现更隐蔽的一层：`Zal`/`Floor2`/`Kitchen`/`Corridor` 是 **Combined Mesh**
（一个 renderer 装整间房的地板+墙+梁+天花板），`bounds` 是**房间体积**
（Zal 12.36×5.21×28.28），几何上永远判不成"薄板地面"。
判据必须补 `roomShell = area >= 100 && bounds.size.y <= 6.0`。

材质名比之前**必须先截 `" (Instance)"` 后缀**，否则精确匹配失败。

## 六、取证操作手册（第 4 类翻车的解药）

**读数错了，后面全错。** 这一章每个坑都曾让我得出相反结论。

### 6.1 两种截图口径，不能混用

| 口径 | 方法 | 特点 | 用途 |
|---|---|---|---|
| **同帧同步** | `cam.Render()` + `RenderTexture` + `ReadPixels` | 单帧内完成，无延迟 | **点采样、A/B 对比** |
| **帧末异步** | `ScreenCapture.CaptureScreenshot` | 帧末才渲染写盘 | 存图存档、给主理人看 |

- `cam.Render` **不走 PPv2 后处理链**（Bloom/tonemap 全绕过），**不能用于绝对标定**，
  只能用于相对比较。实测偏差：cam.Render mean 0.448 vs 屏幕 0.535。
- `ScreenCapture` 是**帧末写盘**：同帧内改字段→截图，抓到的是旧画面（两张图 md5 不同
  但像素完全一致）。必须：改值 → `sleep` 等真实帧 → **另起一次调用**截图。

### 6.2 必测的 6 个指标

| 指标 | 算法 | 健康阈值 |
|---|---|---|
| mean | 全幅亮度均值 | 按分区基线（§7） |
| p95 | 95 分位 | 礼堂 < 0.85 |
| clip% | `>= 0.985` 的像素占比 | **< 0.5%** |
| hi7 | `> 0.70` 的面积占比 | 越低越好，礼堂曾 26.4% |
| **梁区 std** | 梁区域亮度标准差 | **≤ 0.14**（超过就是剪影） |
| floor-mid p95 | 地板中段 95 分位 | 反映白斑 |

### 6.3 🔴 同层判定：取证时最容易自造假故障

```csharp
// MarkEligible：以"分区地面"比，窗口 [FloorY-0.5, FloorY+EyeAboveFloorMax(2.6)]
sameFloor = eye.y >= z.FloorY - 0.5f && eye.y <= z.FloorY + 2.6f;
```

而 `eye` 的选择（Poll 里）：

```csharp
// 相机与角色眼高差 > SameStoreyMaxDy(2m) ⇒ 用相机；否则用角色
```

**踩坑实录**：我把取证相机压到 y=1.41（1F），角色留在礼堂 2F（y=3.59），
眼高差 3.78m > 2m ⇒ 判据切到**相机** ⇒ ActZal 全部 `eligCnt=0`，
看起来像"礼堂灯全坏了"。搬相机必须同时看角色在哪层。

| 分区 | FloorY | 所属楼层 |
|---|---|---|
| `Kitchen`（餐厅） | 0 | **1F** |
| `SportHall`（体育馆） | 0 | **1F** |

### 6.4 关相机脚本时别把 Camera 和 PostProcessLayer 一起关掉

```csharp
// ❌ 错：GetComponents<Behaviour>() 会把 Camera 和 PostProcessLayer 也禁掉
foreach (var b in cam.GetComponents<Behaviour>()) b.enabled = false;

// ✅ 对：只关两个跟随脚本
if (tn == "TwinThirdPersonCamera" || tn == "FreeCameraController") b.enabled = false;
```

- 禁掉 `Camera` → `Camera.main` 变 null，截图 NRE。
- 禁掉 `PostProcessLayer` → Night 档 **−1.45 EV 后期曝光完全失效** → 画面偏亮**是假的**。
  我曾因此测出餐厅天花板 0.665 的虚高值。

### 6.5 取证前必须隐藏 UI

根节点名带方括号 `[TwinUI]` / `[TwinHud]`，用 `IndexOf("TwinUI", OrdinalIgnoreCase) >= 0`
匹配。同时把所有 `Canvas.enabled = false`。
否则面板和小地图盖住画面，量化直接失真；半透明告警面板还会每帧刷新，
在差分图里形成横跨全宽的假"差异条带"。

### 6.6 A/B 必须做「同状态噪声底」

**跨机位比数值无意义。** 判"零影响"的正确做法：

1. 同一状态连拍两帧 → 得到噪声底（实测 ScreenCapture 有 6/765 的编码噪声）
2. A/B 差异 vs 噪声底比较
3. 差异 **落在噪声底以内** 才能说"零影响"

P39f 实例：走廊 A/B `max=287/mean=1.92`，噪声底 `max=288/mean=1.94`
⇒ A/B 差异完全在噪声内 = 走廊零影响。

**FPS 同理**：P42 测出 A(Point) 153.06ms / B(Spot) 155.74ms，
但**同状态复测 160.43ms** ⇒ 漂移 7.4ms > A/B 差 2.7ms ⇒ 只能判"无可测差异"，
不许声称提升。任何"A 比 B 快 X%"的结论都必须先做同状态复测。

### 6.7 反射取值的坑（本包特有）

| 要取的东西 | 正确做法 | 坑 |
|---|---|---|
| 运行主体 | `IndoorFillRunner`（`internal sealed`，**全局命名空间**） | `IndoorFillLight` 是 `static class`，`FindObjectOfType` 必 NRE |
| 分区列表 | `GetField("_zones")` → 强转 `System.Collections.IList` | 强转 `IDictionary` 得 count=0（List 不是 IDictionary） |
| 环境状态 | `EnvironmentState.Instance`（**静态字段**，不是属性） | 它的宿主 GameObject 叫 `ThunderSfx`，不是 `EnvironmentState` |
| 改常量是否生效 | 反射读常量，`NF` = 还没编译 | 改脚本后必须 stop→Refresh→确认 console 零 error→re-play |

### 6.8 编译铁律

play 中改脚本**不触发域重载**。必须：

```
stop → AssetDatabase.Refresh(ForceUpdate) → read_console(types=[error]) 零 error
     → 反射确认新常量已进程序集 → re-play
```

反射读到 `NF` / 旧值 = 程序集还是旧的，此时任何测量都是废的。

### 6.9 昼夜/天气切换会互相打断

`EnvironmentState.Set` 是 **2.4s 异步过渡**，连续调 `ApplyHour` 与 `ApplyWeather`
会落在旧目标上（实测：调完读到 Day，5 秒后变回 Night）。

**正确做法：分步调用 + sleep 5~7s + 读回 `timeOfDay`/`weather` 确认 + 再截图。**

## 八、调光工作流（照这个顺序走，能省掉大半返工）

```
1. 复现 ── 用固定机位、固定档位拍一张，记下 6 项指标（§6.2）
2. 分层 ── 逐面采样（地面/墙中/墙上/天花板/柱），判断"哪个面"的问题
3. 归因 ── 该面属于哪一层管（§1.2 表）？若 cos(N,L) 高却照不到 ⇒ 锥角剔除（§5.1）
4. 排伪 ── 明确排除：名额竞争（改 pixelLightCount 试）/ 高度（抬 Base 试）/
           锥角（扩 spotAngle 试）。这三项无效就别再扫
5. 选档 ── 老师点名了几个空间？按 §3.3 选精度档位
6. 扫参 ── 同机位、同帧 cam.Render 做强度阶梯，找出目标档
7. 换算 ── 扫参值 ÷ (ds × dim × factor) = 常量值（§2.2，最容易漏）
8. 编译 ── stop→Refresh→零 error→反射确认常量已生效（§6.8）
9. 复测 ── 同机位 A/B + 同状态噪声底（§6.6）
10. 回归 ── §7 全表逐项核对
11. 交付 ── 交主理人 play；**play 所见是第一验收标准**
```

> 第 11 步是硬规矩：**数值不得推翻视觉结论。** 我曾用错误机位（贴天花板拍 2F 走廊）
> 测出"回归"，主理人 play 图直接证明走廊合格。取证机位必须站在人眼高度
> `floorY + 1.6`，不能贴天花板。
