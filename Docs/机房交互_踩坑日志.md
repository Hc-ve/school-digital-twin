## 为什么要有这份日志

这个模块前后改了 20 多轮，几乎每一轮都是"修好 A、弄坏 B"。根因不是某一行代码写错，而是**三个前提没人写下来**：

1. 场景里没有 `Room_01` 锚点，但白名单里有它
2. 座位屏的贴图指向哪张 RT，决定了它会跟着谁变
3. `PcScreenPlayer` 不是 MonoBehaviour，不 `Tick` 就不出帧

这份日志按"现象 → 根因 → 修法 → 教训"记录，目的是**下次不要再踩**。

## 一、结构性坑（影响面最大）

### 坑 1：`Room_01` 是个幽灵点位

**现象**：点「联动开机」，只有主脑和投影有反应，18 台座位毫无动静。

**排查过程**：
- 以为命令被拒 → Console 里确实没有 `Room_01` 的 `SetPower` 日志
- 以为视觉没建 → 也没有「Room_01 接管了 N 台显示器」这行
- 最后 `grep _twinId` 场景文件：

```
_twinId: ClassComputer/PC/Master_01      × 1
_twinId: ClassComputer/PC/Seat_01..18    × 18
_twinId: ClassComputer/PC/Room_01        × 0     ← 不存在
```

**根因**：`TwinControlScope` 白名单里有 `Room_01`（历史遗留），但拆座位时场景里从没建过这个锚点。所有依赖它的逻辑全部静默失效。

**修法**：
- `TwinPcMenuDriver.SendRoom()`：遍历 18 个 Seat 逐条发命令
- `AnySeatOn()`：判"机房有没有开着的座位"，不再读 `Room_01`
- 视觉：18 个 Seat 各自建材质，不依赖任何聚合点位

**教训**：
> **白名单里有 ≠ 场景里有。** 任何 `Registry.TryGet(id)` 失败都是静默的，必须用"场景里实际存在的锚点"作为唯一依据。

### 坑 2：18 台座位共用一个播放器 → 必然串台

**现象**（反复出现三次，每次都换个形态）：
- 打开 PPT → 18 台也显示幻灯片
- 打开视频 → 18 台也播视频
- 关闭主脑 → 18 台跟着播关机动画
- 全部关机（主脑已关）→ 18 台白屏，播不了关机

**根因**：座位屏的 `_EmissionMap` 指向**主脑播放器的 RT**。主脑一换片，18 台跟着变；主脑一关，18 台没画面。

**为什么一开始要共用**：为了让单台开机也能播开机视频，省一路解码。

**修法**：给机房单独建一个 `PcScreenPlayer`（`RoomScreenPlayer()`），输出自己的 RT，18 台共用这张。

```csharp
_roomPlayer = PcScreenPlayer.Create(
    "RoomScreen", _roomVideo, uvMin, uvMax, mat, _screenEmission, transform,
    _roomVideoAtlasSize, _screenVideoInset, 0f, _roomVolume, null);
```

成本：**1 个 `VideoPlayer` + 1 张 RT**（不是 18 个）。

**教训**：
> **共享资源 = 共享状态。** 只要两个逻辑角色共用一张 RT，就一定会互相污染。宁可多一路解码，也不要让两个角色共享画面来源。

### 坑 3：`PcScreenPlayer` 不 Tick 就不出帧

**现象**：18 台在联动开机/全部关机时**完全没有动画**，画面直接跳变（黑→桌面、桌面→黑）。

**排查过程**：
- 以为视频没加载 → 主脑同一个文件能播
- 以为 RT 是黑的 → 日志显示贴图名是 `TwinScreenRT_RoomScreen`，RT 存在
- 最后看 `TickScreenVideos()`：

```csharp
foreach (var kv in _screens)     kv.Value.Player?.Tick();
foreach (var kv in _projectors)  kv.Value.Player?.Tick();
// _roomPlayer 是独立字段，从来没进过这两个集合
```

**根因**：`PcScreenPlayer` 不是 `MonoBehaviour`，它靠外部每帧调 `Tick()` 才能 `Graphics.Blit(_videoRT, ScreenRT)`。机房播放器**一次都没被驱动过**，RT 永远停在最后一次写入的那一帧。

**修法**：一行

```csharp
if (_roomPlayer != null) _roomPlayer.Tick();
```

**教训**：
> **自绘组件必须有明确的驱动源。** 新增一个 `PcScreenPlayer` 时，第一件事是问"谁调它的 `Tick`"，而不是"它的材质指向对不对"。

## 二、视觉状态坑

### 坑 4：`Master_01` 收 19 台 → 「开机」变成「全部开机」

**现象**：点「开机」（应只开主脑），19 台全亮；点「关闭主脑」（应只关主脑+投影），19 台全灭。

**根因**：为了让动画和 PPT 回来，我把 `Master_01` 的 `BuildScreen` 恢复成收集 19 台。它的 `ScreenVisual` 就变成了"整间总闸"，和菜单语义完全对不上。

**修法**：按点位角色划分收集范围

```csharp
// 主脑（非房间点位）→ 跳过座位屏，只留自己那台
// 机房（房间点位）  → 收下 18 个座位屏
if (!isRoom && HasSeatAnchor(r)) continue;
```

**教训**：
> **视觉归属必须和业务语义一致。** 一个点位管几块屏，直接决定它的开关等于什么操作。这个映射关系要写进文档，不能靠"当时是这么写的"。

---

### 坑 5：`Detach` 之后忘了 `Restore`

**现象**：关闭主脑 → 再点全部关机 → 18 台停在桌面图几秒，然后直接黑，没有关机动画。

**根因**：关闭主脑时 `DetachSeatScreens()` 把座位切成静态快照，但全部关机时**没有接回去**，座位还在用快照，主脑播关机视频它们毫无反应。

**修法**：

```csharp
if (!includeRoom) DetachSeatScreens();    // 只关主脑 → 摘下来
else              RestoreSeatScreens();   // 全部关机 → 接回去
```

**教训**：
> **`Detach` / `Restore` 必须成对出现。** 新增任何入口都要问：这一步之后，座位该"跟着 RT"还是"定格"？选错就是新一轮 bug。

---

### 坑 6：`RestoreSeatScreens` 里的 `master.IsOn` 条件

**现象**：先关闭主脑，再全部关机，18 台白屏（不是播关机动画）。

**根因**：

```csharp
if (master.IsOn && ...) shared = master.Player.ScreenRT;
```

主脑已经关了，`master.IsOn == false` → `shared` 为 null → 退回白色遮罩。

**修法**：判据改成"RT 还在不在"，不是"主脑开不开"。后来机房播放器独立之后，这里直接读 `_roomPlayer.ScreenRT`，彻底解耦。

**教训**：
> **判据要选"物理存在"而不是"业务状态"。** RT 存在与否是事实，主脑开关是状态——用状态去判断资源可用性，迟早错。

---

### 坑 7：`PlayFile` 在 `_on == false` 时不播

**现象**：关闭主脑后点全部关机，主脑和投影**又被点亮**播了一遍关机动画。

**根因**：我为了修"播不出来"加了无条件 `SetOn(true)`，结果把已经关掉的设备重新点亮。

**修法**：

```csharp
if (mp != null && mp.IsOn) mp.PlayFile(_shutdownVideo);   // 开着的才播
if (pp != null && pp.IsOn) pp.PlayFile(_shutdownVideo);
// 机房播放器不判 IsOn：它是"视频源"不是"某块屏"
```

**教训**：
> **"视频源"和"屏幕"是两个概念。** 播放器有 `_on` 状态是为了防止"关屏时换片把屏幕点亮"，但一个不挂 Renderer 的播放器不该受这个限制。

---

### 坑 8：18 台各调一次 `PlayFile` → 互相打断

**现象**：联动开机时 18 台完全没有开机动画。

**根因**：`ApplyScreen` 的 Seat 分支无条件 `PlayFile(_roomVideo)`。18 个 Seat 依次进来，等于把同一段视频 `Stop → Prepare` 了 18 遍，每一遍都打断上一遍，**视频永远播不到第二帧**。

**修法**：批量窗口内只有第一个座位起播

```csharp
if (bulk) {
    if (!_bulkBootStarted) { _bulkBootStarted = true; roomPlayer.PlayFile(_roomVideo); }
} else {
    DetachSeatScreens(v.TwinId);
    roomPlayer.PlayFile(_roomVideo);
}
```

**教训**：
> **共享播放器只能有一个起播者。** 多台共用一张 RT 时，"谁负责起播"必须显式指定，不能每台都调一次。

---

### 坑 9：单台关机时其他座位跟着播

**现象**：点一台关机，其他 17 台也播关机视频。

**根因**：18 台共用一张 RT，机房播放器换片，所有接 RT 的座位都跟着变。

**修法**：`DetachSeatScreens(exceptTwinId)` —— 关机前把其他开着的座位摘成快照，只留目标台接 RT。

**教训**：
> **单台操作必须先隔离其他台。** 只要共用资源，任何"只影响一台"的操作都要显式排除别人。

---

### 坑 10：`MergeUnits` 把座位材质合并掉

**现象**（早期）：点一台亮全部。

**根因**：`Master_01` 开机动画播完后调 `MergeUnits`，把 19 台的 `sharedMaterial` 统一成一份共享材质。座位手里的独立材质引用失效。

**修法**：

```csharp
// MergeUnits 跳过座位屏
if (HasSeatAnchor(v.Renderers[i])) continue;
```

**教训**：
> **性能优化（合批）会破坏"单台可控"。** 两者不可兼得时，先问"演示时需不需要单台控制"，需要就别合并。

---

### 坑 11：`GetComponentInChildren` 拿错 Renderer

**现象**（早期）：18 个 Seat 里有一半绑到了同一块显示器，点哪台都改同一个。

**根因**：`TwinAnchor` 挂在显示器的根节点，`Renderer` 在子节点，`GetComponent<Renderer>()` 返回 null，退回 `GetComponentInChildren` 时拿到的不是"自己那台"。

**修法**：改成**按位置找最近的显示器**，并且先用快照固定候选列表（避免材质改名后找不到）。

**教训**：
> **层级不确定时，位置比组件查找可靠。** 而且任何"按名字/材质名筛"的逻辑，都要假设"这个名字会被别人改掉"。

## 三、数据层坑

### 坑 12：PC 台数读类型默认值，不读点位配置

**现象**：单台电脑详情页显示 `1800W / 开机 10 台`。

**根因**：`PcUnitCount` 读的是 `TwinDeviceModel` 的类型定义（PC 一律 3000W），不看 catalog 里这个点位自己的量程（300W）。

**修法**：优先读 catalog 的点位量程，取不到才退回 model 默认值。

**教训**：
> **数据生成本来就该以"这个点位的真实配置"为准，类型定义只是兜底。**

---

### 坑 13：座位没有初始状态 → 功率在 0~300W 之间乱摆

**现象**：面板显示"已开"，实际是关机；点开机命令 `Failed（设备状态与期望不一致）`。

**根因**：`SeedInitialState` 只遍历 `TwinControlScope.Ids`（硬编码表），18 个 Seat 是批量生成的，不在表里 → 从来没被压过初始状态 → 走正弦波。

**修法**：`SeedInitialState` 末尾补一轮 `SeedSeatAnchors()`，按前缀扫场景锚点。

**教训**：
> **批量生成的设备必须显式加入初始化流程。** 任何"遍历白名单"的逻辑，都会漏掉动态创建的点位。

---

### 坑 14：CO₂ 22 ppm 物理上不可能

**现象**：详情页显示 CO₂ 浓度 22.05 ppm。

**根因**：量程配置错了。大气本底就是 400+ ppm，22 ppm 是纯氮环境才有的读数。

**修法**：量程改 `400~2000 ppm`，基线按"有人 800 / 无人 500"，告警阈值 1500。

**教训**：
> **模拟数据必须过一遍物理常识。** 答辩时评委一句"22 ppm 是怎么测出来的"就能问住。

## 四、协程 / 生命周期坑

### 坑 15：`Time.deltaTime` 累加做超时 → 退出 Play 卡死 1 分 39 秒

**现象**：退出 Play 卡在 `Application.Shutdown.CleanupEngine`，持续 1:39。

**根因**：

```csharp
float t = 0f;
while (t < _shutdownTimeout)   // 8 秒
{
    t += Time.unscaledDeltaTime;   // ← 退出时恒为 0
    yield return null;
}
```

退出 Play 时 `unscaledDeltaTime` 变 0，`t` 永远不增长 → 死循环 → Unity 等它收尾。

**修法**：
1. 改用 `Time.realtimeSinceStartup` 差值
2. 每帧检查 `Application.isPlaying`，退出立即 `yield break`
3. `OnDisable` 里 `StopAllCoroutines()` 兜底

**教训**：
> **协程里的超时永远用绝对时间，不要累加 delta。** 并且必须有"外部强制终止"的兜底。

---

### 坑 16：`ShowStill` 之后 `Tick` 会盖掉画面

**现象**（早期）：退出 PPT 后又播了一遍开机视频。

**根因**：`ShowStill` 把桌面图合成进 RT，但 `Tick` 每帧无条件 `Blit(_videoRT, ScreenRT)`，把桌面图盖掉了。

**修法**：`Tick` 开头 `if (_showingStill) return;`

**教训**：
> **"当前显示什么"要有唯一权威。** 两个写入源（视频帧 / 静态图）必须有优先级标记。

## 四·五、2026-11-05 第四轮复发（坑 17～21）

> 这一轮跨了 P26 / P29 / P30 三个批次，改的都是**真缺陷**，但**没有一个是根因**。
> 主理人的原话是：「这个 bug 都出现好几次了，之前都修复了，怎么回事。」

### 坑 17：一行名字错的日志，把整轮排查带错方向

**现象**：`grep -c "屏幕视频就绪"` 每次 Play 都有 4 条，我据此断定「前 9 次 Play 都正常，
第 10 次起才坏」，于是全力去查「为什么第 10 次会坏」。

**根因**：那行日志打印在 `p._player.Prepare()` **之后紧接着的同一帧**，
此时一个解码帧都还没产出。它只能证明「发出了准备请求」，
**不能证明「准备好了」**。真正的就绪只可能在 `OnPreparedPlay` 回调里。

**代价**：按一条假日志统计了 16 次 Play，得出完全错误的结论，
并据此修了「播放器泄漏」——改完症状一模一样。

**修法**：改名为 `已请求准备（不是就绪）`，并固化成判据 `P30-01/02`
（`grep0:屏幕视频就绪` + `grep:已请求准备（不是就绪）`）。

**同族第二例（更隐蔽）**：`OnPreparedPlay` 里打印 `frame=` 时，
代码是在 `vp.Play()` **之后立刻**读的，当帧解码还没产出，
所以永远打 `frame=-1`。**字段没错，读的时机错了。**
这一条差点又让我去查「播放启动失败」。

**教训**：
> **日志本身也是被测对象。** 打日志的位置和时机错了，
> 它给出的不是"没用的信息"，而是"错误的信息"——后者更贵。
>
> 判据：**一条日志如果"永远成立"或"永远是同一个值"，它大概率没有信息量。**

### 坑 18：把「看起来像规律」当成了规律

**现象**：两次会话里，`prepareCompleted` 都在某个时刻起永久不触发。
我找到一个"临界值"：

| 会话 | 失效发生在 | 当时累计 Prepare |
|---|---|---|
| 上一次 | Play#3 | 206 次 |
| 本次 | Play#10 | 289 次 |

我据此断定「累计 200~300 次后原生解码器耗尽」。

**这个推理的漏洞**：两个样本、**两个不同的临界点**，恰恰说明它不是一个阈值。
真正的阈值现象应该有一个可复现的固定值。**"量级一致"是我在只有两个数据点时给自己找的说辞。**

**直接反证**（重启 Unity 后）：
```
重启前 Play#18：Prepare=4  建=4  销毁=0 存活=4（全是全新实例）  → 全黑
重启后本次 Play：Prepare=47 建=13 销毁=12 存活=1              → 全正常
```
**故障现场只有 4 次 Prepare 就已经全黑；重启后跑 47 次反而正常。**
「累计耗尽」与这两组数据都不相容。

**教训**：
> **只有两个数据点时，不要得出"规律"，只能得出"待验证的猜疑"。**
> 尤其当两个点还不一致时——不一致本身就是"这不是规律"的证据。

### 坑 19：连续三轮都在"故障现场"里找原因，从没换过环境

| 轮次 | 我断言的根因 | 是真缺陷吗 | 是根因吗 |
|---|---|---|---|

三轮的共同错误模式：**在日志里找到一个"恰好指向资源耗尽"的计数，就停下来不再验证。**

**真正的转折点是主理人一句随口的话**：「我刚刚好像重启了 Unity」。

**教训**（本轮最贵的一条）：
> **当现象"诡异、稳定、位置恒定"且修复无效时，先换环境（重启 / 换机器 / 打包），再换代码。**
>
> "重启一下会怎样？"这个问题零成本、五分钟能验证，我却绕了两小时。
> **这不是找不到答案，是没有问对问题。**

### 坑 20：`errorReceived` 全程 0 条 —— 一个"沉默的失败"

**现象**：解码失败时，`VideoPlayer` **既不回调 `prepareCompleted`、也不报 `errorReceived`**。
日志里 `视频解码错误` 一条都没有，`prep=Pending` 永久挂着。

**为什么这条要单独记**：它意味着「素材坏了 / 路径不可读 / 解码器挂死」
三种完全不同的原因，在现场表现**一模一样** —— 这才是这个 bug 查了这么久的真正原因。

P26 补上 `errorReceived` 订阅是**完全正确**的（判据 `P26-07`），
但要接受一个事实：**它救不了"原生会话挂死"这一类失败，因为挂死不等于出错。**

**判据**：
> `prep=Pending` + `errorReceived` 0 条 + `frame=-1` 长期不变
> = 解码器"既不回成功也不报失败"
> → **大概率是原生层问题，去查环境，不要在 C# 里找**。

### 坑 21：把 `MaxRebuilds` 当成救命手段

**现象**：P30 加了 `RebuildPlayer()`（换一个全新的 `VideoPlayer` 组件实例），
逻辑上无可指摘 —— `DestroyImmediate` 旧组件、重建 `AudioSource`、复用原 RT。

**实际效果**：日志里重建**确实被触发了**（`换了一个新的 VideoPlayer 实例（第 1/2 次重建）`），
**但症状一模一样。** 因为病灶不在「这个 `VideoPlayer` 组件坏了」，
而在「这个进程的原生解码器坏了」—— 换组件换不掉进程。

**结论**：这段代码**留着当兜底**（判据 `P30-03~06` 保留），
但**不要再指望它救命**。真正的救命手段是重启编辑器。

**教训**：
> **"换一个更干净的实例"只能解决"实例被污染"，不能解决"宿主出问题"。**
> 加自救机制之前先问：坏的东西在哪一层？我这一层够得着吗？

| 顺序 | 事项 | 原因 |
|---|---|---|
| 1 | 先 grep 场景，确认哪些锚点真实存在 | 坑 1 浪费了 3 轮 |
| 2 | 画一张"资源归属表"：哪块屏归谁、谁驱动 | 坑 2/3/4 都是归属不清 |
| 3 | 明确 `Detach`/`Restore` 配对规则 | 坑 5/6 都是漏了反向操作 |
| 4 | 所有共享资源，先定"谁起播、谁合并" | 坑 8/9/10 |
| 5 | 协程超时统一用 `realtimeSinceStartup` | 坑 15 |
| 6 | 数据先过一遍物理常识 | 坑 14 |
| 7 | **先验证日志本身说的是不是真的** | 坑 17：假日志带偏整轮 |
| 8 | **修复无效时，先换环境再换代码** | 坑 19：重启五分钟能解决的事绕了两小时 |

**最核心的两条**：

> **① 每修一个现象，先问"这是状态没恢复，还是资源没驱动"。**
> 前者补反向操作，后者补 Tick / 补引用。
> 两类问题的修法完全不同，混在一起改就会越改越乱。

> **② 同一个 bug 修三次还没好，就不是代码的问题了 —— 是"你在哪一层找"的问题。**
> P26/P29/P30 三次修的都是真缺陷，三次都没修好这个 bug。
> 因为它在第四层：**编辑器进程**。
>
> 换层的成本远低于在同一层继续挖。**先问"最便宜的证伪实验是什么"，再动手。**
