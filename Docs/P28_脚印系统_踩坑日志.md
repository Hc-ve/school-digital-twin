## 零、一句话

> **"走远看不见脚印"不是容量不够，是容量和寿命两个参数自相矛盾 —— 我一开始只改了容量，症状只好了三分之一。**

---

## 一、现象（主理人原话）

> 「走远往回看，脚印还会消失，走进又出现了。」

拆成三段：

| 阶段 | 现象 | 主理人感受 |
|---|---|---|
| 刚踩几步 | 有印子 | 正常 |
| 走远（>10m）回头看 | **印子没了** | "雪把印子填平了？" |
| 再走回去 | **印子又出现了** | "这就很假了" |

第三段是整个 bug 的钥匙：**如果印子真的被"填平"了，走回去不该再出现。**
能看到 → 数据还在 → 只是**渲染时被剔除了**。

---

## 二、第一个错误：只改了容量，没查寿命

`PrintMax = 32`，`PrintStride = 0.36m`：

```
32 槽 × 0.36m = 11.52m
按 2.2m/s 步行速度 → 5.2 秒就走满一圈
```

**环形缓冲（`printWrite = (printWrite + 1) % PrintMax`）会把最早的印子覆盖掉。**
所以走 5 秒以上，身后超过 11.5m 的印子就被新印子挤掉了。

看起来根因就是"容量太小"，于是我：

- `PrintMax` 32 → **128**（足迹带 11.5m → **46.1m**）
- 走满需要 20.9 秒，够"走一段回头看"了

**改完只好了三分之一。** 因为还有第二个矛盾：

```
PrintLifeSec = 240f    ← 寿命 4 分钟
```

**32 槽配 240 秒寿命，两个数根本不在一个量级。**
容量决定了"最多记住 5.2 秒"，寿命写 240 秒毫无意义 ——
**它永远轮不到生效。** 这是个"看起来配置得很完整、实际上半条腿是假肢"的参数组合。

**修法**：`PrintLifeSec` 240 → **90**。

现组合：128 槽 × 0.36m = **46.08m**，走满需 20.9 秒；
90 秒寿命中前 63 秒不衰减，最后 27 秒淡出。

## 三、第二个错误：容量加大 4 倍，却没想到性能

`PRINT_MAX` 从 32 提到 128，意味着 **shader 里每个像素多循环 96 次**：

```hlsl
for (int i = 0; i < PRINT_MAX; i++) { ... FootprintAt ... }
```

雪盘是铺满屏幕的地面，这个循环是**逐像素**的。
4 倍开销在这个规模上足以掉帧。

**修法**：加**整片包围盒剔除** —— C# 侧维护一个 `_PrintBounds`（所有脚印的 xz 包围盒），
shader 先判当前像素在不在盒内，不在就直接 `return 0`：

```hlsl
// SnowGround.shader
if (_PrintBounds.x > _PrintBounds.z || _PrintBounds.y > _PrintBounds.w) return 0.0;
float2 bMin = _PrintBounds.xy - _PrintRadius;
float2 bMax = _PrintBounds.zw + _PrintRadius;
```

**效果**：绝大多数像素（远离足迹的地面）走一次比较就退出，实测无可感知帧率下降。

---

## 四、第三个错误：包围盒的两个"退化"陷阱

加剔除之后立刻踩了两个新坑，都是**包围盒在边界情况下退化**：

### 陷阱 1：`min == max` 被当成空盒

单个脚印时，`min == max`（包围盒退化成一个点）。如果判空写成 `<=` 或 `>=`，
**第一个印子会被当成空盒剔掉** —— 走一步不出现，走两步才出现。

**修法**：空盒判据只能判 `min > max`。固化成判据 `P28-06`（`grep0: _PrintBounds.x == _PrintBounds.z`）。

### 陷阱 2：落印后忘了重算包围盒

`EmitPrint` 写入新槽后，如果没调用 `UpdatePrintBounds()`，
**新脚印落在旧包围盒外面 → 被自己刚加的剔除逻辑剔掉 → 走一步不出现。**

这个坑很阴：**剔除逻辑（修性能的）反过来把功能（修可见性的）弄坏了。**
两个改动单独看都正确，组合起来出错。

**修法**：`EmitPrint` 落印后必须 `UpdatePrintBounds()`。判据 `P28-07`。

## 五、第四个错误：`ResetPrints` 只把计数置 0

```csharp
// 错误写法
private void ResetPrints() { printUsed = 0; printWrite = 0; }
```

**只把 `_PrintCount` 置 0，`prints[]` 数组里的旧坐标还在。**
下一次 `EmitPrint` 把 `_PrintCount` 推回 1 时，**那些 w=1 的旧槽全体复活** ——
走一步，地上突然出现一片历史足迹。

**修法**：真清空数组。

```csharp
prints[i] = Vector4.zero;
```

固化成判据 `P28-08`。这个坑在"换场景 / 重新开雪 / 材质重建"三种情况下都会触发。

## 六、一个设计层面的前提（最容易被忘）

> **脚印必须锚在世界坐标，不能锚在雪盘的本地 UV。**

雪盘是**跟着相机跑**的（每帧 `position = 相机 xz`），顶点还会逐帧按地形重铺。
如果在盘的本地 UV 上画，盘一移动脚印就跟着跑 —— **看起来像脚印黏着角色滑**。

这正是水坑那一轮踩过的坑，所以：

- 脚印存的是**世界 xz**（`prints[i].xy`）
- shader 里拿 `i.worldPos.xz` 去比对
- 盘怎么动都不影响印子位置

**判据**：`P28-04` 禁止为修"走远看不见"而搬动历史脚印
（`grep0: ShiftPrints(`）。搬了反而让脚印黏着角色滑。

## 九、运行时诊断（留在代码里，下次复发直接用）

`UpdateFootprints` 里有 3 次诊断日志（`printDiagCount` 限制最多 3 条），
输出这个格式：

```
[P28][脚印诊断 #2/3]
    snowAmount   = 0.000   （< 0.15 → depth 归零，一整段都不留印）
    depth        = 0.000   ← **闸门①未过：雪量太小**
    snowGroundMat= ok
    playerRoot   = TwinPlayer   pos=(-16.00, 3.59, 31.00)
    grounded     = True   cc=有
    printUsed    = 0/128   hasLast=False   已推材质 _PrintCount=0
    足迹带       = 46.1m（128 槽 × 0.36m）  寿命 90s
```

**读法：两个闸门按顺序过，第一个不过就不用看第二个**

| 闸门 | 条件 | 诊断行会直接告诉你 |
|---|---|---|
| ① 雪量 | `snowAmount ≥ 0.15` | `depth = 0.000 ← 闸门①未过：雪量太小` |
| ② 移动 | 相对上一次落印位移 ≥ `PrintStride`(0.36m) | `hasLast=False` 表示刚起步，本帧只记录不落印 |

**排查顺序**：先看 `snowAmount`（天气没切到雪天 → 必然 0），再看 `grounded`（角色没踩地）。

## 十、这一轮的教训

> **一个参数错了，往往不是它一个参数的问题 —— 是它和配对的参数不在同一个量级。**

`PrintMax = 32` 和 `PrintLife = 240` 各自看都不算错，
但放在一起，**寿命那一条是死代码**（永远轮不到）。

> **加优化（剔除）和新功能（更大容量）时，必须验证"优化会不会把功能剔掉"。**

第 4 个坑就是：包围盒剔除剔掉了刚落的印子。
**两个改动单独正确、组合起来错误** —— 和项目里 `SnowOnTrees`（世界坐标 + 跟随相机的父节点 = 平移两次）是同一类。

> **"只清计数不清数组"是经典的幽灵数据来源。**

凡是"环形缓冲 + 写入计数"的结构，重置时必须两个都清。
判据写法：`grep` 到 `ResetPrints` 里必须有对数组元素的赋值，不能只有 `count = 0`。
