## 2. 方案：三件事，缺一不可

| 层 | 问题（阶段 1 结论） | 本轮的解法 | 对应调研条目 |
|---|---|---|---|
| **管体自身** | 只刷 `_EmissionColor`、无 `_EmissionMap` → 整个灯具（含金属端盖）一起发光 = 糊成一块白。旧「0.6 上限」是从这个错误现象反推出来的伪结论 | 运行时以**本盏原材质为底克隆**，只把 `LightLum01On.mat` 的 `_EmissionMap` 与发光色换过去；色取 4500K 冷白 `(1.45,1.55,1.70)` | 调研 1、2、5、7 |

## 3. 「全楼一次生效」是怎么做到的

这不是靠遍历所有灯去改，而是靠**共用同一个资产引用**：

```
LightLum01.mat  guid = 7b70a1dea2a93b54981a71456f01bd63
  ├── LightLum01_01.prefab → 7b70a1de…（同一份）
  └── LightLum01_03.prefab → 7b70a1de…（同一份）
```

场景里 105 个灯具实例全部指向这一个 guid（实测 Day 场景里该 guid 只出现 1 次，作为材质资产本身；所有实例经 prefab 继承）。

**但关态材质不能直接改**（那是共享资产，改了会污染全项目且落盘）。所以每个 Renderer 在 `BuildLamp` 时各自 `r.material` 克隆一份关态，再克隆一份开态：

```csharp
onMat = new Material(m);                                   // 以原材质为底
onMat.SetTexture(EmissionMapId, onTemplate.GetTexture(EmissionMapId));  // 只换发光遮罩
onMat.SetColor(EmissionId, _lampEmission);                 // 冷白 HDR
```

开关时切换 `renderer.sharedMaterial`。**一次配置、逐盏独立、零资产写入**。

### 为什么是「以原材质为底」而不是「直接克隆 On 模板」

两份材质的 shader 变体不同（实测）：

| | `LightLum01.mat`（关） | `LightLum01On.mat`（开） |
|---|---|---|
| `m_Shader` | `fileID: 45`（Standard **Specular**） | `fileID: 46`（Standard） |
| 关键词 | `_EMISSION` `_NORMALMAP` `_SPECGLOSSMAP` | `_EMISSION` `_NORMALMAP` |
| `m_LightmapFlags` | 1（RealtimeEmissive） | 2（BakedEmissive） |

直接克隆 On 模板 ⇒ 开灯瞬间悄悄换掉光泽模型与高光表现，关灯一对比就能看出「灯管材质变了」。
所以只借它的发光口径，外观其余部分在开关两态之间保持一致。

## 4. Bloom 数值的推导（可复核）

来源全部是包内源码实测，不是经验值：

```csharp
// Bloom.cs:171  —— 阈值转线性
float lthresh = Mathf.GammaToLinearSpace(settings.threshold.value);
// Bloom.cs:212  —— 强度是 Exp2 标度
float intensity = RuntimeUtilities.Exp2(settings.intensity.value / 10f) - 1f;
```

着色器合成（`Uber.shader:163-165`）是**加法**：
```hlsl
bloom *= _Bloom_Settings.y;              // y = intensity（已 Exp2 换算）
color += bloom * half4(_Bloom_Color, 1.0);
```

所以 `intensity` 参数到"实际叠加倍率"的换算：

| `intensity` 参数 | 实际倍率 `2^(v/10)−1` | 观感 |
|---|---|---|
| 0.55（旧值） | **0.0389** | 肉眼不可见 ← 上一轮"调了没反应" |
| **1.30（当前·黄昏档）** | **0.0943** | 轻微柔晕 |
| 3.00 | 0.2311 | 接近目标 |
| **3.20（当前·夜晚档）** | **0.2483** | 对应参考图贴管处的柔晕 |
| 6.00（**v1，已废弃**） | 0.5157 | **过曝** ← 本轮事故值 |
| 8.00 | 0.7411 | 偏浓 |

阈值取 **0.90（Gamma）→ 线性 0.7874**：
- 灯管 emission 1.45~1.70 → 线性 ≈1.5，稳过阈值 ✓
- 走廊墙面显示 0.765 → 线性 0.5462，低于阈值 ✓
- 天花板暗区 0.1~0.4 线性 → 远不过 ✓

⚠️ **但光看 `threshold` 不够 —— PPv2 的 `softKnee` 会把它向前延伸**，
真正决定谁进 Bloom 的是 `lthresh - knee`。这一层是 v2 复盘时才发现的，
详见 §4.2，最终取 `softKnee = 0.30`（有效起点 0.5512，墙面被彻底踢出）。

扩散 `diffusion = 8`：参与迭代层数 `log2(max(w,h)) + diffusion − 10`，1080p 下 ≈8 层，对应参考图判读的 3~5 倍管宽柔晕带。

**《异环》参考图量化锚点**（阶段 0 逐像素实测）与目标对照：

| 指标 | 参考图 | 本轮目标 |
|---|---|---|
| 管体屏幕亮度 | p50 0.768 / p90 0.998 | emission 1.45~1.70 → 显示 1.0（本工程无 tonemapper，必然纯白，与参考图 p90 0.998 一致） |
| 光晕带（3~5 倍管宽） | 0.39~0.54 | Bloom 0.248 倍叠加（贴管处） |

## 4.1 v1 过曝事故复盘（2026-11-13 主理人 play 后回调）

这是本轮最重要的一次修正，必须完整留档。

### 现象（主理人原话）

> 「下午两点的走廊电棒」「下午5点后的走廊电棒？？？」「2-1班教室过曝了」「礼堂的灯光 一边过曝一边昏暗」

附 5 张截图 + Console 日志：

```
[TwinLampBloom] 已绑定 1 份 profile（场景内 Volume 共 2 个，含 Bloom 的 2 个）。
[TwinLampBloom] Bloom 已开启：夜晚 档，intensity=6.00（实际倍率 0.516），threshold=0.72 …
[TwinLampBloom] Bloom 已开启：黄昏 档，intensity=3.00（实际倍率 0.231），threshold=0.72 …
```

逐像素实测：教室 2-1 **62.5% 像素 >0.95**（p50 = 1.000）整室炸白；走廊 17:01 天花板与墙面被冲成一片平坦灰白（RGB 0.765/0.764/0.753，亮度恒定 0.765、无任何细节）。

### 定量根因（v2 复盘时重算，比 v1 当时的说法更准确）

v1 当时的推断是「墙面过了阈值 → 被叠一层自己 → 削顶」。**重算后发现这个链条只在方向上对，数量上撑不住**，必须纠正：

按 `Colors.hlsl:242-255` 的 `QuadraticThreshold` 精确计算（脚本 `Docs\QA\evidence\P36_backup\calc_bloom_threshold.py`）：

| v1（threshold 0.72 / softKnee 0.5 / intensity 6.0） | 线性亮度 | 进入 bloom 比例 | 叠加到画面 |
|---|---|---|---|
| 走廊墙面 | 0.5462 | 18.17% | **+0.0512** |
| 天花板暗区 | 0.0355 | 0.00% | 0 |
| 灯管管壁 | 1.70 | 71.94% | **+0.6307** |

墙面被叠加 0.0512 后，显示亮度从 0.765 → **0.798**，**只涨 4%，根本到不了削顶**。

所以「走廊一片平坦灰白」的真正机制是**两个因素叠加**：

1. **墙面的自污染（次要）**：墙面被吸入 18.17%，自己给自己加了一层雾，把墙面的细微脏污、接缝、纹理差异全部抹平 —— 这是「平坦」二字的来源，但它只值 4% 的亮度。
2. **多灯空间叠加（主要）**：走廊有连续多盏灯，每盏的 Bloom 都是全屏采样后模糊扩散的。**一盏灯的 0.63 倍光晕会盖到它前后各 3~5 米**，多盏叠加到墙面处的总能量远超单盏的 0.05。教室灯更密（2-1 班有 4 排 × 多列），叠加层数是走廊的几倍 —— 这才是「教室 p50 = 1.000 整室纯白」的量级来源。

**并且 Bloom 在 ColorGrading 之前执行**（`PostProcessLayer.cs:1262-1267`），采样的是**尚未被 `postExposure` 压暗**的 HDR 缓冲。所以 v1 里"想着夜晚档画面暗、墙面不会发光"的推断是**错的**：阈值必须自己把墙面挡在外面，与昼夜档无关。

### 修法（三处，均已落地）

| 参数 | v1 | v2（当前） | 理由 |
|---|---|---|---|
| `BloomThreshold` | 0.72（线性 0.4770） | **0.90（线性 0.7874）** | 墙面线性 0.5462 < 0.7874 |
| 夜晚 `intensity` | 6.0（0.5157 倍） | **3.2（0.2483 倍）** | 单盏光晕能量减半，多灯叠加的总量随之锐减 |
| 黄昏 `intensity` | 3.0（0.2311 倍） | **1.3（0.0943 倍）** | 黄昏环境光更强、墙面本就更亮，比夜晚更易爆 |
| `softKnee` | 0.5（PPv2 默认） | **0.30** | **见下方 §4.2 —— 这是唯一能把墙面彻底踢出 Bloom 的参数** |

> **为何黄昏不能沿用 3.0**：黄昏档墙面本身被天光推得比夜晚亮，距离阈值更近。同一倍率在黄昏造成的视觉爆炸远大于夜晚。所以 v2 把黄昏/夜晚拆成两个常量（`DuskIntensity` / `NightIntensity`），而不是"黄昏取夜晚一半"的等比关系。

## 4.2 v2 复盘新发现：`softKnee` 才是墙面的真正后门

这是本轮第二个必须留档的技术要点，v1 完全没考虑到。

### 机制（源码级）

```csharp
// Bloom.cs:171-173
float lthresh = Mathf.GammaToLinearSpace(settings.threshold.value);
float knee    = lthresh * settings.softKnee.value + 1e-5f;
var threshold = new Vector4(lthresh, lthresh - knee, knee * 2f, 0.25f / knee);
```

```hlsl
// Colors.hlsl:242-255
half br = Max3(color.rgb);
half rq = clamp(br - curve.x, 0.0, curve.y);   // curve.x = lthresh - knee
rq = curve.z * rq * rq;
color *= max(rq, br - threshold) / max(br, EPSILON);
```

**关键：`curve.x = lthresh - knee`，所以真正开始有贡献的亮度是 `lthresh - knee`，不是 `lthresh`。**

即：`softKnee` 把阈值**向前延伸了 `lthresh × softKnee`**。

对照 threshold = 0.90（lthresh 0.7874）：

| softKnee | 有效起点（线性） | 走廊墙面 0.5462 | 教室墙面 ≈0.75 | 灯管 1.70 |
|---|---|---|---|---|
| 0.50（PPv2 默认） | 0.3937 | **2.70%** ← 墙面仍在里面 | 10.75% | 53.68% |
| 0.35 | 0.5118 | 0.20% | 6.86% | 53.68% |
| **0.30（当前）** | **0.5512** | **0.00%** | 5.58% | **53.68%** |
| 0.20 | 0.6299 | 0.00% | 3.05% | 53.68% |
| 0.10 | 0.7087 | 0.00% | 0.72% | 53.68% |

### 为什么这是"纯赚"的改动

**灯管那一列从 0.5 到 0.1 始终是 53.68%，一分不减。**
原因：灯管线性亮度 1.70 远高于整个膝区（最高只到 0.7874），膝的形状对它毫无影响 ——
softKnee 只改变"刚好在阈值附近"的东西的待遇，而墙面恰好就在那个区间里。

所以这一个参数的调整，等于**只删掉了墙面的自污染，完全不动灯管的光晕**。

取 0.30 而不是 0.10：留一点软过渡，避免灯管边缘出现硬边「描边」；0.30 已把走廊墙面压到 0%，够用。若教室（灯最密）仍泛白，可继续降到 0.20。

## 4.3 第三个发现：全项目没有 Tonemapper（这是硬削顶的根源）

复盘时我回去读了 `PPS_Bloom.asset` 本体，发现一条之前漏掉的配置：

```
ColorGrading.tonemapper:  { overrideState: 0, value: 0 }   ← 0 = None
ColorGrading.gradingMode: { overrideState: 0, value: 1 }   ← 1 = HDR
ColorGrading.postExposure:{ overrideState: 1, value: 0 }
```

**整个项目没有开色调映射（Tonemapper = None，且 `overrideState: 0` 表示从未参与混合）。**

这条事实把「为什么过曝是硬性削顶」解释干净了：

| | 有 Tonemapper（ACES/Neutral） | 本项目现状（None） |
|---|---|---|
| 亮度超过 1.0 | 平滑压缩回 [0,1]，高光保留层次 | **直接 `saturate` 硬截断** |
| 灯管 emission 1.55 | tonemap 后 ≈0.85~0.95，有渐变 | **clamp 到 1.0，纯白平板** |
| 叠加 0.516 倍 Bloom 后 | 仍然平滑 | **整片推到 1.0，一片死白** |
| 教室 p50 | 应 ≈0.8 左右 | 实测 **1.000** ← 典型硬削顶特征 |

这解释了一个关键现象：**教室 62.5% 像素 p50 恰好等于 1.000 不是 Bloom 单独造成的，而是「Bloom + 多灯叠加把亮度推过 1.0」与「没有 Tonemapper 兜底」共同造成的硬削顶。** Bloom 只是让更多像素越过 1.0 这条线，Tonemapper 的缺失让它们全部塌成同一个 1.0 —— 于是「亮的地方有多亮」这个信息彻底消失，画面变成一块平板。

⚠️ **但开启 Tonemapper 属于改变全局色彩基线，超出本任务的硬约束**（会同时改变白天档观感，违反「白天档零变化」；且需要改 `PPS_Bloom.asset`，属「改资产须停下出报告」的情形）。所以：

- 本轮**不改** `tonemapper`，只靠阈值 / 强度 / softKnee 把亮度压在 1.0 以下；
- 把「是否开启 Tonemapper」作为**独立议题**上报（见 §9 ⑦）。这是本工程画面质感的一个系统性短板，值得单独立项，但不应塞进 P36。

## 4.5 诚实标注：仍未完全闭环的部分

## 6. 会踩到但已避开的四个陷阱（都写进代码注释了）

### ① `volume.profile` 是个有副作用的 getter

```csharp
// PostProcessVolume.cs:120-138
if (m_InternalProfile == null) {
    m_InternalProfile = ScriptableObject.CreateInstance<PostProcessProfile>();
    foreach (var item in sharedProfile.settings) { ... 深拷贝 ... }
}
return m_InternalProfile;   // ← 缓存，之后相机只看这份
```

`TwinLightingPreset` 原来写的是 `vol.profile` → **首次访问就克隆一份带旧 `postExposure` 的副本**，此后 `EnvironmentState` 每帧写 `sharedProfile` 的夜晚压暗永久失效（夜晚不暗、天空过曝），而且两边代码"看起来都对"，极难定位。

→ 本轮统一改读/写 `sharedProfile`，物理上不碰那个 getter。

### ② `AddSettings` 会改资产

`PostProcessProfile.AddSettings()` 把新 effect `settings.Add(...)` 进传入的 profile 并置 `isDirty = true`。传进 `sharedProfile` 就是在改**资产本体**。

→ `GetBloom()` 改为只读 `TryGetSettings`，绝不 `AddSettings`。工程里 `PPS_Bloom.asset` 本就含 Bloom，够用。

### ③ `sharedProfile` 仍然是资产对象 → 退出时必须还原

即便不 `AddSettings`，直接写 `Bloom` 组件的字段，改的也是 ScriptableObject 资产的内存。运行时不会自动写盘，但**只要有人在这之后保存，就会带着临时值落盘**。

→ `TwinLampBloomRunner.OnDestroy()` 调 `Shutdown()` → `Restore()` 写回进场原值，让资产内存与磁盘内容重新一致。

（**为什么不改成"克隆一份 profile 赋给 volume"**：那样确实完全不碰资产，但会打断天气系统的夜晚压暗 —— `EnvironmentState` 缓存的是 `sharedProfile` 里的 `ColorGrading`，它每帧往那份写。一旦换掉，相机读克隆、天气写原资产，夜晚就不再压暗。而 `EnvironmentState.cs` 本任务禁止触碰。两害相权，写同一份 + 退出还原是唯一同时满足两边的做法。）

### 4.7 天花板过曝的物理根因（截图即可判定，无需测量）

2026-11-13 21:29 主理人截图「计算机教室 1F 还是过曝」：天花板整片发白，灯管附近偏黄。

**几何算一下就知道**：

```
TwinLampGlow 落点 = 灯管包围盒中心，实测 y ≈ 3.34m
天花板                                      y ≈ 3.50m
⇒ 光源距天花板 0.16m

Unity 点光衰减 = 1 / (1 + 25·d²/r²)
d = 0.16, r = 3  →  1/(1 + 25×0.0256/9) = 1/1.071 = 0.93
⇒ 天花板正上方接收 2.0 × 0.93 ≈ 1.86 倍直射光
```

再叠加 `IndoorFillLight` 的补光点（已在 2.2m 处，`1.6 × 0.60 ≈ 0.96`），合计约 **2.8 倍 × 天花板反照率** —— 必爆，与 Bloom 参数无关。

**最讽刺的地方**：`IndoorFillLight.cs` 的注释早就写明了这个物理事实 ——

> 「补光点比灯管低 1.14m：不放在灯管中心的原因：全向点光源离天花板只有 0.16m 会把管顶烧出白斑，真实荧光灯往上几乎不发光（灯罩兜着）。」

它据此把自己的补光点降了 1.14m，**唯独 `TwinDevicePresenter` 里的 `TwinLampGlow` 还贴在天花板上烧**。这是两个模块对同一条物理规律的不同处理，不是参数没调好。

**修法**：`TwinDevicePresenter` 新增 `_lampGlowDrop`（默认 **0.55m**），点光源从灯管中心下移后再照。配合 F10 热键现场微调 —— 因为合适值取决于灯管到天花板的实际间隙、房间反照率、以及与补光层的叠加程度，**这些离线算不准，只能看**。

### 4.8 关键转折：走廊天花板的光**根本不是 `TwinLampGlow` 打的**

2026-11-13 21:52 主理人反馈「F10 没反应」，截图在**走廊**，Console 里 `F10` 的日志刷了一长串（累计下移 5.40m，即 36 档 × 0.15m），**画面纹丝不动**。

这不是热键失灵 —— 恰恰相反，这是一条**决定性证据**：

```

### 4.9 诊断热键的最终形态（正交组合）

要分清「谁在照天花板」，单关一路是不够的 —— 只关点光源时天花板依然亮，会让人误判「点光源不是主因」。所以做成**正交开关**：

| 键 | 控制 | 用途 |
|---|---|---|
| **F7** | `IndoorFillLight` 补光层 | 关掉它 → 天花板只剩点光源的贡献 |

| **F10 / F8** | 点光源下移 / 归零 | 找几何修正量 |
| **F11** | 2×2 定量探测 | Bloom × 点光源 四帧对照 |
| **F9** | Bloom 光晕层 | 验收光晕本身 |

```

F7 开 + F12 关 → 只剩补光层（走廊看这里）

`ShiftGlows` 现在会统计并打印**当前亮着几盏**；若为 0，日志直接告警「这个分区已被接管，移动它们不会有任何变化」—— 避免再次把「灯是灭的」误判成「热键坏了」。

### 4.10 归因定案：走廊的过曝 100% 来自 `IndoorFillLight` 补光点（实测，可复核）

#### ① 决定性实测：走廊关掉补光层 → 画面几乎全黑

| 区域 | mean | p50 | p90 | >0.95 | 硬削顶 |

| 左墙 | 0.137 | 0.025 | 0.599 | 0.0% | 0.0% |
| 地面 | 0.065 | 0.021 | 0.142 | 0.0% | 0.0% |

**没有任何一块区域超过 0.95，削顶率全部为 0%。** 这不是「过曝减轻」，这是**过曝消失 + 整个画面塌进黑暗**。

⇒ 三条硬结论：

1. **走廊过曝的唯一来源就是补光点。** 把补光层关掉，走廊没有任何别的光照能把画面顶起来 —— `TwinLampGlow` 虽然 `F12` 是「开」，但 `SuppressZoneGlows()` 早已把它们 `enabled = false`（§4.8 已证），灯管自发光（emission）在 `GI = None` 下只影响自身、不照亮房间。
2. **Bloom 是清白的。** `F9 光晕层：开` 的前提下削顶仍为 0% —— 如果 Bloom 是主因，关掉补光层后 Bloom 依然会把残余高光糊开，不可能 0%。（与 §4.2 的定量核算一致：Bloom 对 0.806 显示亮度的叠加仅 +0.0005。）
3. **走廊的问题不在 `TwinDevicePresenter`，我的 `_lampGlowDrop` 对走廊永远无效。** 这条与 §4.8 结论完全一致，现在是双证据互证。

#### ② 补光点对天花板的辐照度：定量 1.39 倍，必爆

`IndoorFillLight.cs` 参数（只读核对，未改）：`TubeFillDrop = 1.14f`（第 190 行）、`CorridorTubeRange = 9.0f`、`CorridorTubeIntensity = 1.7f`。

```
灯管中心     y = 3.34 m
补光点       y = 3.34 − 1.14 = 2.20 m
天花板       y ≈ 3.50 m
⇒ 补光点距天花板 d = 1.30 m（不是注释里说的"降到半高"，仍在天花板下方 1.3m）
```

Unity 内置管线点光衰减 `1/(1 + 25·d²/r²)`，r = 9.0、d = 1.30 → **atten = 0.657**，单管贡献 `1.7 × 0.657 = 1.117`。

再按走廊灯间距 3.5m 累加相邻 6 管（`NdotL = d_vert/d`）：

| 水平偏移 | d | atten | NdotL | 贡献 |
|---|---|---|---|---|
| 0.0 m | 1.30 | 0.657 | 1.000 | 1.117 |
| ±3.5 m | 3.73 | 0.189 | 0.348 | 0.112 ×2 |
| ±7.0 m | 7.12 | 0.060 | 0.183 | 0.019 ×2 |
| ±10.5 m | 10.58 | 0.028 | 0.123 | 0.006 ×2 |
| **合计** | | | | **1.390** |

⇒ **天花板接到的漫反射辐照度约 1.39 倍**。全项目没有 tonemapper（§4.3），任何 >1.0 的亮度被 `saturate` 硬截断成同一个纯白 —— **1.39 倍必然 100% 削顶**，且天花板吊顶板的方块纹理必然消失。这与教室实测的削顶 32.2% 完全吻合。

同一算式下教室（`RoomTubeRange = 8.0`、`RoomTubeIntensity = 1.6`、灯距 3.0m）合计 **1.253** —— 也是必爆。
