## 1.2 项目背景与立项目标

**背景**：这是一个以「1 号教学楼」为主场景的校园数字孪生项目，属于毕业设计 / 竞赛类交付。前期已完成场景搭建、点位体系、设备模型、数据链路、电力回路、机房主脑控制等底层能力，但**上层 UI 长期野蛮生长**——十几个面板各写各的，风格不统一、层级混乱、数据面板不专业。

**立项目标（P28 起）**：

1. 把分散的「数据监测 + 设备管理 + 电力管理 + 告警中心 + 数据统计」收敛进**一个统一的校园管理系统**
2. 交互形态参照《异环》(Neverness to Everness) 的**收纳式面板**：固定入口按钮 → 右侧滑出总控面板 → 点功能入口 → 进子功能面板
3. 建立**统一的科技风视觉体系**，消除风格混乱，后续新增面板沿用同一套规范
4. 设备编号规范化为「场景-位置-设备类型-序号」，例如 `1号教学楼-2F-201-灯具-001`，**确保无设备遗漏**

**原始诉求原文要点（不可偏离）**：

> 我点击总控按钮，弹出总控面板，在总控面板里点击**管理系统**按钮，弹出**管理系统面板**，管理系统分为多个功能模块展开设计……

即**三级结构**：`总控面板 → 校园管理系统 → 5 个功能模块`。这一点在 P1 初版被做错（5 模块直接平铺在总控面板），已返工修正。

## 1.5 核心价值与创新点

1. **3D 场景与数据面板双向联动** —— 点 3D 设备 → 面板更新；点面板列表 → 相机聚焦该设备。这是数字孪生区别于普通看板的核心，也是本项目的卖点。
2. **完整的命令回执链路** —— 不是"点一下改个颜色"，而是 `下发 → 回执 → 执行 → 回读` 四段超时校验（1s/3s/3s/5s），失败有明确拒绝原因。答辩时这是最能讲的技术深度。
3. **零美术资源 UI 体系** —— 所有面板、图标、圆角、渐变全部代码程序化生成（`TwinRoundedRect` 自绘顶点），不依赖任何图片素材。换肤改 token 即可，不会出现"找不到图"。
4. **收纳式单抽屉 + 页栈** —— 区别于常见的"多浮窗并列"，从架构上消灭了"面板互相压、不知道该看哪个"的问题。
5. **分级电力控制** —— 楼栋 → 楼层 → 房间三级回路，支持整层停电、单房间独立停电，并实时计算影响设备数。

### A. Unity 编辑器 / 编译类

| # | 坑 | 现象 | 根因与解法 |
|---|---|---|---|
| A1 | **场景序列化值覆盖字段默认值** | 把 `_toggleKey = KeyCode.F4` 改成 `None`，快捷键照样生效 | 场景里已挂载的实例，其序列化值会覆盖代码默认值。**必须在 `Awake()` 里硬写**。而运行时 `AddComponent` 的组件改默认值才有效——**同一件事，两类组件两种做法** |
| A2 | **Safe Mode 下 Unity 不编译** | 脚本报错后修好了，日志不动、控制台还是旧错误 | 进入 Safe Mode 后需**手动点「退出安全模式」或重启编辑器**，否则永远不重新编译 |
| A3 | **失焦 + Auto Refresh 关闭时不自动编译** | 改完代码等 10 分钟，`Editor.log` mtime 不涨 | 判断是否已编译：看 `Begin MonoManager ReloadAssembly` 轮次是否增加、看 `Library/ScriptAssemblies/Assembly-CSharp.dll` 时间戳是否比脚本新。**日志 mtime 不涨 = 没编译，不是"通过"** |
| A4 | **静态类不能直接调 `FindObjectOfType`** | `CS0103: The name 'FindObjectOfType' does not exist` | `FindObjectOfType` / `Destroy` / `Instantiate` 都是 `UnityEngine.Object` 的静态成员，`static class` 不继承 `Object`，必须写 `UnityEngine.Object.FindObjectOfType<T>()` |
| A5 | **类型名扫描要加词边界** | 静态审计把 `TwinStatusColor` 误判成 `TwinStatus` | 查类型用 `\bTypeName\b`，不能裸子串匹配 |
| A6 | **命名空间被拆成两半** | 10 个 `CS0246` 同一个原因 | `TwinStatus` / `TwinValue` / `TwinSample` / `DataQuality` 在 **`SchoolTwin.Core`**；`TwinAnchor` / `TwinRuntime` / `TwinCircuit` / `TwinControlScope` 在 **`SchoolTwin.Twin`**。凡是用到"状态或数值"，两个 `using` 都要有 |
| A7 | **数 `m_Name` 覆写数 ≠ 数实例数** | 路灯数出来 29 盏，实际 100 盏 | 未改名的预制体实例**不产生 `m_Name` 覆写**。正确做法：按 `m_SourcePrefab` 行统计 |
| A8 | **编辑模式不跑 `Update`，动画停在起点** | 给 L2 页面截图，内容区一片空、Tab 全透明，像是"没建出来" | 页推入动画由 `Update` 驱动，编辑模式不执行 `Update`，alpha 永远停在 0。**截图前把动画状态强制设为完成态**，或在 `OnShow` 里判断 `!Application.isPlaying` 直接置终态 |
| A9 | **batchmode 不能替代 GUI 验收** | 想用 batchmode 跑采集器出运行时截图，工程加载完（15.5s）后无任何输出，采集器零触发 | batchmode **不跑 `EditorApplication.update` 循环**，`[InitializeOnLoad]` 回调没机会执行。且本项目是 **Overlay Canvas，不经过相机**，`Camera.Render → RenderTexture` 抓不到，只能 `ScreenCapture` 读真实窗口。**结论：GUI 类验收必须有真实窗口，没有捷径，别在 batchmode 上反复尝试** |
| A10 | **编辑器异常退出留下 `Temp/UnityLockfile`** | 再启 GUI 时进程活着，但 `-logFile` 指定的日志从不创建，看起来像"启动失败" | 先 `ls Temp/UnityLockfile`，有就先删再启。清了锁仍无日志则不是锁的问题，别再往这个方向查 |

### B. UGUI / 代码类

| # | 坑 | 现象 | 根因与解法 |
|---|---|---|---|
| B1 | **`r.materials` 访问后 `r.sharedMaterials` 返回的是克隆体** | 角色变紫色（材质丢失），且每次面板开关都闪一下 | 想"还原"时写 `r.materials = r.sharedMaterials; Destroy(inst)`，实际把克隆体赋回去又销毁了。**必须先存 `sharedMaterials` 再取 `materials`**；恢复时先 `r.sharedMaterials = origin` 再销毁克隆体 |

### D. 排查方法论（从踩坑里提炼，可复用）

1. 遇到"某块地方不对劲"，**先问"点得到吗"**，再查材质。点不到就已经指向"没有几何"。
2. **材质断裂只查"槽为空"会漏掉一类**：材质完好但 `Renderer.enabled=false` / GameObject 未激活——看起来和材质丢了完全一样。体检脚本要覆盖这一节。
3. 报"某处坏了"时，**先去未改动的旧工程里看一眼**。P26 的黑墙最后就是靠这个定性的——旧工程里也一样黑，说明是资产原生设计。
4. **子症状通过 ≠ 整体正确**。看到 `page.rect.height = 544` 就判"容器对了"，没意识到 544 同时是"抽屉比画布高 54px"的证据——**每个通过的数据都要再问一句"它还能被什么解释"**。判断方向也要反过来一次：不是问"画布该多大"，是先量"画布现在多大"。
5. **主理人说"不对"就是不对，不要用数值去驳**。数值只能证明"我测的那一项没错"，证明不了"他看到的那一项没错"。用数值反驳视觉，会把一个问题拖成三个。
6. **判据不完整时，不要下"没有 X"的绝对结论**。看到"点不中"就判"没有几何"，是因为判据只有三条、缺了「合并网格」这一种。**绝对结论（没有了 / 不存在 / 不可能）必须先有一次独立验证**（隔离显示、洋红扫描、换个角度看），否则一次误判会连带下游白干一轮。
7. **每修一个现象，先分"状态没恢复"还是"资源没驱动"。** 前者补反向操作（`Detach` 之后要 `Restore`），后者补 Tick / 补引用。**两类问题的修法完全不同，混在一起改就会越改越乱**——这是机房 20 多轮反复的总结论。
8. **"不存在"是静默的，"存在"才需要证据。** 白名单、配置表、常量列表都只是"期望"，不是"事实"。凡是用 ID 取对象，先确认它真在场景里（`grep` / `Registry` 计数），否则整条链路会无声失效，连报错都没有。
9. **`grep` 类判据必须先剔除注释**。P5-06 / P5-10 / P5-11 三条判据一天内误报三次，命中的都是注释里引用的**旧文案字面量** —— 代码早改对了，判据一直红。根因不是正则写错，是**判据工具不分注释和代码**；逐个打补丁只会换个地方再犯，所以在 `tools/status.py` 的 `eval_check` 入口统一加 `strip_comments()`。（v1.20 登记，11-03 补进列表）
10. **提修法前必须读被改算法的真实实现，不要凭函数名推断**。我在 P5-5 §5.3 写「正弦均值是 (Min+Max)/2，灯量程 0~120 → 释放 override 后会跳到 60W」，而 `MockSignalGenerator` 实际只在 `[WarnLow, WarnHigh]` 内收 12% 区间做正弦（约 30~90W）。**这条警告是错的，已收回**。
11. **专家给出的替代方案若更优，采纳并写明否决自己方案的理由**。灯具播种我提「释放 override 让波形接管」，断点提「按房型分档」（`LightSeedWatt` 24~68W）。采纳后者：① 不脱离 `WarnLow/WarnHigh` 基线逻辑、不会自造告警；② 答辩可解释「礼堂 12 盏大灯」；③ 改动面更小。**负责人的方案没有天然优先级。**
12. **派工前必须先算期望值，且算式要能被复核**。P7 任务包里我写「联动开机增量 ≈ 3.24 kW = 18 × 180」，断点实算后指出这是错的：180W 是**绝对值不是增量**，每台开机前有 `RatedPower(PC) × 0.15 = 30W` 待机底噪，且下发的是 20 条命令（主脑 + 投影 + 18 座位）不是 18 条 —— 实测 **3.115 kW** 才对，校验和 `1735000 → 8.675 kW`，+3.115 = 11.79 kW 精确闭合。**给专家的验收标准里带算式时，错的算式会让专家拿一把坏尺子去量对的代码。**

13. **回归 bug 的查法是考古，不是调试**。「诡异、稳定、位置恒定」的渲染问题出现时，强制第一步跑 `git log --diff-filter=A -- <目录>` 看**最近新增了什么文件**，而不是从渲染参数开始穷举。白线 bug 实测：按候选清单逐步验证 40 分钟 + 造诊断工具 35 分钟全部落空，`git log` 一条命令 10 分钟锁定真凶（新增的 `SnowOnTrees.cs`）。**排查起点选错，能力再强也是白烧时间。**（P13 白线，11-04）
14. **给执行者派单时，若已有自检日志，先要日志结论再定候选方向；若已判定是回归 bug，不要给候选清单**。候选清单会把执行者锚定在错误方向上做穷举（白线 bug 的三个候选全错且全浪费）。给一句「去查最近新增了什么」比给三个猜测更有效。同理，「派工前必须先算期望值」（第 12 条）之外再加一条：**派工前先问自己，我的候选建立在哪个未验证的前提上**——白线三候选的共同前提是「线来自雪盘」，而自检日志第一轮就已数学排除。（负责人自查，P13 白线，11-04）

15. **第一人称测试通过 ≠ 第三人称通过**。凡是「跟随」「朝向」「遮挡采样」的逻辑，第一人称下相机与角色重合、看不出问题，第三人称下两者分离才露馅。这类功能回归必须**两种视角各测一遍**。（P13 天气水花/室内雨雪，11-04）

16. **多个不相关的现象同时出现时，先找它们的「共用点」，不要分别排查**。一个 bug 引起四个现象，比四个 bug 同时发生更可能。屋顶积雪事故里四个症状分别属于渲染排序、地面采样、粒子系统、屏幕材质四个完全不同的子系统，唯一交点是**新加的雪壳网格与材质**——找到交点，四个现象一次解释完，40 分钟收口；若按"四个独立 bug"分头修，最坏情况是四次自伤。**同时配套一条反向动作**：当「调参数」和「改架构」两条路都不可行时（本次：调 `minRoofY` 会连带漏掉 1~2 层楼屋顶，按建筑分组又没有可信的建筑清单），正确动作是**停用**，不是硬凑——答辩前一天，一个达不成目标还破坏四处的功能，收益是负的。（P13 屋顶雪壳，11-05）

17. **「永不放弃的重试」不是兜底，是把可诊断的故障变成一片噪音**。同一个 bug 的现场出现 255 条重复警告，主理人第一反应是「应该是这些警告引起的」——方向对了但因果反了：警告是**症状的复读**，真因（解码器耗尽）被它埋掉了。重试必须有上限，超限后**放弃 + 清屏 + 只留一条**说明原因与怀疑方向的 `LogError`。配套判据：**日志的用处是定位，不是复读**。（P26 视频泄漏，11-05）

18. **「同一会话内先成功后永久失败」= 资源累积，不是逻辑错**。只要看到这个形状，直接去查**创建了但没释放**的东西，不要从算法时序开始猜。判据：同一份输入 + 同一段代码 + 前 N 次成功、第 N+1 次起必然失败 → 泄漏 / 句柄耗尽 / 静态状态累积。最快的定位动作是**数计数**，不是读代码：本次 `grep -c "就绪后补播"` 得 8 次而播放器创建 20+ 次，一条命令就锁定了。（P26 视频泄漏，11-05）

19. **一个只报告「成功」、不报告「为什么失败」的异步接口，会让所有失败长得一样**。`VideoPlayer` 解码失败时既不回调 `prepareCompleted`、也不打日志，外部只能看到 `isPrepared=false`；于是「素材编码不支持」「文件被占用」「解码器耗尽」三种原因现场表现**完全一致**——这才是该 bug 查得久的真正原因：不是难，是**没有可分辨的证据**。接上 `errorReceived` 的成本是一行代码。（P26 视频泄漏，11-05）
20. **「发黑」先分三族再动手，三族修法完全不同，分错族=白烧一轮**：① 编辑器正常、exe 全黑 = 着色器被剥离（F22，查 Always Included Shaders / Resources）；② 编辑器与 exe 同黑、且「一部分黑一部分正常」= lightmap UV 块无光（D4 / D13，修 `lightmapIndex=-1`，不重烘）；③ 点不中 + y=0 网格可见 = 几何缺失（C4，移交补几何）。判别动作各一条：看 Player.log 有无「找不到着色器」（族①）；选中黑面看 `lightmapIndex` 与 UV 采样值（族②）；点选看 Hierarchy 高亮覆盖范围（族③）。**「部分黑」几乎总是族②**——整块材质丢是粉或全黑，只有 UV 块才会"同一物体一半亮一半黑"。（1F 暖气/窗发黑，11-05）
21. **答辩前夜的修复包必须带「止损闸」：先诊断后动手、限时、超时还原**。开工前先要执行者的三问答案（知道原因吗 / 怎么修 / 把握几成），把握不足或说不清根因就不开工；开工即计时，**20 分钟内验证不过 → git 还原到开工前状态**，缺陷降级「已知限制」+ 答辩口径，绝不带着未验证的改动过夜。**理由**：答辩前夜一个没修好的新 bug，比一个已知的旧缺陷贵得多（旧缺陷有口径，新 bug 没有）。（主理人 11-05 23:24 定，D13 首发适用）

### F. 资源归属与状态机类（2026-11-02 机房交互，20 轮反复的沉淀）

> **这一类的共同特征：单看每一行代码都没错，错的是"谁管谁"从来没写下来。**
> 机房模块前后改了 20 多轮、耗两天，每轮都是"修好 A 弄坏 B"。根因不是某行写错，而是三个前提没人固定：`Room_01` 不存在、座位屏贴图指向谁、播放器谁驱动。

| F22 | **`Shader.Find` 的着色器打包后会被剥离——编辑器里全好，exe 里全黑** | 首次打包 exe（21:52）实测：机房 18 台无视频「退回白屏」、投影幕布无画面、投影光柱不画。Player.log 三行原话：`找不到着色器 SchoolTwin/ScreenComposite，视频不启用`、`找不到着色器 SchoolTwin/ScreenOnModel，幕布视频不启用（注意：打包时需加入 Always Included Shaders）`、`找不到 Legacy Shaders/Particles/Additive，投影光柱不画了` | **不是素材没打进包**——实测 `School-pro_Data/StreamingAssets/PC/` 下 4 个 mp4 + 桌面图 + 12 张 PPT 图**全部齐全**（57MB 完整复制）。真因：这些着色器只被 `Shader.Find("字符串")` 引用，Unity 打包做可达性分析时找不到引用者，判定"没人用"直接剥离。天气那 4 个 shader 之所以没事，是因为它们放在 `Resources/` 下并用 `Resources.Load<Shader>()` 取（见 `ProceduralAssets.cs:550` 注释「放在 Resources 下并用 Resources.Load 取，是为了打包时不会被剥离」——**同一个人早就踩过并写对了，屏幕这条线漏了**）。**修法二选一**：① Project Settings → Graphics → Always Included Shaders 加入 `SchoolTwin/ScreenComposite`、`SchoolTwin/ScreenOnModel`（项目 guid：`573dc4bc14eb6f7498a88fa421b04505` / `1a2ac668da4bb89419bfd0d2b7cb60d6`）；② 把它们移进 `Resources/` 并改 `Resources.Load<Shader>()`。内置着色器（`Legacy Shaders/Particles/Additive`、`Particles/Standard Unlit`、`Skybox/Procedural`）同样会被剥，必须一并进 Always Included 列表。**检查清单（打任何 exe 前必过）**：全项目 `grep -rn "Shader.Find(" Assets/_Project/Scripts` 的每一条命中，都要确认它要么在 Resources 下、要么在 Always Included Shaders 里。**这条是「编辑器通过 ≠ 打包通过」最典型的一例，与 D15 同源**。<br>**⚠️ 反面案例补充（11-06 兜底实测，两次构建崩溃换来的）**：Always Included Shaders **不是越多越安全**——`Hidden/Internal-Colored` 这类 e000 系列（`unity_builtin_extra` 内的引擎内部资产）一旦登记，构建会在 `m_LockCount == 0` 断言崩溃，且报错完全指不到真因。**正确口径：只登记 Player.log 实测「找不到着色器」的项目自有 shader 与可安全内置的 shader（本次实登 6 条：ScreenComposite / ScreenOnModel / Particles-Additive / Particles-Standard-Unlit / Skybox-Procedural / Sprites-Default），引擎内部 Hidden/* 一律不碰**。定盘任务包里原写的「Hidden/Internal-Colored 一并加入」是错误指令，已由兜底纠正 |

**F 类的适用面远不止机房**：凡是「一个数据源驱动多个表现」「多个入口改同一份状态」「批量操作与单台操作并存」的功能，都会撞上这张表。下次接路灯（100 盏）、接天气联动前，先对照 F1/F2/F8/F9/F13 过一遍。

### G. 数据真实性类（2026-11-03 P27，Mock 链路物理建模的沉淀）

> **这一类的共同特征：编译通过、逻辑自洽、看起来完全正常 —— 但数据是假的。**
> 触发场景是主理人一句「数据展示波动范围频率全部依照现实逻辑来处理」，做下来等于把整条 Mock 链路的建模前提重写了一遍。
> 详细过程见 `Docs/P27_数据真实性_踩坑日志.md`（13 条，按"现象→根因→修法→教训"写）。
>
> G1~G12 是**数据**本身的坑；G13 是**验收数据的判据**的坑 —— 落盘阶段才暴露，单列在最后，因为它说明这一类的适用范围要往上抬一层：**体检报告也可能是假的。**

| # | 坑 | 现象 | 根因与解法 |
|---|---|---|---|
| G1 | **`case` 分支存在 ≠ 播种生效** | 给 `SeedOne` 加了 `case "Alarm"`，烟感照旧报 27.27 obs/m | `SeedOne` 只被 3 条路径调（`TwinControlScope.All` / `SeedOnlyIds` / `HeatSeedIds`），烟感一条都不在 → **分支是死代码**。**「写了分支」和「谁调这个分支」必须分开验证；判据要锁 ID 在表里，不能只锁 `case` 存在** |
| G2 | **钳制顺序 = 它在物理上对抗什么** | 供暖季室温算出 15.5~16.2°C（教室偏冷 4°C） | 先加得热再整体钳制，等于把"人产生的热"也压掉了。暖气对抗的是**室外渗入的冷**，人/电脑/照明的得热是**房间内部产热**，既不加也不减 → **钳制必须在得热之前**；`HeatingStiffness` 0.2→0.04 |
| G3 | **百分比量不能线性外推** | 7 月湿度算出 **−3 %RH**（负数） | 写成 `52-(T-20)*4.5`。而 RH = 含湿量 ÷ **饱和含湿量**，后者随温度**指数增长**（20°C=17.3、30°C=30.3 g/m³），跨 10°C 必崩 → 用 Magnus 公式 + 凝结上限 + 蓄湿下限。**凡百分比量先问"它是比值吗？分母随什么变？"** |
| G4 | **经验公式都有适用域，代码不检查** | 7 月供水 **22~33°C**，比室温还低 | 质调节曲线只在供暖季有定义，7 月锅炉没开采暖循环 → 分运行状态，非供暖季走生活热水定温 48°C。**写 `f(室外温度)` 前先问"这段外推会失效吗"，输出是温度/压力/流量时越界立刻露馅** |
| G5 | **注释描述了不存在的实现** | 12:00 室温瞬跳 0.8°C | 原注释写「分段 + 前端小过渡（±0.1）足够」，**代码里根本没有过渡** → 时刻表 + smoothstep。**这比没注释更坏，它会让下一个人相信"已经处理过了"从而跳过检查** |
| G6 | **"参数看着合理"≠"留了余量"** | 湿度下限 5.5 让 11 月晴天最干到 **30.09%RH**，而 `WarnLow=30` | 余量只剩 **0.09**，撑不住"天气变干"或"阈值收紧"两种变更，而失守方向看起来像传感器故障 → 改 6.5，余量 5.18。**贴着阈值的数必须跑最不利组合（最干天气 × 最不利点位 × 最误时刻）** |
| G7 | **状态型默认值不能写死某个具体值** | `_heatingSeason = true` 导致 7 月室温也钳到 20°C | `true`/`false` 都是一种断言，`Auto` 才是"我不知道，让规则决定" → 三态（自动/强制开/强制关）。**凡"季节/时段/运行模式"类状态，默认必须是按现实判定** |
| G8 | **指标如果依赖另一个状态，套通用波形必错** | 刚开机什么程序没跑，CPU 负载 **83.88%** 正在擦告警线 85 | 通用波形基线夹在 10.2~74.8% 且每 45s 冲上限，真实空闲 PC 是 5~15% → 新增 `MetricShape.CpuLoad`（开机冲刺 `0.80·exp(−t/12)` + 空闲 8~14%）。**判断标准：这个量的物理含义里有没有"开关/阶段"在支配它？有 → 它需要自己的形态，不是参数微调** |
| G9 | **记账 key 要用身份，不能用数值** | 我先把理由写错了（说"seq 每帧变"，实际 `seq` 每帧开头重置为 0 是常量） | 真正理由：**相位是数值不是身份** —— 两台机器相位撞了就记成同一次开机。`twinId` 天生唯一。**"结论对"不能免掉"理由对"，写错的理由比没注释更危险** |
| G10 | **静态可变状态 + 会归零的时间基准 = 必然跨会话泄漏** | `BootStart` 存数据源时间轴的 `t`，而 `t` 每次 Play 从 0 重来 → `elapsed` 为负 → clamp 0 → 判"刚刚开机" | 与 `s_muted`/`s_overrides` 同一类坑，已咬过一次 → 并入同一个清理入口 `ResetStaticsOnLoad`。**新增静态表先问"进 Play 要清吗"，答"以后可能需要"就现在清** |
| G11 | **改代码把注释弄坏，编译器不报** | `IsSmooth` 上方留一串悬空 `///` + 孤立 `</summary>` | 插入 `ResetBootClock` 时切断了注释块。**注释不参与编译 → 编译通过、逻辑正确、只有人读才发现**。本项目大量依赖注释讲"为什么" → 已补判据 `P27-60` 断言"成员之间紧邻" |
| G12 | **判据只看得到代码，看不到注释** | 为守护 G11 写的判据连续两版都是 0 处 | `status.py` 的 `strip_comments()` 会整行删掉注释，拿注释句子当模式**必然 0 处**（本项目累计第 4、5 次踩同一根因） → 改断言"注释造成的结构后果"。**判据证明不了"逻辑对"，只能证明"代码长这样"；真正抓出问题的是 192 组 Python 实算** |
| G13 | **锚点要选结构唯一的位置，不能选语义最像结论的句子** | 落盘验收时 P27-66/67/69 三条报红，打开文档发现三段都写得完整 —— **红的是判据不是文档** | 结论句天生在「总览表 / 小节标题 / 正文重申」三处各出现一次，`grep:1` 必然漂移（实测 3 处、2 处）；P27-69 还把 `\|` 误写成 `/\|` → 命中 **470 处**，判据退化成恒真。→ 锚点一律改**行首锚**（`^###` / `^\|`），并新增 `P27-70` 守这类错。**与 G12 同根因的两个面：G12 是"看不见"（注释被删），G13 是"看得太清"（同一句话重复）；写完后必须问"它报的这个数量级可能吗"** |

**G 类的适用面**：凡是「生成/模拟出来的数据要拿去演示或答辩」的功能都适用。
最低自检**四条**：**① 我写的分支真的被调用了吗 ② 我拍的参数跑过最不利组合吗 ③ 我的注释和代码是同一件事吗 ④ 验收它的判据，报出来的数合理吗**。

# 六、团队协作规则

> 这一章是**运行机制**，所有专家必须遵守。规则优先级高于各专家自身偏好。

## 6.1 架构模式

**一个对话对应一位专家。专家之间无法直接通信，也没有共享内存。**

```
┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│  负责人对话   │   │  UI 专家对话  │   │  开发对话     │
│   （定盘）    │   │   （见微）    │   │  （断点）     │
└──────┬───────┘   └──────┬───────┘   └──────┬───────┘
       │                  │                  │
       └──────────┬───────┴──────────────────┘
                  │
            ┌────────────────┐
            │ 老大（项目主理人）│  ← 唯一中转人 + 现场 play 验收
            └────────────────┘
```

## 6.2 调度权限

| 角色 | 能否发起调度 | 说明 |
|---|---|---|
| **Unity 项目负责人（定盘）** | ✅ **唯一有权** | 只有它能生成【调度任务包】 |
| **项目主理人（老大）** | ❌ 不能自行发起，✅ 可提请 | 负责中转与现场验证；发现新问题时**描述现象交负责人判定**，由负责人出包，不自行指定专家与做法 |
| 其余所有专项专家 | ❌ 不能 | 只能接收任务、产出成果，**不能调度其他人**，也不能要求用户去找别的专家 |

## 6.3 中转链路（固定四步）

```
① 负责人在自己对话里输出【调度任务包】
        ↓ 用户人工复制
② 粘贴到目标专家的独立对话里下发
        ↓ 专家工作
③ 专家产出成果
        ↓ 用户人工复制
④ 粘贴回负责人对话，由负责人验收
```

**没有捷径**。负责人不能"直接喊话"给专家，专家也不能"直接交付"给负责人。

## 6.4 调度包固定格式（字段名不得改动）

> **2026-11-02 更新**：模板新增第 6 字段【开工前自检 / 完工后自检】。
> 该字段**每次都带、不许省略**——它把「刷新看板」这件事从主理人手上移交给了专家，
> 主理人复制粘贴即可，不需要记任何命令。理由见 §6.4.2。

```
=====调度任务包=====
目标专家：【专家名称】
任务优先级：P0/P1/P2
任务描述：【清晰需求、上下文、约束、交付目标】
交付物要求：【明确输出格式】
附加项目上下文：【项目统一信息、风格约束、依赖前置产出】
开工前自检 / 完工后自检：【照抄 §6.4.2 的固定块，只改 TASK-ID】
=====调度任务包=====
```

**使用纪律**：

- **一次只发一个包**。需要并行时连续输出多个包，每个包前标注 `【任务 1/3】`、`【任务 2/3】` 及依赖关系
- **【附加项目上下文】不能空**。至少写清：项目类型、运行平台、目标风格、本任务依赖的上游产出
- **【交付物要求】要可验收**。写清结构、是否用表格、是否要具体数值，不能写"给个方案"
- 包外可以有说明，**包内六个字段必须齐全**
- **【开工前自检 / 完工后自检】固定照抄，不许自己缩写** —— 缩写掉的正好是别人看不懂的那部分

### 6.4.1 任务包必须点名上游产物路径（2026-11-02 新增，血案驱动）

**规则：任何依赖上游文档的任务包，必须在【附加项目上下文】里写出该文档的绝对路径 + 行号范围 + 一句话说明"看哪一节"。不写路径 = 专家看不到 = 白出。**

**为什么写这条**：2026-11-02 统计页施工，见微 17:05 出了 `Docs/P5-1_统计页视觉返工优化单_见微.md`（293 行，3 个 P0），负责人发任务包时**没有附这份文件、也没有写路径**。断点 17:23 仍在写滚动条，实证三条全空：

| 优化单要求 | 代码实际 | 结论 |
|---|---|---|
| P0-1 新增 `_nTypeCount` 台数列 | `grep -c _nTypeCount` = **0** | 没做 |
| P0-2 新增 `ResetStatsSpark()` | `grep -c ResetStatsSpark` = **0** | 没做 |
| P1-4 `v0.9` 删掉时间戳 | `TwinFullLayer.cs:223` 仍是 `"v0.9 · HH:mm:ss"` | 没做 |

**专家不会自己去翻 `Docs/` 找没被点名的新文件。** 原因有二：
1. 每个专家是独立对话、独立上下文，**没有"最近新增文件"的感知**；
2. 基线 §6.6 明令「专家禁止扩需求：任务包里没写的，不要顺便加一下」——**主动去读没被派工的文件，在这套规则下属于违规**。

所以"忘了附件"不是专家的失误，是**派工失误**，责任在负责人。

**固定写法（照抄，不许省略）**：

```
附加项目上下文：
- 上游文档（必读）：E:\Unity Projects\School-pro\Docs\<文件名>.md
  只读 §3.5 房间能耗 Top3 与 §3.6 Top3 设备（约 363–417 行），其余节不必看。
- 与代码冲突时：以上游文档为准 / 以代码为准（二选一，必须写明）
```

**"与代码冲突时以谁为准"必须显式写。** 基线 §8.1 默认是"以代码为准"，但当上游文档是**更新的设计变更**时，必须以文档为准 —— 不写明，专家会默认按代码走，等于没收到变更。

**发包含新 Namespace / 新字段名的任务包时，额外自查**（否则专家会重复造一个同功能的）：

```
grep -rn "要新增的字段名\|要新增的方法名" Assets/_Project/Scripts/
```

结果为 0 才说明确实是新的；不为 0 说明已有实现，任务包应改为"复用 X"，而不是"新建 X"。

### 6.4.2 看板刷新由专家做，不由主理人做（2026-11-02 新增）

**主理人 2026-11-02 原话**：「每次都得我刷新吗？好麻烦；你给的任务包里面提醒一下即可，我是直接复制你的任务包发送的」。

这条要求很对。**主理人是唯一的消息中转人，不是工具执行人。**
让他记命令、跑脚本、再把结果贴回来——每多一步，就多一次"这次忘了"的机会。
所以刷新动作必须**内置在任务包里**，主理人复制粘贴，专家自己跑。

**固定块（每次派工照抄这个，只改 `TASK-ID` 和「本次目标」）：**

```
开工前自检 / 完工后自检：
【开工前 · 你自己跑，跑完把结果贴在最前面】
cd "E:\Unity Projects\School-pro" && python tools/status.py
然后读 Docs/STATUS.md，看三件事：
  1. §0.5 验收判据自检里，TASK-ID 带 <TASK-ID> 前缀的条目，现在有几条是 ❌
  2. §1 代码是否已生效 —— 若有别人未生效的改动，**先别动手**，回报给我
  3. §2 未提交改动 —— 确认没有别人正在改你要改的文件，有就停下来问
开工前不要跳这步。跳过 = 你按脑中印象施工 = 我们又要返工一轮。

【完工后 · 你自己跑，把输出贴进回执】
cd "E:\Unity Projects\School-pro" && python tools/status.py
  要求：<TASK-ID> 前缀的判据**全部 ✅** 才算完工。
  还有 ❌ 就不算做完，不要写"基本完成"，直接说哪条没过、为什么。
  如果你的改动需要新增判据（新字段 / 新方法），在回执里把该写的判据行列出来，
  格式：`<TASK-ID>-NN | 一句话描述 | grep+:1:相对路径:模式`
  我会把它加进 tools/status_checks.txt，下一轮自动生效。
```

**为什么完工后要专家自己贴输出，而不是主理人验**：

- 专家贴的是**执行结果**，主理人验的是**视觉结果**。两者不能互相替代，但前者必须先过
- 专家自己跑一次，比事后被质问"到底做完没"便宜得多
- 输出里有 `grep` 行数，**编不了**

**主理人侧只需要做一件事**：收到回执后确认 `[status] 已写入` 那行和判据全绿，
然后去 Unity play。**不需要记任何命令。**

## 6.5 冲突处理规则

专项专家的产出出现**冲突、风格不统一、接口对不上**时，**全部提交负责人裁决对齐**，不得由专家之间自行协商，也不得把选择题原样丢回给用户。

裁决输出格式：

> **冲突点**：{谁和谁在哪一项上不一致，具体到数值或定义}
> **裁决**：采用 {哪一方} 的 {哪一项}，值为 {具体值}
> **理由**：{为什么这样定}
> **影响**：{哪些已完成的产出需要同步修改，需要谁改}

裁决后**必须同步更新本文档基线**，避免同一个冲突反复出现。

## 6.6 权责边界重申

- 各专家**禁止越权**，不跨领域做不属于自己职责的工作
- 负责人**禁止代产**：不自己写 UI 方案、不自己写业务代码、不自己做测试用例
- 专家**禁止扩需求**：任务包里没写的，不要"顺便加一下"
- 所有专家**禁止编造未实现的功能**

## 6.8 并发写入纪律（10-29 新增，优先级等同铁律）

**所有专家共用同一台机器、同一个工程目录。这不是"多人协作"，是"多人在同一个工作区里写同一批文件"。** git 在这里不提供任何保护——冲突不是 merge conflict，是**后写覆盖先写**，被覆盖的一方不会收到任何提示。

### 资源分级

| 资源 | 谁能写 | 并行性 |
|---|---|---|
| `Assets/**/*.cs`（代码） | **只有断点** | **独占** |
| `Assets/**/*.unity`（场景） | 削面 / 打光 / 断点 | **独占，同一时刻只能一人** |
| `Assets/**/*.mat` `.asset` `.prefab`（资产） | 削面 / 打光 | **独占** |
| `Docs/**`（文档） | 见微 / 心跳 / 挑刺 / 落笔 | **可并行**，不碰 Unity |
| Unity 编辑器（play / 编译） | 主理人 / 当前写入者 | **独占** |

### 三条硬规则

1. **同一时刻只能有一个"写入者"**。断点改代码期间，削面不得改模型、打光不得改光照、主理人不得 play。
2. **play 期间任何人不得改 `Assets/` 下文件**。Unity 在 play 模式下**不重新编译**，改了也不生效，写入者会误判"我的改动没起作用"，进而推翻本来正确的实现。
3. **代码生效的判定标准**（不是"我改完了"，是下面这条）：

```
最后一个 .cs 的 mtime  <  Library/ScriptAssemblies/Assembly-CSharp.dll 的 mtime
```

不满足 = 没编译 = 没生效。**写入者宣布"改完"之前必须自己核一遍这个时间戳对比**，主理人验收前也核一遍。

### 交接握手（写入者 → 主理人）

写入者交付时必须附一句：**"最后一次改 `xxx.cs` 是 HH:MM，dll 编译于 HH:MM，已生效/未生效"**。缺这句的交付不验收。

### GUI 验收交接（10-29 新增，因实际卡住一次）

编辑器是独占资源，而 GUI 类验收（Play / 截图 / 手点）**必须占用它**。写入者和主理人抢同一个编辑器会互相卡死，所以交接规则必须写死：

| 阶段 | 谁做 | 规则 |
|---|---|---|
| 写代码 → 编译生效 | 写入者 | 自己按 Ctrl+R 或 batchmode 编译，核 dll 时间戳，然后**立即交还编辑器** |
| GUI 验收（Play / 截图 / 手点） | **只有主理人（老大）** | 写入者交付"已生效"后不再占用编辑器 |
| 写入者想验证画面 | — | **禁止**。写入者不得启动 Unity 编辑器进程，也不得用 batchmode 试图替代 GUI 验收（见 §1.6 A9） |

**写入者的交付边界到"已生效"为止，画面层结论由主理人产出。** 这不是能力问题，是资源归属问题——写入者反复尝试启动 GUI 只会浪费时间、留下锁文件残留、并让工程处于不确定状态。

**定性口径**：写入者交付「已生效 + 待截图」时，验收处置写**「只差交接」**，不写「返工」。返工指实现有错，交接指流程没走完——两者不能混，否则会陷入"打回重做还是做不出来"的循环。

## 6.9 验收判定规则（10-29 新增）

### 一、验收 = 量化 + 视觉，两栏都要过

| 栏 | 谁判 | 判据 | 不过怎么办 |
|---|---|---|---|
| **量化栏** | 负责人 | 规格里写明的数值、坐标、grep 结果、恒等式 | 返工，退给实现者 |
| **视觉栏** | **主理人（老大）** | play 后眼睛看到的满不满意 | **不通过**，退给见微重出规格或断点重做 |

**量化全过 + 视觉不满意 = 不通过。** 数字只能证明"没错"，不能证明"好看"。

### 二、视觉反馈的四要素（缺一条就重来问）

不接受"不好看""怪怪的"这类无法定位的反馈。必须给全：

1. **哪个区域**（L1 第几张卡 / L2 哪一页 / 哪个控件）
2. **什么现象**（字挤在一起 / 颜色发灰 / 空隙太大 / 边框太重）
3. **和什么比不对**（跟 P29 视觉稿比 / 跟左边那张卡比 / 跟上一版比）
4. **期望是什么**（哪怕只说"应该更空一点"也算）

### 三、小样先行（防大返工）

**结构性 UI 变更（新页面、新组件、布局重排）必须先出图确认方向，再写代码。**

P1 初版就是因为"5 个模块直接平铺在总控面板"这个结构做错，整轮返工。结构错了，像素再准也是白做。

判断标准：**改动涉及"东西放在哪"→ 先出图；只涉及"颜色字号间距"→ 可以直接改。**

### 四、视觉快照

每轮视觉定稿后，主理人存一张图到 `Docs/QA/evidence/`，命名 `visual_<阶段>_<日期>.png`。下一轮改完拿新图对比，避免"感觉不如上一版"却说不清哪里变了。

### 五、按对象选判据（10-30 新增，因间距问题连改三轮）

| 验收对象 | 用什么判 | 不用什么判 |
|---|---|---|
| **间距 / 坐标 / 尺寸** | **Inspector 数值或运行时诊断日志** | ❌ 截图目测（有 ±10 逻辑偏差） |
| **是否可见 / 是否重叠** | 截图 | — |
| **像不像 / 好不好看** | 主理人 play 视觉 | ❌ 任何数值 |

**教训**：底带间距连改三轮，代码一直是对的（`hits=12/108/204/300` 日志实证），前两轮全靠截图目测判错。**能读数值就别看图，能看图就别算数。**

## 6.10 调研前置规则（10-31 新增，主理人明确要求，防闭门造车）

**"先查、再有思路、再开工、最后检验"——四段缺一段就是闭门造车。**

### 一、什么任务必须先调研

| 类型 | 例子 |
|---|---|
| **对标行业** | "做得像 Grafana 那样""对标主流数字孪生大屏" |
| **新能力** | 时序历史、图表组件、报表导出——项目里从没有过的东西 |
| **交互形态** | 大屏布局、面板收纳、告警呈现方式 |
| **性能方案** | 要上 10 万点数据、要优化 Draw Call |

**纯修 bug、纯改样式、纯接口对接不需要调研。**

### 二、调研的最低要求（达不到就不许开工）

1. **3–5 个真实案例**，写清是谁（Grafana / ThingsBoard / 组态软件 / 具体厂商），不能是"一般来说""主流做法是"
2. **每个案例给两条结论**：**能照搬什么** / **不能照搬什么，为什么**
3. **"不能照搬"必须落到本项目的具体约束上**（内置管线、零图片资源、无外部存储、1000×720、单机断网）
4. 调研结论要能回答：**"别人为什么这么做"**，不只是"别人做了什么"

### 三、验收调研产出的三问

1. 能说出**具体产品名**吗？（说不出 = 编的）
2. 能说出**它为什么这么做**吗？（说不出 = 抄了个形状）
3. 能说出**我们哪里做不到、为什么**吗？（说不出 = 没考虑落地）

**三问缺一，调研不合格，退回重做。**

### 四、四段流程

```
① 调研  →  出案例表 + 可照搬/不可照搬
② 方案  →  基于调研给方案，明确取舍
③ 开工  →  按方案实现
④ 检验  →  对照调研结论验证"是否真的达到了那个标准"
```

**第 ④ 段最容易被跳过**：做完就说"按行业标准做的"，但没人回头核"到底像不像"。**检验时必须拿调研结论逐条对照。**

## 6.7 验收四问（负责人每次必过）

1. 任务包里要求的东西，是不是都给了？
2. 和项目基线（技术栈、色板、协议、命名）一致吗？
3. 有没有"未标注的假设"——它自己填了本该问的信息？
4. 下一环能直接拿这个干活吗？还需要人再解释一遍吗？

四个都过 → **通过**；第 3、4 项不过 → **返工**；只差交接 → **转交**。

# 七、标准工作流转链路

## 7.1 单次任务完整流转

```
【1】用户提出需求
      ↓
【2】负责人在自己对话里：
      · 对齐信息（项目类型 / 时间 / 交付形式 / 验收指标）
      · 需求评审（可行性、成本、收益、冲突）
      · 给出决策结论：通过 / 修改 / 暂缓 / 放弃
      · 拆解任务，判断该交给哪位专家
      ↓
【3】负责人输出【调度任务包】（一次一个，多个则编号+标依赖）
      ↓
【4】用户复制任务包 → 粘贴到目标专家的独立对话
      ↓
【5】专家在自己的对话里执行任务，产出成果
      ↓
【6】用户复制成果 → 粘贴回负责人对话
      ↓
【7】负责人按【验收四问】判定，三选一：
      ├─ 通过 → 归档到项目基线，宣布下一个任务
      ├─ 返工 → 输出【返工调度包】（原格式 + 返工原因 + 逐条修改点）
      │         → 回到【4】
      └─ 转交 → 输出【转交调度包】，把上游成果原文完整放进【附加项目上下文】
                → 回到【4】
      ↓
【8】负责人更新本文档基线（进度、决策、踩坑）
```

## 7.2 典型多专家串联示例（P2 数据监测模块）

```
负责人
  │
  ├─【任务 1/3】→ 见微（UI）：数据监测模块的页面结构与控件规范
  │                    交付：分区布局 + 控件清单 + token 取值
  │
  ├─【任务 2/3】→ 断点（开发）：按见微的规范实现页面 + 接 Registry 数据
  │                    依赖：任务 1 的产出
  │
  └─【任务 3/3】→ 挑刺（QA）：回归测试
                       依赖：任务 2 的产出
                       只报不修；有问题负责人再发返工包给断点
```

## 7.3 三条排序铁律

1. **落笔（文档）必须排最后** —— 它依赖其他专家的交付原文，且原文要一并放进【附加项目上下文】
2. **兜底（打包验收）必须在答辩前 72 小时启动** —— 之后冻结功能，只修 bug
3. **挑刺（回归测试）必须跟在每次修复之后** —— 且它只报不修，修复任务需负责人再发一次包

## 7.4 并行与依赖判断

# 八、文档使用说明

## 8.1 这份文档是什么

**这是本项目的唯一基线材料。**

- 所有新对话里的专项专家，开工前**先读这份文档**，把它当作统一上下文
- 专家在任务中需要的项目信息（技术栈、约束、编号规则、视觉规范、已知坑），**优先从本文档取**，不要自己脑补
- 如果本文档与代码实际行为冲突，**以代码为准，并回写本文档**

### 8.1.1 进度看板：`Docs/STATUS.md`（2026-11-02 新增）

**本文档记「为什么这么定」，`Docs/STATUS.md` 记「现在到哪一步」。两者分工不同，都要看。**

| 文档 | 内容 | 谁维护 | 更新方式 |
|---|---|---|---|
| `Docs/P00_...基线.md`（本文） | 决策、约束、踩坑、裁决、规范 | 负责人手写 | 每次裁决/验收后 |
| `Docs/STATUS.md` | 谁在动、活干完没、代码生效没、哪份文档过期 | **脚本自动生成** | `python tools/status.py` |

**为什么要有它**：2026-11-02 主理人质问「能否实时跟进进度、是否全成员可见」，
当时的事实是**不能**——§4 台账停在 10-29，断点 6 个 `.cs` 全未提交，
见微的返工项只有负责人一人在脑里。进度只活在对话里，会话一压缩就丢。

**看板不写「完成 80%」这种只能人填的数**，理由是：人填的一定滞后、一定美化，
最后变成「看板说 A、实际在做 B」，比没有看板更坏。它只认三样东西：

1. **`grep` 实证** —— 判据清单在 `tools/status_checks.txt`，格式见该文件头注释
2. **文件时间戳** —— 谁动过哪个文件、多久以前
3. **编译产物** —— `.cs` mtime vs `Assembly-CSharp.dll` mtime（§6.8 唯一生效判据）

**三条使用纪律**：

- **派工前跑一次**：确认你要依赖的上游产出「真的在」，不是「他说做完了」
- **验收前跑一次**：`0.5 验收判据自检` 全绿才进 play；有 ❌ 就说明确实没做完
- **发现的未过项，不要自己补** —— 那是派工依据，交回负责人决定派给谁

**给专家的固定话术**（新对话第一条就贴这句，省去每轮解释）：

```
开工前先读 E:\Unity Projects\School-pro\Docs\STATUS.md（进度看板），
再读 E:\Unity Projects\School-pro\Docs\P00_项目总览_交接基线.md（决策与约束）。
两者冲突时：进度以 STATUS.md 为准，决策以 P00 为准。
```
