## 1.2 项目背景与立项目标

**背景**：这是一个以「1 号教学楼」为主场景的校园数字孪生项目，属于毕业设计 / 竞赛类交付。前期已完成场景搭建、点位体系、设备模型、数据链路、电力回路、机房主脑控制等底层能力，但**上层 UI 长期野蛮生长**——十几个面板各写各的，风格不统一、层级混乱、数据面板不专业。

**立项目标（P28 起）**：

1. 把分散的「数据监测 + 设备管理 + 电力管理 + 告警中心 + 数据统计」收敛进**一个统一的校园管理系统**
2. 交互形态参照《异环》(Neverness to Everness) 的**收纳式面板**：固定入口按钮 → 右侧滑出总控面板 → 点功能入口 → 进子功能面板
3. 建立**统一的科技风视觉体系**，消除风格混乱，后续新增面板沿用同一套规范
4. 设备编号规范化为「场景-位置-设备类型-序号」，例如 `1号教学楼-2F-201-灯具-001`，**确保无设备遗漏**

**原始诉求原文要点（不可偏离）**：

> 我点击总控按钮，弹出总控面板，在总控面板里点击**管理系统**按钮，弹出**管理系统面板**，管理系统分为多个功能模块展开设计……

即**三级结构**：`总控面板 → 校园管理系统 → 5 个功能模块`。这一点在 P1 初版被做错（5 模块直接平铺在总控面板），已返工修正。

## 1.5 核心价值与创新点

1. **3D 场景与数据面板双向联动** —— 点 3D 设备 → 面板更新；点面板列表 → 相机聚焦该设备。这是数字孪生区别于普通看板的核心，也是本项目的卖点。
2. **完整的命令回执链路** —— 不是"点一下改个颜色"，而是 `下发 → 回执 → 执行 → 回读` 四段超时校验（1s/3s/3s/5s），失败有明确拒绝原因。答辩时这是最能讲的技术深度。
3. **零美术资源 UI 体系** —— 所有面板、图标、圆角、渐变全部代码程序化生成（`TwinRoundedRect` 自绘顶点），不依赖任何图片素材。换肤改 token 即可，不会出现"找不到图"。
4. **收纳式单抽屉 + 页栈** —— 区别于常见的"多浮窗并列"，从架构上消灭了"面板互相压、不知道该看哪个"的问题。
5. **分级电力控制** —— 楼栋 → 楼层 → 房间三级回路，支持整层停电、单房间独立停电，并实时计算影响设备数。

### A. Unity 编辑器 / 编译类

| # | 坑 | 现象 | 根因与解法 |
|---|---|---|---|
| A1 | **场景序列化值覆盖字段默认值** | 把 `_toggleKey = KeyCode.F4` 改成 `None`，快捷键照样生效 | 场景里已挂载的实例，其序列化值会覆盖代码默认值。**必须在 `Awake()` 里硬写**。而运行时 `AddComponent` 的组件改默认值才有效——**同一件事，两类组件两种做法** |
| A2 | **Safe Mode 下 Unity 不编译** | 脚本报错后修好了，日志不动、控制台还是旧错误 | 进入 Safe Mode 后需**手动点「退出安全模式」或重启编辑器**，否则永远不重新编译 |
| A3 | **失焦 + Auto Refresh 关闭时不自动编译** | 改完代码等 10 分钟，`Editor.log` mtime 不涨 | 判断是否已编译：看 `Begin MonoManager ReloadAssembly` 轮次是否增加、看 `Library/ScriptAssemblies/Assembly-CSharp.dll` 时间戳是否比脚本新。**日志 mtime 不涨 = 没编译，不是"通过"** |
| A4 | **静态类不能直接调 `FindObjectOfType`** | `CS0103: The name 'FindObjectOfType' does not exist` | `FindObjectOfType` / `Destroy` / `Instantiate` 都是 `UnityEngine.Object` 的静态成员，`static class` 不继承 `Object`，必须写 `UnityEngine.Object.FindObjectOfType<T>()` |
| A5 | **类型名扫描要加词边界** | 静态审计把 `TwinStatusColor` 误判成 `TwinStatus` | 查类型用 `\bTypeName\b`，不能裸子串匹配 |
| A6 | **命名空间被拆成两半** | 10 个 `CS0246` 同一个原因 | `TwinStatus` / `TwinValue` / `TwinSample` / `DataQuality` 在 **`SchoolTwin.Core`**；`TwinAnchor` / `TwinRuntime` / `TwinCircuit` / `TwinControlScope` 在 **`SchoolTwin.Twin`**。凡是用到"状态或数值"，两个 `using` 都要有 |
| A7 | **数 `m_Name` 覆写数 ≠ 数实例数** | 路灯数出来 29 盏，实际 100 盏 | 未改名的预制体实例**不产生 `m_Name` 覆写**。正确做法：按 `m_SourcePrefab` 行统计 |
| A8 | **编辑模式不跑 `Update`，动画停在起点** | 给 L2 页面截图，内容区一片空、Tab 全透明，像是"没建出来" | 页推入动画由 `Update` 驱动，编辑模式不执行 `Update`，alpha 永远停在 0。**截图前把动画状态强制设为完成态**，或在 `OnShow` 里判断 `!Application.isPlaying` 直接置终态 |
| A9 | **batchmode 不能替代 GUI 验收** | 想用 batchmode 跑采集器出运行时截图，工程加载完（15.5s）后无任何输出，采集器零触发 | batchmode **不跑 `EditorApplication.update` 循环**，`[InitializeOnLoad]` 回调没机会执行。且本项目是 **Overlay Canvas，不经过相机**，`Camera.Render → RenderTexture` 抓不到，只能 `ScreenCapture` 读真实窗口。**结论：GUI 类验收必须有真实窗口，没有捷径，别在 batchmode 上反复尝试** |
| A10 | **编辑器异常退出留下 `Temp/UnityLockfile`** | 再启 GUI 时进程活着，但 `-logFile` 指定的日志从不创建，看起来像"启动失败" | 先 `ls Temp/UnityLockfile`，有就先删再启。清了锁仍无日志则不是锁的问题，别再往这个方向查 |

### B. UGUI / 代码类

| # | 坑 | 现象 | 根因与解法 |
|---|---|---|---|
| B1 | **`r.materials` 访问后 `r.sharedMaterials` 返回的是克隆体** | 角色变紫色（材质丢失），且每次面板开关都闪一下 | 想"还原"时写 `r.materials = r.sharedMaterials; Destroy(inst)`，实际把克隆体赋回去又销毁了。**必须先存 `sharedMaterials` 再取 `materials`**；恢复时先 `r.sharedMaterials = origin` 再销毁克隆体 |
| B2 | **构建时机早于布局** | 图标整组溢出抽屉，跑到 3D 场景上（`originX ≈ -144`） | `BuildModules()` 在 `_stack.Push()` 之前调用，而拉伸在 Push 里做。那一刻页面还是 RectTransform 默认尺寸（≈100）。**修法：布局改固定尺寸绝对定位，不量父节点；内容构建挪到 `OnShow()`** |

| B6 | **全局 `Hide()` 让多驱动器互相打** | 交互按钮闪烁、丢失 | 两个驱动器各自在自己 `Update` 里 `Show/Hide`，Unity 不保证顺序。**修法：`Hide()` 只表示"我这边不需要"，裁决放 `LateUpdate`——本帧有任一 `Show` 就显示** |
| B7 | **每帧无条件写 `Text.text` / `SetActive`** | Canvas 每帧重建，掉帧 + 闪烁 | 改成"变了才写" |
| B8 | **抽屉宽度有动画时不能量宽度** | 描述文字永远窄 220 | 420→640 有 200ms 动画，`OnShow` 那一刻量到的是 420。**用左右拉伸（anchor 0→1）而不是固定宽度** |
| B9 | **`WithAlpha` 是"赋值"不是"乘算"** | 禁用按钮的描边比正常态亮 30 倍，禁用反而最显眼 | `WithAlpha(c,a)` 内部是 `c.a = a`。对**已标定**的 token 再叠一次（`WithAlpha(Border, 0.35)`，Border 本是白@0.006）得到白@0.35，不是 0.002。**已标定 token 禁止二次叠 alpha**，要更淡就新增 token；改 token 前 `grep -rn "WithAlpha(TwinTheme\."` 全量审一遍 |
| B10 | **同一个 GameObject 上两个 Graphic 会互相顶掉** | 给面板根节点加网格 Image，背景或网格消失一个 | UGUI 一个物体只有一个 `CanvasRenderer`。**网格必须挂独立子节点**（`_Grid`），描边同理（`_GlowOuter` / `_GlowInner`） |
| B11 | **`ApplyGrid` 不抢 sibling 顺序，晚建的盖住早建的** | 先建头部再铺网格 → 网格线压在文字上 | 为了在"背景也是子节点"的容器里不沉到背景下面，它**刻意不调 `SetAsFirstSibling`**，按调用顺序入栈。**固定构建顺序：背景 → ApplyGrid → 内容** |
| B12 | **双层描边不外扩，外层会吃掉内层** | 双层发光只剩一层，1px 内亮边消失 | 3px 外描边居中绘制时向内占 1.5px，正好盖住 1px 内描边。**外层矩形外扩 3px**（`offsetMin -= (3,3)`、`offsetMax += (3,3)`） |
| B13 | **legacy `Text.fontSize` 是 int，没有半档** | 写 11.5 / 9.5 编译通过，显示被取整，与设计稿对不上 | `UnityEngine.UI.Text.fontSize` 为 `int`。**字号只取整数档**；本项目定为 9/11/13/15/17/22/28（9 仅用于时间戳/角标，不进正文） |
| B14 | **"内容被压住"的根因是余量不足 + 没有裁剪兜底，不是容器高度算错** | L1 第 4 行、L2 异常第 3 行被工具行压住，第一直觉判"容器高度算错" | 实测 `page.rect.height` **精确等于 544**，容器层完全正确。真因：旧 L1 内容下沿距内容底只剩 18px（投影仪缩放下就是"贴着"），且 `_content` 没有 `RectMask2D` 兜底。**先量实际值再判断；按直觉改行高会把本来正确的东西改坏** |

### D. 排查方法论（从踩坑里提炼，可复用）

1. 遇到"某块地方不对劲"，**先问"点得到吗"**，再查材质。点不到就已经指向"没有几何"。
2. **材质断裂只查"槽为空"会漏掉一类**：材质完好但 `Renderer.enabled=false` / GameObject 未激活——看起来和材质丢了完全一样。体检脚本要覆盖这一节。
3. 报"某处坏了"时，**先去未改动的旧工程里看一眼**。P26 的黑墙最后就是靠这个定性的——旧工程里也一样黑，说明是资产原生设计。
4. **子症状通过 ≠ 整体正确**。看到 `page.rect.height = 544` 就判"容器对了"，没意识到 544 同时是"抽屉比画布高 54px"的证据——**每个通过的数据都要再问一句"它还能被什么解释"**。判断方向也要反过来一次：不是问"画布该多大"，是先量"画布现在多大"。
5. **主理人说"不对"就是不对，不要用数值去驳**。数值只能证明"我测的那一项没错"，证明不了"他看到的那一项没错"。用数值反驳视觉，会把一个问题拖成三个。
6. **判据不完整时，不要下"没有 X"的绝对结论**。看到"点不中"就判"没有几何"，是因为判据只有三条、缺了「合并网格」这一种。**绝对结论（没有了 / 不存在 / 不可能）必须先有一次独立验证**（隔离显示、洋红扫描、换个角度看），否则一次误判会连带下游白干一轮。

> **编号说明**：本节 A/B/C 是「技术坑」，D 是「排查方法论」用有序列表；`§3.4 已知待修缺陷` 已占用 `D1/D2/D3` 编号，**本节不得再用 D 编号**，避免与缺陷台账混淆。

### E. 流程与验收纪律（不属于技术坑，但会直接造成返工）

| # | 纪律 | 现象 | 根因与解法 |
|---|---|---|---|
| E1 | **空场景截图必须标注"样例数据"** | 截图里 153/151/2 看着像真数据，验收时被当成 bug 追 | 无运行时数据时用反射注入样例值，**必须在图注/日志里标明"样例"**，并写清真实值由哪个方法采集 |

# 六、团队协作规则

> 这一章是**运行机制**，所有专家必须遵守。规则优先级高于各专家自身偏好。

## 6.1 架构模式

**一个对话对应一位专家。专家之间无法直接通信，也没有共享内存。**

```
┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│  负责人对话   │   │  UI 专家对话  │   │  开发对话     │
│   （定盘）    │   │   （见微）    │   │  （断点）     │
└──────┬───────┘   └──────┬───────┘   └──────┬───────┘
       │                  │                  │
       └──────────┬───────┴──────────────────┘
                  │
            ┌────────────────┐
            │ 老大（项目主理人）│  ← 唯一中转人 + 现场 play 验收
            └────────────────┘
```

## 6.2 调度权限

| 角色 | 能否发起调度 | 说明 |
|---|---|---|
| **Unity 项目负责人（定盘）** | ✅ **唯一有权** | 只有它能生成【调度任务包】 |
| **项目主理人（老大）** | ❌ 不能自行发起，✅ 可提请 | 负责中转与现场验证；发现新问题时**描述现象交负责人判定**，由负责人出包，不自行指定专家与做法 |
| 其余所有专项专家 | ❌ 不能 | 只能接收任务、产出成果，**不能调度其他人**，也不能要求用户去找别的专家 |

## 6.3 中转链路（固定四步）

```
① 负责人在自己对话里输出【调度任务包】
        ↓ 用户人工复制
② 粘贴到目标专家的独立对话里下发
        ↓ 专家工作
③ 专家产出成果
        ↓ 用户人工复制
④ 粘贴回负责人对话，由负责人验收
```

**没有捷径**。负责人不能"直接喊话"给专家，专家也不能"直接交付"给负责人。

## 6.4 调度包固定格式（字段名不得改动）

```
=====调度任务包=====
目标专家：【专家名称】
```

**使用纪律**：

- **一次只发一个包**。需要并行时连续输出多个包，每个包前标注 `【任务 1/3】`、`【任务 2/3】` 及依赖关系
- **【附加项目上下文】不能空**。至少写清：项目类型、运行平台、目标风格、本任务依赖的上游产出
- **【交付物要求】要可验收**。写清结构、是否用表格、是否要具体数值，不能写"给个方案"
- 包外可以有说明，**包内五个字段必须齐全**

## 6.5 冲突处理规则

专项专家的产出出现**冲突、风格不统一、接口对不上**时，**全部提交负责人裁决对齐**，不得由专家之间自行协商，也不得把选择题原样丢回给用户。

裁决输出格式：

> **冲突点**：{谁和谁在哪一项上不一致，具体到数值或定义}
> **裁决**：采用 {哪一方} 的 {哪一项}，值为 {具体值}
> **理由**：{为什么这样定}
> **影响**：{哪些已完成的产出需要同步修改，需要谁改}

裁决后**必须同步更新本文档基线**，避免同一个冲突反复出现。

## 6.6 权责边界重申

- 各专家**禁止越权**，不跨领域做不属于自己职责的工作
- 负责人**禁止代产**：不自己写 UI 方案、不自己写业务代码、不自己做测试用例
- 专家**禁止扩需求**：任务包里没写的，不要"顺便加一下"
- 所有专家**禁止编造未实现的功能**

## 6.8 并发写入纪律（10-29 新增，优先级等同铁律）

**所有专家共用同一台机器、同一个工程目录。这不是"多人协作"，是"多人在同一个工作区里写同一批文件"。** git 在这里不提供任何保护——冲突不是 merge conflict，是**后写覆盖先写**，被覆盖的一方不会收到任何提示。

### 资源分级

| 资源 | 谁能写 | 并行性 |
|---|---|---|
| `Assets/**/*.cs`（代码） | **只有断点** | **独占** |
| `Assets/**/*.unity`（场景） | 削面 / 打光 / 断点 | **独占，同一时刻只能一人** |
| `Assets/**/*.mat` `.asset` `.prefab`（资产） | 削面 / 打光 | **独占** |
| `Docs/**`（文档） | 见微 / 心跳 / 挑刺 / 落笔 | **可并行**，不碰 Unity |
| Unity 编辑器（play / 编译） | 主理人 / 当前写入者 | **独占** |

### 三条硬规则

1. **同一时刻只能有一个"写入者"**。断点改代码期间，削面不得改模型、打光不得改光照、主理人不得 play。
2. **play 期间任何人不得改 `Assets/` 下文件**。Unity 在 play 模式下**不重新编译**，改了也不生效，写入者会误判"我的改动没起作用"，进而推翻本来正确的实现。
3. **代码生效的判定标准**（不是"我改完了"，是下面这条）：

```
最后一个 .cs 的 mtime  <  Library/ScriptAssemblies/Assembly-CSharp.dll 的 mtime
```

不满足 = 没编译 = 没生效。**写入者宣布"改完"之前必须自己核一遍这个时间戳对比**，主理人验收前也核一遍。

### 交接握手（写入者 → 主理人）

写入者交付时必须附一句：**"最后一次改 `xxx.cs` 是 HH:MM，dll 编译于 HH:MM，已生效/未生效"**。缺这句的交付不验收。

### GUI 验收交接（10-29 新增，因实际卡住一次）

编辑器是独占资源，而 GUI 类验收（Play / 截图 / 手点）**必须占用它**。写入者和主理人抢同一个编辑器会互相卡死，所以交接规则必须写死：

| 阶段 | 谁做 | 规则 |
|---|---|---|
| 写代码 → 编译生效 | 写入者 | 自己按 Ctrl+R 或 batchmode 编译，核 dll 时间戳，然后**立即交还编辑器** |
| GUI 验收（Play / 截图 / 手点） | **只有主理人（老大）** | 写入者交付"已生效"后不再占用编辑器 |
| 写入者想验证画面 | — | **禁止**。写入者不得启动 Unity 编辑器进程，也不得用 batchmode 试图替代 GUI 验收（见 §1.6 A9） |

**写入者的交付边界到"已生效"为止，画面层结论由主理人产出。** 这不是能力问题，是资源归属问题——写入者反复尝试启动 GUI 只会浪费时间、留下锁文件残留、并让工程处于不确定状态。

**定性口径**：写入者交付「已生效 + 待截图」时，验收处置写**「只差交接」**，不写「返工」。返工指实现有错，交接指流程没走完——两者不能混，否则会陷入"打回重做还是做不出来"的循环。

## 6.9 验收判定规则（10-29 新增）

### 一、验收 = 量化 + 视觉，两栏都要过

| 栏 | 谁判 | 判据 | 不过怎么办 |
|---|---|---|---|
| **量化栏** | 负责人 | 规格里写明的数值、坐标、grep 结果、恒等式 | 返工，退给实现者 |
| **视觉栏** | **主理人（老大）** | play 后眼睛看到的满不满意 | **不通过**，退给见微重出规格或断点重做 |

**量化全过 + 视觉不满意 = 不通过。** 数字只能证明"没错"，不能证明"好看"。

### 二、视觉反馈的四要素（缺一条就重来问）

不接受"不好看""怪怪的"这类无法定位的反馈。必须给全：

1. **哪个区域**（L1 第几张卡 / L2 哪一页 / 哪个控件）
2. **什么现象**（字挤在一起 / 颜色发灰 / 空隙太大 / 边框太重）
3. **和什么比不对**（跟 P29 视觉稿比 / 跟左边那张卡比 / 跟上一版比）
4. **期望是什么**（哪怕只说"应该更空一点"也算）

### 三、小样先行（防大返工）

**结构性 UI 变更（新页面、新组件、布局重排）必须先出图确认方向，再写代码。**

P1 初版就是因为"5 个模块直接平铺在总控面板"这个结构做错，整轮返工。结构错了，像素再准也是白做。

判断标准：**改动涉及"东西放在哪"→ 先出图；只涉及"颜色字号间距"→ 可以直接改。**

### 四、视觉快照

每轮视觉定稿后，主理人存一张图到 `Docs/QA/evidence/`，命名 `visual_<阶段>_<日期>.png`。下一轮改完拿新图对比，避免"感觉不如上一版"却说不清哪里变了。

## 6.7 验收四问（负责人每次必过）

1. 任务包里要求的东西，是不是都给了？
2. 和项目基线（技术栈、色板、协议、命名）一致吗？
3. 有没有"未标注的假设"——它自己填了本该问的信息？
4. 下一环能直接拿这个干活吗？还需要人再解释一遍吗？

四个都过 → **通过**；第 3、4 项不过 → **返工**；只差交接 → **转交**。

# 七、标准工作流转链路

## 7.1 单次任务完整流转

```
【1】用户提出需求
      ↓
【2】负责人在自己对话里：
      · 对齐信息（项目类型 / 时间 / 交付形式 / 验收指标）
      · 需求评审（可行性、成本、收益、冲突）
      · 给出决策结论：通过 / 修改 / 暂缓 / 放弃
      · 拆解任务，判断该交给哪位专家
      ↓
【3】负责人输出【调度任务包】（一次一个，多个则编号+标依赖）
      ↓
【4】用户复制任务包 → 粘贴到目标专家的独立对话
      ↓
【5】专家在自己的对话里执行任务，产出成果
      ↓
【6】用户复制成果 → 粘贴回负责人对话
      ↓
【7】负责人按【验收四问】判定，三选一：
      ├─ 通过 → 归档到项目基线，宣布下一个任务
      ├─ 返工 → 输出【返工调度包】（原格式 + 返工原因 + 逐条修改点）
      │         → 回到【4】
      └─ 转交 → 输出【转交调度包】，把上游成果原文完整放进【附加项目上下文】
                → 回到【4】
      ↓
【8】负责人更新本文档基线（进度、决策、踩坑）
```

## 7.2 典型多专家串联示例（P2 数据监测模块）

```
负责人
  │
  ├─【任务 1/3】→ 见微（UI）：数据监测模块的页面结构与控件规范
  │                    交付：分区布局 + 控件清单 + token 取值
  │
  ├─【任务 2/3】→ 断点（开发）：按见微的规范实现页面 + 接 Registry 数据
  │                    依赖：任务 1 的产出
  │
  └─【任务 3/3】→ 挑刺（QA）：回归测试
                       依赖：任务 2 的产出
                       只报不修；有问题负责人再发返工包给断点
```

## 7.3 三条排序铁律

1. **落笔（文档）必须排最后** —— 它依赖其他专家的交付原文，且原文要一并放进【附加项目上下文】
2. **兜底（打包验收）必须在答辩前 72 小时启动** —— 之后冻结功能，只修 bug
3. **挑刺（回归测试）必须跟在每次修复之后** —— 且它只报不修，修复任务需负责人再发一次包

## 7.4 并行与依赖判断

| 情况 | 做法 |
|---|---|
| 两个任务无依赖（如"模型减面"和"UI 规范"） | 连续输出两个包，标注可并行 |
| 有依赖（如"开发"依赖"UI 规范"） | 标注 `【任务 2/3】依赖任务 1 的色板产出`，按序下发 |
| 需要同一专家做两件事 | 合成一个包，避免同一对话被反复切换上下文 |

# 八、文档使用说明

## 8.1 这份文档是什么

**这是本项目的唯一基线材料。**

- 所有新对话里的专项专家，开工前**先读这份文档**，把它当作统一上下文
- 专家在任务中需要的项目信息（技术栈、约束、编号规则、视觉规范、已知坑），**优先从本文档取**，不要自己脑补
- 如果本文档与代码实际行为冲突，**以代码为准，并回写本文档**

## 8.2 怎么用

| 场景 | 做法 |
|---|---|
| **新开一个专家对话** | 把本文档完整粘贴进去，作为第一条消息，再加一句"你是 {专家名}，请基于以上项目基线等待任务" |
| **收到调度任务包** | 任务包里的【附加项目上下文】是对本文档的**局部摘要**，冲突时以本文档为准 |
| **不确定某个约定** | 回本文档查：§2 技术栈、§3.5 约束、§3.6 UI 层级、§1.6 踩坑日志 |
| **发现文档有错/过期** | 不要自行修改，**报告给负责人**，由负责人统一更新 |
