## 一、A 类：写了分支，但没人调用

### 坑 1：烟感的 `case "Alarm"` 是死代码

**现象**（主理人截图 + 一句话）：

> 「处于关闭状态，数据波动还比较频繁」

截图里那条：`走廊 烟感 浓度 27.27 obs/m 警告`。

而且更难受的是——**烟感是只读设备，界面上没有按钮**。用户看着它报警，什么都做不了。

**我当时的判断（错的）**：

上一轮我已经发现了这个问题，并且"修好"了：给 `SeedOne` 加了一个 `case "Alarm"` 分支，写 `SetState(twinId, "Smoke", 0f)`。逻辑上完全正确 —— 洁净空气读数接近 0，散射式烟感大约 0.0~0.5 obs/m。

**真相**：

`SeedOne` 一共只被**三条**路径调用，我一条都没对上：

```
① SeedInitialState() → TwinControlScope.All     ← 烟感是只读设备，不在白名单
② SeedInitialState() → SeedOnlyIds              ← 原来只有教师机一条
③ SeedInitialState() → HeatSeedIds              ← 只写 ValveOpen，不碰 Smoke
```

给一个**永远不会被调用的方法**加分支，等于写了一行注释。

**修法**：

```csharp
private static readonly string[] SeedOnlyIds =
{
    "ClassTeachers/PC/Room_01",
    "Corridor1/Alarm/Fire_01",     // ← 真正让烟感被播种的那一行
};
```

**教训**：

> **`case` 分支存在 ≠ 播种生效。**
> 「写了分支」和「谁调这个分支」是**两件事**，必须分开验证。
>
> 判据也要跟着改：不能只断言 `case "Alarm":` 存在（那是我上一版判据，它一直绿着），
> 必须**锁 ID 在播种表里**。见 `P27-46`（断言 `Corridor1/Alarm/Fire_01` 出现在 `SeedOnlyIds`）。

**这一类怎么预防**：新增"只读设备要压状态"时，先问一句「它走哪条路径进来？」。
答不出来，就是还没做完。

### 坑 2：暖气的 9 台从来没被压过

同一个病灶的另一半。9 台暖气**一个都不在** `TwinControlScope.Ids` 白名单里（没有可视化部件，点了看不出反应），也从来没进过 `SeedOnlyIds`。

于是它们的 `ValveOpen` 自由跑正弦波，在 0~100% 之间上下摆。

**后果不是"数字在跳"这么轻**：暖气阀门的正常区是 **0~100（全量程）**，所以它**永远不会报警** —— 但它一直在动。一个"永远正常但一直抖动"的只读点位，是"假数据"最隐蔽的形态：没有任何告警会揭发它，只有人盯着看才会觉得不对。

**修法**：`HeatSeedIds` 表 + 播种 `ValveOpen = 45`（居中的"半开"状态，远离两端，视觉上是一条平稳直线）。

**教训**：

> 「不报警」不等于「数据是真的」。
> 全量程正常带的指标（`ValveOpen`、`OnCount`、`Ring`、`Open`）**在告警层面永远是绿的**，
> 它们只能靠"状态有确定值"来证明自己是真的 —— 而这件事只能靠播种。

## 二、B 类：物理模型不能靠"读起来对"

这一类是本轮最值钱的。**四个错误全部是实算算出来的，没有一个能靠读代码发现。**

### 坑 3：供暖季室温只有 15.5~16.2°C

**我的第一版设计**：

```csharp
// ① 热惯性 → 天气项
double indoors = dayMean + WeatherBiasC(w) + inAmp * Math.Cos(phase);
// ② 室内得热
indoors += OccupancyGainC(hour);
// ③ 供暖钳制：把室温拉回 20°C 附近
if (ResolveHeatingSeason())
    indoors = HeatingTargetC + (indoors - HeatingTargetC) * HeatingStiffness;  // 0.2
```

读起来完全合理：算天气 → 加得热 → 暖气收口。

**实算结果**：1 月（室外 −4~0°C）室内 **15.5~16.2°C**。供暖季的教室 16°C —— 这是主理人说的"不符合现实"的典型。

**根因**：**把「得热」也一起钳掉了。**

`HeatingStiffness = 0.2` 的意思是"残留 20%"，它作用在整个 `indoors` 上。而 `indoors` 里已经包含了 `OccupancyGainC`（满课 +1.2°C）。

数学上：
```
(20 + 1.2 - 20) × 0.2 = 0.24     ← 1.2°C 的得热被压成了 0.24°C
```

**物理上正确的对应关系**：

| 项 | 暖气对它的作用 |
|---|---|
| 室外渗入的冷（天气项） | **对抗它** —— 这是暖气存在的理由 |
| 人 / 电脑 / 照明的得热 | **既不加也不减** —— 那是房间内部产热 |

所以钳制**必须在得热之前**：

```csharp
double indoors = dayMean + WeatherBiasC(w) + inAmp * Math.Cos(phase);   // ① 天气项
if (ResolveHeatingSeason())                                            // ② 只压天气项
    indoors = HeatingTargetC + (indoors - HeatingTargetC) * HeatingStiffness;
indoors += OccupancyGainC(hour);                                       // ③ 得热全额保留
```

`HeatingStiffness` 同时从 0.2 改到 **0.04**（残余 4%，留给"靠窗位置偏低"和教室之间的差异）。

**修后实测**：1 月 **19.3~20.3°C**，日内变幅 **1.0°C** —— 这才是真实暖气教室：一整天几乎不动。

**教训**：

> **钳制类操作的顺序，等于「它在物理上对抗什么」的声明。**
> 想不清楚"它压的是哪一项"，就一定压错。
>
> 而且这条**读代码绝对发现不了** —— 三步都是合法的数学运算，没有一行报错。

### 坑 4：7 月湿度算出 −3 %RH（负数）

**我的第一版**：

```csharp
return 52.0 - (indoor - 20.0) * 4.5;
```

意图："与室温反相关"。7 月室温 30.5°C → `52 - 10.5×4.5 = 52 - 47.25 = 4.75`…… 实际算出来是负数。

**根本错误**：相对湿度**不是温度的线性函数**。

它是「含湿量 ÷ 饱和含湿量」，而饱和含湿量随温度**指数增长**：

| 温度 | 饱和含湿量（g/m³） |
|---|---|
| 10°C | 9.4 |
| 20°C | 17.3 |
| 30°C | 30.3 |

跨度 10°C，分母就变了 75%。线性式在小范围内近似，跨 10°C 必崩。

**修法**：直接按物理公式算，用 Magnus/Tetens：

```csharp
public static double SatVaporDensity(double tempC)
{
    double es = 6.112 * Math.Exp(17.67 * tempC / (tempC + 243.5));   // 饱和水汽压 hPa
    return 216.7 * es / (tempC + 273.15);                            // 理想气体 → g/m³
}
```

然后五个环节：室外含湿量 → 渗入 → 产湿 → 物理上下限 → 除以**室内温度**的饱和含湿量。

**顺便得到一个白捡的好处**：「与室温反相关」在这个结构里是**自洽的**，不是硬凑的相位 —— 同一份含湿量除以一个更大的分母。天气变冷、室温一降，湿度自己就往上走，不需要额外调参。

**教训**：

> 凡是"百分比"类的物理量（RH、效率、占空比），先问一句：
> **它是某个比值吗？分母随什么变？**
> 如果分母不是常数，线性外推就是错的。

### 坑 5：7 月供水温度 22~33°C（比室温还低）

**第一版**：直接套质调节曲线

```csharp
supply = 75.0 + (outdoor + 10.0) * (-1.2);     // 室外 −10°C → 75°C；+15°C → 45°C
```

7 月室外 29°C → `75 + 39×(-1.2) = 28.2°C`。**供水 28°C，比室温还低** —— 暖气不供热，反而在制冷。

**根因**：质调节曲线**只在供暖季有定义**。7 月锅炉根本没开采暖循环，这条公式的适用域不包含夏天。

**修法**：分运行状态。

```csharp
if (TwinClimate.HeatingSeasonOn)
    supply = 75.0 + (outdoor + 10.0) * (-1.2);   // 采暖季：质调节
else
    supply = 48.0;                               // 非采暖季：生活热水定温
```

**教训**：

> **每条经验公式都有适用域，而代码不会替你检查。**
> 写 `f(outdoor)` 之前先问："这个关系在哪一段外推会失效？"
> 尤其当输出量是**温度 / 压力 / 流量**这类有物理下限的量 —— 越界立刻露馅。

### 坑 6：12:00 室温瞬跳 0.8°C

**第一版**：

```csharp
if (hour < 12.0) return 1.2;
if (hour < 13.5) return 0.4;
return 1.1;
```

纯阶跃。后果：**12:00:00 那一刻室温瞬间掉 0.8°C**。一个 50 吨的建筑不可能这样。

**最坏的一点不是代码**，是注释。原注释写着：

> 「分段 + 前端的小过渡（±0.1）足够」

**代码里根本没有过渡。** 注释描述了不存在的实现 —— 比没有注释更坏，因为它会让下一个人相信"这里已经处理过了"，从而跳过检查。

**修法**：时刻表 + smoothstep 插值（两端切线为 0，段边界不留折角）。

```csharp
private static readonly double[] GainHours  = { 0, 6, 7, 8.5, 11.5, 12.5, 13, 14, 17, 18, 20, 24 };
private static readonly double[] GainValues = { 0.2, 0.2, 0.5, 1.2, 1.2, 0.4, 0.4, 1.1, 1.1, 0.6, 0.2, 0.2 };
// 段内：
t = t * t * (3.0 - 2.0 * t);
```

实测最大变化速率约 **1.1°C/小时**，与真实房间（墙体蓄热决定）同一量级。

**教训**：

> **注释描述的实现，必须和代码是同一件事。**
> 写"已经处理过了"之前，回头看一眼那一行到底在不在。
> 这轮我犯过一次，见坑 12（`BootElapsedSeconds` 的理由写错了），同一个毛病。

## 三、C 类：参数拍了但没实算

### 坑 7：湿度下限 5.5，余量只剩 0.09%RH

这个坑是**收工复核**时才发现的 —— 前面六个坑修完，主理人已经说"验收通过"了，是我不放心又跑了一遍全年实算。

**当时的状况**：

`MoistureFloorGm3 = 5.5`（建筑蓄湿下限）。它本身是对的，物理上有据：北方冬季室外可能只有 2~3 g/m³ 含湿量，而室内实测很少低于 30%RH@20°C（≈ 5.2 g/m³）。

**实算出的问题**：

| 项 | 值 |
|---|---|
| 11 月晴天最干时刻 RH | 31.3% |
| 叠上 `GenerateHumidity` 的点位差 −1.2%RH | **30.09** |
| `Humidity.WarnLow` | **30** |
| **余量** | **0.09** |

**为什么 0.09 不能接受**：它撑不住两件事。

1. **天气系统上线后会立刻失守** —— 华北春季沙尘天室外 RH 可到 30%，比现在假设的"晴 38%"更干。
2. **阈值口径一旦收紧**（比如按国标 GB/T 18883 改到 40%），这段会整体失守。

而失守的**方向极其误导**：湿度低是**天气**的表现，但界面上看起来像"传感器故障"。

**修法**：5.5 → **6.5**。

| 下限 | 最干时刻 | 点位差后 | 余量 |
|---|---|---|---|
| 5.5 | 31.3% | 30.09 | **0.09** |
| 6.5 | 36.4% | 35.18 | **5.18** |

物理含义仍站得住：6.5 g/m³ @20°C ≈ **37%RH**，正是北方供暖季未加湿房间的典型值（有暖气、没加湿器，实测 30~40%）。

**教训**：

> **"参数看着合理"和"参数留了余量"是两件事。**
> 凡是贴着阈值的数，必须跑一遍**最不利组合**（最干的天气 × 最不利的点位 × 最低的时刻），
> 看余量够不够吃掉未来的变更。
>
> 这轮的实算脚本一共跑了 **192 组**（12 月 × 4 天气 × 每 15 分钟）——正是它把这 0.09 抓出来的。

### 坑 8：`_heatingSeason = true` 导致 7 月也钳到 20°C

**第一版**：

```csharp
private static bool _heatingSeason = true;
```

一个 Bool，默认永远供暖。7 月室温会被暖气钳到 20°C，而夏天真实的教室是 28~31°C。

**这条错误的性质**：它不是"参数没调好"，是**把"从来没有"写成了"永远存在"**。

**修法**：三态。

```csharp
private static volatile int _heatingMode = HeatingAuto;   // -1 自动 / 0 强制关 / 1 强制开
private static bool ResolveHeatingSeason()
{
    if (_heatingMode == HeatingOn) return true;
    if (_heatingMode == HeatingOff) return false;
    return IsHeatingMonth(DateTime.Now.Month);            // 11/12/1/2/3 月
}
```

**为什么留三态而不是只按月份**：南方学校 / 夏季答辩演示都需要"强制不供暖"。
`SetHeatingSeason(null)` 恢复自动。

**教训**：

> **凡是"季节 / 时段 / 运行模式"这类状态，默认值必须是"按现实判定"，不能是某个具体值。**
> `true` / `false` 都是一种断言；`Auto` 才是"我不知道，让规则决定"。

## 四、D 类：改代码把注释弄坏

### 坑 9：`<summary>` 开标签被插入切断（编译器不报）

**现象**：收工复核时顺手通读 `MockSignalGenerator`，在 `IsSmooth` 上方看到：

```csharp
public static void ResetAllBootClocks()
{
    BootStart.Clear();
}
///                                    ← 悬空的 ///
/// 调用方（`MockDataSource` / `MqttLoopbackPublisher`）在生成值之后会加
/// `±span × noiseRatio` 的均匀噪声……
/// </summary>                         ← 孤立的收尾标签
public static bool IsSmooth(TwinMetricDefinition metric)
```

`<summary>` 开标签不见了。

**根因**：上一轮我把 `ResetBootClock` **插在** `IsSmooth` 的 `<summary>` 前面 —— 插入点是"`}` 之后、`<summary>` 之前"这种锚点选择，结果切断了注释块。

**最坏的点**：**编译器不报。** 注释不参与编译，所以：
- 编译通过
- 逻辑正确
- 单元测试（如果有）全绿
- 只有人读文件时才会发现

而本项目**大量依赖注释讲"为什么"**（这份文档本身就是证明）。注释结构坏了，等于把最贵的东西弄坏了。

**修法**：补回开标签。并加了一条判据 `P27-60`。

**这条判据我写错了三版**，过程值得记：

| 版本 | 模式 | 结果 |
|---|---|---|
| 1 | `这个指标的数据是否需要**跳过外部噪声叠加**` | ❌ 0 处 —— 它在注释里，`strip_comments` 会剔除 |
| 2 | `</summary>[\s\S]{0,80}?public static bool IsSmooth` | ❌ 0 处 —— 同样在注释里 |
| 3 | `\}[\s]*public static bool IsSmooth` | ✅ 1 处 —— 断言**代码结构** |

第三版换成断言「`IsSmooth` 前紧邻一个 `}`」：如果那种"插入把注释切断"再发生，中间会夹进别的成员声明，这条立刻变红。

**教训**：

> **判据只看得到代码，看不到注释。**
> 想守护注释，只能去断言**注释造成的结构后果**（比如"成员之间必须紧邻"）。
>
> 这是本项目第 **4、5** 次踩同一个根因（前三次见 `status_checks.txt` 顶部说明）。

## 五、E 类：模型选错（不是参数错）

### 坑 10：CPU 负载套通用正弦 → 开机就擦告警线

**现象**（主理人第二张截图）：

> 「开机后」—— 电源「正常 / 已开 180W / 开机台数 1 台」，但 **CPU 负载 83.88%**，正擦告警线 85。

一台**只开了机、什么程序都没跑**的电脑，负载 83.88%。而通用波形还有第二个毛病：基线夹在 10.2~74.8%，意味着空闲时常态在 30~60% 之间飘 —— 真实台式机空闲是 **5~15%**。

**根因**：通用波形对"功率 / 亮度 / 开度"够用，但 CPU 负载有一个它们没有的特征：**它和"开机多久"强相关**。

**修法**：新增 `MetricShape.CpuLoad`。

```
boot = 0.80 · exp(−sinceOn / 12)         开机冲刺，τ=12s
idle = 0.11 + 0.03 · sin(2πt/90 + φ)     空闲基线 8~14%
load = max(boot, idle)                   量化 0.1%，上限 92%
```

实测回落：

| 开机后 | 0s | 5s | 12s | 20s | 25s | 60s+ |
|---|---|---|---|---|---|---|
| 显示 | 80.0% | 52.7% | 29.4% | 15.1% | **11.0%** | 11.0% |

峰值 80% **永不越过 WarnHigh=85** —— 这是"开机拱一下但不再擦线"的关键。

**为什么不能直接拿 `t` 当开机时长**：`t` 是**数据源启动至今的秒数**，不是"这台机器开了多久"。直接用会导致"跑了一会儿之后所有机器都自动变成空闲"，即使你刚点亮它。

真正的开机时刻只能从 `MockDeviceAgent.SetPcRunning` 来 —— 它开机时清掉 override，波形才从那一刻开始跑。

**教训**：

> **当某个指标存在"它依赖的另一个状态"时，套通用波形一定会错。**
> 判断标准：这个量的物理含义里，有没有一个"开关 / 阶段"在支配它？
> 有 → 它需要自己的形态（`MetricShape`），而不是参数微调。

### 坑 11：记账 key 用 `phase`，把理由也写错了

这是本轮**我唯一一次"结论对了但理由写错了"**。

**第一版做法**：`BootElapsedSeconds` 用 `phase` 当 key。

**第一版理由**（我写在注释里的）：

> 「`MockDataSource.PhaseOf` 里那个 **`seq` 每采一次就自增** —— 相位根本不稳定，每帧都不一样。拿它当 key 会每帧插入一条新记录，`sinceOn` 恒等于 0。」

**这段话是错的。** 收工复核时我把 `RunWorker` 从头读了一遍：

```csharp
while (!token.IsCancellationRequested)
{
    double t = clock.Elapsed.TotalSeconds;
    ...
    int seq = 0;                       // ← 每帧开头重置
    for (int i = 0; i < points.Length; i++)
        for (int k = ...)
            value = Next(metric, t, PhaseOf(i, k, seq), ...);
            seq++;                     // ← 只在一帧内递增
}
```

`PhaseOf(i, k, seq)` 其中 `seq` 在**每个固定 `(i, k)`** 上恒等于 `i` 之前的指标总数 —— 是一个**常量**。所以对同一台机器，相位每帧都是同一个数，根本不会"每帧变"。

（另一半也错了：`MqttLoopbackPublisher` 干脆 `pointIndex*1.7 + metricIndex*2.9`，连 `seq` 都没有。）

**真正的理由**：

> **相位是数值，不是身份。**

`phase` 是一个 float。两台不同的机器只要算出了同一个值，就会被记成同一次开机，表现为"同时开机，一台直接显示空闲值"。

这里恰好不会撞（步长 1.1/2.3 与 1.7/2.9 在 149 个指标范围内基本唯一），但那是**运气，不是设计** —— 一旦有人改了步长就可能悄悄撞上，且不会报错。

`twinId` 天生唯一，和相位怎么调无关。

**修法**：注释重写成正确的理由（结论没变，本来就用的是 `twinId`）。

**教训**：

> **"结论对"不能免掉"理由对"。**
> 一条写错理由的注释，比没有注释更危险 —— 下一个人会拿它当依据去改别的地方。
>
> 复盘的具体做法：把"我以为的机制"回去读一遍源码，别凭印象。

## 六、F 类：静态状态跨 Play 泄漏

### 坑 12：`BootStart` 记的是会归零的时间轴

**问题**：

`BootStart` 存的是**数据源时间轴上的 `t`**。而 `t` 每次进 Play 都从 0 重来。

上一轮记下 `start = 42.0`，这一轮 `t=0` → `elapsed = 0 − 42 = −42` → 被 `clamp` 到 0 → **判定为"刚刚开机"** → CPU 直接从 80% 起跳。

**当时其实不会表现**：开局播种把 21 台 PC 的 `CPULoad` 压成了 override 0（override 优先于波形），用户真去点开机时 `SetPcRunning` 又会 `ResetBootClock`。

**为什么还是要修**：它和 `s_muted` / `s_overrides` 是**同一类坑**，那个坑在本项目已经咬过一次：

`MockDataSource` 里原本就有一段：

> 「「停发」的残留后果极其隐蔽：上一轮断过电的设备，这一轮开局就一个字节都不发，场景里表现为"这几个点位永远没数据"，而 Console 干干净净 —— 排查方向会被引到数据源/点位上，而不是这里。」

同一种病，只是还没发作。而**"第一轮正常、第二轮才开始怪"的 bug 是最难查的一类**。

**修法**：并入同一个清理入口，不要分散。

```csharp
[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
private static void ResetStaticsOnLoad()
{
    s_muted.Clear();
    s_overrides.Clear();
    MockSignalGenerator.ResetAllBootClocks();   // ← 同一个入口
}
```

**教训**：

> **静态可变状态 + 会归零的时间基准 = 必然的跨会话泄漏。**
> 每次新增一张静态表，先问："进 Play 时它需要清吗？"
> 答案是"以后可能需要" → 现在就清，四行代码买断一类。

## 十、坑 14（2026-11-04，P12 遗留 · **本轮最严重的坑**）

### 现象

## 坑 15：硬抄一个"联动常数"，抄错不报错（2026-11-04，P12 健康度卡片）

### 现象

主理人 play 截图：窄态「统计」页底部的「数据源健康度」卡片，
标题下**只显示 3 行**（Mock / MQTT / 回放），第 4 行「录制」和脚注整行不见。

同时第二行显示 **MQTT · 不存在** —— 而 MQTT 明明配在场景里。

### 两个根因，都不是"写错了"，而是"抄错了"和"问错了"

**① 硬抄数字（显示不全）**

卡片实际占高 `HeadH 22 + 4×30 + 8 + 16 = 166`，从 `y=690` 起到 `856` 结束。
而滚动内容的高度我在上一版**手写**成 `802`。

- 第 3 行（录制）起点 = `690 + 22 + 3×30 = 802` —— 正好压在内容下边界上
- `RectMask2D` 按整数像素裁，起点在边界上 = 整行 0 像素可见
- **不报错、不警告、不抛异常**，只是"看起来少了一行"

**② 只问"注册了没"，没问"配了没"（显示假话）**

`TwinRuntime.Sources` 是 `DataSourceBase.OnEnable` 里 `RegisterSource` 加进去的。
组件被 `m_Enabled: 0` 禁用时，`OnEnable` 根本不执行 → 不进列表 → 查不到。

而 P12 为了把默认源改成 Mock，恰好把 MQTT 的 `m_Enabled` 改成了 0。
于是健康度卡片每次都说 MQTT「不存在」。

**这是我自己上一轮的改动，亲手给这一轮埋的。**

### 为什么这类 bug 特别难发现

| 特征 | 说明 |
|---|---|
| 布局常数在两处 | 卡片算高度、页面算内容高，各写一遍 |
| 抄错不报错 | `802` 是个合法 float，编译器无从判断它"应该"是 856 |
| 裁切静默 | `RectMask2D` 裁掉不抛异常、不写日志 |
| 语义相近 | 「不存在」和「已禁用」在代码里都是 `src == null` / `!enabled`，最容易被合并成一句 |

### 落盘规则（建议进 §1.6 G 类第六条）

> **凡是"两处要一致"的数，只能有一处定义，另一处必须从它推导。**
>
> 判断方法：把其中一个数字改成 `+1`，另一个会不会自动跟上？
> 不会 → 它就是一颗定时炸弹，只是还没到响的时候。
>
> 具体动作：
> 1. 布局尺寸公开成 `public const`，不要留成实例属性（属性只能被读到，不能被 `const` 表达式引用）
> 2. 调用方写 `Y + XxxCard.TotalHeight`，不写 `856`
> 3. 判据锁"推导式"而不是锁"数字"——锁数字等于把炸弹焊死

> **问"这个源在不在"之前，先问"在"是什么意思。**
>
> 至少三层，不能合并：
> - 已注册且在跑 = 这次在用
> - 场景里有、被禁用 = 配好了没开（点一下就能开）
> - 场景里真没有 = 这个通道没做
>
> 合并成一句，排查方向就全歪了 —— 而且对观众说的是假话。

### 修法

- `TwinSourceHealthCard`：`TotalHeight` / `Rows` 改 `public const`，删掉实例属性 `Height`
- `TwinSystemPage`：`NStatsContentH = NStatsHealthY + TwinSourceHealthCard.TotalHeight + 24f`（880）
