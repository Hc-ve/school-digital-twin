## 0-2. P39c 系统性整改（2026-11-15，用户视觉验收**不通过**：光照不均匀 / 区域昏暗或过曝 / 礼堂顶不明光斑 / 体育馆也不达标）

> 用户明确："不达标的场景太多了，没必要一个个截图" → 判定为 wash 层**体系性缺陷**，停止逐场景打补丁，做系统性整改。

### 根因（引擎实测）
1. **洗顶灯同区高度方差**：逐盏各自射线命中不同面（梁/桁架/楼板）→ 实测同区 washY：SportHall 5.85~6.85、ActZal 6.71~7.26、Corridor2 5.65~6.00、ClassComputer 2.33~3.06——距顶远近不一 → 光斑大小/亮度参差 = **礼堂"不明光斑"**（违背"同一房间灯具吊高一致"的现实逻辑）。
2. **步距 8m 过疏**：150° 锥在顶面有效亮半径 ~2.7m，8m 步距相邻光斑间留黑段 → 走廊顶一段亮一段暗、房间端头黑。
3. **房间墙面垫亮不足**：底光 2 盏 × 0.85 / range 4.5 压不住 5m 跨墙面 → 教室/主任室半边黑。

### 修复（`IndoorFillLight.cs`，一组"覆盖与均匀度"）
1. **全区统一吊顶高**：先按 wash XZ 布点逐点探测，取**最高命中**为全区 CeilY（miss 走 Renderer 估顶），所有洗顶灯挂 `CeilY - WashDropBelowCeiling` 同一高度；梁底等低矮面由锥体侧面自然洗到（真实走廊的梁正是这样受光）。实测 16 区 Y 方差全部归零。
2. **`WashSpanStep 8→6`、`WashMax 8→14`**：走廊 70m → 12 盏铺满全程（含西端 x=-45 junction 空洞）；大房间 5 行×2=10 盏；教室 2~3 盏。
3. **`BaseIntensityRoom 0.85→1.1`**：墙面垫亮归底光管（洗顶灯管顶、底光管墙）。
4. 洗顶灯总量 62 → **83 盏**。

## 2. 根因链（三条，全部实测取证）

### R1 逐相机光分配抖动
95 盏实时灯（62 Spot + 33 Point）抢 `pixelLightCount=48` 预算，而走廊是 **70m 巨型合并网格**（包围盒罩全楼）——每个活动灯都在它的"范围内"，逐渲染器像素光分配随相机姿态重排，同一面天花板不同视角吃到的像素灯集合不同。铁证实验：
- 关掉 40 盏 Base 垫底灯，画面中央亮度 0.357→**0.702**（分配重排，而非简单的"变暗"）；
- 三 pitch（0/-25/-55）采样天花板亮度差 **0.116**（0.165/0.203/0.281）。

### R2 贴顶反弹灯双面失败
P37 的 BaseCeil 反弹灯本意洗亮天花板，实际：朝下的灯打不亮顶（法线背向），关掉全部 40 盏画面**逐字节不变**（0.281→0.281）——零贡献。而 P37j 爆破试验（强度 30）证明"灯→顶板"通路本身是通的，只是贴顶高辐照会白斑（礼堂红圈同源）。

### R3 无 tonemapper
关掉后处理天花板反而 0.281→0.420 变亮——夜档 −1.45EV 在压黑全场，bloom 成为黑顶上唯一可见的"光"，形成"黑顶 + 耀斑"的观感。

### 潜伏 bug（礼堂特供）
原代码 `!alongX` 分支把 x 中心误用 `(MinZ+MaxZ)*0.5`——ActZal 是全楼唯一 `!alongX` 分区，其底光被放到房外 x=25.25，礼堂永远照不亮。

## 5. FPS 现状与结论（如实）

- **实测**：后台帧数采样 7.2~8.4 fps（多轮，含节流排除实验）；FrameTiming 单帧 GPU 108~198ms、CPU 主线程 94~244ms。**编辑器失焦 + 桥接调用会污染帧数采样**，本数据仅供量级参考，最终以用户目视为准。
- **关键实验**：`pixelLightCount 48→16`：GPU 帧时 152-198ms→108ms（降 ~40%），走廊亮度反升（0.204→0.294）——预算收紧后挤占预算的远处无关灯让位。**但**三 pitch 带读数变为 0.169/0.294/0.236（差 0.125），出现随视角/内容波动的风险信号，**已回滚 48**。结论：plc 是一把"亮度/稳定性/FPS"三刃参数，动它必须全 pitch 复验。
- **预算归属链路（双写，改预算前必读）**：`IndoorFillLight.TryMount` 挂载时 20→`PixelLightCountTarget`(32，有日志) → **`RoomShellLayer.cs:160` 再抬到 48（静默无日志）**。play 期权威值 = 48，且 `IndoorFillLight.cs:240` 注释明确"候选光数必须压到 48 以下"。要动预算必须同时审这两处。
- **结构性认识**：洗顶灯 41→22 无 FPS 收益，因为预算瓶颈不在洗顶灯数量——巨型合并网格的逐像素 pass 由预算上限（48）+ ForcePixel 灯决定。36.6fps 基线是"灯没生效"的黑暗场景换来的。
- **下一步 FPS 结构选项**（按性价比排序）：
  1. Wash/fill 烘焙进 lightmap（ForcePixel 逐帧成本归零，室内静态灯本就该烘）；
  2. 合并网格空间切分（走廊 70m 单体 → 分段，缩小包围盒让范围剔除生效）；
  3. 分区灯光预算（按楼层裁剪活动灯，当前 86 活动灯/全楼）。

## 6. 事故与教训（本轮新增）

### 6.1 固定机位会被弹簧臂夺回
`TwinThirdPersonCamera` 挂在 **Camera 对象本体**上且 LateUpdate 每帧施姿——禁用 `TwinPlayerController` 不等于固定机位。本轮中段相机被 rig 拽回角色机位一次，导致一批截图/读数作废（0.054 那张）。**正确姿势**：测光前 `tpc.enabled=false` 或反射 `ApplyFreeCamMode(true)` 交权给 FreeCamera，测完恢复。
另：告警面板的"跳转推进"提示说明 Mock 告警场景也有潜在相机拽动能力，验收测光时建议先暂停告警源。

### 6.2 三模式无法程序化认证
F5（第一/第三人称）/ V（观景）走 `Input.GetKeyDown`，execute_code 无法注入按键；反射改 `_firstPerson` / 调 `ApplyFreeCamMode` 均未引起可见相机变化（rig 依赖真实输入与角色锚点）。三张"模式"截图逐位相同，已如实作废。**结构性论据**：三模式共用同一相机与灯光管线，模式只改机位；机位依赖的分配抖动已往返实验根除，Bug1（三模式均在）的结构条件不复存在。最终验收 = 用户 F5/V 目视一分钟。

### 6.3 其他
- **play 期 console 5 条引擎 error "PlayerLoop internal function called recursively"（00:26:12~13）已销案**：堆栈指向 MCP for Unity 包自身的 `ScreenshotUtility.CaptureCompositedAfterFrame`（ScreenshotUtility.cs:197，经 ManageScene.CaptureScreenshotCommand 触发）——桥接截图工具重入 PlayerLoop 的工具缺陷，与本项目灯光代码无关。批量截图时可能复现，属已知噪音。
- Mock 告警含"灯具 LampHouses 抖动"条目，曾疑似灯光闪烁——连拍 delta 0.000 排除。
- 存量 warning（P39 前即有）：`TwinStatusColor 找不到 TwinAnchor：LightLum01_01 (28)`，一处灯点位锚缺失致状态着色不生效，待修数据。
- EditorPrefs `InteractionMode=2`（无节流）反射刷新可让后台编辑器全速跑（测 FPS 用），测完 `DeleteKey` 还原。
- 断点文档与代码常量存在漂移（如底光走廊文档 1.05 / 实测 1.25）——以代码为准，正式文档已标注。
