### N1. 屋顶积雪：逐三角形复制朝上面

**试过**：`SnowOnRoofs.cs` 用「遍历所有 Mesh，把朝上的三角形复制一份、抬高 0.02m、赋雪材质」生成雪壳，`minRoofY` 用世界绝对高度筛屋顶。

**结果**：**一套改动同时坏了四件不相干的事**——机房幕布发黑 / 角色浮空 / 脚印消失 / 屋顶反而仍无雪。四个现象分属渲染排序、地面采样、粒子、屏幕材质四个子系统，**唯一交点是新加的雪壳网格与材质**。

**被否原因**：
1. 真根因是 `minRoofY` 用**世界绝对高度** —— 机房 1F 天花板 3m 就被判成"屋顶"，雪壳混进大量室内水平面。
2. 调 `minRoofY` 会连带漏掉 1~2 层楼屋顶；按建筑分组又没有可信建筑清单（1393 个 PrefabInstance，网格全在 prefab 里）。
3. 两条路都不可行 → **正确动作是停用，不是硬凑**。

**证据**：`Docs/P13_踩坑日志_屋顶雪壳事故.md`；commit `f2557a3`；`SnowOnRoofs.cs` 内 `DISABLED_BY_INCIDENT_20261105 = true`；判据 P13-67/68/69 锁"必须停用"。

**副产品（已升格 P00 §1.6 F20）**：**加一层几何之前，先查它会不会被别人的全局遍历捡走。** 当时三处捡走它的代码都不在我改的文件里：`SampleGroundHeight`（向下射线取地面）、`IndoorByRendererRoof`（全场景 Renderer 判屋顶遮挡）、`SnapshotMonitorRenderers`（全场景筛材质）。

### N4. `lightmapIndex = -1` 修暖气片（D13 第一次尝试）

**试过**：按任务包要求扩展 `P30FixCeilingLightmap.cs` 的路径清单，加 3 个 1F 走廊暖气片，运行时置 `lightmapIndex = -1`。

**结果**：主理人 play 后指出「**安错材质了**」——暖气片变成**纯白平板**，失去了灰色金属的明暗与翅片立体感。

**被否原因**：`-1` = 该渲染器**脱离烘焙、改吃全局环境光**。环境光是全局常量、不分朝向，所以**靠烘焙明暗撑立体感的曲面小件会被压平**。

**这条本不该发生** —— `P30_发黑修复_成果报告_断点.md` §1.3 是我自己写的，原文就写着：

> | 桌椅 / 门板 / 马桶 / 海报（有立体感） | 直接变"一块纯色板"，失去体积 | ❌ 不能改 |

**我违反了自己写下的原则。** 我看到分类字段是「墙/隔断」、UV 块亮度 0.13，就把它归进"结构件"，没回到 §1.3 复查。

**核心教训**：**「结构件 / 家具件」不能按分类字段判，要按「是否有靠烘焙撑起的立体明暗」判。** 曲面 / 翅片 / 多凹槽的金属或塑料小件，一律排除，不看它的分类字段。

**证据**：本次尝试已完整还原（`git diff` 为空）；主理人截图两张（修复后白板 / 正常灰金属）；裁决 C-67 证伪 B；P00 §1.6 D22。

### N5. 「两个低通相减」做带通滤波（P14 音频）

**试过**：白噪声分别过 `fc=2400` 和 `fc=180` 两个低通，然后 `high - low`，看着是"高频减低频 = 带通"。

**结果**：实测 40Hz 只有 **−8.1dB（2级）/ −2.5dB（4级）**，**加级数低频反而更响**。

**被否原因**：两个低通在低频都趋近 1，相减趋近 0；但**级数越高它们"趋近"得越慢，差值反而更大**。这个结构在低频**不是高通**。

**改法**：高通级联 + 低通级联串联，各 2 级。

**教训**：**直觉给的算法，先用 Python 验一遍频响。** 一个 10 行的 z 域计算就能否掉，比在 Unity 里反复试听快得多。

**证据**：`Docs/P14_空调反馈_踩坑日志.md` 频响实测表；`Docs/P14_空调反馈_成果报告.md` B18。

### N6. 噪声循环做交叉淡化（P14 音频）

**试过**：直觉"噪声首尾不连续必须淡化"，写了多生成 0.5s + 末尾与开头交叉混合。

**结果**：**反而制造了唯一可听的变化**——每次循环末尾「突然变轻」。

**被否原因**：
1. 接缝本身不可听：4s 直接截断的跳变 0.1059 落在噪声自身相邻采样差的 **76.9 百分位**（被完全掩蔽）。
2. 交叉淡化让末尾 0.5s 变成两段独立噪声混合 → **方差减半 → 那才是真正可听的**。

**教训**：**不要为了解决一个听不见的问题，引入一个听得见的问题。**

**证据**：同上两文档；判据 P14-28（`grep0:xfade`）。

### 3.1 场景序列化值会覆盖代码默认值（A1）

**位置**：所有**已挂载在场景里**的 MonoBehaviour 的 `[SerializeField]` 字段。

**为什么不能碰**：你把代码里的 `private const float HumMaxVolume = 0.18f` 改成 `0.3f`，`const` 会生效；但把 `[SerializeField] private float _volume = 0.18f` 改成 `0.3f`，**场景里已序列化的旧值仍然覆盖它**。

**实证**：P14 时 `P30FixCeilingLightmap` 的 `autoPaths` 在场景里被序列化成**空数组**（`autoPaths: []`），不是 `null`。所以判断必须写 `autoPaths != null && autoPaths.Length > 0` 两个条件 —— **只判 `!= null` 会拿到空数组直接跳过内置清单，什么都不做且不报错**。

**证据**：`P30FixCeilingLightmap.cs:184`；场景 `SchoolSceneDay.unity` 中该组件序列化段。

### 3.3 `r.materials` 访问会克隆材质（B1）

**位置**：`Assets/_Project/Scripts/Present/TwinDevicePresenter.cs:4478` / `:4482`

```csharp

// ...

```

**为什么不能碰**：**访问 `r.materials` 会返回克隆体**，而 `r.sharedMaterials` 之后拿到的也是克隆体。想"还原"时写 `r.materials = r.sharedMaterials; Destroy(inst)` 会把克隆体赋回去又销毁 → 材质丢失、角色变紫。

## 四、D13 / P30 完整脉络

### 4.1 我写 `P30BlackSurfaceAudit.cs` 时的思路

**目标**：给主理人一个「点一下就能列出全场景哪些面发黑」的只读工具。

**当时的推理链**：
1. 发黑 = 光照贴图采样结果接近 0。
2. 每个渲染器的每个面按 **UV2** 坐标去图集上取光。
3. 所以：**逐点采样 UV2 在图集上对应的像素亮度**，均值低 = 这块面黑。
4. 图集均值不可用（1024² 图集里大部分像素是没被 UV 覆盖的空白 padding，纯黑，会把均值拉低 → 误报率 87.4%）。
5. 所以要按每个面的 UV2 去采样，得到「黑点占比」。

**当时我没想到的**：
- **UV2 不是直接用**，要过 `lightmapScaleOffset` 的 ST 变换（scale + offset）。这是我漏掉的（缺陷 A）。
- **采样分辨率要匹配图集尺寸**（我写 256，图集 1024）（缺陷 B）。
- **`GuessCategory` 的关键词表不全**（缺陷 C）。

**为什么当时没发现**：工具跑出来的数字「看起来合理」——它确实给出了 108 条、770 条的分档，主理人拿着这个清单去派工，打光按清单修，一路都有"进展感"。**一个错得自洽的指标，比一个明显报错的工具更危险。**

### 4.2 打光证伪 108 条清单后，我知道了什么

**打光的证据**：`ZalTop` 采样值 **0.0351**（判为近全黑），**渲染出来却是全场最亮**的矿棉板。

**这一条反例推翻了什么**：
1. 不只是"这 108 条里有几条误报" —— 而是**整个指标的物理基础是错的**。0.0351 与"全场最亮"相差到无法用阈值调整弥补。
2. 所以 `P30_UV采样区分析.md` 的 108 条 / 770 条**整份清单作废**，不是"挑着用"。
3. 同理 `P30_发黑构件盘点_原始数据.md` 的「图集亮度 < 0.25 的 Renderer 856」只是**图集级**统计，**不等于「这块面在屏幕上黑」**。

**我此前拿这份数据做的事全部要重新审视**：
- P30 的 12 条修复清单里，**8 条**来自打光自己的洋红扫描指认（`Box001`、`Corridor`、`BuildingBottomFloor`、`Border9` 等），这部分**不依赖我的工具**，仍然可信（已 play 验收）。
- 另外 **4 条**（`Floor2` / `ZalTop` / `PCClassTop` / `DirectorTop`）来自我的 UV 采样 + 打光复核，**建议重新验证**。

> **凭记忆、未验证**：我不确定这 4 条当时是否都有打光的独立复核。`Floor2` 有（主理人 play 确认恢复正常），其余三条的状态我记不清。

### 4.3 v1.43 证伪 A / B，我是否认可

**证伪 A（`:318` 缺 ST 变换）—— 我认可，而且这是我写代码时的真实疏漏。**

补充说明：**这个疏漏有一个"很难被发现"的性质** —— 它不会报错，不会给出荒谬数字，它给出的是「看起来合理但系统性偏移」的结果。而且**在 UV2 恰好没被 packer 重排过的对象上，它是完全正确的**（`scale=1, offset=0` 时 ST 变换是恒等）。所以它会「对一部分、错一部分」，这比全错更难识别。

> 这也是为什么 `Floor2` 那条能修成功 —— 它可能恰好是 `scale=1, offset=0`。

**证伪 B（`lightmapIndex=-1` 对曲面小件证伪）—— 我认可，并且我用一次实际失败验证了它。** 见 N4。

**我要补充一条（v1.43 未提）**：**「抬环境光可修 105 处」被证伪的机制，和证伪 B 是同一个** —— 环境光对**烘焙构件零影响**，因为烘焙构件的光完全来自 lightmap，环境光只在 `lightmapIndex = -1` 时才参与。所以：
- 「抬环境光」修不了任何烘焙构件（证伪）
- 「设 `-1` 改吃环境光」能修黑，但压平立体感（证伪 B）

**两条修法构成一个死结：想让烘焙构件变亮，只能重烘；任何不重烘的办法，都要先放弃烘焙（= 放弃立体感）。**

**这是我认为 D13 的真正结论**，建议新断点从这个前提出发，不要在"运行时绕过"上再花时间。

### 4.4 对 D13 后续路径的建议（我的判断，供参考）

按 C-67 三步法，第一步是修工具指标。我的建议：

1. **重写而不是修补** `P30BlackSurfaceAudit.cs`。三个缺陷（ST 变换、采样率、分类）叠加，且缺陷 A 的性质决定它"对一部分错一部分"，修补无法验证修没修对。
2. **换指标口径**：v1.43 说「改用渲染实测亮度而非 UV 采样值」，我赞成。具体建议：**用相机渲染到 RT，逐对象遮挡测试**（Hide Others 渲染一次，比对该对象像素区域的平均亮度）。这是唯一能直接回答「屏幕上这块面是不是黑的」的方法，绕开所有 UV/烘焙/采样推断。
