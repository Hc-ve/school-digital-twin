## 1. 核心方法论：发黑三族判别法（基线 §1.6 方法论第 20 条）

### 1.1 主判别表

| 族 | 判据 | 一个动作定性 | 修法 | 分错族的代价 |
|---|---|---|---|---|
| **① 着色器剥离** | 编辑器正常、**exe 全黑** | `Player.log` 有「找不到着色器 XXX」原话 | 补 Graphics → Always Included Shaders；或移进 `Resources/` 改用 `Resources.Load<Shader>()` | 会去翻素材目录，白查 57MB 的 mp4 |
| **② Lightmap UV 块无光** | 编辑器与 exe 同黑、**部分黑部分正常** | 选中黑面看 `lightmapIndex`；按 UV2 采样该块亮度 | 运行时 `lightmapIndex = -1`，不重烘 | 会去改材质、抬环境光，两者都无效 |
| **③ 几何缺失 / 合并网格** | 点不中 + y=0 网格可见 | 点选后看 Hierarchy 高亮**覆盖范围** | 真缺失 → 补几何；合并网格 → 按对象整体修 | 会去加 Plane，和已有几何 z-fighting |

### 1.2 三条补充判据（都是踩坑换来的）

1. **点选不到 ≠ 没有几何**。若该对象是「合并网格」（一个 Renderer 包办整间房所有表面），点选会高亮整个房间，看着像没选中，其实选中了别处。
2. **y=0 网格能显示在那里 = 那里能看穿**。网格只会在没有不透明几何遮挡时露出。
3. **材质坏只有三种形态**：粉色（shader 丢）/ 纯黑但点得到 / 隐形但 Hierarchy 里有（`Renderer.enabled=false` 或未激活）。

### 1.3 扩展族（不属于三族，但症状相同）

| 族 | 触发条件 | 本项目实例 |
|---|---|---|
| **④ 自定义 shader / 视频末帧** | 黑的是动态画面而非静态几何 | P26「关机后幕布发黑」三因叠加 |
| **⑤ 渲染链污染** | 新增 mesh 之后**多个不相关现象同时出现** | F20 雪壳事故：幕布发黑 + 角色浮空 + 脚印消失 + 屋顶仍无雪 |
| **⑥ 实时光预算不足** | 参数全对、日志全对、就是不亮 | P17 逐像素灯只有 4 盏，小光源全被降级成顶点光 |

> **族⑤ 的识别口令**：**多现象先找共用点**。四处同时坏，几乎必然是同一个新对象被多处全局遍历捡走，不是四个独立 bug。

## 3. 族② 深挖：Lightmap UV 块无光（P30 主线）

### 3.1 三层原因

**第 1 层 · 直接现象**：不是整张图黑，是**该对象在图集上占的那一小块是纯黑**。

| 对象 | 图集整体均值 | 该对象 UV 块平均亮度 |
|---|---|---|
| `SchoolBuilding/ZalTop` 走廊吊顶 | **0.3132（正常）** | **0.0353（全黑）** |
| `SchoolBuilding/PCClassTop` 计算机教室吊顶 | 0.1617 | 0.1093 |
| `SchoolBuilding/DirectorTop` 主任办公室吊顶 | 0.1135 | 0.0851 |
| `SchoolBuilding/Box001` 篮球场整面墙 | 0.1443 | 0.1785（**62% 的面为 0**） |

> 所以「换材质」「提图集亮度」全都没用——**图集本身有光，黑的是它占的那一块**。

**第 2 层 · 为什么这块 UV 收不到光**：

- 内置管线，场景 `1 Directional (Baked) + 68 Area (Mixed)`；**内置管线下 Area Light 没有实时直接光 → 室内 100% 依赖烘焙**
- Directional 烘焙**按法线投影 `N·L`** 计算贡献。吊顶下表面、朝内墙面的法线朝下 / 朝内，与主光方向投影 = **0**
- 68 盏灯都装在天花板下方，照的是地面和桌面，**照不到吊顶下表面自己**
- 于是这块 UV 被烘成 0，永久写进 `LightingData.asset`

**第 3 层 · 是不是迁移改坏的**：**不是**。老工程 `School/` 与新工程 `School-pro/` 的 `SchoolSceneDay` **48 张 lightmap 字节级相同**（L0~L3 md5 全等）。导入期即存在，属资产原生缺陷。

### 3.2 ⚠️ 法线澄清（本项目被反复怀疑的一点）

| 判断 | 结论 |
|---|---|
| 模型法线反了？ | ❌ **没反**。吊顶下表面法线朝下是几何上正确的 |
| 反了会怎样？ | 若真朝上，**反而会收到主光变亮**；且背面剔除会让这块面直接看不见 |
| 法线的角色 | **致病条件，不是病**——「正确的朝下法线」+「只有上方主光的烘焙配置」= 收不到光 |
| 法线贴图 / 关键字？ | 已排除。`_NORMALMAP` / `_METALLICGLOSSMAP` / `_SPECGLOSSMAP` 关键字数量新旧完全一致（159 / 38 / 46） |

> **结论定性**：**不是材质问题，不是模型法线错误，是光照烘焙资产缺陷**。硬要归类算"光照问题"，但不是"实时光照没调好"。

### 3.3 修法：一行代码

```csharp
renderer.lightmapIndex = -1;
```

| 项 | 说明 |
|---|---|
| `>= 0` | 去第 N 张贴图取光（这块取到 0，所以黑） |
| **`-1`** | **不参与烘焙**，回落实时光 + 环境光（Ambient） |
| 为什么有效 | Ambient 是全局常量，**不看面朝向**，纯黑面变均匀水泥色 |
| 实现文件 | `Assets/_Project/Scripts/Twin/P30FixCeilingLightmap.cs` |
| 挂载 | 场景常驻对象 `TwinPlayer`；`Awake()` 里按路径逐级 `Transform.Find` + `HashSet` 去重 |
| 为什么不用 `GameObject.Find` | 场景 12 万行、**184 个重名对象**，路径不可靠（基线 C3） |
| 修复范围 | **12 条路径**：`Floor2` / `ZalTop` / `PCClassTop` / `DirectorTop` / `Box001` / `Border011` / `BuildingBottom` / `Stairs02Concrete` / `Kitchen` / `Corridor` / `BuildingBottomFloor` / `Border9` |
| 零改动保证 | 没改材质、没改 `RenderSettings`、没重烘、没动 `.asset`、没加 Plane、场景只多一个组件 |

### 3.4 两条看似可行、实测证伪的路

| 方案 | 为什么不行 |
|---|---|
| **抬环境光** | Standard shader 在 `LIGHTMAP_ON` 分支直接采样光照贴图，**不叠加 `unity_Ambient*` SH 项**——环境光在烘焙时就已烤进贴图。实测改前改后 PNG **字节完全一致**，对任何带光照贴图的构件都是空操作 |
| **重烘** | 要动 1992 个 Renderer，答辩期不可行 |

### 3.5 为什么必须运行时赋值

`lightmapIndex` 存在 `LightingData.asset` 的**二进制**里，场景 `.unity` 中 **0 处 `m_LightmapIndex` 文本字段**（已实测），保存场景无法持久化。

> 因此也**不能加 `[ExecuteAlways]`** —— 编辑器里执行但存不进去，只会把场景弄脏。

### 3.6 筛选原则与副作用（技术债 D4）

| 类型 | 改了的效果 | 判断 |
|---|---|---|
| 墙 / 吊顶 / 楼板 / 边条（大面积平面） | 从纯黑变均匀色，**看不出变平** | ✅ 可以改 |
| 桌椅 / 门板 / 洁具 / 海报 / 电脑（靠明暗撑立体感） | 变「一块纯色板」，近看像贴纸 | ❌ 不能改 |

**副作用**：脱离烘焙 = 失去「靠窗亮、角落暗」的渐变。12 处结构件画面变平，语义上不再"真实"。
**处置**：登记为技术债 **D4**，**将来重烘时应移除该组件**。
**范围纪律**：506 处检测命中里只修 12 处——室外背光件（80）本就该暗、UI 文字（10）本就 unlit、`Door02_1` 空材质槽（2）是缺陷 D1 与光照无关、家具（约 400）改了会毁体积感。

## 5. 一次误判的完整复盘：合并网格

**事情经过**：主理人反馈「走廊天花板点不中」，按当时 `C4` 的两条判据（点不中 = 空 / 能看到网格 = 看穿）判为**几何缺失**，建议打光加 Plane 遮挡。

**打光用洋红扫描推翻**：

| 检查 | 结果 |
|---|---|
| 站走廊正中抬头渲染，洋红 = 无几何 | **0% 洋红** —— 有几何、纯黑、灯管浮空 |
| 沿 X 每 2m 向上渲染 26 次 | z ≥ 28.5 全段 0.0%；z 18~27 是露天庭院（本就无顶，正常） |
| 计算机教室 -Z 墙，36 次渲染 | 全部 0.0% 洋红，墙在，只是有一条黑带 |

**真相**：`SchoolScene/Exterior/SchoolBuilding/Corridor` 是 **1 个 Renderer、13 个材质槽**的巨型单网格。点天花板、点墙、点地面，选中的必然是同一个 `Corridor`。「点不中」的真相是「**没有第二个对象可选**」，不是「那里没有几何」。

**修复**：把 `Corridor` / `BuildingBottomFloor` / `Border9` 加进路径表，主理人 play 确认走廊天花板恢复正常，地面也没有明显变平（走廊铺地胶，本来明暗就弱）。

**沉淀**：`P00 §1.6 C4` 从两条判据补成**四条**，新增「合并网格」+「隔离显示判别法」；同时新增 **D6「判据不完整时不下绝对结论」**。

## 6. ⚠️ 修法适用性边界（最容易翻车的一节）

> **「已验证的修法」不等于「普适的修法」。**

### 6.1 证伪 B：`lightmapIndex = -1` 不是万能钥匙

P30 的 `lightmapIndex = -1` 对**吊顶 / 楼板**（大面积平表面、看不出明暗损失）12 处全成，对**暖气片翅片**（靠烘焙明暗撑立体感的曲面小件）**立即证伪**——脱离烘焙改吃全局环境光，立体感直接压平成白板。

**为什么当时会归错类**：P30 报告 §1.3 其实早就写了「桌椅/门板/马桶/海报不能改」，但执行者看到分类字段是「墙/隔断」就把它归进了结构件。

> ✅ **正确判定标准不是分类字段，是「该表面是否依赖烘焙明暗呈现立体感」**。
> 曲面 / 翅片 / 多凹槽的金属或塑料小件，**一律排除**。

### 6.2 按族分治速查

| 表面类型 | 能不能用 `lightmapIndex=-1` | 替代方向 |
|---|---|---|
| 大面积墙 / 顶 / 楼板 / 边条 | ✅ 可以 | — |
| 走廊铺地胶（明暗本来就弱） | ✅ 可以 | — |
| 暖气片翅片 / 窗框竖梃 | ❌ 会压平成立体感白板 | 需重做诊断，或按材质槽局部重烘 |

## 7. 排查动作清单（拿到「发黑」报障后照着做）

| 步 | 动作 | 判据 |
|---|---|---|
| 1 | **先问：编辑器里也黑吗？** | 编辑器正常、exe 黑 → 直接跳族① |
| 2 | exe 黑 → 开 `Player.log` 搜「找不到着色器」 | 有原话 → 族①，查 Always Included Shaders / `Shader.Find` |
| 3 | **点一下那块黑面** | 点得到 → 排除纯几何缺失；点不中 → 继续第 4 步 |
| 4 | 看 **Hierarchy 高亮的是哪个对象**、包围盒多大 | 高亮对象包办整间房 → **合并网格**，不是缺失几何（必要时 Hide Others / 洋红扫描隔离） |
| 5 | 选中 Renderer，看 `lightmapIndex` | `-1` → 已脱离烘焙，另找原因；`>=0` → 族② 候选 |
| 6 | 按 **UV2 + `lightmapScaleOffset` ST 变换**采样该面亮度，同时看平均亮度 + 黑点占比 | 图集整体亮、该块近 0 → 族② 确诊 |
| 7 | 确认「是不是刚加了新 mesh / 新功能」 | 多现象同时出现 → 族⑤，查全场景 `FindObjectsOfType<Renderer>` 遍历与 `renderQueue` |
| 8 | **去未改动的旧工程看一眼** | 旧工程也一样 → 资产原生设计，不修（P26 黑墙就是这么结案的） |
| 9 | **确认修法边界**：这块面靠不靠烘焙明暗撑立体感？ | 靠 → 禁用 `lightmapIndex=-1`，换路线 |
| 10 | 修完 play 目视复核 | 用户 play 所见是第一验收标准，数值只作辅助 |

## 9. 纪律与教训汇总

| # | 教训 |
|---|---|
| 1 | **先分族再动手**。三族修法完全不同，分错族等于白烧一轮 |
| 2 | **「部分黑」几乎总是族②**。整块材质丢是粉或全黑，只有 UV 块才会一半亮一半黑 |
| 3 | **判据不完整时不下绝对结论**（D6）。C4 缺「合并网格」这一条，导致一次误判、白绕一圈、差点加一个会 z-fighting 的 Plane |
| 4 | **平均值会掩盖局部缺陷**。平均亮度、黑点占比、图集均值三个指标各有失效场景，大对象尤其会稀释 |
| 5 | **proven 路线换对象类别前，先问「它靠什么撑起现在的样子」**（方法论 22 条）。判定标准不是分类字段 |
| 6 | **派工清单必须来自实测**（方法论 23 条）。数值要算过、对象要数过 |
| 7 | **加一层新几何之前，必查它会不会被别人的全局遍历捡走**（F20）。四项必过：全场景 `FindObjectsOfType<Renderer/MeshFilter>` / 上下 `Raycast` 采样 / 依赖 `renderQueue` 排序的材质 / `bounds` 撑大后的视锥与后处理 |
| 8 | **多现象先找共用点**。四处同时坏，先找同一个新对象，别当四个 bug 分开查 |
| 9 | **调参和改架构都不可行时，正确动作是停用**（D16），不是硬撑 |
| 10 | **用户 play 所见是第一验收标准**，不得用数值或公式推翻视觉结论；数值只作辅助说明 |
| 11 | **报「某处坏了」先去旧工程看一眼**。P26 黑墙与 D13 都靠这一步排除了「今天改坏 / 迁移改坏」 |
