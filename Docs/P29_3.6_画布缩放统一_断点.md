## 〇、一句话

根因是**两套参考分辨率 + 两种 match 模式**：主画布 `1000×720 / match=0`，两个自建 Canvas `1920×1080 / match=0.5`。
`match=0` 只按宽度缩放，画布高度被窗口宽高比压到 611.8（1069×654 时）—— 所有按 720 排的布局全部出屏。
改法是**把三个画布统一到 `1000×720 + Expand`**：Expand 让画布逻辑尺寸**只增不减**，高度恒 ≥ 720，零布局常量改动。

## 一、① 两个自建 Canvas 统一口径

### 1.1 `TwinMinimap.cs`（第 119-127 行）

| 项 | 原值 | 新值 |
|---|---|---|
| `referenceResolution` | `1920 × 1080` | **`1000 × 720`** |
| `screenMatchMode` | `MatchWidthOrHeight` | **`Expand`** |
| `matchWidthOrHeight` | `0.5` | **`0`**（Expand 下无效，归零避免误读） |

### 1.2 `TwinInteractMenu.cs`（第 120-128 行）

同上三项，值与 1.1 完全一致。

### 1.3 这两处的影响面（必须说清）

它们都在 `FindOverlayCanvas()` 的**兜底分支**里 —— 只有场景里一个 `ScreenSpaceOverlay` Canvas 都没有时才会执行。
当前场景有 `[TwinUI]`，所以**正常运行走不到这里**。

那为什么还要改？因为这两处是「按 1920×1080 设计」的历史残留：
一旦哪天主画布被禁用、或换场景跑，兜底 Canvas 会以 0.581 的缩放（1069×654 下）接管全部 UI，
而主画布是 1.069 —— 差 1.84 倍，**这类问题只在换环境的瞬间爆发，最难当场定位**。
既然发现了就一起收口，成本为零。

**文件**：`TwinUIFactory.cs`（文件末尾新增，第 268-372 行）

| 项 | 内容 |
|---|---|

**没有改场景文件**：只改运行时实例的 CanvasScaler 组件。

### 2.1 Expand 带来的画布尺寸变化

`scaleFactor = min(screenW / 1000, screenH / 720)`

| 窗口 | 原（match=0） | 新（Expand） |
|---|---|---|
| 1000 × 720 | scale 1.000 → 画布 **1000 × 720** | scale 1.000 → 画布 **1000 × 720**（不变） |
| 1069 × 654 | scale 1.069 → 画布 1000 × **611.8** | scale **0.9083** → 画布 **1176.9 × 720** |

- **高度**：611.8 → **720**，抽屉（720 高）不再出屏 → 标题、关闭 ×、工具行四项全部可见
- **宽度**：1000 → 1176.9，比窗口比例更宽 —— 这是 Expand 的代价（宁可变宽不裁内容）

> 这正好解释了上一轮「按钮消失」：不是按钮被删，是抽屉 720 高在 611.8 高的画布里上下各溢 54px，
> 头部与工具行被裁到屏幕外。上一轮我用「把抽屉写死 720」去对抗，方向反了 ——
> 应该让**画布**回到 720，而不是让**抽屉**脱离画布。已回退那个错误改动。

## 三、③ F3 调试面板（TwinDebugHud）

### 3.1 尺寸来源：屏幕像素，与 Canvas 无关

原实现（第 160-169 行）：

```csharp
const int width = 560;                                    // 屏幕像素
float height = Mathf.Min(Screen.height - 20f, 22f * _lineCount + 20f);
GUILayout.BeginArea(new Rect(10f, 10f, width, height), GUI.skin.box);
```

IMGUI 的坐标系是**屏幕像素**，完全不经过 CanvasScaler —— 所以它和别的面板从来就不在同一个尺度上。

| 项 | 原值 | 新值 |
|---|---|---|
| 宽度 | `const int width = 560`（屏幕像素） | `const float width = 560f`（**逻辑单位**） |
| 高度上限 | `Screen.height - 20`（屏幕像素） | `Screen.height / scale - 20`（**逻辑单位**） |
| 位置 | `(10, 10)` 屏幕像素 | `(10, 10)` **逻辑单位** |
| 坐标系 | 屏幕像素 | **画布逻辑坐标**（`GUI.matrix` 整体缩放） |

### 3.2 改法（第 160-200 行）

```csharp
float scale = ResolveCanvasScale();
Matrix4x4 prev = GUI.matrix;
GUI.matrix = Matrix4x4.Scale(new Vector3(scale, scale, 1f));
// …按逻辑单位画…
GUI.matrix = prev;
```

`ResolveCanvasScale()`（新增）：优先读主画布 `canvas.scaleFactor`（Unity 的权威值），
拿不到就按 Expand 语义算 `min(w/1000, h/720)`。**只在 Screen 尺寸变化时重算**，不每帧 Find。

### 3.3 效果

| 窗口 | 逻辑尺寸 | 物理像素 |
|---|---|---|
| 1000 × 720 | 560 × H，左上 (10,10) | 560 × H |
| 1069 × 654 | 560 × H，左上 (10,10) | 508.7 × H·0.908 |

**逻辑尺寸与位置完全一致**，只是物理像素等比缩 —— 这才是"基于主 Canvas 逻辑坐标"。

## 四、④ 物体详情面板（TwinDetailPanel）

### 4.1 确认：正常路径本来就对，不用改

`ViewportHeight()` / `ViewportWidth()`（第 313-370 行）**首选**走：

```csharp
Canvas canvas = _uiRoot != null ? _uiRoot.GetComponentInParent<Canvas>() : null;
if (canvas != null && canvas.scaleFactor > 0.0001f)
    return Screen.height / canvas.scaleFactor;
```

它直接问 Unity「一个 UI 单位 = 多少屏幕像素」，**不手算 match 语义**。
Expand 下 `canvas.scaleFactor` 就是 Unity 算好的 0.9083，反推 `654 / 0.9083 = 720` ✔ 正确。

> 这段代码的注释里已经写了「本工程就被改成 1000×720、匹配值 0，手算和实际一旦不一致面板就会错」——
> 原作者（也是我）踩过一次，所以留了这条捷径。本次不用动主路径。

### 4.2 改了什么：兜底分支补 Expand/Shrink

原来兜底是：

```csharp
float factor = Mathf.Lerp(sx, sy, Mathf.Clamp01(scaler.matchWidthOrHeight));
```

**问题**：`Expand` / `Shrink` 模式下 `matchWidthOrHeight` **根本不参与计算**。
主画布已切 Expand，一旦走到兜底（拿不到 Canvas 引用时），手算值 = `Lerp(1.069, 0.908, 0)` = **1.069**，
而 Unity 实际是 **0.9083** —— 差 18%，面板尺寸就跟着错。

改成按模式分派（`ViewportHeight` 第 337-352 行、`ViewportWidth` 第 366-381 行，两处同样）：

```csharp
float factor;
switch (scaler.screenMatchMode)
{
    case CanvasScaler.ScreenMatchMode.Expand: factor = Mathf.Min(sx, sy); break;
    case CanvasScaler.ScreenMatchMode.Shrink: factor = Mathf.Max(sx, sy); break;
    default: factor = Mathf.Lerp(sx, sy, Mathf.Clamp01(scaler.matchWidthOrHeight)); break;
}
```

正常路径不经过这里，纯防御。

## 五、⑤ 四个面板在两个尺寸下的数值

### 5.1 画布基准（Expand 公式的确定性输出）

| 窗口 | sx | sy | scaleFactor | 画布逻辑尺寸 |
|---|---|---|---|---|
| 1000 × 720 | 1.0000 | 1.0000 | **1.0000** | **1000.0 × 720.0** |
| 1069 × 654 | 1.0690 | 0.9083 | **0.9083** | **1176.9 × 720.0** |

### 5.2 四个面板

| 面板 | 锚点 | 逻辑尺寸 | 逻辑位置 | 1069×654 物理 | 1000×720 物理 | 逻辑一致？ |
|---|---|---|---|---|---|---|
| **小地图** | 左上 | 160 × 190（圆 160） | (24, −24) | 145.3 × 172.6 | 160 × 190 | **✔ 完全一致** |
| **总控抽屉 L1** | 右缘垂直拉伸 | 420 × 720 | 右缘贴边 | 381.5 × 654 | 420 × 720 | **✔ 尺寸一致**；位置见 §5.3 |
| **总控抽屉 L2** | 同上 | 640 × 720 | 右缘贴边 | 581.3 × 654 | 640 × 720 | **✔ 尺寸一致** |
| **F3 调试面板** | 左上 | 560 × H | (10, 10) | 508.7 × H·0.908 | 560 × H | **✔ 完全一致** |
| **物体详情卡** | 贴抽屉左缘 | 470 × H | 相对抽屉左缘 −470 | 426.9 × H·0.908 | 470 × H | **✔ 尺寸一致** |

`H` = 由内容行数决定的高度（F3：`min(viewH−20, 22·行数+20)`，viewH 两尺寸都是 720）。

### 5.3 「位置一致」的准确含义（必须说清，否则验收会卡）

**左锚的两个**（小地图、F3）：逻辑坐标 (24,−24) / (10,10)，两尺寸**逐值相同** ✔

**右锚的两个**（抽屉、详情卡）：贴着画布右缘，**相对右缘的距离两尺寸都是 0 / −470，完全相同**；
但**绝对逻辑 x 不同**（画布宽 1176.9 vs 1000，差 176.9）。

这是 Expand 的数学必然：它把缩放因子交给**高度**（保证 720 不缩水），宽度就只能随窗口比例变。
如果要求绝对坐标也一致，只有两条路：

| 方案 | 效果 | 代价 |
|---|---|---|
| A. 改 `Shrink` / `match=1` | 画布宽高都固定，绝对坐标一致 | 窗口比 1000:720 窄时**内容被裁** —— 正是 R7 要避免的 |
| B. 接受宽度可变（当前） | 高度恒定、左右锚点相对位置恒定 | 右锚元素绝对 x 随窗口变 |

**我建议 B**，也是本次实现的方案。理由：任务的核心诉求是"不出现面板出屏或元素消失"，
而 Expand 是唯一能做到这一点的零布局改动方案（任务包原话）。绝对坐标一致与"内容不被裁"在这里互斥。

> 如果验收坚持按"绝对屏幕坐标 ±2px"判，那这条**不满足**，请按 §七 C-11 裁决。
> 我不改口径去凑标准 —— 那样改回 Shrink 会立刻重现"按钮消失"。
