# 第二部分 · 实习报告素材（7 份）

> 每份三段：**实习内容**（照抄职责，逐字一致）／**主要工作**（3~5 条，可核实的具体事项）／
> **实习收获**（围绕本人职能域）。粘贴后把「本项目」换成实习单位要求的表述即可。

## 2.1 何超臣（组长）

**实习内容**
担任项目组长，负责团队统筹与任务分工、项目进度管控与推进；承担总控面板与校园设备监测管理系统的架构设计与开发（数据监测、设备管理、电力管理、告警中心、数据统计五大模块，含电力系统）；负责设备数据接入与真实数据链路模拟、项目整体交互设计与开发、缺陷排查与修复、漫游三模式（第一人称／第三人称／观景模式）设计开发、天气系统融合开发与仿真优化，以及答辩 PPT 的设计与制作。

**主要工作**
1. 建立项目基线文档与任务台账，累计 26 项已完成任务、29 个版本记录，形成可交接的统一上下文。
2. 开发孪生框架五层（TwinRuntime／TwinAnchor／TwinRegistry／TwinCatalog／数据总线），接入 71 个设备点位、17 个分区，实现 Mock（10Hz 本地仿真）与 MQTT 双数据源切换。
3. 实现电力三级回路模型（20 节点：楼栋／楼层／房间）与 SBO 两步确认操作，命令链路做「下发→回执→执行→回读」四段超时校验（1s／3s／3s／5s），失败给出明确拒绝原因。
4. 主导数据真实性专项：室温、供水、CO₂、湿度四条曲线由物理模型派生（建筑热惯性＋Magnus 公式），全年 192 组实算校验；修复 Power 指标单位混用（kW／W 直接相加导致空调少算 1000 倍）与设备编号撞号（70 台中 51 台不可单独指认）两处答辩级缺陷。
5. 建立 273 条可执行验收判据与 76 条踩坑日志（七类方法论），形成「改完必须能验证」的工程纪律。

**实习收获**
最大的收获是理解了数字孪生项目的难点不在三维展示，而在**数据口径的一致性**。同一个功率值在 KPI 卡、楼层聚合、能耗榜单三处若各算一遍，必然出现「2.8 kW 与 22.3 kW 同屏」的矛盾；把口径收敛到唯一出口后，问题才真正消失。其次是工程化管理的价值：判据与踩坑日志看起来是额外工作，实际把返工次数压到了最低——一次「代码改对了但判据还报红」的排查，最后发现是判据工具没剔除注释，这类问题只有沉淀成文档才不会重复踩。

## 2.2 杨续

**实习内容**
参与天气系统的设计与开发，为天气系统的建成提供模块化的打包产物，支撑其与主项目的融合联调；参与部分设备交互的开发（开关门、开关灯、风扇启停等）；负责机房交互视频素材与铃声参数的收集整理。

**主要工作**
1. 独立设计并实现程序化天气系统：雨、雪、雷暴、雾、多云等天气状态，以及云穹顶、星空、地面积水、地面积雪、树根积雪等视觉层，共 8 个 C# 脚本与 4 个 Shader。
2. 坚持零外部素材路线：雨丝、雪花、云体积、星空、雪斑、水洼遮罩等全部纹理，以及雨声、风声、雷声音效，均在运行时用代码程序化生成。
3. 输出 1200 余行移植技术文档，含系统架构、参数调优速查表、18 条已知坑与验收清单，使该系统可零依赖迁移到其他 Unity 工程。
4. 交付模块化打包产物并配合组长完成融合联调，处理源工程 URP 管线与目标工程内置管线的 Shader 适配问题。
5. 融合期针对积雪表现异常提供排查依据（室内外判定、雪面高度抬升量、远场兜底盘等经验直接复用）。
6. 收集并整理机房交互所需视频素材（开机／关机动画、科普与大屏演示共 4 段 mp4，置于 StreamingAssets 供运行时播放）与打铃器铃声参数（三音上行铃音高与时值、音量、打铃持续秒数）。

**实习收获**
最大的体会是「程序化生成」这条路线的价值：不依赖任何外部素材，既规避了版权与体积问题，也让效果参数可以随时调整。另一个收获是模块可移植性的重要——系统在原工程运行时正常，迁移到不同渲染管线的工程时，Shader 的光照函数、雾效宏、纹理采样写法全部需要改写，只有在交付时把架构和踩坑写清楚，接收方才能快速定位问题而不是从头猜。

## 2.3 赵朕

**实习内容**
负责项目面板 UI 设计与界面视觉规范（token）落地，输出设计稿与设计样式图；参与部分设备交互的开发（开关门、开关灯等）。

**主要工作**
1. 参与制定项目视觉体系：确立「深色是画布、数据与告警才是光源」的设计原则，主色采用青蓝 #33BFFF，告警橙仅用于告警语义，避免强调色与告警色混淆造成误读。
2. 建立视觉 token 规范：颜色（卡片底色、描边、分隔线、四级状态色）、字号整数六档（11／13／15／17／22／28）、圆角四档（8／12／16／胶囊）、间距按 4 的倍数，所有面板统一取值。
3. 输出界面设计稿 10 张（设计语言总纲、现状诊断、改版方案、L2 骨架小样、全屏 L1 监控态、全屏 L2 数据态、窄态对照、数据统计页，以及时间天气面板白天／夜晚两态试绘图）。
4. 落实「先出图再施工」流程：设计稿逐区核算到坐标，横纵向闭合校验误差为零后才交付编码，避免边写边改导致的反复返工。
5. 针对本项目零图片资源的约束，确定所有图形（圆角、描边、渐变、虚线、图标）均由代码绘制图元拼合的方案，例如时间天气面板的表盘用圆环＋12 刻度＋指针圆点拼成，天气图标用 4~6 个图元拼出。
6. 参与门、灯等设备交互的实现与联调，并负责交互控件在面板侧的视觉一致性（选中态、禁用态与命中区尺寸）。

**实习收获**
最深的体会是设计规范的价值在于**约束而非美化**。项目初期界面因为「不好看」被退回过一次，根因不是审美能力不足，而是没有先定规范就直接编码，导致每个面板各自取色、各自定字号。建立 token 体系后，新增面板只需查表取值，视觉一致性不再依赖个人判断。另一点是零图片资源带来的设计挑战：不能画图标就只能用几何图元拼，反而逼着设计走向克制——这也让界面在任何分辨率下都不会因贴图缩放而失真。

## 2.4 张俊才

**实习内容**
负责场景模型素材的收集、整理与轻量化（减面）处理；参与部分设备交互的开发（开关门、开关灯等）；负责演示素材的录制。

**主要工作**
1. 收集整理校园场景三维素材（教学楼主体、教室家具、机房设备、门窗、体育器材等），按功能与区域归类，制定素材命名与目录规范。
2. 参与场景轻量化处理：对重复实例化的桌椅、灯具、门等构件采用合批与 GPU Instancing 思路，剔除不可见构件，控制场景规模以满足实时运行帧率要求。
3. 参与门、灯等设备交互的实现与联调：门绕门轴转动、开关角度由几何推导（场景中门初始为半开姿态，需用相对初始姿态的偏移量而非绝对角度）；灯具亮度与开关状态联动。
4. 负责答辩演示素材录制：按演示动线（设备点选联动、机房联动开机、拉闸归零、告警定位、天气切换）逐段录制，供演示视频剪辑使用。

**实习收获**
收获最大的是理解了三维资产「数量」与「可用性」的矛盾：一个场景里两千多个重复网格看起来是资产丰富，实际是性能负担，必须靠合批与实例化处理。另一个体会是交互实现里几何推导的重要性——门的开启角度如果写死，换一个初始姿态就全错，只有从模型当前姿态反推基准才能通用。此外，录制演示素材让我完整走了一遍系统全流程，反而比看代码更快理解了各模块之间的联动关系。

## 2.5 王绍锋

**实习内容**
负责空调开关反馈仿真交互的设计与开发（气流粒子＋程序化嗡鸣）；参与部分设备交互的开发（摄像头交互等）；参与场景的视觉美术调优，以及场景模型导入异常黑面缺陷的排查与修复。

**主要工作**
1. 设计并实现空调开关的多通道反馈：开启时出风口位置生成气流粒子并伴随程序合成的嗡鸣音（50／100／150Hz 谐波叠加，0.7s 音量淡入淡出，常驻循环靠音量控制而非反复播放）；关闭时粒子停止发射但让残留自然飘散，避免画面突断。
2. 出风口位置自动推导：按空调机身包围盒计算顶部格栅位置与朝向房间内侧的吹风方向，避免硬编码坐标导致换模型即失效。
3. 参与摄像头类交互与监控视角表现的实现（多视角切换、画面滤镜叠层）。
4. 排查并修复模型导入后大面积发黑的缺陷：定位根因为吊顶下表面背对全部光源，烘焙光照按法线投影结果为 0（光照图集整体有光，但该 UV 区块无光），采用运行时将相关结构件 lightmapIndex 置 −1、改用实时光与环境光的方案，共修复 12 处结构件。
5. 参与场景视觉与美术调优：材质参数、灯光预设与后处理配置的统一，使各区域明暗关系一致。

**实习收获**
最有价值的一课是**「现象」与「根因」之间的距离远比想象远**。模型发黑最初被当成材质丢失，查了材质槽、查了 Renderer 开关都正常，最后才定位到烘焙光照的法线投影问题——排查这类问题必须建立判据（点得到吗、材质槽为空吗、是否合并网格、隔离显示后如何），逐条排除而不是凭经验猜。另一点是反馈设计要符合物理常识：空调关闭时如果粒子瞬间消失，看起来就像程序出错；让它自然飘散，用户才会读作「风停了」。这些细节决定了仿真系统是否可信。

## 2.6 李文玉

**实习内容**
负责演示视频的剪辑与制作；参与部分设备交互的开发（开关门、开关灯等）；对同方向的数字孪生项目及交互功能设计与实现进行调研，整理成标准的 Markdown 协作文档。

**主要工作**
1. 完成答辩演示视频的剪辑制作：确定片头与分段字幕样式模板，按演示动线组织素材（系统总览 → 设备点选联动 → 机房联动开机 → 拉闸归零 → 告警定位 → 天气切换），添加字幕与解说词。
2. 参与门、灯等设备交互的实现与联调。
3. 开展数字孪生方向调研：梳理本项目已实现的交互功能（设备点选与详情钻取、三级电力回路分级停电、告警点击定位、机房 20 块屏联动、时间天气控制），并对照同类数字孪生项目（如 51WORLD、Hightopo、施耐德 EBO、优锘 ThingJS-X、Siemens Building X 等）的做法，总结共性设计规律。
4. 将调研结果整理为标准 Markdown 协作文档，含功能对照表、共性设计要点、本项目取舍说明，供组员查阅与答辩引用。

**实习收获**
调研让我看清了本项目在行业坐标系里的位置：商业孪生平台的共性做法是「单容器＋页栈而非多浮窗并列」「渐进披露，先总览再下钻」「三维与看板双向联动」「主色只承载状态语义」，本项目在这些原则上与行业一致，差异在于用零图片资源、纯代码 UI 的方式实现，以适应断网部署与轻量交付的约束。视频剪辑方面的收获是：演示视频不是功能罗列，而要按「从轻到重」的节奏组织，让观众先看懂一个简单联动，再接受复杂的分级停电，理解成本才低。

## 2.7 王雯信

**实习内容**
负责项目踩坑日志的归档与整理；负责答辩素材的收集与整理；参与部分设备交互的开发（开关门、开关灯等）；负责项目的性能调试与目标平台打包。

**主要工作**
1. 归档整理项目踩坑日志：将分散在各阶段的 76 条问题记录按七类归并（编辑器与编译类、UI 布局类、材质与渲染类、排查方法论、流程与验收纪律、资源归属与状态机类、数据真实性类），每条统一为「现象 → 根因 → 修法 → 教训」四段结构，并建立索引便于检索。
2. 收集整理答辩素材：设计稿、运行截图、技术图表（架构图、数据流图、命令链路时序图、电力回路树、告警状态机、编号体系等）分类归档并统一命名规范。
3. 参与门、灯等设备交互的实现与联调。
4. 负责性能调试与目标平台打包：配置 Windows x64 构建，验证可执行程序运行；针对答辩现场投影设备做 16:9／16:10／4:3 三种分辨率适配实测，记录帧率数据；核查中文字体在打包后的显示完整性。

**实习收获**
整理踩坑日志的过程本身就是一次系统学习：76 条记录里最让我印象深刻的不是某个具体技术错误，而是几类**反复出现的模式**——「写了分支但没人调用」（编译通过、逻辑自洽，但功能根本没生效）、「参数看着合理却没算过最不利组合」（湿度下限设 5.5，实测最干时余量只剩 0.09）、「注释描述的实现和代码不是一回事」。这些错误的共同点是**不会报错**，只能靠建立判据主动验证。打包环节则让我体会到「编辑器里能跑」与「交付物能跑」是两件事：字体、分辨率、资源剥离路径都可能在打包后暴露问题，必须真打一次才算完成。
