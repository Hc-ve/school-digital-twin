## 1. 项目概览

### 1.1 项目背景

建筑室内空间的数字化长期存在两条割裂的路线：一条是「表达」——从效果图到全景图、视频漫游，画面好看但不能操作，门永远开着、灯永远亮着；另一条是「管理」——从 BIM 到运维平台，数据完整却脱离空间语境，本质上只是一个带模型的仪表盘。真正把两者连起来的，是实时三维引擎在普通设备上的普及：使用者不再「看」一个空间，而是「进入」一个空间，在其中行走、开门、按开关，并在操作的同时看到数据因行为而改变。

本项目就落在这个中间位置：**用一间校园卫生间，做一个能走、能动、能算的最小闭环**。

### 1.2 核心业务场景

| 场景 | 谁在用 | 用它做什么 |
|---|---|---|
| 教学实训 | 数字媒体 / 建筑表现 / 虚拟现实方向的学生 | 在一个周期内走完「资产处理 → 场景搭建 → 交互开发 → 数据呈现 → 联调测试」的完整链路 |
| 方案评审 | 设计方与校方 | 在真实视距与视高下判断空间尺度、采光、窗外景观是否成立，替代静态效果图 |
| 数据演示 | 后勤 / 智慧校园项目组 | 用模拟数据演示「人流—厕位—用水」的联动关系，验证指标口径与界面形态是否合理 |
| 交互原型验证 | 引擎开发者 | 把门、灯、窗、冲水、看板做成可复用的交互范式，迁移到其它室内场景 |

### 1.3 解决的核心问题

| 常见做法 | 问题 | 本项目如何解决 |
|---|---|---|
| 全景图 / 视频漫游 | 只能沿预设路径观看，无法自由行动；状态固定，门开不了、灯关不掉 | 第一人称漫游 + 角色控制器碰撞，全部交互对象可操作 |
| 静态模型展示 | 没有碰撞、没有光照、没有状态，本质仍是「看模型」 | URP 实时渲染 + 灯光系统 + 状态机驱动的交互对象 |
| 三维运维平台 | 建设成本高，需服务器、数据库、硬件对接，画面精度低 | 本地单机、零服务器、零联网；数据模型结构与真实系统一致，可平滑替换数据源 |
| 手工搭场景 | 改一次资产就要重搭一遍，无法复现、无法交接 | 七组编辑器菜单命令，一键重建，幂等可重复执行 |

### 1.4 交付形态

- 一个可在编辑器中直接 Play 的场景：`Assets/JP_School restroom_V2/Scenes/School_Restroom_Day.unity`
- 25 个 C# 脚本（运行时 15 个 + 编辑器 10 个），共 **5,420 行**
- 全部 UI 由代码在运行时生成，场景中不存在手工搭建的 Canvas
- 全部音效由代码实时合成，工程中不包含任何音频素材文件

## 3. 三大亮点功能

### 3.1 亮点一：推开窗就能看见树（低成本室外景观）

![窗前景观](docs/shot-window.jpg)

**现象**：男厕推拉窗推开一扇，窗外是近处树冠、中景草地与远处天空，玩家在窗前左右移动时会有轻微视差；关闭窗扇后视野被磨砂玻璃挡住，符合真实卫生间的采光逻辑。

**实现原理**：没有建室外场景，而是在窗外若干米处竖立**带 Alpha 通道的分层贴图背景板**（近树 / 中景 / 天空三层），配合 URP 的 Unlit + `_Cull Off` + `_ALPHATEST_ON` 材质——关闭背面剔除保证侧视可见，开启 Alpha 裁剪让透明区域不写深度，避免「透明块挡住后方物体」。背景板的垂直位置被抬到接近人眼高度（约 1.6m），让画面中的地平线落在平视线附近，否则树会像是「长在一堵上坡墙上」。相机远裁剪面同步放大到 260m 以覆盖背景板距离，雾密度调低只保留空气感。贴图本身经过裁水印、洋红键控、反预乘去紫边、Alpha 腐蚀四步处理，边缘没有紫边。

> 关键代码：`SlidingWindow.cs`（滑动插值 + 随动碰撞体）、`CampusToiletOutdoorSetup.cs`（背景板生成与材质配置）

背景板素材本身长这样——树是带 Alpha 通道的贴片，草地与天空各是一层，从引擎里直接看就是一片「假树林」，但放进窗框、加上透视与雾之后，观感就成立了：

![背景板素材](docs/shot-outside.jpg)

### 3.2 亮点二：右上角的实时数据看板

![实时数据看板](docs/shot-hud.png)

**现象**：屏幕右上角常驻一块半透明面板，实时显示在场人数、今日进场人次、空位总数、男女厕分别的空位条与数量、冲水次数、累计用水量与节水量；按 `Tab` 展开人均用水、节水率与分房间明细，按 `H` 整体隐藏。

**实现原理**：`ToiletStats` 是运行时单例数据中心，按房间（男/女）各持一份 `ToiletRoomData`，字段包括厕位总数、真实占用、模拟占用、进出人次、冲水次数、累计用水与节水量。所有派生指标（占用、空位、在场人数、平均冲水、占用率）都是只读属性，保证口径只有一处。`ToiletStatsHUD` 在 `Awake` 里用纯代码构建 Canvas：锚定右上角、偏移 (-26, -26)、面板 500×180，`CanvasScaler` 按 1920×1080 等比缩放；刷新用 0.25 秒轮询而不是事件推送，数值高频变化时更稳。数据来源双轨：玩家开门/关门/冲水是真实计入的，场景中无 NPC，另有一套 4~9 秒随机间隔的模拟客流让数字「活」起来，两者在数据层分字段存放，界面上可解释。

> 关键代码：`ToiletStats.cs`、`ToiletStatsHUD.cs`、`ToiletEntrySensor.cs`、`SwingDoor.StateChanged` 事件

### 3.3 亮点三：门的状态直接驱动业务计数

![室内场景](docs/shot-interior.jpg)

**现象**：走进男厕，灯自动亮起；推开一扇隔间门再关上，面板上男厕空位从 3/3 变成 2/3；走回门厅，在场人数与空位同步变化。门、灯、数据三者不是三套独立逻辑，而是同一条事件链。

**实现原理**：`SwingDoor` 继承自 `Interactable` 基类，开合由协程按 `rotateSpeed = 220°/s` 插值旋转，`autoClose` 默认 4.5 秒后自动回弹，`closeBlockRadius` 会在关门时检测门后是否站人。状态一旦迁移就广播 `StateChanged(door, isOpen)`。`ToiletStats` 在自动扫描阶段订阅所有隔间门的事件，用「关门 = 占用 +1、开门 = 占用 -1」把物理状态翻译成业务状态；判定厕位的规则是**路径包含 booth/partition 关键字 + 对象下存在 lock 子物体**，以此排除没有门的开放式开口，最终得到男厕 3 个、女厕 6 个厕位，与图纸一致。灯光则走另一条支线：`LightingManager` 按房间锚点判断玩家所处房间，进哪间亮哪间，关灯时同步压低 `RenderSettings.ambientIntensity`，视觉上是「真的黑了」而不是「贴了层灰」。

> 关键代码：`SwingDoor.cs`、`ToiletStats.AutoScanStalls()`、`LightingManager.cs`

## 5. 技术实现方案

### 5.1 分层架构

![系统分层架构](docs/arch-layers.png)

分层的关键约束是**单向依赖**：上层可以引用下层，下层不反向引用上层。数据层不知道界面长什么样，界面层也不直接修改门的状态。这样替换界面（比如把 uGUI 换成 UI Toolkit）不会影响交互逻辑，替换数据源（模拟 → 真实传感器）也不会影响表现层。

### 5.2 交互流程

![交互流程](docs/flow-interaction.png)

整条链路是「输入 → 命中 → 交互 → 状态迁移 → 事件广播 → 数据与呈现」，没有任何反向控制。这也是为什么面板可以独立开关、音效可以整体静音而交互照常工作。

### 5.3 漫游与碰撞

- **移动**：`CharacterController.Move`，速度按步行速度设定，`Shift` 切快走；`stepOffset = 0.25m` 刚好跨过门槛而不会被家具卡住。
- **视角**：水平转角色、垂直转相机，`Mathf.Clamp` 限制俯仰；相机挂在角色子节点，高度 1.6m。
- **碰撞**：墙体、地面、家具用 MeshCollider/BoxCollider；薄片装饰（挂画、标识牌）用内缩的薄碰撞体，避免「撞空气」。
- **出生点**：`(4.05, 1.84, -5.84)`，朝向室内，near 0.3 / far 260。

### 5.4 交互识别（`PlayerInteractor` + `InteractionHUD`）

```
每帧：
  1. 从相机中心发射射线 → Physics.RaycastAll(2.5m)
  2. 过滤非 Interactable 图层，按距离排序取最近
  3. 命中 → hud.SetPrompt(target.Prompt, target.SecondaryPrompt)
     未命中 → hud.ClearPrompt()
  4. 按下 E → target.Interact(this)
     按下 R → target.SecondaryInteract(this)   （仅冲水对象有实现）
```

`Prompt` / `SecondaryPrompt` 是 `Interactable` 的虚属性，子类按自身状态返回文案，这是「提示随状态变化」的实现方式，而不是在 UI 层写 if-else。

### 5.5 门系统（`SwingDoor`）

| 参数 | 默认值 | 作用 |
|---|---|---|
| `openAngle` | 95° | 开启角度 |
| `rotateSpeed` | 220°/s | 旋转速度上限 |
| `autoClose` / `autoCloseDelay` | 开 / 4.5s | 自动回弹，模拟公共卫生间弹簧门 |
| `closeBlockRadius` | 0.8m | 门后有人则不关，改写为反向开启 |
| `autoHinge` | 开 | 按合页子物体推断旋转轴与正负号 |
| `passableWhileMoving` | 开 | 动画过程中允许穿过，避免夹住玩家 |

状态迁移用协程而非 `Update` 累加角度：协程有明确的起止与可取消性，连按时的行为更容易控制。门的角度变化过程中会实时更新碰撞体朝向，保证「门开到一半也能挡住人」。

### 5.6 照明系统（`LightingManager` + `LightFixture` + `LightSwitch`）

- **房间判定**：每个 `Room` 配置一个世界坐标锚点与半径，玩家位置落在哪个房间就激活哪组灯。
- **过渡**：亮度用协程在 0.6 秒内插值，光源强度与灯罩自发光材质同步，避免「啪」地突变。
- **环境光联动**：关灯时把 `RenderSettings.ambientIntensity` 压到低位，否则会出现「灯灭了但房间还是亮的」的穿帮。
- **性能取舍**：室内点光源大部分关闭实时阴影，只保留方向光阴影；阴影分辨率与距离做了限制。

### 5.7 推拉窗（`SlidingWindow`）

沿本地轴滑动 0.76m，插值速度 0.9；额外加 0.015m 的法向偏移，让两扇窗错层，避免共面 Z-fighting。开启方向根据玩家站位自动判断（`autoDirection`），从哪边推就往哪边滑。碰撞体作为子物体随窗扇移动。

### 5.8 数据系统（`ToiletStats`）

```
ToiletRoomData
├─ totalStalls    厕位总数（自动扫描或手填）
├─ realOccupied   玩家造成的占用
├─ simOccupied    模拟客流造成的占用
├─ entered / exited
├─ flushes / liters / savedLiters
└─ 派生：Occupied / Empty / Inside / AvgFlush / Occupancy
```

- **自动扫描**：`Start` 里等两帧（保证运行时补全的门已就位）→ `AutoScanStalls()` 遍历 `SwingDoor` → `IsStallDoor()` 双重条件过滤 → 按路径归属到男/女厕 → 订阅 `StateChanged`。
- **事件驱动计数**：`OnDoorStateChanged` 只比较「上一次是否打开」与「这一次是否打开」，变化才计数，重复事件不会重复累加。
- **模拟客流**：`simTimer` 到点后随机选房间、随机选「进入/离开/占位/释放」，间隔在 4~9 秒之间重抽。
- **口径保护**：`Occupied` 用 `Mathf.Clamp(0, totalStalls)`，`Inside` 用 `Mathf.Max(0)`，异常数据不会把面板打成负数。

### 5.9 数据面板（`ToiletStatsHUD`）

- **纯代码构建**：`BuildUI()` 里创建 Canvas → CanvasScaler（1920×1080，宽高折中 0.5）→ 底板 Image（深色 0.78 透明）→ 标题 / 正文 / 明细三段 Text。
- **锚点**：`anchorMin = anchorMax = (1,1)`、`pivot = (1,1)`、`anchoredPosition = (-26,-26)`，永远贴右上角。
- **刷新**：`Update` 里 0.25 秒计时轮询 `Refresh()`；用 `StringBuilder` 拼接，避免每帧产生大量临时字符串。
- **富文本**：正文里用 `<b>` 强调关键数字，`Text.supportRichText` 默认开启；空位用 `|` 字符拼成条形图（如 `|||` 表示 3 个空位），比进度条更省事也更清晰。
- **字体**：`InteractionHUD.GetCJKFont()` 统一取系统 CJK 字体，解决「中文显示为方框」。

### 5.10 程序化音效（`ProceduralSfx`）

`AudioClip.Create` + 手写采样：开门声是低频振荡叠加短噪声并加抖动的摩擦感，关门声是低频闷响加一次短促碰击，锁扣是极短高频脉冲，滑轨是带通滤波噪声，冲水是粉红噪声配音量包络。每个 Clip 生成后静态缓存，避免重复分配。好处是工程零音频资源、参数可调、能精确对齐动画时序；代价是不如真实录音自然，需要靠叠加层与包络补偿。

## 10. 踩坑日志

> 记录原则：**现象 → 原因 → 解法 → 规避**。每条都是实际踩过并修复的。

### 10.1 材质全粉：URP 下 Built-in 材质失效

- **现象**：导入资产包后整个场景是荧光粉色，只有轮廓没有质感。
- **原因**：素材包材质使用 `Standard`（Built-in 管线）着色器，URP 不认识，回退到错误着色器。
- **解法**：批量把所有 `Standard` 材质转为 `Universal Render Pipeline/Lit`，保留原贴图引用与颜色。
- **规避**：换管线时先跑一次材质转换；新项目导入外部资产后第一件事就是检查材质。

### 10.2 窗外一片空白：远裁剪面短于背景板距离

- **现象**：窗推开后看不到树，只有空白或天空色。
- **原因**：相机 `farClipPlane` 只有几十米，背景板在更远处，被整体裁掉。
- **解法**：`farClipPlane` 提到 260m，并同步复核雾浓度（雾太浓会把背景板糊成一片）。
- **规避**：任何「远景贴片」方案都要先确认相机裁剪范围，再调雾。

### 10.3 背景板变黑块：透明材质写了深度

- **现象**：贴图明明有 Alpha，放进场景却是一个黑矩形，或者把后面的树挡住。
- **原因**：材质没开 Alpha 裁剪，透明区域仍然写入深度缓冲。
- **解法**：用 Unlit + `_ALPHATEST_ON` + `_Cull Off`，透明区不写深度；渲染队列设为 AlphaTest。
- **规避**：所有「抠图贴片」统一用同一套材质模板，不要每个物体单独配。

### 10.4 树像长在上坡墙上：地平线与视平线错位

- **现象**：窗外景观看起来是斜的，像一堵带草的斜坡。
- **原因**：背景板底边与地面齐平，而人眼在 1.6m，画面里的地平线落在视平线下方，透视关系不成立。
- **解法**：把背景板整体抬高到接近视线高度，让地平线落在平视位置。
- **规避**：贴片式远景必须以「视高」而不是「地面」为基准定位。

### 10.5 抠图边缘紫边

- **现象**：树冠轮廓有一圈淡紫色描边，放大后更明显。
- **原因**：洋红背景与前景混合后，边缘像素是半透明混合色，直接阈值抠图会残留背景色。
- **解法**：先按 Alpha 做反预乘把边缘颜色还原为前景色，再做阈值；随后对 Alpha 通道腐蚀 2~3 像素并把轮廓内缩 1 像素。
- **规避**：纯色键控必须配反预乘 + 腐蚀，不能只调阈值。

### 10.6 门「整扇翻倒」

- **现象**：按 E 后门不是绕合页转，而是像被风刮倒一样整块翻过去。
- **原因**：不同门的局部坐标轴朝向不一致，统一绕某个轴旋转必然出错。
- **解法**：`autoHinge` 按合页子物体的相对位置推断旋转轴与正负号，写入每扇门的配置。
- **规避**：批量处理来自不同建模批次的模型时，永远不要假设坐标轴一致。

### 10.7 门关起来把人「切」了

- **现象**：玩家站在门后，门继续旋转，直接穿过身体。
- **原因**：推门/关门没有做空间检测。
- **解法**：`closeBlockRadius` 内检测到玩家占据空间时，改为反向开启或给出提示。
- **规避**：所有带自动回弹的门都要有「门后有人」分支。

### 10.8 灯具越跑越亮：脚本不幂等

- **现象**：重复执行「生成灯光系统」后场景越来越亮，最后过曝。
- **原因**：脚本每次执行都新建灯具，旧灯具没清理，光源叠加。
- **解法**：执行前按「命名前缀 + 组件类型」清理旧对象，保证执行 N 次 = 执行 1 次。
- **规避**：把幂等写进编码约定，所有编辑器命令都要能重复执行。

### 10.9 播放模式下改场景直接抛异常

- **现象**：`EditorSceneManager.MarkSceneDirty` 报 `InvalidOperationException`。
- **原因**：播放模式下不允许标记场景为脏并保存。
- **解法**：修改前检查 `EditorApplication.isPlaying`，先退出播放；必要时用标记文件把「待还原」动作延后到退出后执行。
- **规避**：所有会写场景的编辑器脚本，开头统一做播放状态守卫。

### 10.10 编辑器暂停，探针计时永不超时

- **现象**：调试探针卡在等待循环里不动，日志停在第一行。
- **原因**：编辑器暂停时 `Time.time` 不推进，基于它的超时永远不成立。
- **解法**：改用 `EditorApplication.timeSinceStartup` 计时，并主动解除暂停。
- **规避**：编辑器侧计时一律用编辑器时间，不要用运行时的 `Time`。

### 10.11 面板缩到几乎看不见

- **现象**：世界空间看板做出来只有几毫米，几乎不可见。
- **原因**：根节点与 Canvas 内层各设了一次 scale，两层相乘导致尺寸被平方级压缩。
- **解法**：只在一层设置缩放，另一层保持 1；用「米/像素」单一参数换算出总尺寸。
- **规避**：Canvas 的缩放来源必须唯一，最好在构建函数入口注释写明。

### 10.12 中文字显示成方框

- **现象**：所有 UI 文字是「□□□」。
- **原因**：Unity 内置 Arial 不含 CJK 字形。
- **解法**：运行时加载系统 CJK 字体，并统一走 `InteractionHUD.GetCJKFont()` 一个入口。
- **规避**：字体获取只留一个入口，杜绝「这个面板正常、那个面板方框」。

### 10.13 截图工具抓到错误的窗口

- **现象**：脚本截出来的图是 Unity Hub 或启动器，不是编辑器。
- **原因**：按标题模糊匹配（包含 "Unity"）会命中多个窗口；且窗口句柄会随窗口重建而变化。
- **解法**：每次截图前重新枚举窗口，按精确标题匹配，并校验句柄有效性。
- **规避**：不要缓存 HWND；任何窗口自动化都要「先枚举再操作」。

### 10.14 场景文件多人同时改必冲突

- **现象**：两人同时改场景，合并后大量对象丢失或重复。
- **原因**：`.unity` 是按对象 ID 组织的文本，几乎无法自动合并。
- **解法**：场景由一人统一修改，其他人先告知；改完立刻提交并写清改了什么。
- **规避**：把「场景所有权」写进协作约定，比事后合并便宜得多。

## 11. 已知限制与后续规划

### 11.1 已知限制

| 项 | 说明 |
|---|---|
| 单人场景 | 无联机、无 NPC 实体，客流为模拟数据 |
| 数据不持久化 | 关掉 Play 数据清零，不写存档 |
| 未适配 VR | 交互基于键鼠射线，未做手柄/头显输入 |
| 视觉打磨不足 | 材质反射、光斑、构图引导仍有提升空间 |
| 极端分辨率 | 超宽屏下右上角面板间距需微调 |
| 窗边帧率 | 背景板 + 雾效叠加，帧率略低于室内其它位置 |

### 11.2 路线图

- **短期**：材质与光照细化；门后障碍提示文案优化；面板异常值保护提示
- **中期**：把模拟数据源抽象为接口，预留真实传感器接入；把编辑器工具抽象为可配置的通用场景搭建器
- **长期**：多房间扩展（走廊、洗手区独立统计）；导出为 WebGL 供浏览器直接体验

## 12. 维护约定

1. **命名空间**：所有自定义脚本置于 `CampusToilet` / `CampusToilet.EditorTools`，不污染全局。
2. **序列化字段**：需要在 Inspector 调的字段一律 `[Tooltip("中文说明")]`，方便非程序成员调参。
3. **幂等**：编辑器命令必须可重复执行，创建前先清理。
4. **单向数据流**：交互层只写事件，UI 层只读数据，不允许 UI 反向改状态机。
5. **口径唯一**：任何派生指标只在数据中心定义一次，界面不得自行计算。
6. **场景修改**：改场景前先备份 `School_Restroom_Day.unity`；预览类脚本必须自带还原逻辑。
7. **文档同步**：新增菜单项或参数时，同步更新本 README 的第 5.11 节与第 6 节。
