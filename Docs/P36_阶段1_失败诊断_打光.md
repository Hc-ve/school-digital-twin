# P36 · 阶段 1 失败诊断（上一轮实现为何「效果不行」）

**日期**：2026-11-13 · 打光（unity-tech-artist）
**对象**：上一轮已被主理人判定「效果不行」并整体回退的实现
　`TwinDevicePresenter._lampEmission 0.60 → 1.40 HDR` + 黄昏/夜晚运行时启用 Bloom
　（`intensity 0.55 / threshold 1.1 / softKnee 0.4`，写 `FindObjectOfType` 第一个
　`PostProcessVolume` 的 `sharedProfile`）
**结论**：**四个排查点里至少三处致命错误，且互相叠加**。该实现连「让 Bloom 真正运行」这一步都没做到，
　因此 `_lampEmission` 调到多少都不可能产生管外光晕。以下逐条给出可复核证据。

---

## ① 写入的 volume / profile 是否相机真正混合的那份？——❌ 不是，且错了两层

**第一层：`sharedProfile` ≠ 相机读取的 `profile`。**

- 实测源码 `Library/PackageCache/com.unity.postprocessing@3.2.2/PostProcessing/Runtime/PostProcessManager.cs:228`
  ```csharp
  var profile = volume.profile;     // ← 混合用的是克隆实例
  ```
- `PostProcessVolume.cs:120-139` 的 `profile` getter：
  ```csharp
  if (m_InternalProfile == null) {
      m_InternalProfile = ScriptableObject.CreateInstance<PostProcessProfile>();
      foreach (var item in sharedProfile.settings)
          m_InternalProfile.settings.Add(Instantiate(item));   // 逐项深拷贝
  }
  return m_InternalProfile;
  ```
  → **只要访问过一次 `profile`，PPv2 就持有一份独立克隆；此后改 `sharedProfile` 完全不影响渲染**。
- 上一轮明确写的是 `sharedProfile`。而本工程 `EnvironmentState.BindPostProcess()`（`:444-475`）
  与 `TwinLightingPreset.ApplyPost()`（`:121-150`）在运行时**早已访问过 `vol.profile`**，
  克隆必然已生成 ⇒ 上一轮写的是一份「相机早已不看的资产本体」。

**第二层：两个 Volume 都指向同一份资产，但各有各的克隆。**

- 场景实测 `SchoolSceneDay.unity`：
  | 行号 | sharedProfile | isGlobal | weight | priority | blendDistance |
  |---|---|---|---|---|---|
  | L34160-34175 | `d19e4711…`（PPS_Bloom.asset） | 1 | 1 | 10 | 0 |
  | L56591-56595 | **同一份** `d19e4711…` | 1 | 1 | 10 | 0 |
- `FindObjectOfType<PostProcessVolume>()` 返回顺序**不保证**，两个都是 isGlobal、权重相同；
  即使写对了对象，也只改到一个 Volume 的克隆，另一个仍以原参数参与混合，
  结果按权重被稀释/覆盖。任务包担心的「多 volume 写错对象」成立，但**更根本的是写错了 profile 层级**。

**结论**：① 失败。正确做法必须遍历**所有** `PostProcessVolume`，对每一个取 `volume.profile`（克隆）
写入，或统一改用 `Instantiate` 出来的专用 profile 并替换 `volume.profile`。

## ③ Linear 亮度与 threshold 的实际关系（emission 1.4 到底过没过阈值）

**实测源码 `…/Runtime/Effects/Bloom.cs`**：

```csharp
// :171  —— 阈值走 Gamma→Linear 转换
float lthresh = Mathf.GammaToLinearSpace(settings.threshold.value);
// :212  —— intensity 是 Exp2 标度，不是线性倍数
float intensity = RuntimeUtilities.Exp2(settings.intensity.value / 10f) - 1f;
// :94-97 PostProcessEffectSettings.IsEnabledAndSupported()
return enabled.value;                    // ← 只看这个
// Bloom.cs:96 额外条件： intensity.value > 0f
```

逐项验算上一轮的参数：

| 项 | 上一轮值 | 实际效果 |
|---|---|---|
| `Bloom.enabled.value` | **未写**，资产 `PPS_Bloom.asset` 实测为 `enabled: { overrideState: 1, value: 0 }` | 🔴 **硬关闭**。`IsEnabledAndSupported()` 返回 false，Bloom 整段被跳过，后面所有参数都是空转 |
| `Bloom.active` | 上一轮未必写；`TwinLightingPreset` 写了 `bl.active = intensity > 0.001` | `active` ≠ `enabled.value`。**PPv2 的开关是 `enabled.value`，`active` 只表示该组参数是否参与混合** |
| `intensity = 0.55` | `Exp2(0.55/10) - 1` | ≈ **0.039**，几乎不可见（要达到 1.0 倍强度需 intensity ≈ 10） |
| `threshold = 1.1` | `GammaToLinearSpace(1.1)` ≈ **0.79**（线性） | 阈值本身不算高，emission 1.4 线性值确实 > 0.79 → **本可过阈值** |
| `emission = 1.4` | Standard shader 线性空间 | 叠加白色 albedo 后管体过曝为纯白，但**没有 Bloom 就不会晕开** |

**渲染顺序**（`PostProcessLayer.cs:1262-1267`）：`RenderEffect<Bloom>()` **在 `ColorGrading` 之前**，
所以 `postExposure` 不会先把高亮压掉再判阈值——③ 这一环其实是**唯一站得住的**。

**结论**：③ emission 1.4 在 Linear 下**本来能过** `GammaToLinearSpace(1.1)≈0.79` 的阈值；
失败不在阈值，而在 **`enabled.value=false` 让整个 Bloom 从未执行**，以及 `intensity=0.55` 即使执行也只有 0.039 倍。
上一轮「调大 emission + 写一个很小的 intensity」是双重错位。

## ④ 主理人 play 的机位 / 档位下，该效果本应可见吗？

**实测项目代码**：

- `TwinLightingPreset.cs:47 / :60 / :73` 三档 `bloomIntensity`：
  **白天 0** / 黄昏 0.15 / **夜晚 0.50**，`bloomThreshold` 分别 1.1 / 1.05 / 0.85。
  `ApplyPost()` 会写 `bl.intensity.value`、`bl.threshold.value`、`bl.active`，
  **唯独不写 `bl.enabled.value`** —— 与上一轮同病（现有基线里 Bloom 就一直是关的）。
- `EnvironmentState.cs:383-435` 每帧写 `sharedProfile` 的 `ColorGrading.postExposure`
  （夜晚为负 EV，把整体压暗），这是「暗顶」的来源，也让高亮灯管更显眼——方向是对的。
- `IndoorFillLight.cs` 提供室内实时补光，夜晚生效；它**不产生管外光晕**。
- 灯管开关 `TwinDevicePresenter.ApplyLamp`（`:912-945`）只做 `m.SetColor("_EmissionColor", …)`，
  用的是 `r.material` 克隆（`:737`），不污染共享资产 ✅；并 `EnableKeyword("_EMISSION")` ✅。

**判定**：主理人夜晚档、室内机位下，灯管确实在画面里、相机 HDR 开启、后处理层覆盖全层，
**若 Bloom 正确启用，效果本应清晰可见**。所以「看不出在发光」不是机位/档位问题，
而是 ①③ 两处让 Bloom 从未运行 +  emission 只让管体自身发白（Unity 官方：GI=None 时只影响自身外观）。

> 附带发现（已写进 P36 调研第 8 条）：`TwinDevicePresenter.cs:50-53` 注释仍写着
> 「本项目…没装 Post Processing Stack，没有 Bloom」，与实测（包 3.2.2 + Layer + 2 Volume + HDR 相机）矛盾。
> 这条**过期注释**很可能正是上一轮只敢调 emission、不敢上 Bloom 的思想来源。
