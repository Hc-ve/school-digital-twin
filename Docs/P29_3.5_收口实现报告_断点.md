## 五、关键决策与根因修正

### 5.1 根因修正：不是「容器层」，是「安全区不足 + 无裁剪兜底」

规格 §1.1 的判断是「预算没算错，是容器没被约束住」，诊断方向指向「页面根没继承 `_content`」。
**实测结果是：容器层完全正常** —— 两个页面 `rect.height` 都精确等于 544.0。

真实原因两条：

1. **内容下沿离内容底太近。**
   旧 L1 时间线从 312 起、竖线到 526，距内容底 544 只剩 **18px**。
   数字上「没溢出」，但工具行分隔线就在 544，18px 的间隙在投影仪缩放下就是「贴着」，
   视觉上和「压住」没有区别 —— 这是规格 §1.2 I4 要求「≤528 留 16 安全区」要解决的东西。
2. **`_content` 没有裁剪。** 任何一次布局算错都会直接画到工具行上，没有任何兜底。

对应修法：
- 时间线上移到 **296**（4 行到 504，安全区 40px）；
- L2 按规格整体下移（Top3 行 384/430/476，第 3 行 516，安全区 28px）；
- `_content` 加 `RectMask2D`（**加在 content 不加 root**，否则主入口的发光描边会被裁掉）；
- 加运行时断言：下沿越线直接 `Debug.LogError`，下次不靠肉眼。

### 5.2 抽屉高度锁死 720（防御性改动，非当前溢出的根因）

`TwinDrawer` 原来 `anchorMin(1,0) / anchorMax(1,1) / sizeDelta(w, 0)`，高度跟着**画布**走。
而画布高度由 `CanvasScaler`（match=0，只按宽度缩放）决定：`画布高 = screenHeight × 1000 / screenWidth`。
一旦 GameView 不是 1000×720 这个比例（16:9 的 1920×1080 会算成 562.5），
内容区就变成 `562.5 − 96 − 80 = 386.5`，而内容按 544 排到 504/516 —— 直接超 117~130px。

本次实测画布高度正常（544 成立），说明当前 GameView 是 1000×720，**这条隐患没有引爆**。
但 `HeightRef = 720` 这个常量在文件里定义着却**从未被引用**，就是漏接了这一步。
已改为 `anchor(1, 0.5) + sizeDelta(w, 720)` 垂直居中，让「96 + 544 + 80 = 720」在任何分辨率下都成立。

> 顺带说明：这也是基线 R7「答辩投影仪非 16:9 会崩版」的技术入口之一 ——
> 锁死 720 只能保证**布局一致**，不能保证**整屏可见**；真要适配 4:3 还得整体缩放，那是打包阶段的事。

### 5.3 健康条与 Top3 接真实数据（验收倒逼，非扩需求）

任务包 ③ 只列了 5 项 UI 改动，但验收标准要求「健康条三段和 = 总数」。
而原代码里：

- 健康条写死 `ratio {0.92, 0.05, 0.03}`、图例 `正常 141 / 警告 7 / 告警 5`（141+7+5 = **153**）；
- 异常 Top3 写死 `B1-001-配电-001` 等三行示例。

这两处会让「设备总数 53」与「健康条 153」同屏矛盾，且「告警 0」与「异常 Top3 三行」自相矛盾 ——
正是 R10 要消灭的东西。所以一并接真实数据：

- 健康条：正常 = 在线 − 告警、警告+告警 = 告警、离线 = 离线；**和 ≠ 总数则整卡转「数据不一致」**，不画假条。
- Top3：从 `TwinAlarmHistory` 取「仍在持续」的异常，严重度降序 + 时长降序取前 3，无异常显示「暂无异常」。
  走 `TwinAlarmHistory` 而不是遍历 Registry，正是 UI 层 `Registry.All` 能归零的前提。

### 5.4 新增 `TwinDeviceStats.AllDevices`（为「grep 归零」补的必要入口）

心跳 §4.1 的签名只管**计数**。但告警列表 / 调试 HUD 需要**逐点遍历**筛行，
直接写 `Registry.All` 会让 grep 不为 0。所以补一个只读遍历入口，把「谁在遍历注册表」也收成一处。
**没有改动心跳的任何既有签名**，只是新增。
